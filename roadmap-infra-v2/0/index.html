Linux: факты, ресурсы и базовые команды

6-8 часов

🎭Аналогия

Сервер похож на диспетчерскую: прежде чем чинить отдельный прибор, диспетчер сверяет питание, температуру, список работающих систем и журнал событий. Команда без вопроса - шум; факт с timestamp - начало диагностики.

🗺Карта мест

Это версия 1 - базовая (кнопка переключения версий вверху страницы сайта). Полный самодостаточный минимум - построчный разбор команд, YAML-структура, термины I/O/TCP/UDP/PID. Версия 2 добавляет к этому же слою покупку VPS, историю про sudo echo >, квиз «Проверь себя» и живые истории.

Сделать: создать отдельного администратора, закрыть прямой root-login, настроить ключ SSH и firewall, собрать baseline.txt с состоянием CPU/RAM/disk/network/services.

Понять: Linux-диагностика идёт от симптома к наблюдаемому факту. Сервис, процесс, сокет, файловая система и сеть - разные слои с разными инструментами.

Где смотреть: /etc - конфигурация; systemctl - lifecycle; journal - события; /proc и ps - процессы; df/lsblk - storage; ip/ss - сеть; /var/log - файловые логи приложения.

Критерий: можешь объяснить, почему проверил именно эту команду, что в выводе норма и какой следующий дешёвый тест сделаешь.

📖Теория

Вопрос Первый факт Норма Симптом Дальше
Хост жив? uptime, date есть ответ, load сопоставим с CPU load быстро растёт процессы, I/O, память
Хватает RAM? free -h есть available, swap стабилен available низкий, swap растёт top, logs, limits
Хватает диска? df -hT, df -ih volume и inode < порога 100% или inode 100% du, logs, cleanup policy
Сервис жив? systemctl status unit active (running) failed/inactive/restarting journal, config, dependency
Процесс жив? ps, pgrep ожидаемый PID PID нет/завис logs, exit code, restart
Есть socket? ss -ltnp process слушает expected IP:port socket отсутствует service/config/firewall

📖Теория

Эти команды надо знать уверенно и без поиска. Полный построчный разбор с флагами - в подразделе ниже.

Команда Что делает и flags Когда применять Что смотреть → следующий шаг
systemctl status NAME состояние systemd unit сервис недоступен Active, Main PID, exit code → journalctl
journalctl -u NAME -n 100 --since '15 min ago' журнал unit; -f follow restart/error first error и timestamp → config/dependency
ps aux --sort=-%cpu процессы; сортировка CPU host slow top consumers → owner/logs/limits
top / htop live CPU/RAM/load моментный pressure %CPU, %MEM, load, state → disk/network/process
free -h RAM/cache/swap OOM/slowdown available, swap → process/limits
df -hT; df -ih space/type; inodes write failure volume/inode 100% → du, deleted-open files
du -xhd1 PATH sizes under one filesystem disk full largest directory → drill down safely
ss -ltnp; ss -tanp listening and TCP sessions port/network issue Local Address, State, PID → service/firewall
lsof -i :PORT; lsof +L1 port owner; deleted-open files conflict/disk mismatch PID → process restart or owner decision
dmesg -T \| tail -n 80 kernel events OOM/I/O/NIC issue OOM, filesystem, device errors → escalate/storage

Термины, которые легче перепутать вслух, чем на бумаге

Термин Расшифровка Что это Как произносится
I/O Input/Output операции обмена данными между программой и внешним устройством (диск, сеть, терминал) по буквам: «ай-оу», не «ио» слитно
TCP Transmission Control Protocol протокол с установлением соединения, гарантированной и упорядоченной доставкой по буквам: «ти-си-пи»
UDP User Datagram Protocol протокол без соединения, без гарантии доставки и порядка, зато быстрее по буквам: «ю-ди-пи»
PID Process ID уникальный номер, который ядро присваивает каждому запущенному процессу целиком «пид» или по буквам «пи-ай-ди» - по буквам однозначнее

Команды строка за строкой - синтаксис, флаги, интерпретация

То же самое ядро команд без сокращений, для самодостаточности сайта.

systemctl status <unit>

  • Syntax: systemctl <verb> <unit> - управление и опрос systemd-юнитов.
  • Флаги/verbs: status - состояние (active/failed, PID, последние строки журнала, без изменения состояния); start/stop/restart - запустить/остановить/перезапустить; enable/disable - вкл/выкл автозапуск при загрузке; --failed - показать все упавшие юниты сразу; --no-pager - не открывать вывод через pager.
  • Expected output: блок ● name.service - description, строка Active: active (running) since ... или failed (Result: exit-code), Main PID: NNNN, последние 5-10 строк журнала внизу.
  • What to look at: слово после Active:, Main PID (есть ли вообще), timestamp последнего изменения, exit code в скобках при failed.
  • Interpretation: active (running) - процесс жив с точки зрения systemd (не гарантирует, что порт слушает или приложение отвечает - см. ss); failed - юнит завершился с ошибкой и не перезапускается сам; activating - висит дольше ожидаемого.
  • Next inference: failed → journalctl -u <unit> -n 100; active, но приложение не отвечает → ss -ltnp → логи приложения.
  • Incident/interview use: «сервис недоступен» начинается именно отсюда - первый факт, до чтения логов и до сети.

journalctl -u <unit> -n 100 --since "15 min ago"

  • Syntax: journalctl [опции] - чтение systemd journal.
  • Флаги: -u <unit> - только события юнита; -n N - последние N записей; -f - follow; -p err - только error и выше; --since/--until - временное окно; -b - только текущая загрузка; -x - пояснения к сообщениям, где есть; --no-pager.
  • Expected output: хронологические строки <timestamp> <hostname> <unit>[PID]: <message>.
  • What to look at: первая строка с ошибкой (не последняя - от неё считать назад), timestamp относительно инцидента, повторяющийся ли паттерн.
  • Interpretation: одиночная ошибка при старте - вероятно конфигурация/зависимость; повторяющаяся с равным интервалом - retry-цикл, не может восстановиться; нет новых строк при -f - процесс не пишет в journal.
  • Next inference: нашли конкретную ошибку (например bind: address already in use) → ss -ltnp на этот порт.
  • Incident/interview use: ответ на «где смотреть, почему сервис не стартует» - читать с первой ошибки после --since, не листать весь журнал.

ps aux --sort=-%cpu

  • Syntax: ps <опции> - снимок процессов на момент вызова (не live, в отличие от top).
  • Флаги: aux - a процессы всех пользователей с терминалом, u - user-oriented формат, x - процессы без терминала (демоны), BSD-стиль без дефиса; --sort=-%cpu - сортировка по убыванию; -ef - System V full-format с PID/PPID.
  • Expected output: таблица USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND.
  • What to look at: верхние строки после сортировки, колонка STAT (R running, S sleeping, D uninterruptible sleep - I/O, Z zombie, T stopped).
  • Interpretation: один процесс стабильно с высоким %CPU - runaway process; много процессов в D - I/O bottleneck, не CPU; Z сам по себе CPU не жрёт, но означает, что родитель не собрал exit status.
  • Next inference: нашли PID → top -p PID или lsof -p PID прежде чем kill.
  • Incident/interview use: идёт сразу после uptime, до любых предположений о причине.

free -h

  • Syntax: free [опции].
  • Флаги: -h human-readable; -m/-g принудительно MiB/GiB; -s N повторять каждые N секунд.
  • Expected output: строки Mem: и Swap: со столбцами total used free shared buff/cache available.
  • What to look at: столбец available (не free!), тренд Swap: used.
  • Interpretation: низкий free, но нормальный available - Linux использует свободную память под файловый кэш, норма; низкий именно available - реальный memory pressure; растущий Swap used - активный своп.
  • Next inference: pressure подтверждён → ps aux --sort=-%mem → dmesg -T | grep -i oom.
  • Incident/interview use: классический вопрос «почему free показывает мало свободной памяти», см. также ❓ ниже.

df -hT и df -ih

  • Syntax: df [опции] [путь].
  • Флаги: -h human-readable; -T тип файловой системы; -i inode usage вместо байтов.
  • Expected output: таблица Filesystem Type Size Used Avail Use% Mounted on или Inodes IUsed IFree IUse% Mounted on.
  • What to look at: Use%/IUse% для нужного mountpoint - не путать переполнение по месту с переполнением по inode.
  • Interpretation: Use% = 100 - место кончилось, write падает; IUse% = 100 при свободном месте - кончились inode, новые файлы создать нельзя.
  • Next inference: Use% высокий → du -xhd1 на этот mount; IUse% высокий → искать директорию с огромным числом мелких файлов.
  • Incident/interview use: «диск полон, но du показывает мало» - см. lsof +L1 ниже и ❓.

du -xhd1 <path>

  • Syntax: du [опции] [путь].
  • Флаги: -x не пересекать границу FS; -h human-readable; -d1/--max-depth=1 только один уровень; -s только итог по пути.
  • Expected output: список <размер>\t<путь> по поддиректориям первого уровня.
  • What to look at: самая крупная строка - с неё начинать спуск глубже.
  • Interpretation: явный «тяжеловес» среди подпапок - конкретный источник роста; равномерное распределение - органический рост, не аномалия.
  • Next inference: найден источник → проверить retention-политику до удаления, не удалять активные логи/файлы БД вслепую.
  • Incident/interview use: связка df → df -i → du - ожидаемый порядок диагностики disk full.

ss -ltnp

  • Syntax: ss [опции] - современная замена netstat.
  • Флаги: -l listening; -t TCP; -u UDP; -n numeric, не резолвить в имена; -p PID/имя процесса (может требовать sudo); -a все сокеты; -i внутренняя TCP-информация. Короткие флаги комбинируются: ss -lntp = -l -n -t -p.
  • Expected output: таблица State Recv-Q Send-Q Local Address:Port Peer Address:Port Process.
  • What to look at: Local Address:Port - какой интерфейс (0.0.0.0/* все, 127.0.0.1 только локально, конкретный IP - только он); Process - какой PID держит порт.
  • Interpretation: порт отсутствует - сервис не слушает вообще; порт на 127.0.0.1, а стучимся снаружи - архитектурное решение или ошибка биндинга, не firewall; порт на 0.0.0.0 слушает широко, что само по себе не значит «доступен снаружи» - firewall может блокировать.
  • Next inference: порта нет → systemctl status/journalctl; порт есть, снаружи не достучаться → ufw status/iptables -L.
  • Incident/interview use: «порт не слушается» - ss -lntp даёт первый факт, до tcpdump и предположений про firewall.

dmesg -T | tail -n 80

  • Syntax: dmesg [опции] - сообщения кольцевого буфера ядра.
  • Флаги: -T человекочитаемые timestamp; -w follow; --level=err,warn фильтр severity.
  • Expected output: строки ядра с меткой времени и подсистемой (Out of memory, Killed process, I/O error, link up/down).
  • What to look at: строки Out of memory/Killed process (OOM killer), I/O error/filesystem error, смена состояния линка.
  • Interpretation: OOM killer в логе - процесс принудительно завершён ядром из-за нехватки памяти; I/O errors - аппаратная/драйверная проблема, не проблема приложения.
  • Next inference: OOM → сопоставить время с free -h/логами, пересмотреть лимиты памяти; I/O errors → эскалация на storage.
  • Incident/interview use: «сервис исчез без ошибки в своих логах» - dmesg часто единственное место, где видно, что убил не он сам.

lsof +L1 и lsof -i :PORT

  • Syntax: lsof [опции].
  • Флаги: -p PID файлы процесса; -i только сетевые сокеты; -i :PORT кто использует порт; +L1 файлы с link count < 1 - удалённые, но открытые файлы, которые держат место на диске, невидимое du.
  • Expected output: таблица COMMAND PID USER FD TYPE DEVICE SIZE/OFF NODE NAME, для +L1 в NAME пометка (deleted).
  • What to look at: SIZE/OFF - сколько места держит удалённый файл; PID/COMMAND - кто держит.
  • Incident/interview use: прямой ответ на «df полон, du не находит крупных файлов» - см. ❓ и практику ниже.

Как читать структуру docker-compose.yml (и любого декларативного документа)

services:                           # верхний уровень - список контейнеров, которыми управляет этот файл
  db:                                # имя сервиса - произвольная метка, по ней контейнеры видят друг друга по DNS
    image: postgres:16               # образ:тег - откуда взять контейнер и зафиксированная версия
    environment:                     # переменные окружения, которые увидит процесс внутри контейнера
      POSTGRES_PASSWORD: stand       # пароль суперпользователя базы - переменная конкретного образа postgres
    ports:                           # проброс портов host:container
      - "127.0.0.1:5432:5432"        # биндинг только на loopback - снаружи хоста порт не виден, осознанный выбор
    volumes:                         # точки монтирования постоянного хранилища
      - pgdata:/var/lib/postgresql/data   # именованный volume : путь внутри контейнера - данные переживут пересоздание
volumes:                             # верхний уровень - объявление именованных volume, на которые ссылались выше
  pgdata:                            # имя volume - управляется Docker, физически живёт вне контейнера
  • Как читать: найти верхний уровень секций (карта документа) → внутри секции понять, значение это, список или вложенная секция (отступ = вложенность, как в Python) → искать перекрёстные ссылки между секциями (pgdata в volumes внутри services.db ссылается на pgdata в верхнем volumes).
  • Что про безопасность: без явного 127.0.0.1 в ports: Docker по умолчанию биндит на 0.0.0.0 - тот же вопрос, что с Zabbix на 10050, только на уровне синтаксиса Compose.
  • Применимо и к nginx.conf/Prometheus: та же логика секций/вложенности/перекрёстных ссылок (upstream ↔ proxy_pass в nginx; job_name в scrape_configs ↔ Grafana datasource).

🔧Практика

  • Создай обычного администратора, добавь в sudo, проверь sudo -v.
  • Настрой SSH key. Открой вторую сессию и только после успешного входа запрети password/root login. Проверь sshd -t до systemctl reload ssh.
  • Включи firewall c allow только для SSH и требуемых web ports. С внешней машины проверь SSH и закрытый тестовый port.
  • Выполни и сохрани baseline: date; uptime; free -h; df -hT; df -ih; lsblk -f; ip -br a; ip route; ss -ltnp; systemctl --failed.
  • Создай unit hello.service, проверь daemon-reload, enable --now, status, journal и socket.
  • Подними PostgreSQL через compose.yml (структура разобрана выше), зайди в него через psql -c "select version();".

💥Сломай намеренно

  • Останови hello.service. Пройди status → journal → start → curl/ss; запиши exit code и recovery proof.
  • Создай большой тестовый файл в отдельной временной filesystem или Docker volume. Найди его через df → du; очисти и повтори df.
  • Запусти CPU-bound test process с низким приоритетом. Найди PID через top и ps; останови через TERM, проверь отсутствие PID.

✅Задание

Сервер стал медленным

Симптом: latency выросла, alert CPU/RAM/load.

Проверка Норма Аномалия Следующий шаг
uptime load соразмерен CPU load устойчиво выше CPU top/ps
top no single runaway CPU consumer, D-state, swap process или I/O branch
free -h available есть, swap stable swap/OOM pressure top + dmesg
df -hT enough free full volume disk incident
dmesg -T без OOM/I/O errors OOM or device errors limits/restart or storage escalation

Гипотезы: runaway process, memory pressure, disk I/O, external dependency. Первый дешёвый тест: read-only uptime, free, df, top. Fix: изменить только подтверждённую причину. Verification: metric вернулась, request latency normal, logs без новых errors.

Disk full

Симптом: No space left on device, DB/service write error.

df -hT и df -ih → определить space или inode → du -xhd1 /mount → largest path → lsof +L1 для deleted-open files → cleanup по retention/runbook → повторить df, service write и alert.

Нельзя удалять файлы вслепую. Удаление active database/WAL/log без политики превращает capacity incident в data incident.

SSH unavailable

Симптом: client timeout/refused/auth failed.

ssh -vvv user@host фиксирует класс ошибки → консоль/monitoring проверяет host and systemctl status ssh → ss -ltnp | grep :22 → firewall/security group → journalctl -u ssh.

  • Permission denied - сеть дошла, проверять key/user/permissions/sshd config.
  • Connection refused - host reachable, listener отсутствует или reject rule.
  • timeout - route/firewall/security group/host availability.

❓Вопросы с ответами

Почему free показывает мало free memory?

Linux использует свободную RAM для cache. Для capacity важнее поле available, swap trend и OOM events.

df показывает полный disk, а du мало. Почему?

Процесс может держать удалённый файл. lsof +L1 показывает такой PID; место вернётся после controlled restart/close.

Когда L1 эскалирует?

После фиксации impact, timestamps, status, relevant logs and metrics, если known procedure не восстановила сервис или change выходит за разрешённый runbook.
