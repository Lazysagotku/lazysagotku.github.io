Тестирование

🎭Аналогия

Та же приёмка, что в слое 5 инфра-роадмапа. Критерий формулируется до проверки.

📖Теория

Инструменты

Что Чем
Фреймворк xUnit - стандарт в .NET, поддерживается лучше остальных
Утверждения FluentAssertions - читаемые сообщения о падении
Моки Moq или NSubstitute
Интеграционные WebApplicationFactory
База в тестах Testcontainers с настоящим PostgreSQL

⚠️ In-memory провайдер EF - ловушка. Он не PostgreSQL: не проверяет ограничения, иначе ведёт себя с транзакциями, не знает про типы. Тесты зелёные, прод падает. Testcontainers поднимает настоящую базу в Docker.

Структура теста

[Fact]
public async Task Get_ReturnsNotFound_WhenNoteMissing()
{
    // Arrange
    var service = new Mock<INoteService>();
    service.Setup(s => s.GetAsync(42, It.IsAny<CancellationToken>()))
           .ReturnsAsync((NoteDto?)null);
    var controller = new NotesController(service.Object);

    // Act
    var result = await controller.Get(42, CancellationToken.None);

    // Assert
    result.Result.Should().BeOfType<NotFoundResult>();
}

Имя теста отвечает на три вопроса: что тестируем, что ожидаем, при каких условиях.

Интеграционные тесты

public class ApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;
    public ApiTests(WebApplicationFactory<Program> factory) =>
        _client = factory.WithWebHostBuilder(b => b.ConfigureServices(services =>
        {
            // подменить базу на тестовую
        })).CreateClient();

    [Fact]
    public async Task Create_And_Read()
    {
        var created = await _client.PostAsJsonAsync("/api/notes", new { title = "Тест" });
        created.StatusCode.Should().Be(HttpStatusCode.Created);
    }
}

WebApplicationFactory поднимает приложение целиком в памяти, с настоящим конвейером middleware. Аналог TestClient из FastAPI.

Что покрывать

Покрывать Не покрывать
бизнес-логику сервисов автосвойства
граничные случаи и ошибки код фреймворка
контракты API тривиальные обёртки
то, что уже ломалось геттеры DTO

Правило: каждый исправленный баг получает тест, который падал бы до исправления.

🔧Практика

  • xUnit с FluentAssertions на сервисный слой.
  • Моки репозиториев через Moq, логика тестируется без базы.
  • Интеграционные тесты через WebApplicationFactory на основные маршруты.
  • Testcontainers с PostgreSQL для тестов, где нужна настоящая база.
  • Параметризованные тесты через [Theory] и [InlineData] на валидацию.
  • Покрытие через Coverlet с порогом в пайплайне.

💥Сломай намеренно

  • Написать тест на in-memory провайдере, добавить в модель ограничение уникальности - убедиться, что тест зелёный, а на PostgreSQL падает.
  • Замокать всё в тесте контроллера, сломать сервис - убедиться, что тест не заметил.
  • Тест, зависящий от порядка - один создаёт данные, второй их ждёт. Запустить в другом порядке.
  • Тест без утверждений - посмотреть, что покрытие выросло, а проверок нет.
  • Забыть await в асинхронном тесте - увидеть, что он проходит, ничего не проверив.

✅Задание

Life Notes с юнит- и интеграционными тестами, покрытие сервисного слоя выше 70 процентов, тесты гоняются в пайплайне и роняют сборку при падении.

Критерий: объясняешь, почему база в интеграционных тестах настоящая, а не in-memory.

🌍Из жизни

Про in-memory провайдер. Классика: набор из ста зелёных тестов, а на проде падает ограничение уникальности, которого in-memory не знает. Testcontainers стоит нескольких секунд на запуск и закрывает этот класс проблем.

Про тест на каждый баг. Практика, которая окупается быстрее всех остальных: исправленный баг без теста возвращается. С тестом - нет.

❓Вопросы с ответами

Как тестируете ASP.NET Core приложение?

Юнит-тесты на сервисный слой с моками репозиториев, интеграционные через WebApplicationFactory - он поднимает приложение целиком с настоящим конвейером. Базу в интеграционных беру настоящую через Testcontainers.

Почему не in-memory база?

Она не PostgreSQL: не проверяет ограничения, иначе работает с транзакциями, не знает про типы. Тесты зелёные, прод падает. Testcontainers поднимает настоящую базу в Docker за пару секунд.

Что мокаете?

Внешние зависимости и слой данных в юнит-тестах. Свою логику - нет. Тест, где замокано всё, проверяет моки и остаётся зелёным при сломанном приложении.

Какое покрытие считаете достаточным?

Смотрю не на цифру, а на то, что покрыто: бизнес-логика, граничные случаи, ошибки, контракты API. Автосвойства и обёртки не покрываю. И правило - каждый исправленный баг получает тест, который падал бы до исправления.
