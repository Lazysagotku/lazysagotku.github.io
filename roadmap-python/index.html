    Мост от C#: yield здесь работает как yield return в IEnumerable.

    def read_lines(path):
    """Читает лог построчно. Файл в гигабайты не влезет в память целиком."""
    with open(path, encoding="utf-8", errors="replace") as f:
        for line in f:
            yield line.rstrip("\n")

    Декораторы

    Мост от C#: атрибуты плюс обёртки, только выполняются во время исполнения.

    import functools, time, logging

def timed(fn):
    @functools.wraps(fn)              # сохраняет имя и docstring
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            logging.info("%s заняло %.2f с", fn.__name__, time.perf_counter() - start)
    return wrapper

@timed
def collect(query): ...

    ⚠️ Без functools.wraps у обёрнутой функции пропадают __name__ и __doc__. Отладка превращается в набор функций с именем wrapper.

    Параметризованный декоратор - три уровня вложенности:

    def retry(times=3, delay=1.0):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except OSError:
                    if attempt == times - 1:
                        raise
                    time.sleep(delay * (2 ** attempt))   # экспоненциальная пауза
        return wrapper
    return decorator

@retry(times=5, delay=0.5)
def fetch(url): ...

    🌍Из жизни

    Про изменяемые значения по умолчанию. Это баг, который живёт годами: функция работает правильно при каждом отдельном вызове и накапливает мусор при повторных. Ловится обычно тогда, когда кто-то замечает, что список растёт между запросами.

    Про генераторы и память. Разбор лога на десять гигабайт через read() съедает десять гигабайт оперативной. На сервере с четырьмя это MemoryError или OOM killer. Построчный цикл занимает килобайты.

    Про mypy на живом коде. Первый запуск --strict на существующем проекте даёт сотни ошибок и желание всё выключить. Рабочий путь: включить без --strict, починить, потом добавлять строгость по одному флагу.

    ❓Вопросы с ответами

    Чем изменяемые типы отличаются от неизменяемых и почему это важно?

    Присвоение копирует ссылку. Изменяемый объект, переданный в функцию, меняется у всех, кто на него ссылается. Самая известная ловушка - изменяемое значение по умолчанию: оно вычисляется один раз при определении функции и живёт между вызовами. Пишу None и создаю внутри.

    Что такое генератор и когда он нужен?

    Функция с yield, отдающая элементы по одному без материализации. Нужен, когда данных больше, чем памяти, или когда достаточно первых нескольких элементов. В C# это тот же yield return у IEnumerable.

    Зачем functools.wraps?

    Переносит имя, docstring и аннотации с исходной функции на обёртку. Без него все декорированные функции превращаются в wrapper, и отладка становится мучением.

    Что такое контекстный менеджер?

    Объект с __enter__ и __exit__, гарантирующий освобождение ресурса даже при исключении. Аналог using с IDisposable в C#. Свой пишу через @contextmanager и try/finally вокруг yield.

    Чем dataclass лучше словаря?

    Явная структура, автоматические __eq__ и __repr__, проверка типов через mypy, автодополнение в редакторе. frozen=True делает объект неизменяемым и хешируемым, slots=True экономит память.

    Аннотации типов что-то проверяют во время выполнения?

    Нет, интерпретатор их игнорирует. Проверку даёт mypy на этапе разработки или в CI. Плюс аннотации читает FastAPI и Pydantic - там они превращаются в реальную валидацию.

    Async и параллелизм

    6 часов    0/10

    🎭Аналогия

    Одна касса в магазине. Пока кассир пробивает товар, очередь стоит - это счёт, процессор занят. Но если кассир ждёт, пока клиент найдёт карту, он успевает обслужить соседнего - это ожидание, ввод-вывод.

    asyncio - один кассир, который умеет переключаться на время ожидания. multiprocessing - несколько касс. threading - один кассир с несколькими окошками, помогает только на ожидании.

    📖Теория

    Развернуть теорию

    GIL

    Global Interpreter Lock - блокировка, из-за которой в один момент байткод Python выполняет только один поток. На вводе-выводе GIL отпускается, поэтому потоки там работают. На счёте не отпускается, поэтому не работают.

    Задача Инструмент Почему
    Сетевые запросы, файлы, база asyncio сотни одновременных ожиданий на одном потоке
    То же, но библиотека синхронная threading GIL отпускается на вводе-выводе
    Вычисления, обработка данных multiprocessing отдельные процессы, каждый со своим GIL
    Смешанное asyncio плюс run_in_executor тяжёлое уходит в пул

    ⚠️ В 3.13 появился экспериментальный режим без GIL (free-threaded). Упомянуть можно, полагаться пока нет.

    asyncio

    import asyncio, httpx

async def fetch(client: httpx.AsyncClient, url: str) -> dict:
    response = await client.get(url, timeout=10)
    response.raise_for_status()
    return response.json()

async def main(urls: list[str]) -> list[dict]:
    limit = asyncio.Semaphore(10)          # не больше 10 одновременно

    async def guarded(client, url):
        async with limit:
            return await fetch(client, url)

    async with httpx.AsyncClient() as client:
        tasks = [guarded(client, u) for u in urls]
        return await asyncio.gather(*tasks, return_exceptions=True)

asyncio.run(main(urls))

    Что тут важно: - Semaphore ограничивает одновременность. Без него сто задач уйдут разом и получат отказ от сервера. - return_exceptions=True не даёт одной упавшей задаче обрушить весь gather. - Таймаут обязателен на каждом сетевом вызове.

    Мост от C#: async/await тот же паттерн, Task соответствует корутине, SemaphoreSlim соответствует asyncio.Semaphore. Разница в рантайме: в C# потоки из пула, в Python один поток с циклом событий.

    Главная ошибка async

    async def bad():
    time.sleep(5)          # БЛОКИРУЕТ весь цикл событий
    requests.get(url)      # тоже блокирует

async def good():
    await asyncio.sleep(5)
    async with httpx.AsyncClient() as c:
        await c.get(url)

    Одна синхронная блокирующая строка внутри корутины останавливает все остальные задачи. Внешне выглядит как «async не работает».

    Если библиотека только синхронная:

    result = await asyncio.to_thread(blocking_call, arg)

    Отмена и таймауты

    async with asyncio.timeout(30):        # 3.11+
    await long_operation()

task = asyncio.create_task(work())
task.cancel()
try:
    await task
except asyncio.CancelledError:
    pass

    Задача, созданная через create_task, должна где-то ожидаться. Иначе исключение внутри неё исчезнет молча, а сборщик мусора выдаст предупреждение Task exception was never retrieved.

    Про GIL и собеседования. Вопрос про GIL задают почти всегда, когда в резюме есть Python. Плохой ответ - «это глобальная блокировка интерпретатора». Хороший - через практический вывод: потоки для ожидания, процессы для счёта.

    ❓Вопросы с ответами

    Что такое GIL и что он блокирует?

    Блокировка, из-за которой байткод Python в один момент выполняет только один поток. На вводе-выводе она отпускается, поэтому потоки там помогают. На вычислениях не отпускается, поэтому там нужны процессы.

    Когда asyncio, когда threading, когда multiprocessing?

    Asyncio - когда много одновременных ожиданий и библиотеки асинхронные. Threading - то же, но библиотека синхронная и переписывать её нельзя. Multiprocessing - когда задача считает, а не ждёт.

    Что произойдёт при time.sleep() внутри корутины?

    Остановится весь цикл событий вместе со всеми остальными задачами. Нужен await asyncio.sleep(), а для синхронного кода без замены - asyncio.to_thread.

    Как ограничить число одновременных запросов?

    asyncio.Semaphore вокруг вызова. Без него все задачи стартуют разом, и внешний сервис отвечает отказом. Это тот же принцип, что SemaphoreSlim в C#.

    Что будет, если не дождаться задачу из create_task?

    Исключение внутри неё исчезнет молча, а при сборке мусора появится предупреждение о непрочитанном исключении. Задачи надо собирать через gather или явно ожидать.

    🎭Аналогия

    Ресепшн с анкетой. Посетитель заполняет форму, на входе её проверяют по бланку и разворачивают неправильно заполненную сразу, не пуская внутрь. Pydantic - это бланк: он описывает, что считается правильным, и проверка происходит до того, как данные дошли до логики.

    Почему FastAPI

    Flask Django FastAPI

    Аннотации типов в FastAPI работают, а не украшают: из них строится валидация, документация и подсказки редактора.

    Слои приложения

    routers/     маршруты, только приём и отдача
schemas.py   что приходит и что уходит - Pydantic

database.py  подключение и фабрика сессий

    Ровно так устроен трекер откликов. Разбирать надо именно его: код перед глазами, база с данными, и видно, что происходит при изменении.

    Схемы запроса и ответа отдельно

    from pydantic import BaseModel, Field, field_validator

class VacancyIn(BaseModel):
    title: str = Field(min_length=3, max_length=300)
    salary_min: int | None = Field(default=None, ge=0)
    priority: int = Field(default=3, ge=1, le=5)

    @field_validator("title")
    @classmethod
    def strip_title(cls, v: str) -> str:
        return v.strip()

class VacancyOut(BaseModel):
    id: int
    title: str
    status: str
    model_config = {"from_attributes": True}    # читать из ORM-объекта

    ⚠️ Одна модель на вход и на выход - типичная ошибка. Наружу утекают внутренние поля, а внутрь можно передать id и created_at. Разделение схем закрывает это.

    Зависимости

    from fastapi import Depends, HTTPException

def get_session():
    session = SessionLocal()
    try:
        yield session
    finally:
        session.close()

@router.get("/vacancies/{vid}", response_model=VacancyOut)
def read(vid: int, session: Session = Depends(get_session)):
    item = crud.get(session, vid)
    if item is None:
        raise HTTPException(404, "Вакансия не найдена")
    return item

    Depends - это DI-контейнер. Зависимость с yield работает как контекстный менеджер: код после yield выполняется после ответа.

    Вложенные зависимости - так строится авторизация:

    def current_user(token: str = Depends(oauth2_scheme)) -> User: ...
def admin_only(user: User = Depends(current_user)) -> User:
    if not user.is_admin:
        raise HTTPException(403, "Нужны права администратора")
    return user

    Middleware

    @app.middleware("http")
async def add_timing(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Process-Time"] = f"{time.perf_counter() - start:.3f}"
    return response

    Middleware видит все запросы. Годится для логирования, замера времени, идентификатора запроса. Аутентификацию лучше держать в зависимостях - там она привязана к конкретным маршрутам.

    Basic-аутентификация в трекере сделана именно middleware, потому что закрывать надо всё сразу.

    Фоновые задачи

    from fastapi import BackgroundTasks

@router.post("/vacancies")
def create(data: VacancyIn, tasks: BackgroundTasks, session=Depends(get_session)):
    item = crud.create(session, data)
    tasks.add_task(notify, item.id)      # выполнится после ответа
    return item

    ⚠️ BackgroundTasks живёт внутри процесса. Перезапуск - задача потеряна. Для важного нужна очередь: Celery, RQ или таблица заданий в базе.

    Обработка ошибок

    @app.exception_handler(IntegrityError)
async def on_conflict(request: Request, exc: IntegrityError):
    return JSONResponse(status_code=409, content={"detail": "Такая запись уже есть"})

    Общий обработчик держит формат ошибок одинаковым по всему приложению. Без него часть ошибок отдаётся как 500 с трассировкой наружу.

    Аутентификация

    OAuth2 с JWT: маршрут выдаёт токен, зависимость его проверяет.

token = jwt.encode({"sub": user.name, "exp": expires}, SECRET, algorithm="HS256")

    ❓Вопросы с ответами

    Почему FastAPI, а не Flask?

    Валидация и документация строятся из аннотаций типов, async родной. Flask даёт больше свободы и требует собирать это руками. У меня опыт есть с обоими, для нового API беру FastAPI.

    Зачем разделять схемы запроса и ответа?

    Чтобы наружу не уходили внутренние поля, а внутрь нельзя было передать то, что приложение проставляет само - идентификаторы, даты создания. Одна модель на оба направления даёт обе проблемы сразу.

    Что делает Depends?

    Это DI-контейнер: FastAPI сам вызывает зависимость и подставляет результат. Зависимость с yield работает как контекстный менеджер - код после yield выполняется после ответа, там закрывают сессию.

    Middleware или зависимость - что выбрать?

    Middleware, когда правило касается всех запросов: логирование, замер времени, общая аутентификация. Зависимость, когда правило привязано к конкретным маршрутам: права доступа, сессия базы.

    Как реализована аутентификация?

    Basic через middleware Starlette со сравнением hmac.compare_digest, чтобы не утекало время сравнения - разбирал на своём трекере, там она стоит, и я понимаю, зачем именно постоянное по времени сравнение. С нуля такое не писал. Для публичного API брал бы OAuth2 с JWT: пароли хешами через bcrypt, у токена срок жизни, секрет в переменных окружения.

    ⚠️ Этот ответ можно давать только после того, как фаза пройдена. До этого на уточняющий вопрос «а почему именно middleware, а не зависимость» ответить нечем.

    Core и ORM

    Core ORM
    Что пишешь выражения близко к SQL классы и объекты
    Когда лучше массовые операции, аналитика обычная бизнес-логика
    Контроль над SQL полный через настройки загрузки

    В трекере используется ORM. Знать про Core стоит: массовая вставка и сложные отчёты пишутся там проще и работают быстрее.

    Декларативные модели, стиль 2.0

    from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    pass

class Vacancy(Base):
    __tablename__ = "vacancies"

    id: Mapped[int] = mapped_column(primary_key=True)
    company_id: Mapped[int] = mapped_column(ForeignKey("companies.id", ondelete="CASCADE"), index=True)
    title: Mapped[str] = mapped_column(String(300))
    status: Mapped[Status] = mapped_column(Enum(Status, name="vacancy_status"), index=True)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())

    company: Mapped["Company"] = relationship(back_populates="vacancies")
    events: Mapped[list["Event"]] = relationship(back_populates="vacancy", cascade="all, delete-orphan")

    Mapped[...] - типизация, которую понимает и mypy, и SQLAlchemy. Это стиль 2.0, старый через Column(...) встречается в примерах из интернета.

    N+1 - главная проблема любой ORM

    # ПЛОХО: один запрос за списком плюс по запросу на каждую компанию
for v in session.scalars(select(Vacancy)):
    print(v.company.name)

# ХОРОШО: один запрос с соединением
stmt = select(Vacancy).options(joinedload(Vacancy.company))
for v in session.scalars(stmt).unique():
    print(v.company.name)
    Стратегия Что делает Когда
    lazy="select" грузит при обращении, по умолчанию связь нужна редко
    joinedload одним запросом с JOIN связь «много к одному»
    selectinload вторым запросом с IN связь «один ко многим»
    raiseload бросает исключение при ленивой загрузке чтобы найти N+1 в тестах

    ⚠️ raiseload("*") в тестах - способ поймать все N+1 разом, вместо того чтобы искать их по логам.

    Сессия и жизненный цикл

    with SessionLocal() as session:
    with session.begin():          # commit при выходе, rollback при исключении
        session.add(item)

    Три состояния объекта: transient (создан, не в сессии), pending (добавлен, не сохранён), persistent (сохранён). После commit объекты по умолчанию устаревают и при следующем обращении делают новый запрос. expire_on_commit=False это отключает - в трекере так и сделано.

    Как посмотреть настоящий SQL

    engine = create_engine(url, echo=True)          # всё в лог

print(stmt.compile(compile_kwargs={"literal_binds": True}))   # один запрос

    Это первое, что надо делать при разборе медленной страницы: увидеть, во что превратился код.

    Alembic

    alembic revision --autogenerate -m "добавить приоритет"
alembic upgrade head
alembic downgrade -1
alembic history --verbose

    ⚠️ Autogenerate не всесилен. Он не видит переименования (показывает как удаление плюс добавление), изменения типов в некоторых случаях, изменения в данных. Каждую сгенерированную миграцию надо читать глазами до применения.

    Правила миграций в проде: 1. Читать сгенерированное перед применением. 2. Писать downgrade, а не оставлять pass. 3. Разделять изменение схемы и перенос данных на разные миграции. 4. Добавлять колонку с NOT NULL в три шага: колонка допускающая пустоту, заполнение, ограничение. 5. Индексы на больших таблицах - CREATE INDEX CONCURRENTLY через op.execute.

    Асинхронный доступ

    from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

engine = create_async_engine("postgresql+asyncpg://...")
Session = async_sessionmaker(engine, expire_on_commit=False)

async with Session() as session:
    result = await session.scalars(select(Vacancy).limit(10))

    ⚠️ В асинхронном режиме ленивая загрузка связей не работает - обращение к незагруженной связи бросает исключение. Загрузку надо указывать явно через selectinload.

    🌍Из жизни

    Про N+1 на проде. Страница со списком из двадцати элементов делает двадцать один запрос. На тестовых данных незаметно, на реальных с сетевой задержкой до базы страница открывается секундами. Это самая частая причина «сайт стал тормозить, а код не меняли» - выросло число строк.

    Про autogenerate и переименование. Реальный сценарий потери данных: разработчик переименовал колонку, autogenerate сгенерировал drop_column плюс add_column, миграция уехала на прод, данные из колонки исчезли. Поэтому правило читать сгенерированное глазами.

    Про пустой downgrade. Alembic вставляет pass в downgrade, если не смог придумать обратное. Обнаруживается это в момент, когда откат нужен срочно.

    ❓Вопросы с ответами

    Что такое N+1 и как его найти?

    Один запрос за списком и по запросу на каждый элемент за связанными данными. Нахожу через echo=True в логе или через raiseload("*") в тестах, который бросает исключение на ленивой загрузке. Лечится joinedload для связи «много к одному» и selectinload для «один ко многим».

    Чем joinedload отличается от selectinload?

    joinedload тянет одним запросом через JOIN, хорош для «много к одному». selectinload делает второй запрос с IN, хорош для «один ко многим» - JOIN там размножает строки основной таблицы.

    Как делаете миграции без простоя?

    Читаю сгенерированное перед применением. Колонку с NOT NULL добавляю в три шага: сначала допускающая пустоту, потом заполнение, потом ограничение. Индексы на больших таблицах - CREATE INDEX CONCURRENTLY. Изменение схемы и перенос данных - разные миграции.

    Что autogenerate не увидит?

    Переименования - он покажет их как удаление плюс добавление, то есть потерю данных. Часть изменений типов. Изменения в самих данных. Поэтому каждую миграцию читаю глазами.

    Когда Core вместо ORM?

    Массовые операции и аналитика. Обновление тысяч строк через ORM означает загрузить их в память и обновить по одной. Через Core это один update() на стороне базы.

    Пирамидой: много быстрых юнит-тестов, меньше интеграционных на связку с базой, единицы сквозных. Каждый тест идёт в своей транзакции с откатом, поэтому тесты не видят друг друга и не зависят от порядка.

    Что мокаете, а что нет?

    Мокаю внешние вызовы, отправку сообщений, время. Не мокаю свою логику и базу в интеграционных тестах. Тест, где замокано всё, проверяет моки и остаётся зелёным при сломанном приложении.

    Как тестируете FastAPI-приложение?

    TestClient для синхронного, httpx.AsyncClient с ASGITransport для асинхронного. Зависимость сессии подменяю через dependency_overrides на тестовую, идущую в транзакции с откатом.

    Покрытие 100 процентов - это хорошо?

    Покрытие показывает выполненные строки, а не проверенные. Смысл цифры - находить непокрытые куски. Как цель она даёт тесты без утверждений.

    ⚠️ Незакреплённые версии - причина «вчера собиралось, сегодня нет». В requirements.txt версии должны быть точными.

    Контейнер для Python

    FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
RUN useradd -m app
COPY --from=builder /install /usr/local
COPY . .
USER app
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

    Что тут важно: - многоэтапная сборка - в итоговый образ не попадают инструменты сборки; - PYTHONUNBUFFERED=1 - обязательно, иначе логи буферизуются и в docker logs пусто; - USER app - не root внутри контейнера; - requirements.txt копируется отдельно и раньше кода: слой с зависимостями кешируется и не пересобирается при каждом изменении кода; - .dockerignore с .venv, __pycache__, .git, иначе образ распухает.

    Как запускают в проде

    # один процесс
uvicorn app.main:app --host 0.0.0.0 --port 8000

# несколько рабочих процессов
gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 4 --bind 0.0.0.0:8000

    Число процессов обычно 2 × ядра + 1, но для асинхронного приложения меньше: каждый и так держит много соединений. Больше процессов означает больше соединений к базе - это надо согласовать с пулом.

    🌍Из жизни

    Про пустые логи в контейнере. Классика первого дня с Docker: приложение работает, docker logs пуст. Причина - буферизация вывода Python. Одна переменная окружения, а ищут её часами.

    Про размер образа. Наивный Dockerfile на python:3.12 с копированием всего каталога даёт образ под гигабайт. Многоэтапная сборка на slim плюс .dockerignore дают 150-200 МБ. Разница видна на каждом деплое.

    ❓Вопросы с ответами

    Как запускаете FastAPI в проде?

    Gunicorn с воркерами uvicorn, число процессов согласовано с пулом соединений к базе. Перед ним nginx, который терминирует TLS и раздаёт статику. Логи в stdout, забирает их сборщик.

    Чем отличается контейнер для Python от контейнера для .NET?

    Нет отдельного шага компиляции: собирать нечего, ставятся зависимости. Зато нужен PYTHONUNBUFFERED, иначе логи не видны, и многоэтапная сборка нужна, чтобы в итоговый образ не попали инструменты сборки.

    Как передаёте настройки?

    Через переменные окружения, читаю pydantic-settings. Отсутствие обязательной переменной ловится при старте, а не в момент первого обращения. Секреты в репозитории не лежат, там только .env.example.

    Почему requirements.txt копируется отдельно?

    Docker кеширует слои. Если сначала скопировать весь код, любое изменение в нём инвалидирует слой с установкой зависимостей, и они ставятся заново при каждой сборке.

    Repository и Unit of Work

    class VacancyRepo:
    def __init__(self, session: Session):
        self._session = session

    def get(self, vid: int) -> Vacancy | None:
        return self._session.get(Vacancy, vid)

    def by_status(self, status: Status) -> list[Vacancy]:
        return list(self._session.scalars(
            select(Vacancy).where(Vacancy.status == status)
        ))

def top_vacancies(limit: int = 20) -> list[dict]:
    key = f"top:{limit}"
    if (cached := r.get(key)):

    Три вопроса к любому кэшу: 1. Сколько живёт запись. 2. Что происходит при изменении данных - сбрасываем или ждём истечения. 3. Что будет при недоступности Redis - приложение падает или работает медленнее.

    Третий вопрос забывают чаще всего. Правильный ответ: кэш - ускоритель, приложение обязано работать без него.

    Cache stampede: запись истекла, сто запросов одновременно пошли считать заново. Лечится блокировкой на пересчёт или разбросом времени жизни.

    Отказоустойчивость

    Приём Что делает
    Таймаут ограничивает ожидание внешнего вызова
    Повтор с ростом паузы переживает кратковременный сбой
    Джиттер разводит одновременные повторы
    Circuit breaker перестаёт звонить в мёртвый сервис
    Деградация отдаёт часть данных вместо ошибки

    ⚠️ Повтор без ограничения одновременности превращает мелкий сбой в лавину: сервис прилёг на секунду, все клиенты ретраятся разом, он ложится совсем.

    ❓Вопросы с ответами

    Как организуете код в проекте?

    Слоями: маршруты только принимают и отдают, сервисы держат логику, слой данных знает про базу. Зависимости идут внутрь: сервисы не импортируют FastAPI, домен не импортирует SQLAlchemy. В маленьком проекте трёх слоёв хватает, полная чистая архитектура там даёт больше папок, чем пользы.

    Когда нужна очередь, а когда хватит фоновой задачи?

    BackgroundTasks для мелочи, потеря которой не страшна: она живёт в процессе и исчезает при перезапуске. Очередь нужна, когда задачу нельзя потерять, нужны повторы, расписание или видимость статуса.

    Как кэшируете?

    С явным временем жизни и сбросом при изменении данных. Главное правило - приложение обязано работать при недоступности кэша, медленнее, но работать. Плюс защита от одновременного пересчёта после истечения.

    Как защищаетесь от отказов внешних сервисов?

    Таймаут на каждый вызов, повтор с растущей паузой и джиттером, ограничение одновременности. Для часто отказывающего - размыкатель, чтобы не звонить в мёртвый сервис. И деградация: отдать часть данных с пометкой лучше, чем ошибку.

    FastAPI, Django или Flask - как выбираете?

    По задаче. FastAPI для нового API с async и автодокументацией. Django, когда нужны админка, ORM и аутентификация из коробки. Flask для маленького сервиса с полным контролем. Работал с Flask и Django на реальных задачах, поэтому выбор осознанный.
