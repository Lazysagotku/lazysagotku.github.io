Упаковка и эксплуатация

4 часа

🎭Аналогия

Разница между «работает у меня» и «работает у всех». Рецепт в голове повара против рецепта, записанного с граммовкой: второй воспроизводится на другой кухне.

📖Теория

Зависимости и окружение

Инструмент Что делает
venv изолированное окружение, встроен
pip-tools requirements.in в закреплённый requirements.txt
poetry зависимости плюс сборка пакета
uv быстрая замена pip и venv, набирает популярность

⚠️ Незакреплённые версии - причина «вчера собиралось, сегодня нет». В requirements.txt версии должны быть точными.

Контейнер для Python

FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
RUN useradd -m app
COPY --from=builder /install /usr/local
COPY . .
USER app
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Что тут важно: - многоэтапная сборка - в итоговый образ не попадают инструменты сборки; - PYTHONUNBUFFERED=1 - обязательно, иначе логи буферизуются и в docker logs пусто; - USER app - не root внутри контейнера; - requirements.txt копируется отдельно и раньше кода: слой с зависимостями кешируется и не пересобирается при каждом изменении кода; - .dockerignore с .venv, __pycache__, .git, иначе образ распухает.

Как запускают в проде

# один процесс
uvicorn app.main:app --host 0.0.0.0 --port 8000

# несколько рабочих процессов
gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 4 --bind 0.0.0.0:8000

Число процессов обычно 2 × ядра + 1, но для асинхронного приложения меньше: каждый и так держит много соединений. Больше процессов означает больше соединений к базе - это надо согласовать с пулом.

Конфигурация

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    app_password: str
    debug: bool = False
    model_config = {"env_file": ".env"}

settings = Settings()

Мост от C#: это IOptions. Отсутствие обязательной переменной обнаруживается при старте, а не в момент первого обращения.

⚠️ .env в .gitignore, в репозитории только .env.example без значений.

Логирование

import logging, sys, json

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({
            "ts": self.formatTime(record),
            "level": record.levelname,
            "msg": record.getMessage(),
            "logger": record.name,
        }, ensure_ascii=False)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(JsonFormatter())
logging.basicConfig(level=logging.INFO, handlers=[handler])

В контейнере логи идут в stdout, а не в файл - их забирает демон Docker или сборщик логов. Структурированный формат нужен, если логи попадают в Elastic или Loki.

🔧Практика

  • Собрать многоэтапный образ трекера, посмотреть размер до и после.
  • Добавить .dockerignore, пересобрать, сравнить размер.
  • docker-compose с трекером и PostgreSQL, проверить, что приложение находит базу по имени сервиса.
  • Перевести настройки на pydantic-settings, убрать чтение .env руками.
  • Убрать PYTHONUNBUFFERED, посмотреть на пустой docker logs, вернуть.
  • Запустить через gunicorn с четырьмя процессами, посмотреть число соединений в pg_stat_activity.

💥Сломай намеренно

  • Убрать PYTHONUNBUFFERED=1 и убедиться, что логи не появляются в docker logs до заполнения буфера.
  • Скопировать код до requirements.txt в Dockerfile, поменять одну строку кода, пересобрать - увидеть, что зависимости ставятся заново.
  • Не поставить .dockerignore и собрать образ с .venv внутри - посмотреть на размер.
  • Убрать обязательную переменную окружения и убедиться, что pydantic-settings падает на старте с понятным текстом.
  • Поставить 16 процессов gunicorn при пуле базы на 20 и погонять нагрузку - упереться в max_connections.

✅Задание

Трекер собирается многоэтапным Dockerfile, образ меньше 200 МБ, запускается из docker-compose с базой, настройки через pydantic-settings, логи структурированные и видны в docker logs.

Критерий: объясняешь каждую строку Dockerfile и почему requirements.txt копируется раньше кода.

🌍Из жизни

Про пустые логи в контейнере. Классика первого дня с Docker: приложение работает, docker logs пуст. Причина - буферизация вывода Python. Одна переменная окружения, а ищут её часами.

Про размер образа. Наивный Dockerfile на python:3.12 с копированием всего каталога даёт образ под гигабайт. Многоэтапная сборка на slim плюс .dockerignore дают 150-200 МБ. Разница видна на каждом деплое.

Про число процессов и пул базы. Четыре процесса gunicorn с пулом по 10 соединений каждый - это 40 соединений от одного приложения. Три экземпляра - 120. При max_connections 100 всё встаёт, и выглядит это как «база отказала».

❓Вопросы с ответами

Как запускаете FastAPI в проде?

Gunicorn с воркерами uvicorn, число процессов согласовано с пулом соединений к базе. Перед ним nginx, который терминирует TLS и раздаёт статику. Логи в stdout, забирает их сборщик.

Чем отличается контейнер для Python от контейнера для .NET?

Нет отдельного шага компиляции: собирать нечего, ставятся зависимости. Зато нужен PYTHONUNBUFFERED, иначе логи не видны, и многоэтапная сборка нужна, чтобы в итоговый образ не попали инструменты сборки.

Как передаёте настройки?

Через переменные окружения, читаю pydantic-settings. Отсутствие обязательной переменной ловится при старте, а не в момент первого обращения. Секреты в репозитории не лежат, там только .env.example.

Почему requirements.txt копируется отдельно?

Docker кеширует слои. Если сначала скопировать весь код, любое изменение в нём инвалидирует слой с установкой зависимостей, и они ставятся заново при каждой сборке.
