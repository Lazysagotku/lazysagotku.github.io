Классический набор SQL-вопросов среднего/продвинутого уровня. Пересекается с PostgreSQL_Companion.md (индексы, EXPLAIN) и CSharp_Interview_Questions.md (раздел 15) — не дублирую там, где уже разобрано, только ссылаюсь.

1. Разница между WHERE и HAVING

Суть: WHERE фильтрует СТРОКИ до группировки — не может использовать агрегатные функции. HAVING фильтрует ГРУППЫ после GROUP BY — работает именно с результатами агрегации.

SELECT department, COUNT(*) AS cnt
FROM employees
WHERE status = 'active'   -- фильтр строк ДО группировки
GROUP BY department
HAVING COUNT(*) > 5;      -- фильтр групп ПОСЛЕ агрегации

Частая ошибка на собесе: попытка написать WHERE COUNT(*) > 5 — не скомпилируется, агрегат в WHERE недоступен.

2. Как работают JOIN (INNER, LEFT, RIGHT, FULL, CROSS)

Аналогия из жизни: два списка гостей — со стороны жениха и со стороны невесты. INNER JOIN — только те, кто в ОБОИХ списках. LEFT JOIN — весь список невесты, плюс пересечение с женихом (для остальных — пусто). RIGHT JOIN — зеркально, весь список жениха. FULL JOIN — оба списка целиком, объединённые. CROSS JOIN — вообще без сверки списков: каждый гость невесты танцует с каждым гостем жениха (декартово произведение).

-- INNER: только совпадения
SELECT * FROM orders o INNER JOIN customers c ON c.id = o.customer_id;

-- LEFT: все заказы, даже если клиент удалён (customer_name = NULL)
SELECT * FROM orders o LEFT JOIN customers c ON c.id = o.customer_id;

-- FULL: все заказы И все клиенты, даже без взаимных совпадений
SELECT * FROM orders o FULL JOIN customers c ON c.id = o.customer_id;

-- CROSS: декартово произведение — n × m строк, без ON
SELECT * FROM sizes CROSS JOIN colors; -- все комбинации размер×цвет

Частый вопрос: как найти клиентов БЕЗ заказов? → LEFT JOIN orders o ON ... WHERE o.id IS NULL (уже разобрано в PostgreSQL_Companion.md, раздел про support-запросы).

3. В чём суть оконных функций (OVER, PARTITION BY)

Аналогия из жизни: класс, разбитый на группы за партами (PARTITION BY = разбивка на группы). В отличие от классного журнала (GROUP BY), который сводит каждую группу в одну строку с итогом, оконная функция считает итог ПО ГРУППЕ, но оставляет видимым каждого отдельного ученика — никто не пропадает из результата.

SELECT name, department, salary,
       AVG(salary) OVER (PARTITION BY department) AS dept_avg
FROM employees;
-- каждая строка — отдельный сотрудник, но рядом видно средний оклад ЕГО отдела

GROUP BY дал бы одну строку на отдел (со средним), потеряв имена людей. Оконная функция даёт и то, и другое сразу.

4. Как найти вторую по величине зарплату

Три рабочих способа (от простого к надёжному):

-- 1. LIMIT/OFFSET — ловушка: без DISTINCT два одинаковых максимума дадут неверный ответ
SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;

-- 2. Через MAX с исключением текущего максимума
SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees);

-- 3. Самый надёжный — DENSE_RANK, корректно обрабатывает дубли по максимуму
SELECT salary FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
) t
WHERE rnk = 2;

Почему важен DISTINCT в способе 1: если два человека получают одинаковый максимум, LIMIT 1 OFFSET 1 без DISTINCT вернёт ТОТ ЖЕ максимум второй раз, а не настоящую вторую по величине зарплату.

5. RANK(), DENSE_RANK(), ROW_NUMBER() — разница

Аналогия из жизни: олимпийское награждение. Если два спортсмена делят золото, RANK даёт им обоим 1-е место, а следующий получает СРАЗУ 3-е (2-е место "сгорает", как в реальной олимпийской системе). DENSE_RANK тоже даёт обоим 1-е, но следующий получает 2-е — мест не теряется. ROW_NUMBER вообще не смотрит на равенство — просто нумерует по порядку 1,2,3,4, будто оценки разные, даже если они одинаковые.

-- Зарплаты: 100, 100, 90, 80
SELECT salary,
    ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn,
    RANK()       OVER (ORDER BY salary DESC) AS rnk,
    DENSE_RANK() OVER (ORDER BY salary DESC) AS drnk
FROM salaries;
-- 100 → rn=1  rnk=1  drnk=1
-- 100 → rn=2  rnk=1  drnk=1
-- 90  → rn=3  rnk=3  drnk=2   ← RANK прыгает на 3, DENSE_RANK идёт подряд на 2
-- 80  → rn=4  rnk=4  drnk=3

6. Что такое CTE и зачем их использовать

Аналогия из жизни: именованный под-рецепт, который пишешь один раз ("соус для пасты — вот шаги"), а потом просто ссылаешься на него по имени в основном рецепте, вместо того чтобы каждый раз переписывать все шаги заново.

Суть: WITH name AS (...) — временный именованный результат запроса, живёт только в рамках этого запроса. Делает сложный запрос читаемым (разбивка на логические шаги) и позволяет рекурсию (WITH RECURSIVE — подробно разобрано в PostgreSQL_Companion.md, раздел про циклы/RBAR).

WITH high_earners AS (
    SELECT * FROM employees WHERE salary > 100000
)
SELECT department, COUNT(*) FROM high_earners GROUP BY department;

Нюанс для глубины ответа: до PostgreSQL 12 CTE ВСЕГДА материализовался отдельным шагом (optimization fence — планировщик не мог "протолкнуть" фильтры внутрь него). С версии 12 непереиспользуемый CTE по умолчанию инлайнится в основной запрос, если явно не помечен MATERIALIZED.

7. Как оптимизировать медленный запрос

Чек-лист (детали каждого пункта — в PostgreSQL_Companion.md и CSharp_Interview_Questions.md, разделы 13-15):

  1. EXPLAIN ANALYZE — искать Seq Scan там, где ожидался Index Scan.
  2. Проверить sargability предикатов (функция над индексируемой колонкой в WHERE ломает использование индекса).
  3. Проверить, есть ли индексы на колонках в JOIN/WHERE/ORDER BY.
  4. Проверить актуальность статистики (ANALYZE table_name) — устаревшая статистика вводит планировщик в заблуждение.
  5. Не тянуть SELECT *, если нужны не все колонки.
  6. Для больших смещений — курсорная пагинация (WHERE id > последний_id) вместо LIMIT/OFFSET, который деградирует на больших смещениях.
  7. Проверить N+1 на уровне приложения, если запрос вызывается в цикле.

8. Как работают индексы и почему они ускоряют поиск

Аналогия из жизни: указатель терминов в конце книги (уже использовалась для поисковых БД в NoSQL_Companion.md) — вместо чтения всей книги искать нужное слово по алфавитному списку со страницами.

Суть: индекс — отдельная, отсортированная структура (обычно B-Tree), которая позволяет находить строки через что-то похожее на бинарный поиск (O(log n)), вместо перебора всей таблицы (O(n), Seq Scan). Плата за это — индекс занимает место на диске и замедляет INSERT/UPDATE/DELETE (каждое изменение обновляет ещё и индекс, не только саму таблицу).

9. UNION и UNION ALL

Суть: оба объединяют результаты двух запросов с одинаковым числом и типом колонок. UNION убирает дубликаты строк (требует неявной сортировки/сравнения — дороже). UNION ALL оставляет всё как есть, включая дубли — быстрее, если дубликаты не мешают или их точно не будет.

SELECT city FROM customers
UNION          -- уникальные города
SELECT city FROM suppliers;

SELECT city FROM customers
UNION ALL      -- все города, включая повторы
SELECT city FROM suppliers;

10. Работа с NULL в агрегатных функциях

Ключевые факты: - SUM, AVG, MAX, MIN, COUNT(column) — все ИГНОРИРУЮТ NULL, не учитывают их в расчёте. - COUNT(*) считает ВСЕ строки (включая те, где есть NULL в каких-то колонках). COUNT(column) считает только строки, где ЭТА колонка НЕ NULL — классическая разница, которую любят спрашивать. - AVG() = SUM()/COUNT(), но раз оба игнорируют NULL — среднее считается только по реально заполненным значениям, NULL НЕ приравнивается к нулю. Частая ошибочная интуиция — что NULL "учтётся как 0" и снизит среднее, это не так. - SUM() по колонке, где ВСЕ значения NULL, вернёт NULL, а не 0. Если нужен именно 0 — COALESCE(SUM(col), 0).
