Реляционные БД — живой companion-документ

84 строк · источник l2code/RelationalDB_Companion.md

Часть 3 из видео-конспектов ("реляционные базы данных с нуля"). Пересекается с основами SQL из NoSQL_Companion.md (ACID, примеры БД) — не дублирую, фокус здесь на том, чего там не было: нормализация, типы связей, транзакции подробнее.

С чего всё начинается

Аналогия из источника (сохраняю — простая и рабочая): собираешь деньги на подарок другу, записываешь на бумажке, кто сколько скинул — таблица с именами и суммами, разделённая и структурированная. Это уже база данных. Excel-файл — тот же принцип, но удобнее редактировать/сортировать/удалять.

Почему одной таблицы/файла недостаточно: когда данных много и они логически связаны (пользователи, каналы, видео — как в клоне YouTube), одна таблица становится неудобной и медленной. Разделение на несколько связанных таблиц = реляционная БД (relation = связь).

Нормализация, Primary Key, Foreign Key

Нормализация — процесс разбиения данных на несколько таблиц, чтобы избавиться от избыточных (повторяющихся) данных.

Primary Key (первичный ключ) — уникальный ID записи в таблице. Foreign Key (внешний ключ) — то же значение, но в ДРУГОЙ таблице, которая ссылается на первую.

Три типа связей между таблицами

One-to-Many / Many-to-One (один-ко-многим)

У одного канала — много видео, но у каждого видео — только один канал. Это одно и то же отношение, просто смотреть на него можно с двух сторон (канал→видео = один-ко-многим, видео→канал = многие-к-одному).

One-to-One (один к одному)

Редкий тип связи. Пример из источника: один пользователь — максимум один канал.

[!info]+ Уточнение — не только про безопасность Источник объясняет one-to-one как способ "для безопасности". На практике причин больше: бизнес-правило (один юзер — один канал), разделение редко используемых/чувствительных полей в отдельную таблицу с другими правами доступа, или вынесение опциональных полей (не у каждой записи они есть) в отдельную таблицу вместо кучи NULL-столбцов в основной.

Many-to-Many (многие ко многим)

Нужна промежуточная (junction) таблица. Пример из источника — таблица лайков: хранит пары (ID пользователя, ID видео) — каждый пользователь может лайкнуть любое видео, каждое видео может быть лайкнуто многими пользователями.

СУБД и SQL

СУБД (система управления базами данных) — программа для создания/редактирования/администрирования БД. SQL (Structured Query Language) — язык запросов к ней.

SELECT name FROM videos WHERE channel_id = 201;
-- "выбери имена из таблицы видео, где ID канала = 201"

Для данных из нескольких таблиц сразу — JOIN.

Схема и ограничения (constraints)

Схема (schema) — описание структуры таблицы, её полей и ограничений. Изменение схемы (добавить/убрать столбец) касается ВСЕХ строк таблицы.

Зачем нужны ограничения: для целостности данных. Primary/Foreign Key не дают вставить запись, ссылающуюся на несуществующий ID. Другие ограничения — запрет дублей, запрет пустых (NULL) значений там, где это критично.

Транзакции

Суть: склеивает несколько SQL-запросов в одну неделимую операцию.

Пример из источника (хороший, наглядный): вставляешь запись в первую таблицу, затем во вторую — с ID только что вставленной записи. Без транзакции: если между двумя шагами обрывается соединение, первая запись уже в базе, вторая — нет. При повторной попытке — ошибка "запись уже существует" (из-за первой половины) при том что нужного результата так и нет. С транзакцией: при сбое на любом шаге — полный откат к состоянию ДО начала транзакции, никаких "половинчатых" данных.

ACID — подробный разбор (дополняет краткую версию из NoSQL_Companion.md)

  • Atomicity (атомарность) — операция выполняется целиком или не выполняется вообще (см. транзакции выше).
  • Consistency (согласованность) — записываемые данные обязаны соответствовать всем ограничениям (PK/FK/уникальность/NOT NULL).
  • Isolation (изолированность) — параллельно идущие транзакции не влияют друг на друга — критично для высоконагруженных БД.
  • Durability (надёжность) — если транзакция подтверждена (committed), данные сохранены даже при сбое сразу после этого.

Примеры реляционных БД: Microsoft SQL Server, Oracle Database, MySQL, MariaDB, PostgreSQL.
