🗺️ AI Product Engineer Roadmap

115 строк · источник l2code/AIEngineer_Roadmap.md

💤 СПЯЩИЙ план — Tier 2, двойное условие активации: не раньше сентября 2026 И после трудоустройства. До этого — ноль обязательных часов, файл существует для просмотра "в перерывах". Отличие от классического ML/Data Science трека: здесь не про обучение моделей, а про встраивание готовых LLM в реальные продукты — инженерия вокруг модели, не внутри неё. Стратегическое преимущество: C# backend + Python + практический ежедневный опыт работы с Claude — редкое сочетание, большинство AI-инженеров не имеют production backend бэкграунда.

📊 Статус

  • [ ] Фаза 1 — Фундамент LLM (концептуально, без матчасти)
  • [ ] Фаза 2 — Работа с LLM API
  • [ ] Фаза 3 — RAG (Retrieval Augmented Generation)
  • [ ] Фаза 4 — Агенты и MCP
  • [ ] Фаза 5 — Продакшен AI-инженерия
  • [ ] Фаза 6 — Прикладной проект

Уже есть предпосылки (не с нуля): REST API — знаешь; PostgreSQL — уверенно (прямой мост к pgvector, Фаза 3); ежедневная практика работы с Claude Code — уже реальный, а не гипотетический опыт промпт-инжиниринга.

🔵 Фаза 1 — Фундамент LLM

Цель: понимать, с чем работаешь, не как с чёрным ящиком

Темы

  • [ ] 1.1 Как устроены токены — почему модель "не считает буквы в слове", context window как реальное ограничение
  • [ ] 1.2 Роли в диалоге — system/user/assistant, зачем system prompt отдельно
  • [ ] 1.3 Temperature, top-p — что реально меняют в поведении модели
  • [ ] 1.4 Промпт-инжиниринг — структура хорошего промпта, few-shot vs zero-shot
  • [ ] 1.5 Где модель "галлюцинирует" и почему — не баг, а свойство архитектуры (важно для честного объяснения на собесе)

🎯 Итоговое задание

Написать короткий разбор (для себя, не для публикации): 5 промптов, которые ты уже интуитивно писал хорошо в работе с Claude Code — разложить, ПОЧЕМУ они сработали, в терминах фазы 1.

🟢 Фаза 2 — Работа с LLM API

Цель: уметь встроить вызов модели в реальный код, не только в чат

Темы

  • [ ] 2.1 Claude API / OpenAI API — базовый вызов, структура ответа
  • [ ] 2.2 Streaming — IAsyncEnumerable<T> в C# SDK (прямая связь с уже пройденным Phase1 §1.8)
  • [ ] 2.3 Tool use / function calling — как модель "вызывает" твой код
  • [ ] 2.4 Structured outputs — заставить модель вернуть валидный JSON под твою схему
  • [ ] 2.5 Управление стоимостью — токены на вход/выход, кэширование промптов
  • [ ] 2.6 Обработка ошибок API — rate limits, retry-логика (прямой мост к Polly, C#-роадмап §9.9)

🎯 Итоговое задание

Консольное приложение на C#, вызывающее Claude API: отправляет вопрос, стримит ответ токен-за-токеном в консоль, корректно обрабатывает CancellationToken (мост к Phase3_Advanced.md §3.4).

🟡 Фаза 3 — RAG (Retrieval Augmented Generation)

Цель: научить модель отвечать по ТВОИМ данным, не только по тому, что она "помнит" Прямой мост — PostgreSQL уже уверенно.

Темы

  • [ ] 3.1 Эмбеддинги — что это такое, как текст превращается в вектор
  • [ ] 3.2 pgvector — векторный поиск прямо в PostgreSQL, без отдельной векторной БД
  • [ ] 3.3 Chunking-стратегии — как правильно резать документы перед индексацией
  • [ ] 3.4 Гибридный поиск — векторный + полнотекстовый (мост к уже изученным GIN-индексам, PostgreSQL_Companion.md)
  • [ ] 3.5 Оценка качества RAG — как понять, что поиск реально находит релевантное

🎯 Итоговое задание

RAG поверх собственных заметок из Life Notes — на вопрос пользователя находит релевантные заметки через pgvector и передаёт их в промпт модели.

🟠 Фаза 4 — Агенты и MCP

Цель: не просто вызвать модель один раз, а построить цикл "думает → действует → проверяет"

Темы

  • [ ] 4.1 ReAct loop — промпт → tool call → observe → repeat
  • [ ] 4.2 Дизайн инструментов агента — что делает инструмент "хорошим" (чёткое имя, описание, схема параметров)
  • [ ] 4.3 MCP (Model Context Protocol) — написать СВОЙ сервер, не только пользоваться готовыми (уже трогал как потребитель)
  • [ ] 4.4 Многошаговое планирование — когда агенту нужно несколько шагов подряд
  • [ ] 4.5 Human-in-the-loop — где агенту нужно подтверждение перед действием (тот же принцип, что "Human review" в вакансиях автоматизации, которые уже разбирали)

🎯 Итоговое задание

Свой MCP-сервер (например поверх Life Notes API) + простой агент, который через ReAct loop находит и суммирует заметки по теме.

🔴 Фаза 5 — Продакшен AI-инженерия

Цель: то, что отличает демо от реального продукта

Темы

  • [ ] 5.1 Evaluation — как систематически проверять качество ответов модели, не "на глаз"
  • [ ] 5.2 Guardrails — защита от нежелательного ввода/вывода
  • [ ] 5.3 Observability для AI — логирование промптов/ответов, трейсинг агентных цепочек
  • [ ] 5.4 Версионирование промптов — промпт меняется так же, как код, нужен контроль версий
  • [ ] 5.5 Задержка и UX — почему стриминг критичен для восприятия скорости
  • [ ] 5.6 Semantic Kernel (C#) vs LangChain/LangGraph (Python) — выбор трека, оба языка уже есть, стоит попробовать оба

🎯 Итоговое задание

Взять агента из Фазы 4, добавить логирование каждого шага цепочки (какой инструмент вызван, что вернул) — минимальная observability, не полноценный APM.

🏗️ Фаза 6 — Прикладной проект

Цель: не учебный пример, а фича, которая реально используется

Темы

  • [ ] 6.1 AI-инсайты по заметке в Life Notes через Claude API — Life Notes уже готов как база
  • [ ] 6.2 Собрать всё вместе — RAG (Фаза 3) + агент (Фаза 4) + observability (Фаза 5) в одной фиче
  • [ ] 6.3 Rate limiting и retry на реальном трафике — Polly в действии, не в теории
