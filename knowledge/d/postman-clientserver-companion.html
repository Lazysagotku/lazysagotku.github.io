Postman и клиент-серверная архитектура — живой companion-документ

104 строк · источник l2code/Postman_ClientServer_Companion.md

Клиент-серверная архитектура — база

Аналогия из жизни: ресторан. Клиент (посетитель) не готовит еду сам и не заходит на кухню — он делает ЗАПРОС официанту (отправляет HTTP-запрос), кухня (сервер) готовит и возвращает ОТВЕТ. Один и тот же повар (сервер) обслуживает много столиков (клиентов) одновременно, не зная заранее, кто именно закажет.

Суть: клиент инициирует запрос, сервер обрабатывает и возвращает ответ — разделение того, ЧТО показывается (представление, на стороне клиента) от того, ГДЕ обрабатываются данные и бизнес-логика (сервер). Клиент и сервер могут быть написаны на разных языках, главное — общий протокол общения (обычно HTTP).

HTTP-методы — что означают: - GET — получить данные, безопасный (не меняет состояние), можно повторять много раз без побочных эффектов (идемпотентный). - POST — создать что-то новое, НЕ идемпотентный (повторный вызов создаст ещё одну запись). - PUT — заменить целиком, идемпотентный (повторный вызов даёт тот же результат). - PATCH — частично обновить. - DELETE — удалить, обычно идемпотентный.

Коды ответа — самое частое на собесе: | Код | Значение | |---|---| | 200 | OK — успех | | 201 | Created — успешно создано (после POST) | | 400 | Bad Request — клиент прислал некорректные данные | | 401 | Unauthorized — не авторизован (нет/неверный токен) | | 403 | Forbidden — авторизован, но доступа нет | | 404 | Not Found — ресурс не найден | | 500 | Internal Server Error — упал сам сервер | | 502/503 | Bad Gateway/Service Unavailable — сервер недоступен/перегружен |

Q&A: - В чём разница между 401 и 403? → 401 — тебя не узнали (нет/невалидный токен), 403 — узнали, но прав нет. - Почему GET считается безопасным, а POST — нет? → GET не должен менять состояние сервера, только читать; POST создаёт новые данные, повторный вызов = новая запись.

Вебхуки — обратная сторона API

Аналогия из жизни: обычный API-запрос - ты сам звонишь в компанию узнать статус заказа (pull). Вебхук - компания сама тебе звонит, как только статус изменился, тебе не нужно спрашивать (push). "Не звони нам - мы сами позвоним."

Суть: вебхук - HTTP-запрос, который сервис-источник отправляет НА заранее указанный тобой URL, когда происходит событие. Ты просто держишь эндпоинт наготове и ждёшь.

HTTP vs HTTP/2

HTTP/1.1 - текстовый протокол, по умолчанию по одному запросу за раз на соединение (keep-alive помогает переиспользовать соединение, но всё равно последовательно - head-of-line blocking, один медленный запрос тормозит следующие).

HTTP/2 - бинарный протокол, мультиплексирование (много запросов и ответов одновременно через ОДНО соединение, без взаимной блокировки), сжатие заголовков (HPACK). Именно поэтому gRPC (см. API_Companion.md) выбирает HTTP/2 - быстрее гонять много мелких вызовов между сервисами.

Postman — практика

Аналогия из жизни: Postman — это как звонок в компанию по заранее заготовленному списку вопросов, вместо того чтобы писать код, который "разговаривает" с их сервером. Ты вручную собираешь запрос (номер/адрес — URL, что сказать — body, кто звонит — заголовки авторизации) и сразу видишь ответ, не поднимая для этого целое приложение.

Основные элементы запроса в Postman: - Method + URL — GET https://api.example.com/incidents - Params — query-параметры (?status=open&limit=10) - Headers — метаданные запроса, чаще всего Authorization: Bearer <token>, Content-Type: application/json - Body — тело запроса (для POST/PUT/PATCH) — обычно JSON - Tests — скрипт на JS, который проверяет ответ автоматически (например pm.response.to.have.status(200))

Практический пример — проверка API перед релизом:

POST https://api.internal/incidents
Headers: Authorization: Bearer eyJhbGc...
Body (JSON): { "title": "Сервер недоступен", "priority": "high" }

Ожидаем: статус 201, в ответе — id новой записи

Коллекции и окружения (Environments): - Коллекция — набор сохранённых запросов, сгруппированных по проекту/сервису. - Environment — набор переменных ({{base_url}}, {{token}}), которые подставляются в запросы — позволяет один и тот же запрос гонять на dev/staging/prod, меняя только окружение, не сам запрос.

Проверка API перед релизом — практический workflow

Аналогия из жизни: пилот перед каждым взлётом проходит один и тот же чек-лист механически, не полагаясь на память. Collection Runner делает то же самое для API — прогоняет один и тот же набор проверок перед каждым релизом, не давая забыть что-то важное.

  1. Happy path + ошибки — не только "отправил, получил 200", но и негативные сценарии: без обязательного поля (400), без токена (401), несуществующий ID (404). Разработчики часто тестируют только успешный путь — находка ошибок именно здесь ценится на собесе и в работе.
  2. Автоматические проверки (вкладка Tests, JS) — превращает ручной клик в тест, который либо зелёный, либо красный:
pm.test("Статус 200", () => pm.response.to.have.status(200));
pm.test("Есть поле id", () => {
    const data = pm.response.json();
    pm.expect(data).to.have.property('id');
});
  1. Collection Runner — прогнать ВСЮ сохранённую коллекцию одной кнопкой вместо ручного прохода по каждому эндпоинту — отчёт "что упало, что прошло" за один прогон.
  2. Цепочка запросов через переменные — POST создаёт ресурс → сохраняешь id в переменную окружения → GET использует этот id, чтобы проверить весь CRUD-цикл, а не отдельные вызовы вслепую.
  3. Newman — тот же набор тестов, но из командной строки, встраивается в CI/CD — проверка идёт автоматически при каждом деплое, не только когда кто-то вспомнил проверить руками.

Q&A: - Как проверить, что API работает правильно, не только что он "отвечает"? → смотреть не только код ответа (200), но и содержимое тела ответа — соответствует ли оно ожидаемой структуре/данным. - Зачем нужны Environments в Postman? → не хардкодить URL/токены в каждом запросе — переключение dev/staging/prod одной переменной, не переписыванием всех запросов. - Что делать, если API вернул 500? → это ошибка НА СТОРОНЕ СЕРВЕРА — проверять логи сервера, не искать ошибку в своём запросе (в отличие от 400, где проблема в самом запросе).
