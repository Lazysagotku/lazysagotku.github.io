🎭 Аналогия

Иностранный язык. Грамматику можно выучить за неделю, беглость набирается только ежедневными двадцатью минутами. С командной строкой так же: список команд запоминается быстро, уверенность приходит от повторения.

Иван прямо сказал, что Linux его раздражает. Поэтому малыми дозами и только то, что спрашивают.

🗺 Карта мест

Сделать: по 20 минут в день - права и файловая система, сеть, планировщик и сигналы, logrotate и strace; в конце - разведчик как systemd-сервис с таймером.

Понять: в Linux всё - либо файл, либо процесс. Три темы, вокруг которых крутятся вопросы на собеседовании: права (кто что может), сигналы (как процесс умирает), порты (кто кого слушает).

Где писать: терминал сервера; /etc/systemd/system/scout.service и scout.timer.

Чем запустить: команда дня на реальной задаче; sudo systemctl enable --now scout.timer.

Где смотреть результат:

ls -l файл                    # права и владелец
ss -tlnp                      # порты
systemctl list-timers         # когда таймер сработает в следующий раз
journalctl -u scout -n 30     # что сделал последний запуск
strace -p PID                 # что процесс делает прямо сейчас

Как понять, что получилось: воспроизвёл «сломай намеренно» дня и объяснил текст ошибки своими словами; разведчик собирает вакансии по таймеру без твоего участия, и это видно в journalctl.

📖 Темы по неделям

Неделя 1. Файловая система и права

ls -l                      # -rw-r--r-- 1 ivan devs
chmod 600 ~/.ssh/id_ed25519
chown ivan:devs file.txt
umask                      # какие права у создаваемых файлов

r = 4, w = 2, x = 1.

Число Означает Где
644 владелец пишет, остальные читают обычные файлы
755 плюс право входа каталоги, скрипты
600 только владелец ключи, файлы с паролями
700 только владелец, полный ~/.ssh

⚠️ SSH откажется работать с ключом, у которого права шире 600. Первая причина, по которой «ключ не подходит».

x на каталоге - право войти внутрь, а не выполнить. Каталог без x виден по имени, но заглянуть нельзя.

Структура каталогов, которую спрашивают: /etc конфиги, /var/log логи, /opt стороннее ПО, /usr/bin программы, /proc виртуальная информация о процессах, /tmp временное с очисткой при перезагрузке.

Неделя 2. Сеть

ss -tulpn                  # кто на каких портах слушает
ss -tan state established  # активные соединения
curl -I https://host       # только заголовки
curl -v https://host       # весь диалог, включая TLS
nc -zv host 5432           # достучаться до порта
dig host                   # что отдаёт DNS
ip a && ip r               # адреса и маршруты
traceroute host
tcpdump -i any port 5432 -nn

Порядок при «сервис недоступен»: 1. Слушает ли: ss -tulpn | grep <порт> на сервере. 2. Отвечает ли локально: curl localhost:<порт>. 3. Пускает ли firewall: ufw status. 4. Резолвится ли имя: dig. 5. Проходит ли снаружи: nc -zv с другой машины.

Если 2 работает, а 5 нет - проблема между ними: firewall, прокси, балансировщик, группа безопасности облака.

⚠️ ss вместо netstat - последний устарел и в свежих дистрибутивах его может не быть.

Неделя 3. Планировщик и сигналы

crontab -e && crontab -l
systemctl list-timers      # systemd-таймеры

Формат cron: минута час день месяц день_недели

*/5 * * * *   /opt/scripts/check.sh
0 3 * * *     /opt/scripts/backup.sh
0 9 * * 1-5   /opt/scripts/report.sh

systemd timer против cron: таймер пишет логи в journald, умеет зависимости от других юнитов и Persistent=true для запуска пропущенного после включения машины.

Сигналы - важно для Kubernetes. При остановке пода приходит SIGTERM, и приложение должно успеть корректно завершиться, иначе через таймаут прилетит SIGKILL. Это связывает Linux и Kubernetes, и об этом спрашивают.

Неделя 4. Что осталось

  • Ротация логов: logrotate, директива copytruncate и почему нельзя просто удалить лог, пока сервис в него пишет.
  • strace -p <PID> - посмотреть системные вызовы живого процесса.
  • /proc/<PID>/ - cwd, fd, limits, environ.
  • ulimit -n - лимит открытых файлов, частая причина «too many open files».
  • fail2ban - автоматическая блокировка перебора по логам.
  • SELinux и AppArmor - на уровне «знаю, что существует, и что они могут запретить соединение, которое по правам разрешено».

🔧 Практика

1. Неделя 1 - права, chmod, umask, структура каталогов. Каждый день одна команда на реальной задаче.

2. Неделя 2 - сеть: ss, curl, dig, tcpdump, порядок диагностики «сервис недоступен».

3. Неделя 3 - cron, systemd timers, сигналы TERM против KILL.

4. Неделя 4 - logrotate, strace, /proc, ulimit, fail2ban.

5. Оформить Скаута как systemd-сервис с автозапуском и сбором по таймеру.

💥 Сломай намеренно

1. Поставить на приватный ключ права 644 и попробовать зайти - получить отказ и прочитать текст ошибки.

2. Снять x с каталога и попробовать в него зайти при живом r.

3. Упереться в ulimit -n: открыть больше файлов, чем разрешено, получить «too many open files».

4. Удалить лог, в который пишет logrotate без copytruncate, и увидеть, что новый файл не создаётся.

✅ Задание

Скаут как systemd-сервис с таймером, переживающий перезагрузку. Плюс уверенное владение списком команд без подглядывания.

❓ Вопросы с ответами

Как запускать задачу по расписанию?

cron для простого, systemd timer там, где нужны логи в journald и зависимости. В cron всегда абсолютные пути и перенаправление вывода - у него урезанное окружение.

Что происходит при остановке пода в Kubernetes?

Приходит SIGTERM, приложение должно корректно завершить текущие запросы и закрыть соединения. Не успело за grace period - прилетает SIGKILL. Поэтому приложение обязано обрабатывать SIGTERM.

Почему не работать под root постоянно?

Любая опечатка выполняется без подтверждения, и в логах не видно, кто именно сделал. sudo даёт разовое повышение и оставляет след в auth.log.

Как посмотреть, что слушает порт?

ss -tulpn. netstat устарел и в свежих дистрибутивах может отсутствовать.

«Too many open files» - что это?

Процесс упёрся в лимит дескрипторов. Смотрю ulimit -n и /proc/<PID>/limits, считаю открытые через lsof -p <PID> | wc -l. Причина обычно в утечке: соединения или файлы открываются и не закрываются.

«Не открывается по имени» - в чём разница симптомов? (добавлено 15.09)

Три разных отказа, и они указывают на разные слои. Connection refused - до хоста дошли, порт закрыт или сервис не слушает, смотрю ss -tulpn на целевой машине. Таймаут без ответа - пакет теряется по дороге: firewall режет молча, маршрута нет, или сервис висит и не принимает новые соединения - ping и traceroute покажут, докуда доходит. Ошибка TLS-рукопожатия - до порта достучались, а сертификат не подошёл: просрочен, имя не совпадает, устаревший протокол - curl -v печатает весь диалог, включая точный шаг, на котором упало.

Как устроен DNS на уровне, который спросят?

A-запись - имя в IPv4, AAAA - в IPv6, CNAME - имя в другое имя, по нему идёт повторный поиск. dig +short host вместо nslookup - короче и не деприкейтед. Если dig отдаёт адрес, а curl всё равно не может подключиться - проблема не в DNS, дальше по цепочке firewall и порт.

Как отличить медленный бэкенд от медленного nginx?

В логе nginx $request_time - весь путь до ответа клиенту, $upstream_response_time - сколько ответа ждали от приложения. Близки - виноват бэкенд. request_time заметно больше апстрима - время съедает сам nginx или сеть до клиента. Смотрю access log за инцидент, при 502/504 - error log за тот же момент, там обычно upstream timed out с адресом апстрима.
