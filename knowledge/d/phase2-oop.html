2.1 Классы и объекты — конструкторы, деструкторы, инициализаторы

Почему это важно

До сих пор весь код был статическим (static class Task17, методы без состояния). Классы вводят объекты с собственным состоянием — это переход от "функций, обрабатывающих данные" к "данным, которые знают, что с собой делать".

Аналогия из жизни

Чертёж дома (класс) - один. Домов, построенных по нему (объекты), может быть сколько угодно, у каждого свой участок, забор, мебель - независимые друг от друга, хоть и построены по одному чертежу.

Теория

Класс — чертёж. Объект — конкретный экземпляр, построенный по чертежу.

public class Product
{
    public string Name;
    public decimal Price;
}

var p1 = new Product(); // объект 1
var p2 = new Product(); // объект 2 — независимый от p1

Пример A — просто данные (POCO)

Самый простой класс — только поля, без логики. "POCO" (Plain Old CLR Object).

public class Point
{
    public int X;
    public int Y;
}

var origin = new Point();      // X=0, Y=0 (дефолтные значения)
var p = new Point { X = 3, Y = 5 };

Пример B — конструкторы и цепочка через this(...)

public class Rectangle
{
    public double Width;
    public double Height;

    // Полный конструктор
    public Rectangle(double width, double height)
    {
        Width = width;
        Height = height;
    }

    // Квадрат — цепочка к полному конструктору
    public Rectangle(double side) : this(side, side) { }

    // Дефолтный — цепочка дальше
    public Rectangle() : this(1, 1) { }
}

var r1 = new Rectangle(4, 6);  // прямоугольник 4x6
var r2 = new Rectangle(5);     // квадрат 5x5 — через this(5,5)
var r3 = new Rectangle();      // квадрат 1x1 — через this(1,1)→this(1,1,1)

Каждый конструктор передаёт работу следующему по цепочке — не дублируй логику инициализации, это частая причина багов (поправил в одном месте, забыл в другом).

this — полное объяснение (а не только для конструкторов)

this — ссылка на ТЕКУЩИЙ экземпляр объекта, внутри которого выполняется код. У него несколько РАЗНЫХ применений — важно не путать их.

Применение 1 — устранение неоднозначности имён

public class Person
{
    private string name;

    public Person(string name)
    {
        this.name = name; // this.name — поле класса, name (без this) — параметр
    }
}

Без this. строка name = name присвоила бы параметр самому себе — поле класса осталось бы нетронутым (null). this. явно говорит компилятору "это поле МОЕГО объекта, а не локальная переменная".

Применение 2 — this(...) как constructor initializer (то, что было в Примере B)

Вот тут и была путаница. : this(side, side) — не вызов метода внутри тела конструктора. Это отдельный синтаксический слот, стоящий МЕЖДУ сигнатурой и телом:

public Rectangle(double side) : this(side, side) { }
//   сигнатура ──┘             └── инициализатор   └── тело (здесь пустое)

Порядок выполнения: 1. Сначала выполняется this(side, side) — вызывается ДРУГОЙ конструктор ЭТОГО ЖЕ класса (тот, что принимает width, height), полностью, от начала до конца 2. Только ПОТОМ выполняется тело { } текущего конструктора

Если бы тело не было пустым, это стало бы очевиднее:

public Rectangle(double side) : this(side, side)
{
    Console.WriteLine("Квадрат создан"); // выполнится ПОСЛЕ this(side, side), не до
}

То есть this(...) здесь — не "вызови метод this", а специальный синтаксис "сначала выполни вот тот конструктор, потом уже моё тело".

Применение 3 — передать "себя" в другой метод

public class Button
{
    public void Click()
    {
        EventLogger.Log(this); // передаём ссылку на ТЕКУЩИЙ объект куда-то ещё
    }
}

Что ещё называется this, но это другое (встретишь позже, не сейчас)

  • base(...) — то же самое место в синтаксисе, что и this(...), но вызывает конструктор РОДИТЕЛЬСКОГО класса, а не текущего. Увидишь в 2.3 (Наследование).
  • this в extension methods — первый параметр с модификатором this (public static void Foo(this MyClass obj)) — совсем другое использование того же слова, встретишь в Фазе 3 (3.8, Extension methods). Не путай с этой темой сейчас.
  • this[index] — индексаторы, если понадобится сделать свой класс с доступом через obj[0], как у массива. Не входит явно в текущий план, но встретишь в чужом коде/библиотеках.

Пример C — класс с поведением, не только данными

public class Product
{
    public string Name;
    public decimal Price;

    public Product(string name, decimal price)
    {
        Name = name;
        Price = price;
    }

    // Метод, использующий состояние объекта
    public decimal GetPriceWithDiscount(decimal discountPercent) =>
        Price * (1 - discountPercent / 100);
}

var bread = new Product("Хлеб", 50m);
Console.WriteLine(bread.GetPriceWithDiscount(10)); // 45

Object initializer

var p3 = new Product { Name = "Молоко", Price = 89.90m };
// Компилятор вызывает пустой конструктор, потом присваивает поля/свойства
// Работает ТОЛЬКО если есть доступный конструктор без параметров (явный или дефолтный)

Деструкторы (финализаторы) — почти никогда не нужны

public class Product
{
    ~Product() // деструктор — вызывается GC перед удалением объекта
    {
        // Освобождение НЕуправляемых ресурсов
    }
}

Важно: ты НЕ решаешь, когда это вызовется — решает Garbage Collector. Для управляемых ресурсов (списки, строки, другие объекты) деструктор не нужен вообще. Для файлов/сокетов/соединений — используй IDisposable и using (Фаза 1, 1.8) — это предсказуемо, а деструктор нет.

Современный синтаксис — primary constructors (C# 12+)

// То же самое, что Пример C, но короче — параметры конструктора сразу в заголовке класса
public class Product(string name, decimal price)
{
    public decimal GetPriceWithDiscount(decimal discountPercent) =>
        price * (1 - discountPercent / 100);
}

Встретишь в новом коде и на собесах спросят "что это за синтаксис" — но для учебных целей продолжай писать явные конструкторы, пока не станет интуитивно понятно, что происходит "под капотом".

🎤 Вопросы с собеседования

Q: Чем конструктор отличается от обычного метода? A: Нет возвращаемого типа (даже не void), имя совпадает с именем класса, вызывается автоматически при new, может быть перегружен как обычный метод.

Q: Что вызовется первым — конструктор базового класса или производного? A: Базового (через неявный или явный base(...)), потом производного. Построение идёт "снизу вверх" по иерархии — производный класс может полагаться на уже готовое состояние базового.

Q: Что произойдёт, если не написать ни одного конструктора? A: Компилятор сгенерирует пустой public конструктор без параметров автоматически — но только если не написан НИ ОДИН другой конструктор. Как только пишешь хотя бы один явный — дефолтный пропадает, и new MyClass() перестаёт работать, если ты не написал версию без параметров сам.

Q: Работает ли это правило одинаково для class и struct? A: Нет — у struct implicit-конструктор без параметров ВСЕГДА доступен, даже если написан свой явный конструктор с параметрами (до C# 10 у struct нельзя было даже объявить СВОЙ parameterless-конструктор — компилятор всегда добавлял его сам). У class дефолтный пропадает, как только появляется хотя бы один явный. Struct в этом смысле "мягче" class.

Q: Чем object initializer отличается от конструктора по факту выполнения? A: Это не замена конструктора, а надстройка над ним: сначала вызывается конструктор (дефолтный или явно указанный), и только ПОСЛЕ этого присваиваются свойства через set/init. Значит, в момент выполнения тела конструктора эти свойства ещё не установлены.

Q: Когда деструктор в C# действительно нужен? A: Практически никогда для управляемого кода. Только как "страховка" при работе с неуправляемыми ресурсами напрямую (P/Invoke, нативные хендлы) — и то обычно вместе с полноценным IDisposable, а не вместо него.

Q: Что выполнится раньше — this(...) инициализатор или тело конструктора? A: Всегда сначала this(...) (или base(...)) целиком, потом тело { } текущего конструктора. Это не вызов метода из тела — это отдельный этап конструирования объекта, стоящий синтаксически ПЕРЕД телом.

Q: Зачем нужен именно this. перед полем, если у поля и параметра разные имена? A: Не нужен — this. обязателен только при совпадении имён (иначе неоднозначность). Но многие команды требуют его ВСЕГДА по конвенции кода — так с первого взгляда видно, что это поле объекта, а не локальная переменная, без чтения объявлений выше.

2.2 Инкапсуляция — модификаторы доступа, свойства (get/set/init)

Почему это важно

Инкапсуляция — не "спрятать поля от других", а контролировать, как меняется состояние объекта. Без неё баланс банковского счёта можно было бы установить в -1000000 напрямую, без единой проверки.

Аналогия из жизни

Банкомат не даёт залезть руками в сейф банка. Ты взаимодействуешь через контролируемый интерфейс - ввёл PIN, запросил сумму - а сам сейф (приватные поля) скрыт и защищён от прямого доступа снаружи.

Модификаторы доступа

Модификатор Кто видит
public Все
private Только этот класс (дефолт для полей/методов)
protected Этот класс + наследники
internal Весь текущий проект/сборку
protected internal Наследники ИЛИ текущая сборка
private protected Наследники И ТОЛЬКО текущая сборка

Пример A — свойство с валидацией

public class BankAccount
{
    private decimal _balance;

    public decimal Balance
    {
        get => _balance;
        private set // менять можно только изнутри класса
        {
            if (value < 0) throw new ArgumentException("Баланс не может быть отрицательным");
            _balance = value;
        }
    }

    public void Deposit(decimal amount) => Balance += amount;
}

Пример B — auto-property (компилятор сам создаёт backing field)

public class Person
{
    public string Name { get; set; }               // читать/писать может кто угодно
    public string Id { get; private set; }          // читать снаружи, менять — только изнутри
    public DateTime CreatedAt { get; } = DateTime.Now; // только для чтения, задаётся один раз
}

Пример C — вычисляемое свойство (get-only, без backing field)

public class Person
{
    public string FirstName { get; set; }
    public string LastName { get; set; }

    // Не хранит своё значение — вычисляется каждый раз при обращении
    public string FullName => $"{FirstName} {LastName}";
}

var p = new Person { FirstName = "Иван", LastName = "Архипов" };
Console.WriteLine(p.FullName); // "Иван Архипов" — пересчитается, если поменять FirstName

Пример D — init и современный required (C# 11+)

public class Order
{
    public required string Id { get; init; } // обязателен при создании, неизменяем после
    public string? Comment { get; init; }    // необязателен, тоже неизменяем после создания
}

var order = new Order { Id = "123" };       // OK
// var bad = new Order();                  // ОШИБКА — Id обязателен (required)
order.Id = "456";                            // ОШИБКА — init нельзя менять после создания

Это ровно то, что уже негласно используешь в record Contact(string Name, ...) — позиционные свойства record'ов автоматически init-only.

[!info]+ 🆕 Добавлено 2 августа — readonly, const и init уже встречались в примерах без объяснения (DI в 2.7, _lock в 2.8) — вот разница Все три про "нельзя поменять", но на разных уровнях: csharp const int MaxRetries = 3; // значение известно уже на этапе КОМПИЛЯЦИИ, вшито в IL private readonly IDatabase _db; // значение задаётся в конструкторе ОДИН раз, дальше поле нельзя переприсвоить public string Owner { get; init; } // то же самое, но для СВОЙСТВА, а не поля, и видно снаружи класса - const — для полей класса/локальных переменных, значение должно быть константой compile-time (числа, строки, null) — нельзя присвоить результат вызова метода или new. - readonly — для полей. Присвоить можно либо сразу при объявлении, либо в конструкторе (в том числе разными конструкторами по-разному) — но нигде больше. В отличие от const, значение может быть вычислено в рантайме (new List<T>(), результат метода). - init — для свойств (то есть readonly, но с автогенерируемым get/set через property-механизм, и доступно для присвоения через object initializer new Order { Id = "123" }, не только из конструктора). Практическое правило: приватное поле, которое просто хранит зависимость/состояние и снаружи не нужно — readonly поле (как _db в 2.7). Публичное значение, которое клиент класса должен видеть и задавать при создании — init-свойство. Compile-time константа (лимиты, коэффициенты) — const.

🎤 Вопросы с собеседования

Q: Зачем нужны private-поля, если можно сделать public property с get; set;? A: Обычный auto-property не даёт контроля над изменением — любой снаружи может поставить любое значение. Приватное поле + свойство с логикой в set — стандартный способ защитить инвариант объекта (например, не пустить отрицательный баланс).

Q: Чем { get; private set; } отличается от { get; init; }? A: private set разрешает менять значение из ЛЮБОГО метода внутри класса в ЛЮБОЙ момент жизни объекта. init разрешает установить значение только один раз — в момент создания (конструктор/object initializer), после — нельзя даже изнутри класса.

Q: Что такое auto-property "под капотом"? A: Компилятор сам генерирует приватное backing-поле (что-то вроде <Name>k__BackingField) и обычные get/set методы вокруг него — синтаксический сахар, ты просто не видишь поле явно.

Q: Могут ли get и set одного свойства иметь разную видимость? A: Да: public string Name { get; private set; } — читать может кто угодно снаружи, менять — только сам класс.

Q: В чём разница между required (C# 11) и обычным конструктором с обязательным параметром? A: required заставляет задать свойство через object initializer, но НЕ требует именно конструктор — гибче для случаев когда полей много и не все обязательны. Конструктор с обязательным параметром жёстче: без него объект вообще не создать, а required даёт компилятору проверить это на этапе new Type { ... }.

2.3 Наследование — base, virtual, override, sealed

Почему это важно

Наследование моделирует отношение "является" (Dog является Animal). Без него пришлось бы копипастить общий код в каждый похожий класс.

Аналогия из жизни

Семейные черты: ребёнок (производный класс) получает базовые черты от родителя (базовый класс) автоматически, но может развить СВОЮ версию какой-то черты (override), оставаясь при этом узнаваемым потомком того же рода.

Пример A — базовая иерархия с virtual/override

public class Animal
{
    public string Name { get; init; }
    public Animal(string name) => Name = name;

    public virtual void MakeSound()
    {
        Console.WriteLine($"{Name} издаёт звук");
    }
}

public class Dog : Animal
{
    public Dog(string name) : base(name) { } // base(...) вызывает конструктор Animal

    public override void MakeSound()
    {
        Console.WriteLine($"{Name} лает: Гав!");
    }
}

Частая ошибка новичков: забыть virtual в базовом классе — тогда override в наследнике попросту не скомпилируется (CS0506). Оба ключевых слова обязательны и работают в паре.

Пример B — protected: видно наследнику, не видно снаружи

public class Employee
{
    protected decimal BaseSalary; // видно в Employee И в наследниках, но НЕ снаружи

    public Employee(decimal baseSalary) => BaseSalary = baseSalary;
}

public class Manager : Employee
{
    public Manager(decimal baseSalary) : base(baseSalary) { }

    public decimal GetTotalSalary() => BaseSalary * 1.5m; // доступ есть, т.к. protected
}

var m = new Manager(1000);
// m.BaseSalary; // ОШИБКА — снаружи protected не виден

Пример C — трёхуровневая иерархия с цепочкой base()

public class Vehicle
{
    public string Brand { get; init; }
    public Vehicle(string brand) => Brand = brand;
    public virtual void Describe() => Console.WriteLine($"Транспорт: {Brand}");
}

public class Car : Vehicle
{
    public int Doors { get; init; }
    public Car(string brand, int doors) : base(brand) => Doors = doors;
    public override void Describe() => Console.WriteLine($"Машина {Brand}, дверей: {Doors}");
}

public class SportsCar : Car
{
    public int TopSpeed { get; init; }
    public SportsCar(string brand, int topSpeed) : base(brand, doors: 2) => TopSpeed = topSpeed;
    public override void Describe()
    {
        base.Describe(); // можно вызвать реализацию родителя И добавить своё
        Console.WriteLine($"Макс. скорость: {TopSpeed}");
    }
}

Пример D — sealed

public sealed class Cat : Animal // от Cat нельзя унаследоваться дальше
{
    public Cat(string name) : base(name) { }
    public sealed override void MakeSound() // и это переопределение нельзя переопределить дальше
        => Console.WriteLine($"{Name} мяукает: Мяу!");
}

Пример E — hiding через new (не путать с override!)

Если базовый метод НЕ помечен virtual, но нужно определить в наследнике метод с тем же именем — используй new. Это НЕ override, это скрытие (hiding) — принципиально другой механизм.

public class Bird
{
    public void Move() // обычный метод, БЕЗ virtual
        => Console.WriteLine("Птица передвигается");
}

public class Penguin : Bird
{
    public new void Move() // 'new' — явно говорим "скрываю метод родителя, не переопределяю"
        => Console.WriteLine("Пингвин ковыляет");
}

Ключевое отличие от override — где решается, какой метод вызвать:

Penguin p = new Penguin();
p.Move();               // "Пингвин ковыляет" — переменная объявлена как Penguin

Bird b = p;              // тот же объект, но переменная теперь типа Bird
b.Move();                // "Птица передвигается" — вызывается версия Bird, НЕ Penguin!

С override результат был бы другой — вызвалась бы версия Penguin в обоих случаях (см. 2.4, динамический полиморфизм). Разница: - override — решение в рантайме, по реальному типу объекта - new (hiding) — решение на этапе компиляции, по объявленному типу переменной

Зачем это нужно: если базовый метод не virtual (например, класс из чужой библиотеки, которую не контролируешь), а в наследнике всё равно нужен метод с тем же именем — без new компилятор выдаст ПРЕДУПРЕЖДЕНИЕ CS0108 ("скрывает унаследованный член, отсутствует ключевое слово new"), а не ошибку. new явно говорит "да, я знаю, это осознанно".

🎤 Вопросы с собеседования

Q: Почему в C# нет множественного наследования классов? A: Чтобы избежать "diamond problem" — неоднозначности, если два родителя дают одинаковый член с разной реализацией. Вместо этого — множественная реализация интерфейсов, где такой проблемы нет (интерфейс до C# 8 вообще не содержал реализации).

Q: Что произойдёт, если явно не вызвать base(...)? A: Компилятор неявно вызовет пустой конструктор базового класса, если такой есть. Если у базового класса нет конструктора без параметров — ошибка компиляции, base(...) придётся вызвать явно.

Q: virtual vs abstract — в чём разница для наследника? A: virtual — есть реализация по умолчанию, override необязателен (можно не переопределять). abstract — реализации нет вообще, override ОБЯЗАТЕЛЕН в первом же неабстрактном наследнике.

Q: Что такое "hiding" через new и чем оно отличается от override? A: new скрывает член базового класса, но НЕ участвует в полиморфизме — вызов через переменную БАЗОВОГО типа вызовет базовую версию, даже если реальный объект — наследник. override участвует в динамической диспетчеризации — вызовется версия реального типа объекта, независимо от типа переменной.

Q: Можно ли вызвать метод базового класса из переопределённого метода наследника? A: Да, через base.MethodName() — как в примере C (SportsCar.Describe() вызывает base.Describe() и добавляет своё). Это позволяет расширять поведение, а не полностью заменять.

2.4 Полиморфизм — статический и динамический

Почему это важно

"Полиморфизм" звучит абстрактно, но смысл прост: один и тот же вызов ведёт себя по-разному в зависимости от контекста (перегрузки) или конкретного типа объекта (переопределения).

Аналогия из жизни

Кнопка "Вкл" на универсальном пульте - для телевизора она включает экран, для кондиционера запускает охлаждение. Один и тот же вызов ведёт себя по-разному в зависимости от того, что реально стоит за кнопкой.

Пример A — статический полиморфизм (перегрузка, compile-time)

public class Calculator
{
    public int Add(int a, int b) => a + b;
    public double Add(double a, double b) => a + b;
    public string Add(string a, string b) => a + b; // конкатенация
}

var calc = new Calculator();
calc.Add(1, 2);       // компилятор выбирает int-версию — известно ЗАРАНЕЕ, на этапе компиляции
calc.Add(1.5, 2.5);   // double-версию
calc.Add("a", "b");   // string-версию

Пример B — динамический полиморфизм (virtual/override, runtime)

List<Animal> animals = new() { new Dog("Рекс"), new Cat("Мурка") };

foreach (var a in animals)
    a.MakeSound(); // решается В РАНТАЙМЕ, по реальному типу объекта, а не по типу переменной (Animal)

Это работает благодаря virtual/override из 2.3 — компилятор не может знать заранее, что окажется в списке Animal, поэтому решение откладывается до момента выполнения.

Пример C — классическая ловушка: virtual-вызов из конструктора

public class Base
{
    public Base() => Init(); // ВЫЗОВ virtual-метода ИЗ конструктора — опасно!
    public virtual void Init() => Console.WriteLine("Base.Init");
}

public class Derived : Base
{
    private string _name = "готово";
    public override void Init() => Console.WriteLine($"Derived.Init, _name = {_name}");
}

new Derived();
// Выведет: "Derived.Init, _name = " (ПУСТАЯ строка!)
// Потому что Base() выполняется ДО того, как Derived успел инициализировать _name = "готово"

Это реальная ловушка продакшн-кода — вызов virtual-метода из конструктора вызовет override-версию, даже если наследник ещё не полностью готов.

🎤 Вопросы с собеседования

Q: Что произойдёт, если вызвать virtual-метод из конструктора базового класса? A: Вызовется override-версия наследника — даже если поля наследника ещё не инициализированы (см. Пример C). Считается плохой практикой и частым источником труднообъяснимых багов.

Q: Как компилятор выбирает нужную перегрузку при неоднозначности? A: Выбирает наиболее специфичную сигнатуру среди применимых. Если однозначного "победителя" нет (например, null передан методу с перегрузками на string и object, обе одинаково подходят) — ошибка компиляции CS0121 "вызов неоднозначен".

Q: Можно ли достичь полиморфизма без наследования от общего класса? A: Да — через интерфейсы. Разные несвязанные классы реализуют один интерфейс, и вызов через переменную типа интерфейса — тоже динамический полиморфизм, просто без общего предка.

Q: В чём принципиальная разница между overload (перегрузкой) и override (переопределением)? A: Overload — РАЗНЫЕ методы с одинаковым именем, но разной сигнатурой (параметры), выбор происходит на этапе компиляции. Override — ОДИН и тот же метод, переопределённый в наследнике, выбор происходит в рантайме по реальному типу объекта.

2.5 Абстракция — abstract классы vs интерфейсы

Почему это важно

И abstract class, и interface не дают создать объект напрямую и заставляют наследника реализовать методы. Разница — в философии: abstract class — "мы близкие родственники, у нас общий код и состояние". interface — "мы умеем делать одно и то же, но можем быть совершенно не связаны".

Аналогия из жизни

Руль и педали в машине - абстракция: жмёшь на газ, не зная, что происходит в двигателе. abstract класс/интерфейс - тот же контракт "вот что можно делать", детали реализации скрыты от того, кто пользуется.

Пример A — abstract class с общим кодом и абстрактным методом

public abstract class Shape
{
    public string Name { get; init; }
    public void PrintName() => Console.WriteLine(Name); // общая реализация — наследуется как есть
    public abstract double Area(); // контракт без реализации — наследник обязан написать

    public double AreaRoundedUp() => Math.Ceiling(Area()); // может использовать абстрактный метод!
}

public class Circle : Shape
{
    public double Radius { get; init; }
    public override double Area() => Math.PI * Radius * Radius;
}

// var s = new Shape(); // ОШИБКА — нельзя создать объект абстрактного класса

Пример B — interface, множественная реализация

public interface IShape { double Area(); }
public interface ITaxable { decimal CalculateTax(); }

// Один класс реализует СРАЗУ два интерфейса — invalid для abstract class (только один базовый)
public class TaxableProperty : IShape, ITaxable
{
    public double Width, Height;
    public double Area() => Width * Height;
    public decimal CalculateTax() => (decimal)Area() * 0.05m;
}

Пример C — несвязанные классы, объединённые общим "умением"

public interface INotifiable { void Notify(string message); }

public class EmailSender : INotifiable
{
    public void Notify(string message) => Console.WriteLine($"Email: {message}");
}

public class SmsSender : INotifiable // совершенно другая природа класса, но тот же контракт
{
    public void Notify(string message) => Console.WriteLine($"SMS: {message}");
}

List<INotifiable> senders = new() { new EmailSender(), new SmsSender() };
foreach (var s in senders) s.Notify("Привет!"); // единый вызов, разное поведение

Когда что

abstract class interface
Общий код/состояние Да, можно Нет (только контракт, редко default-методы)
Множественное наследование Нет (только один base class) Да (реализуй сколько угодно интерфейсов)
Семантика "Это разновидность X" "Это умеет делать Y"

Q: Может ли abstract класс иметь конструктор, если объект напрямую создать нельзя? A: Да — конструктор abstract класса вызывается через base(...) из наследника при создании ЕГО объекта. Сам abstract класс просто нельзя инстанцировать напрямую через new.

Q: Может ли интерфейс иметь реализацию метода по умолчанию? A: С C# 8+ — да (default interface methods), но на практике используется редко, в основном чтобы добавить новый метод в существующий публичный интерфейс библиотеки, не ломая всех, кто его уже реализовал.

Q: Когда выбрать abstract class, а когда interface, если контракт можно объявить и там, и там? A: Если есть общее СОСТОЯНИЕ или код, который должен быть у всех наследников — abstract class. Если классы совершенно не связаны по природе, но должны "уметь одно и то же" — interface (плюс даёт множественную реализацию, что abstract class не может).

Q: Что произойдёт при попытке создать объект интерфейса напрямую, new IShape()? A: Ошибка компиляции — интерфейсы, как и abstract-классы, нельзя инстанцировать. Единственный способ получить объект — создать конкретный класс, реализующий интерфейс.

2.6 Интерфейсы — IDisposable, IComparable, IEnumerable

Почему это важно

Это стандартные интерфейсы фреймворка. Реализовав их в своём классе, ты "подключаешь" объект к языковым механизмам: using, Array.Sort, foreach.

Аналогия из жизни

Интерфейс - разъём USB: неважно, что внутри устройства (флешка, мышь, клавиатура), если разъём совпадает - оно подключится и заработает по общим правилам порта.

Пример A — IComparable\<T> — твой тип можно сортировать

public class Product : IComparable<Product>
{
    public string Name { get; init; }
    public decimal Price { get; init; }

    public int CompareTo(Product? other)
    {
        if (other is null) return 1;
        return Price.CompareTo(other.Price); // сортировка по цене
    }
}

var products = new List<Product> { ... };
products.Sort(); // теперь работает — использует твой CompareTo

Пример B — IDisposable — реализуй сам (не только пользуйся)

Уже разбирали подробно в Фазе 1 (1.8) — using, GC не управляет неуправляемыми ресурсами, паттерн с _disposed флагом. Здесь тема — "реализуй сам":

public class FileLogger : IDisposable
{
    private readonly StreamWriter _writer = new("log.txt");
    public void Log(string msg) => _writer.WriteLine(msg);
    public void Dispose() => _writer.Dispose();
}

using var logger = new FileLogger(); // теперь твой класс работает с using

🎤 Вопросы с собеседования

Q: Зачем нужен generic IComparable<T>, если есть не-generic IComparable? A: Не-generic IComparable.CompareTo(object) требует boxing и приведения типов, не типобезопасен (можно передать вообще другой тип и упасть в рантайме). Generic-версия работает напрямую с нужным типом, без boxing, компилятор ловит несовпадение типов на этапе компиляции.

Q: Почему у IEnumerable<T> два метода GetEnumerator() — generic и нет? A: IEnumerable<T> наследует не-generic IEnumerable (для обратной совместимости с кодом до дженериков). Оба обязательны; не-generic версию обычно реализуют явно (IEnumerator IEnumerable.GetEnumerator()) и просто делегируют вызов в generic-версию, как в Примере C.

Q: В чём разница между IDisposable.Dispose() и деструктором для одного и того же класса? A: Dispose() вызывается ЯВНО и предсказуемо (через using или прямой вызов) в момент, который ты контролируешь. Деструктор вызывается ТОЛЬКО GC, когда сочтёт нужным — непредсказуемо по времени. Правильный production-паттерн — реализовать оба: Dispose() как основной путь, деструктор как страховку на случай если Dispose() забыли вызвать.

Q: Что будет, если реализовать IComparable<T>.CompareTo, но не переопределить Equals/GetHashCode? A: Сортировка (CompareTo) будет работать нормально, но сравнение на равенство (==, .Equals(), использование как ключа в Dictionary/HashSet) продолжит сравнивать по ССЫЛКЕ (для class), а не по значениям полей — потенциальный источник багов, если ожидается value-based равенство.

2.7 Принципы SOLID

Почему это важно

SOLID — самая частая тема на собеседованиях Middle+. Не абстрактная философия, а конкретные признаки того, что код будет легко менять через полгода.

Аналогия из жизни

Хорошо организованная кухня ресторана: у каждого повара своя чётко очерченная зона (SRP). Меню расширяется новым блюдом, не переписывая работу остальных поваров (OCP). Любой повар может заменить другого на своей позиции без сюрпризов для остальной кухни (LSP). Никто не обязан знать рецепты блюд, которые не готовит (ISP). А шеф-повар не бегает лично на рынок за морковью, а просто говорит "нужна морковь по спецификации X" - неважно, кто именно её принесёт (DIP).

S — Single Responsibility (единственная ответственность)

// ПЛОХО — ContactBook и хранит, и печатает в консоль, и валидирует
public class ContactBook
{
    public void Add(Contact c) { /* валидация + сохранение */ }
    public void PrintAll() { Console.WriteLine(...); } // ← лишняя ответственность
}

// ХОРОШО — разделено (именно так уже сделано в твоём Contact Manager!)
public class ContactBook { public void Add(Contact c) { ... } }         // хранение
public class ContactPrinter { public void Print(Contact c) { ... } }    // вывод

O — Open/Closed (открыт для расширения, закрыт для изменения)

// ПЛОХО — новый тип скидки требует править существующий метод
decimal GetDiscount(string customerType) => customerType switch
{
    "regular" => 0.05m,
    "vip" => 0.15m,
    _ => 0m
};

// ХОРОШО — новый тип скидки = новый класс, старый код не трогаем

public class VipDiscount : IDiscountStrategy { public decimal GetDiscount() => 0.15m; }

// ПЛОХО — нарушение LSP
public class Bird { public virtual void Fly() { /* летит */ } }

// ПЛОХО — жёсткая привязка к конкретному классу
public class OrderService
{

[!info]+ 🆕 Добавлено 2 августа — куда DIP вырастает в масштабе целого приложения (Hexagonal / Ports & Adapters) OrderService(IDatabase db) выше — это DIP в одном классе. В масштабе целого приложения та же идея называется Hexagonal Architecture (Ports & Adapters): изолированное ядро бизнес-логики в центре, а всё внешнее подключено через порты. - Driving ports — внешний мир зовёт ядро (HTTP-контроллер, UI). - Driven ports — ядро зовёт внешний мир (БД, очереди, чужие API) — это ровно IDatabase из примера выше, только на уровне приложения, а не одного класса. - Входные и выходные адаптеры реализуют эти порты (конкретный EF Core репозиторий — адаптер для IDatabase-порта).

Важно на собесе: Clean Architecture (уже встречалась в собесе #4 — слои Domain/Application/Infrastructure/Presentation) — это более поздняя и детализированная версия ТОЙ ЖЕ идеи, что и Hexagonal, а не конкурирующий подход. Называть их взаимозаменяемо не ошибка.

Зачем это даёт практически: ядро можно юнит-тестировать без моков БД/сети вообще — оно ни от чего внешнего не зависит. Минус (честно, не только плюсы) — на маленьком проекте это оверинжиниринг: лишние интерфейсы и слои ради проекта, который и так меняется раз в год.

🎤 Вопросы с собеседования

Q: Приведи пример нарушения Single Responsibility из реального проекта. A: Класс UserService, который одновременно валидирует входные данные, сохраняет пользователя в БД и отправляет приветственное письмо — три РАЗНЫЕ причины для изменения (правила валидации, схема БД, шаблон письма) живут в одном классе.

Q: Как SOLID связан с Dependency Injection? A: D (Dependency Inversion) — теоретический принцип "зависеть от абстракций, а не от конкретных реализаций". Dependency Injection — практический механизм КАК эти абстракции передаются объекту (обычно через конструктор), часто автоматизированный DI-контейнером (в ASP.NET Core — встроенный).

Q: Может ли код соблюдать один принцип SOLID, но нарушать другой? A: Да, принципы независимы, хоть и взаимосвязаны. Например, класс может иметь идеальный SRP (одна чёткая ответственность), но нарушать OCP — для добавления нового поведения приходится лезть внутрь и редактировать существующий проверенный код.

Q: Что "закрыт для изменения" в Open/Closed НЕ означает? A: Не означает "никогда не трогай этот код вообще" — баги всё равно чинятся, рефакторинг возможен. Означает: для ДОБАВЛЕНИЯ нового поведения (новый тип скидки, новый формат экспорта) не нужно модифицировать существующий работающий код — только дописывать новый.

Q: Приведи пример, когда Liskov Substitution нарушается неочевидно (не через exception). A: Наследник переопределяет метод так, что он выполняется в разы медленнее или с побочными эффектами, которых не ожидает вызывающий код, рассчитывающий на поведение базового класса — формально сигнатура совпадает, но контракт (ожидания вызывающей стороны) нарушен.

2.8 Статические классы и синглтон

Почему это важно

Ты уже неявно использовал static в ContactManager.Book — теперь разберём, что это значит формально и чем отличается от паттерна Singleton.

Аналогия из жизни

Один принтер на весь этаж офиса. Все сотрудники обращаются к ОДНОМУ и тому же устройству, никто не заводит себе персональную копию принтера "для себя".

Пример A — статический класс

public static class MathHelper // нельзя создать объект (new MathHelper() — ошибка компиляции)
{
    public static double Square(double x) => x * x; // все члены обязаны быть static
}

MathHelper.Square(5); // вызов без создания объекта

Пример B — классический Singleton (ручная блокировка)

public class ConfigManager
{
    private static ConfigManager? _instance;
    private static readonly object _lock = new();

    private ConfigManager() { } // приватный конструктор — извне new() недоступен

    public static ConfigManager Instance
    {
        get
        {
            lock (_lock) // потокобезопасность — только один поток может сюда попасть одновременно
            {
                _instance ??= new ConfigManager();
                return _instance;
            }
        }
    }
}

ConfigManager.Instance.DoSomething(); // всегда один и тот же объект

Пример C — современный Singleton через Lazy<T> (без ручной блокировки)

public class ConfigManager
{
    private static readonly Lazy<ConfigManager> _lazy = new(() => new ConfigManager());
    public static ConfigManager Instance => _lazy.Value;

    private ConfigManager() { }
}
// Lazy<T> сам гарантирует потокобезопасность и создание "по требованию" (при первом обращении)

Важное отличие от твоего Book: в ContactManager.cs поле private static readonly ContactBook Book = new(); — это просто "один статический экземпляр", а не Singleton-паттерн: конструктор ContactBook остался публичным, ничто не мешает создать new ContactBook() где-то ещё. Настоящий Singleton запрещает это через приватный конструктор.

🎤 Вопросы с собеседования

Q: Почему Singleton считается антипаттерном многими разработчиками? A: Это скрытая глобальная зависимость — код, использующий Singleton.Instance напрямую, невозможно протестировать изолированно (нельзя подменить mock-реализацией без дополнительных ухищрений), плюс скрытая связанность между частями системы, не видная по сигнатурам методов.

Q: Как сделать Singleton потокобезопасным без ручного lock? A: Lazy<T> (Пример C) — по умолчанию использует LazyThreadSafetyMode.ExecutionAndPublication, гарантированно создаст только один экземпляр даже при параллельном первом обращении из нескольких потоков.

Q: Чем static class отличается от Singleton по возможностям, если оба гарантируют "один экземпляр логики"? A: static class — вообще не объект, его нельзя передать как зависимость через интерфейс, нельзя протестировать с моком, нет полиморфизма. Singleton — обычный объект (просто гарантированно единственный), его можно спрятать за интерфейсом и подменить в тестах.

Q: Как обычно решают проблему тестируемости, свойственную Singleton, в современных .NET-проектах? A: Через Dependency Injection вместо ручного Singleton-паттерна — регистрируют сервис с Lifetime.Singleton в DI-контейнере (services.AddSingleton<IMyService, MyService>()), получают гарантию "один экземпляр на всё приложение", но при этом сохраняют возможность подменить реализацию в тестах через интерфейс.

2.9 Record типы — глубже

Почему это важно

record Contact уже использовался в Фазе 1 интуитивно. Теперь — что происходит под капотом и когда record явно лучше class.

Аналогия из жизни

Record - как бланк техпаспорта: если два бланка заполнены одинаковыми данными (тот же VIN, год, цвет), они СЧИТАЮТСЯ одним и тем же документом по содержанию (value equality) - не потому что это физически один и тот же лист бумаги, как было бы с class (reference equality, где важно, что это именно ТОТ ЖЕ конкретный экземпляр).

Пример A — value equality

public record Point(int X, int Y);
public class PointClass { public int X, Y; }

var r1 = new Point(1, 2);
var r2 = new Point(1, 2);
Console.WriteLine(r1 == r2); // True — record сравнивает ЗНАЧЕНИЯ

var c1 = new PointClass { X = 1, Y = 2 };
var c2 = new PointClass { X = 1, Y = 2 };
Console.WriteLine(c1 == c2); // False — class сравнивает ССЫЛКИ

Пример B — with-выражение (неразрушающая мутация)

var original = new Contact("Ivan", "123", null);
var updated = original with { Phone = "999" };
// original не изменился, updated — новая копия с другим Phone
Console.WriteLine(original.Phone); // "123"
Console.WriteLine(updated.Phone);  // "999"

Пример C — record vs record struct

public record Point(int X, int Y);        // reference type (в куче)
public record struct Coord(int X, int Y); // value type (на стеке, копируется целиком)

Пример D — ловушка: value equality ломается с mutable reference-полями

public record Order(string Id, List<string> Items);

var o1 = new Order("1", new List<string> { "хлеб" });
var o2 = new Order("1", new List<string> { "хлеб" });
Console.WriteLine(o1 == o2); // False! Не то, что ожидалось

// Почему: record сравнивает поле Items через Equals — а у List<T> Equals
// НЕ переопределён по значению, значит сравниваются ССЫЛКИ на два разных списка.
// record даёт value equality только для того, что само умеет сравниваться по значению.

[!info]+ 🆕 Добавлено 28 июля — почему string-поля работают правильно, а List<T> нет (реальный вопрос с собеседования, Senior-уровень) Дело не в том, что record "особенный" со строками — а в том, что сам string в C# УЖЕ переопределяет Equals/== для сравнения по содержимому, на уровне языка, независимо от records. Record генерирует сравнение через EqualityComparer<T>.Default для КАЖДОГО поля по отдельности: ```csharp public record Person(string Name, List Tags);

var p1 = new Person("Ivan", new List { "dev" }); var p2 = new Person("Ivan", new List { "dev" }); // p1.Name и p2.Name — разные объекты строк в памяти, но string.Equals // сравнивает по содержимому → для этого поля всё ОК // p1.Tags и p2.Tags — разные объекты List, а у List Equals НЕ переопределён // → сравнение по ссылке → p1 == p2 будет False из-за ЭТОГО поля `` Общее правило: record's value equality рекурсивно зависит от того, переопределяет ли **каждое отдельное поле** собственное сравнение по значению. Строки — да, коллекции (List,Dictionary` и т.п.) — нет.

🤖 AI-инженерия: request/response тела для LLM API — идеальный кандидат на record: неизменяемые данные, value equality удобна для кэширования по содержимому промпта (одинаковый запрос = одинаковый хэш = можно закэшировать ответ).

🎤 Вопросы с собеседования

Q: Как работает Equals у record, если внутри есть List<T>? A: Record генерирует Equals, сравнивающий каждое поле через его собственный Equals. Для List<T> это сравнение ССЫЛОК (список не переопределяет Equals по содержимому), а не элементов внутри — частая ловушка (см. Пример D).

Q: Можно ли унаследовать record от обычного class, или наоборот? A: Нет — record может наследовать только от другого record. Смешивать record и class в одной цепочке наследования нельзя.

Q: Что обычно быстрее для маленьких неизменяемых объектов — record или record struct? A: record struct — value type, не требует выделения в куче и работы GC, для маленьких объектов (2-3 примитивных поля) обычно быстрее. Но копируется целиком при каждой передаче в метод, что для больших структур может быть накладнее, чем передача ссылки.

Q: Что делает with-выражение "под капотом"? A: Вызывает специальный скрытый copy-конструктор, сгенерированный компилятором для record, копирует все поля из оригинала, а затем присваивает те, что указаны в { ... } после with.

// Абстракция (2.5): контракт для любого типа сотрудника
public interface IPayable
{
    decimal CalculatePay();
}

// Наследование (2.3) + Инкапсуляция (2.2): общая база с защищённым состоянием
public abstract class Employee : IPayable
{
    public string Name { get; init; }
    protected decimal BaseSalary { get; init; }

    protected Employee(string name, decimal baseSalary)
    {
        Name = name;
        BaseSalary = baseSalary;
    }

    public abstract decimal CalculatePay(); // абстрактный — реализации нет
}

// Полиморфизм (2.4): каждый наследник считает зарплату по-своему
public class Developer : Employee
{
    public Developer(string name, decimal baseSalary) : base(name, baseSalary) { }
    public override decimal CalculatePay() => BaseSalary; // без бонусов
}

public class SalesManager : Employee
{
    public decimal SalesAmount { get; init; }
    public SalesManager(string name, decimal baseSalary, decimal salesAmount)
        : base(name, baseSalary) => SalesAmount = salesAmount;

    public override decimal CalculatePay() => BaseSalary + SalesAmount * 0.05m; // + процент с продаж
}

// Использование — динамический полиморфизм через список базового типа
List<Employee> employees = new()
{
    new Developer("Иван", 100_000m),
    new SalesManager("Анна", 80_000m, salesAmount: 500_000m)
};

foreach (var e in employees)
    Console.WriteLine($"{e.Name}: {e.CalculatePay():C}"); // вызовется правильная версия для каждого

Что здесь произошло: IPayable (абстракция) задаёт контракт → Employee (наследование + инкапсуляция) даёт общую базу с защищённым BaseSalary → Developer/SalesManager (полиморфизм) считают зарплату каждый по-своему → цикл foreach работает с ОДНИМ списком базового типа, не зная заранее, какой конкретно тип там лежит.
