🎭 Аналогия

Приёмо-сдаточные испытания из слоя 5 инфра-роадмапа, только автоматические. Тот же принцип: критерий формулируется до проверки, иначе проверка превращается в спор о том, работает оно или нет.

📖 Теория

Пирамида

Уровень Чего много Что проверяет Скорость
Unit больше всего одна функция без внешнего мира миллисекунды
Integration средне связка приложения и базы десятки миллисекунд
E2E мало сценарий целиком секунды

Перевёрнутая пирамида - когда почти всё покрыто медленными сквозными тестами - даёт набор, который никто не гоняет, потому что он идёт двадцать минут.

Фикстуры

import pytest
from fastapi.testclient import TestClient

@pytest.fixture(scope="session")
def engine():
    """Одна база на весь прогон."""
    eng = create_engine(TEST_URL)
    Base.metadata.create_all(eng)
    yield eng
    Base.metadata.drop_all(eng)

@pytest.fixture
def session(engine):
    """Каждый тест в своей транзакции с откатом - тесты не видят друг друга."""
    connection = engine.connect()
    trans = connection.begin()
    s = Session(bind=connection)
    yield s
    s.close()
    trans.rollback()
    connection.close()

@pytest.fixture
def client(session):
    app.dependency_overrides[get_session] = lambda: session
    with TestClient(app) as c:
        yield c
    app.dependency_overrides.clear()

Транзакция с откатом - главный приём: тесты не оставляют следов и не зависят от порядка выполнения.

dependency_overrides - способ подменить зависимость FastAPI на тестовую. Именно так подставляется тестовая сессия.

Параметризация

@pytest.mark.parametrize("title,expected", [
    ("DevOps-инженер", 25),
    ("Инженер сопровождения", 30),
    ("Курьер", 0),
    ("Руководитель отдела", 0),
])
def test_prescore(title, expected):
    assert prescore({"name": title})["score"] == expected

Один тест вместо четырёх, и в отчёте видно, какой именно случай упал.

Моки: что подменять, а что нет

Подменять Не подменять
внешние HTTP-вызовы свою бизнес-логику
отправку почты и сообщений базу в интеграционных тестах
текущее время структуры данных
файловую систему при необходимости ORM-модели

⚠️ Тест, где замокано всё, проверяет моки. Такой набор остаётся зелёным при полностью сломанном приложении.

def test_collect(monkeypatch):
    monkeypatch.setattr(collector, "fetch", lambda url: SAMPLE_HTML)
    assert len(collector.parse(SAMPLE_HTML)) == 20

Интеграционные тесты API

def test_create_and_read(client):
    response = client.post("/vacancies", json={"title": "Инженер сопровождения"})
    assert response.status_code == 201
    vid = response.json()["id"]

    got = client.get(f"/vacancies/{vid}")
    assert got.status_code == 200
    assert got.json()["title"] == "Инженер сопровождения"

def test_not_found(client):
    assert client.get("/vacancies/999999").status_code == 404

Для асинхронного приложения - httpx.AsyncClient с ASGITransport и pytest-asyncio.

Покрытие

pytest --cov=app --cov-report=term-missing --cov-fail-under=70

⚠️ Покрытие показывает, какие строки выполнились, а не какие проверены. Сто процентов покрытия при пустых assert ничего не значат. Смысл цифры - находить непокрытые куски, а не отчитываться.

🔧 Практика

На трекере и разведчике: 1. Фикстуры: база на прогон, сессия в транзакции с откатом, клиент с подменённой зависимостью. 2. Интеграционные тесты на основные маршруты трекера: создание, чтение, 404, конфликт. 3. Параметризованный тест на prescore разведчика - вынести туда все накопленные случаи, включая стоп-слова и вилку ниже планки. 4. Тест на resume_for: заголовок решает, описание не перебивает. Это был реальный баг. 5. raiseload("*") в тестовой конфигурации - ловить N+1 автоматически. 6. pytest --cov с порогом, встроить в GitHub Actions из слоя 2 инфра-роадмапа.

💥 Сломай намеренно

  1. Убрать откат транзакции из фикстуры и запустить набор дважды - получить падения на дублях.
  2. Сделать тесты зависимыми от порядка - один создаёт данные, второй их ждёт. Запустить с -p no:randomly и без.
  3. Замокать всё в одном тесте, потом сломать функцию под моком - убедиться, что тест зелёный.
  4. Написать тест без assert и посмотреть, что покрытие выросло, а проверок нет.
  5. Сломать prescore на одном случае и посмотреть, как параметризованный тест показывает именно его.

✅ Задание

Трекер и разведчик покрыты тестами, набор проходит за секунды и не зависит от порядка. pytest --cov с порогом стоит в пайплайне и роняет сборку при падении покрытия.

Критерий: объясняешь, почему сессия в фикстуре откатывается, и что именно проверяет каждый интеграционный тест.

🌍 Из жизни

Про тесты, зависящие от порядка. Набор проходит локально и падает в CI, потому что там другой порядок или параллельный запуск. Причина - общее состояние между тестами. Транзакция с откатом закрывает это целиком.

Про замоканные тесты. Реальный случай из практики: набор из двухсот зелёных тестов при полностью нерабочем приложении, потому что все внешние вызовы подменены, а проверяется поведение моков.

Про покрытие как цель. Требование «80 процентов покрытия» без требований к качеству проверок даёт тесты, которые вызывают код и ничего не утверждают. Цифра растёт, польза нет.

❓ Вопросы с ответами

Как устроены ваши тесты?

Пирамидой: много быстрых юнит-тестов, меньше интеграционных на связку с базой, единицы сквозных. Каждый тест идёт в своей транзакции с откатом, поэтому тесты не видят друг друга и не зависят от порядка.

Что мокаете, а что нет?

Мокаю внешние вызовы, отправку сообщений, время. Не мокаю свою логику и базу в интеграционных тестах. Тест, где замокано всё, проверяет моки и остаётся зелёным при сломанном приложении.

Как тестируете FastAPI-приложение?

TestClient для синхронного, httpx.AsyncClient с ASGITransport для асинхронного. Зависимость сессии подменяю через dependency_overrides на тестовую, идущую в транзакции с откатом.

Покрытие 100 процентов - это хорошо?

Покрытие показывает выполненные строки, а не проверенные. Смысл цифры - находить непокрытые куски. Как цель она даёт тесты без утверждений.
