Big O — теория (то, что раньше было только стратегией "выучи это первым")

Что это вообще такое. Big O описывает, как время (или память) работы алгоритма РАСТЁТ с увеличением размера входных данных n — не секунды на конкретном железе, а форму роста. Считаем худший случай по умолчанию (если не оговорено иное), берём только САМОЕ БЫСТРОРАСТУЩЕЕ слагаемое и выбрасываем константы: O(2n + 100) → O(n), потому что при n → ∞ константы перестают иметь значение по сравнению с ростом самого n.

Иерархия от быстрого к медленному (для интуиции — не нужно запоминать формулы):

Обозначение Название Пример
O(1) константа достать элемент по индексу массива
O(log n) логарифмическая бинарный поиск
O(n) линейная пройти массив один раз
O(n log n) линейарифмическая эффективная сортировка (merge sort, quicksort в среднем)
O(n²) квадратичная вложенные циклы по одному и тому же массиву
O(2ⁿ) экспоненциальная перебор всех подмножеств
O(n!) факториальная перебор всех перестановок

Про O(k) — конкретно то, что смутило. k — это НЕ n. Это отдельная, самостоятельная переменная, которая появляется, когда сложность зависит не только от размера всего входа, а ещё и от какого-то ДОПОЛНИТЕЛЬНОГО параметра задачи. Частые случаи: - Размер окна — как раз твоя задача из трекера "Maximum Sum Subarray of Size K": проход O(n), но если бы алгоритм зачем-то пересчитывал сумму окна заново на каждом шаге (а не сдвигал её), было бы O(n·k) — n сдвигов, каждый пересчёт занимает k шагов. - "Топ-K" задачи — "верните K самых частых элементов": часто решается через кучу (heap) размера k, сложность O(n log k) — n элементов проходим, но куча держит только k из них. - Отдельный второй вход — если на вход подаются ДВА независимых массива размером n и m, корректно писать O(n + m) (последовательно) или O(n · m) (вложенно) — нельзя просто написать O(n) и забыть про m, если m может быть большим независимо от n.

Ещё то, что часто путают: - Amortized (амортизированная) сложность — List<T>.Add() кажется O(n) из-за редких resize-ов (см. Phase1_CSharp_Fundamentals.md §1.7), но В СРЕДНЕМ по многим вызовам — O(1) amortized, потому что resize случается всё реже по мере роста списка. Указывается отдельно от обычного Big O, когда единичный "плохой" случай регулярно компенсируется массой "хороших". - Time vs Space complexity — Big O описывает не только время, но и ПАМЯТЬ. Решение может быть быстрым по времени (O(n)), но платить за это памятью (O(n) дополнительного места под хэш-таблицу) — на собесе часто спрашивают оба показателя, не только время. - Best/average/worst case — по умолчанию Big O = худший случай. Но иногда явно говорят "в среднем" (quicksort — O(n log n) в среднем, но O(n²) в худшем, если пивот выбирается неудачно каждый раз) — если не уточнить, какой случай имеется в виду, легко попасть впросак на собесе.

Q&A: - Почему O(2n) = O(n), а O(n + m) НЕЛЬЗЯ упростить до O(n)? → константы (2, 100 и т.п.) всегда выбрасываются, но РАЗНЫЕ переменные (n и m — два независимых входа) выбрасывать нельзя, потому что m может расти независимо и стать доминирующим слагаемым. - Что важнее на собесе — точная формула или порядок роста? → порядок роста. "Грубая оценка 2^(2n) вместо точной формулы Каталана" уже отмечено в разделе про backtracking ниже — та же логика применима везде.

Порядок изучения (источник: видео "Как выучить алгоритмы и решать LeetCode", канал "абоба")

  1. Базовые понятия — что такое алгоритмы/структуры данных, какие бывают.
  2. Big O — приоритетно и отдельно, до практики: уметь по коду прикидывать время/память.
  3. Практика — но НЕ рандомными задачами с самого начала. Сначала фильтр по теме, которую только что изучил, рандом — когда тема закрыта уверенно.
  4. После каждой темы — реализовать структуру/алгоритм самому, даже если он уже встроен в язык.

Важное разрешение себе: не нужно знать всё. 1-2 самых эффективных алгоритма сортировки наизусть достаточно, остальное — на уровне "знаю название и идею". Ориентир из видео — ~150 решённых задач за пару лет хватило автору для уверенности на собесах. Полный разбор — research/2026-08-08_leetcode-algorithms-strategy.md.

Таксономия паттернов LeetCode (источник: видео "Ты будешь страдать от алгоритмов...", канал Максим Фатин)

Идея видео: все ~3000 задач LeetCode сводятся к ~30 паттернам в 11-12 темах — не запоминать решение конкретной задачи, а узнавать паттерн по "гринфлагам" в условии. Это узнаваемая, реально существующая методология (в духе "Grokking the Coding Interview"), не выдумка конкретного автора.

⚠️ Что не проверяемо и не факт: цветовая частотность (зелёная/жёлтая/оранжевая/красная зона "как часто спрашивают в русском бигтехе") — личная категоризация автора, без методологии/выборки. Держать как ориентир приоритета, не как рыночную статистику. Видео также рекламирует платный курс (~2000₽) — техническая часть от этого не хуже, но это на заметку.

Конкретные, проверенные (не рекламные) советы, которые стоит забрать: - BFS vs DFS — простое правило: если в условии слово "минимум"/"кратчайший" — почти всегда BFS. - Деревья — первая строчка всегда проверка на пустой узел (частая ошибка №1); вторая частая ошибка — лишние null-проверки, которые пропускают edge case. - На собесе про сложность backtracking не бойся сказать грубую оценку (2^(2n)) вместо точной формулы Каталана — грубую оценку принимают нормально. - Алгоритм Кана (Kahn's algorithm) для топологической сортировки — через BFS-очередь, стартуя с узлов с нулевой входящей степенью — если топологическая сортировка всплывёт, это стандартный ответ.

Как использовать: не смотреть видео целиком (~1ч43м, визуальное, с кодом на экране — транскрипт часть теряет). Смотреть точечно, конкретный раздел, когда реально дошёл до этой темы на практике — таблица выше как чек-лист/навигация, что смотреть и когда.

Теория по паттернам зелёной зоны (даю сам, по мере практики)

Хэш-таблицы — три техники

  • Техника подсчёта — вхождения через Dictionary<T, int> (частоты символов/чисел).
  • КВВК (ключ-значение ↔ значение-ключ) — ищешь ДОПОЛНЕНИЕ до цели, а не саму цель (классический Two Sum).
  • Выбор ключа — ключом бывает не само значение, а производное от него (например, отсортированная строка для поиска анаграмм).
public int[] TwoSum(int[] nums, int target)
{
    var seen = new Dictionary<int, int>(); // значение → индекс
    for (int i = 0; i < nums.Length; i++)
    {
        int complement = target - nums[i];
        if (seen.TryGetValue(complement, out int j))
            return new[] { j, i };
        seen[nums[i]] = i; // добавляем ПОСЛЕ проверки — иначе элемент сматчится сам с собой
    }
    return Array.Empty<int>();
}

O(n) время, O(n) память.

Два указателя — три техники

  • С двух сторон — старт с обоих концов, схождение к середине (нужен отсортированный массив).
  • Каждому по указателю — идут по ДВУМ разным массивам одновременно (слияние отсортированных списков).
  • Быстрый и медленный — оба по одному массиву/списку, разная скорость (обнаружение цикла в связном списке).
public int[] TwoSum(int[] numbers, int target) // numbers — ОТСОРТИРОВАН (Two Sum II)
{
    int left = 0, right = numbers.Length - 1;
    while (left < right)
    {
        int sum = numbers[left] + numbers[right];
        if (sum == target) return new[] { left + 1, right + 1 }; // LeetCode ждёт 1-индексацию
        if (sum < target) left++; else right--;
    }
    return Array.Empty<int>();
}

O(n) время, но O(1) память — выигрыш у хэш-таблицы именно за счёт использования отсортированности массива. Хороший ответ на собесе на "а почему тут не хэш-таблица".

Плавающее окно — три техники

  • Фиксированной длины — размер K задан заранее, сдвиг O(1) вместо пересчёта O(K).
  • Непересекающиеся окна — массив режется на блоки без пересечения, каждый блок обрабатывается независимо.
  • Пересекающиеся (плавающий размер) — самый частый вариант на собесах: окно растёт правым указателем, схлопывается левым при нарушении условия.
// Фиксированное окно
public int MaxSumSubarray(int[] nums, int k)
{
    int windowSum = 0;
    for (int i = 0; i < k; i++) windowSum += nums[i];
    int maxSum = windowSum;
    for (int i = k; i < nums.Length; i++)
    {
        windowSum += nums[i] - nums[i - k];
        maxSum = Math.Max(maxSum, windowSum);
    }
    return maxSum;
}

// Плавающий размер — самая длинная подстрока без повторов
public int LengthOfLongestSubstring(string s)
{
    var lastSeen = new Dictionary<char, int>(); // хэш-таблица + окно — паттерны комбинируются!
    int left = 0, maxLen = 0;
    for (int right = 0; right < s.Length; right++)
    {
        if (lastSeen.TryGetValue(s[right], out int idx) && idx >= left)
            left = idx + 1;
        lastSeen[s[right]] = right;
        maxLen = Math.Max(maxLen, right - left + 1);
    }
    return maxLen;
}
