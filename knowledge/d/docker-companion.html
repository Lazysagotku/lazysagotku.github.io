Зачем вообще Docker, если есть виртуальные машины

Аналогия из жизни: VM - это отдельный дом для каждого жильца, со своим фундаментом и всеми коммуникациями с нуля (свой полноценный "гостевой" фундамент = ядро ОС). Container - это квартиры в ОДНОМ доме: общий фундамент и коммуникации (ядро хост-ОС), но у каждой квартиры своя закрытая дверь и обстановка (изоляция процессов/файловой системы). Строить отдельный дом на каждого жильца дольше, дороже и медленнее, чем нарезать квартиры в уже готовом доме.

Виртуальные машины (VM): на сервере с хост-ОС работает гипервизор (Hyper-V, VMware ESX, VirtualBox), который эмулирует железо и управляет виртуальными машинами. У каждой VM своя полноценная гостевая ОС, приложения работают уже внутри неё - поэтому на винде можно поднять линукс-VM и наоборот.

[!info]+ Уточнение - гипервизоры бывают двух типов Источник описывает все три гипервизора (Hyper-V, VMware ESX, VirtualBox) одинаково - "хост-ОС, а поверх неё гипервизор". Это точно только для VirtualBox (Type 2, hosted - реально работает как обычная программа поверх готовой ОС). VMware ESXi и Hyper-V - Type 1, bare-metal: ESXi сам по себе и есть минимальная ОС сервера, ставится прямо на железо; Hyper-V при включении встраивается НИЖЕ Windows в загрузке, а не работает как обычное приложение поверх неё. Частый вопрос на собесе про инфраструктуру - "чем Type 1 отличается от Type 2".

Проблема VM в мире микросервисов: каждая VM тащит за собой полную отдельную ОС - при большом числе копий одного приложения (типично для микросервисов) это дорого по ресурсам и медленно по старту.

Docker: убирает гипервизор и не виртуализирует железо - виртуализирует только ОС. Контейнеры используют ядро хост-ОС напрямую через Docker Engine, поэтому не нужна отдельная гостевая ОС на каждый экземпляр - легче и быстрее VM, при этом приложения всё ещё изолированы друг от друга и от системы.

Docker - не единственная технология контейнеризации (есть Podman, containerd напрямую, LXC), но самая распространённая.

Три элемента Docker

Аналогия из жизни: Dockerfile - рецепт (пошаговая инструкция). Image (образ) - уже приготовленное блюдо, готовое к раздаче (можно скопировать сколько угодно раз). Container (контейнер) - конкретная порция этого блюда у тебя на тарелке - можно "взять добавку" и запустить ещё один контейнер из того же образа.

  • Dockerfile - набор инструкций: как собрать образ и что в нём должно оказаться.
  • Image (образ) - готовое к запуску приложение: исходный код, библиотеки, зависимости, инструменты. Собирается из Dockerfile.
  • Container (контейнер) - запущенный экземпляр образа.

Docker Registry - хранилище образов, которыми можно делиться. Docker Hub - самый крупный публичный registry, откуда можно скачать готовый образ приложения или ОС и собрать на его основе свой.

Пример Dockerfile

FROM ubuntu:20.04
RUN apt-get update
RUN apt-get -y install nginx
EXPOSE 80/tcp
CMD ["/usr/sbin/nginx", "-g", "daemon off;"]
  • FROM - базовый образ, от которого отталкиваемся (тянется из Docker Hub).
  • RUN - команда, выполняется ВО ВРЕМЯ сборки образа (docker build).
  • EXPOSE - какой порт слушает приложение внутри контейнера.
  • CMD - команда, которая выполняется при ЗАПУСКЕ контейнера (docker run), не при сборке.
  • daemon off для nginx обязателен - иначе nginx уйдёт в фон и завершится как процесс, а Docker посчитает, что главный процесс контейнера умер, и остановит сам контейнер.

[!tip]+ Частый вопрос на собесе - "что не так с этим Dockerfile" Два отдельных RUN apt-get update и RUN apt-get install - рабочий, но не best-practice вариант. Docker кэширует каждый RUN как отдельный слой: если потом изменить только строку install (добавить пакет), Docker может переиспользовать СТАРЫЙ закэшированный слой update и попытаться поставить пакет по устаревшему списку версий. Правильно - объединять в один слой: RUN apt-get update && apt-get install -y nginx.

Команды: - docker build - собрать образ из Dockerfile. - docker run - запустить контейнер из образа. - docker pull nginx - скачать готовый образ с Docker Hub без своего Dockerfile, если кастомизация не нужна.

Данные и остановка контейнера

[!info]+ Реальная неточность источника В видео сказано: "все изменения внутри контейнера теряются при его остановке (docker stop)". Это НЕВЕРНО в таком виде: изменения в файловой системе контейнера живут в его собственном "слое для записи" и переживают docker stop/docker start - тот же контейнер после повторного запуска содержит те же изменения. Данные реально теряются, когда контейнер УДАЛЯЮТ (docker rm) или создают НОВЫЙ контейнер из образа взамен старого (частый сценарий деплоя - docker run каждый раз создаёт свежий контейнер "с нуля" из образа, старые изменения в нём отсутствуют). Поэтому для данных, которые должны переживать пересоздание контейнера, используют volumes (именованные тома) или bind mounts (примонтированную папку с хоста) - они существуют отдельно от жизненного цикла конкретного контейнера.

Несколько контейнеров сразу - docker-compose

Аналогия из жизни: банкетный заказ одним листом - вместо того чтобы заказывать каждое блюдо отдельно, один документ описывает сразу весь стол (все сервисы приложения), и по одной команде подаётся всё сразу.

Суть: docker-compose.yml описывает несколько сервисов (контейнеров) и их настройки в одном файле. docker-compose up поднимает весь набор контейнеров разом, вместо ручного запуска каждого по отдельности.

Оркестрация - когда контейнеров десятки/сотни

Управление большим числом контейнеров (мониторинг, обновление, распределение ресурсов, балансировка нагрузки) руками не масштабируется - для этого нужны инструменты оркестрации: Docker Swarm (родной инструмент самого Docker) или Kubernetes (сейчас фактический стандарт индустрии).

Базовые понятия Kubernetes (Pod/Deployment/Service), команды kubectl и разбор "Docker vs containerd в проде" - уже в Kubernetes_Companion.md, здесь не дублируется.

Итог - если Docker такой удобный, почему VM всё ещё нужны

Docker решает не все задачи виртуализации:

  1. Другое ядро ОС. Контейнер использует ядро ХОСТА - линукс-контейнер не запустится напрямую на голом Windows-хосте (и наоборот) без прослойки. Если нужно гонять реально другую ОС - нужна VM.
  2. Более сильная изоляция. Контейнеры делят одно ядро хоста - если в ядре найдётся уязвимость, потенциально она затрагивает ВСЕ контейнеры на хосте. VM изолированы на уровне гипервизора сильнее - это критично для настоящего multi-tenant хостинга чужого недоверенного кода (например, облачные провайдеры продают VM клиентам именно из-за этого).
  3. Легаси-приложения, завязанные на конкретное ядро/драйверы/полноценную ОС, которые не переносятся в контейнер без серьёзной переделки.
  4. Комплаенс/регуляторные требования, которые явно требуют изоляции на уровне отдельной ОС или железа, а не просто изоляции процессов.

На практике VM и контейнеры часто комбинируют: контейнеры запускают ВНУТРИ VM (например, в облаке) - получая изоляцию VM между разными клиентами/командами и лёгкость контейнеров внутри одной команды.
