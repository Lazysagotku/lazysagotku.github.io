Мониторинг — три опоры (metrics/logs/traces)

Аналогия из жизни: приборная панель автомобиля. Метрики — спидометр и датчик температуры (текущие числовые показатели прямо сейчас). Логи — бортовой журнал поездок (что произошло и когда, событие за событием). Трейсинг — GPS-трек маршрута (путь одного конкретного запроса через несколько систем).

Метрики — числовые показатели во времени: CPU, память, число запросов в секунду, процент ошибок. Смотрятся на дашборде, по ним настраиваются алерты ("CPU > 90% дольше 5 минут → уведомление").

Логи — записи событий (что произошло). Первое, куда смотрят при инциденте — journalctl/tail -f /var/log/... (уже разбирали под Спецавтобазу).

Трейсинг — путь одного запроса через несколько сервисов (актуально для микросервисной архитектуры) — показывает, на каком именно шаге запрос затормозил.

Популярные инструменты: - Zabbix — классический, agent-based, силён в мониторинге инфраструктуры (CPU/диск/сеть серверов). - Prometheus — pull-based, хранит метрики как time-series, стандарт в cloud-native/K8s мире. - Grafana — визуализация (дашборды), может подключаться к Prometheus, Zabbix, даже напрямую к PostgreSQL. - Elasticsearch (в связке ELK/EFK-стек) — третья опора, логи в МАСШТАБЕ. journalctl/tail -f (уже разбирали выше) работают для одного сервера — когда логов много и они с десятков серверов/сервисов, нужен централизованный поиск. ELK = Elasticsearch (хранит и индексирует логи — тот же движок, что разобран как поисковая БД в NoSQL_Companion.md) + Logstash/Fluentd (собирает и парсит логи с источников) + Kibana (визуализация — аналог Grafana, но заточен под логи, не метрики).

Мониторинг конкретных систем

RabbitMQ и Kafka - реальный опыт есть. Через PIX Robotics: RabbitMQ настраивал внутри RPA-процессов, Kafka была привязана к личному кабинету с портфелями брокеров/инвесторов - работал на уровне подключения и мониторинга очереди (список сообщений, прохождение).

Что конкретно мониторят у RabbitMQ: глубина очереди (queue depth - сколько сообщений скопилось необработанными: если растёт без остановки, консьюмеры не успевают), число активных консьюмеров, неподтверждённые сообщения (unacked). Встроенный плагин rabbitmq_management даёт веб-дашборд и HTTP API для этих метрик "из коробки".

Что конкретно мониторят у Kafka: consumer lag - разрыв между последним записанным сообщением и тем, что консьюмер реально уже обработал - САМАЯ важная метрика Kafka (растущий lag = потребитель отстаёт от потока). Плюс здоровье брокеров, распределение партиций, throughput (сообщений/байт в секунду).

Redis - встроенный мониторинг: - INFO - память, число подключений, операций в секунду, hit/miss ratio для кэша. - redis-cli --latency - замер задержки напрямую. - MONITOR - поток команд в реальном времени (осторожно в проде - нагружает сам сервер).

PostgreSQL - внутренний мониторинг без внешних инструментов: - pg_stat_activity - какие запросы выполняются прямо сейчас, кем, как долго. - pg_stat_statements (расширение) - агрегированная статистика по ВСЕМ выполненным запросам за время работы - находит самые тяжёлые запросы без внешнего APM. - pg_stat_user_tables - Seq Scan vs Index Scan по каждой таблице, число "мёртвых" строк (сигнал, что пора VACUUM). - pg_stat_database - коммиты/роллбэки/hit ratio кэша на уровне базы целиком.

Q&A: - Zabbix vs Prometheus — в чём разница подхода? → Zabbix обычно опрашивает агенты сам (push от агента или pull от сервера, гибко), Prometheus типично сам "стучится" (pull) на /metrics-эндпоинт приложения по расписанию. - Что такое alert fatigue? → слишком много алертов на несущественные вещи — люди начинают их игнорировать, и по-настоящему важный алерт теряется в шуме.

Диагностика "сервер не работает" — структурный подход

Порядок проверки (от внешнего к внутреннему): 1. Сеть доступна? → ping <host>, curl -I <url> — отвечает ли сервер вообще. 2. Сервис запущен? → systemctl status <service> — процесс жив или упал. 3. Ресурсы не исчерпаны? → top/htop (CPU/память), df -h (место на диске — забитый диск роняет сервисы неочевидным образом). 4. Что говорят логи? → journalctl -u <service> / tail -f /var/log/... — что произошло непосредственно ПЕРЕД сбоем.

Такой порядок — от "видно ли сервер вообще" к "что конкретно внутри сломалось" — стандартная логика диагностики, которую ждут от support-инженера.

Как остальные companion-файлы — пополняется по ходу. Уровень намеренно "базовое понимание" — именно так K8s указан почти во всех вакансиях, которые встречались (МТС, рыночный анализ Middle C#/.NET: "чаще плюс, не жёсткое требование"). Не курс по администрированию кластеров.

Зачем вообще нужен Kubernetes

Аналогия из жизни: Kubernetes — как автоматизированный логист склада. Без него: если один грузчик (сервер) заболел, никто не заметит, что заказы (запросы) перестали обрабатываться. С K8s: система сама следит, сколько "грузчиков" реально работает, автоматически нанимает нового взамен заболевшего, и может временно нанять больше людей в пиковый сезон (авто-масштабирование).

Суть: K8s — оркестратор контейнеров. Он не заменяет Docker (контейнеры всё ещё Docker/containerd), а управляет ИМИ: где запустить, сколько копий держать, что делать при падении, как балансировать трафик между копиями.

Базовые понятия

Container (контейнер) vs виртуальная машина: - VM — полноценная копия ОС внутри другой ОС, тяжёлая (гигабайты), своё ядро. - Container — использует ЯДРО ХОСТА, изолирует только процесс/файловую систему — легче (мегабайты), быстрее стартует.

Pod — минимальная единица развёртывания в K8s. Обычно один под = один контейнер (иногда несколько тесно связанных). Поды — временные (эфемерные): K8s может в любой момент убить под и создать новый вместо него — поэтому нельзя хранить важные данные ВНУТРИ пода.

Deployment — описывает, СКОЛЬКО копий пода (реплик) должно работать одновременно и как их обновлять (rolling update — по одной копии за раз, без простоя).

Service — стабильный "адрес" для доступа к подам, которые постоянно пересоздаются с новыми IP. Service — как стабильный номер телефона колл-центра: конкретный сотрудник (под), который ответит, может меняться, но номер (Service) остаётся тем же.

ReplicaSet — следит, чтобы всегда работало ЗАДАННОЕ число подов (обычно управляется через Deployment, напрямую редко трогают).

Namespace — логическая "перегородка" внутри кластера — разделяет ресурсы разных команд/окружений (dev/staging/prod) в одном кластере.

Архитектура кластера - Control Plane и Data Plane

Аналогия из жизни: оркестр. Каждый музыкант (под с контейнером) сосредоточен только на своей партии и не видит картину целиком. Дирижёр (Control Plane) слушает весь оркестр, смотрит партитуру (желаемое состояние) и следит, чтобы всё звучало слаженно - если виолончелист сломал смычок (упал под), дирижёр обеспечивает, чтобы кто-то тут же подхватил партию (Auto-heal), а на кульминации подключает всех разом, когда нужна полная мощь (Auto-scale).

Кластер - объединение серверов для совместной работы. Нода (node) - один сервер внутри кластера. Ноды делятся на два типа:

  • Master-нода (Control Plane) - "мозг" кластера, управляет остальными нодами.
  • Worker-нода (Data Plane) - "рабочая лошадка", на ней реально крутятся контейнеры приложения.

Master-нода - из чего состоит

  • API Server - точка входа для ЛЮБОГО взаимодействия с кластером (включая kubectl) - все запросы идут через него.
  • Controller Manager - следит за состоянием кластера. Ключевая идея всего Kubernetes: есть desired state (желаемое состояние - как всё должно работать, задаётся конфигом) и current state (текущее реальное состояние). Задача Controller Manager - постоянно приводить текущее состояние к желаемому (например, было указано 3 реплики пода - одна упала - контроллер поднимает новую взамен).
  • Scheduler - решает, НА КАКУЮ ноду поставить новый под, с учётом загруженности нод и доступных ресурсов.
  • etcd - распределённое key-value хранилище, где лежит всё состояние кластера (конфиги, статусы нод и подов). При сбое именно отсюда кластер восстанавливает картину происходящего.

Мастер-нода критична для управления кластером, поэтому в продакшне обычно держат несколько master-нод для отказоустойчивости (одна не переживёт сбоя - всегда нужен резерв).

[!info]+ Терминология Официальная документация Kubernetes постепенно уходит от термина "master" в пользу "control plane node" - смысл тот же, но если встретишь оба термина (в старых материалах чаще "master", в новых - "control plane"), это не разные вещи.

Worker-нода - из чего состоит

  • kubelet - агент на каждой worker-ноде, общается с master и следит, чтобы на этой конкретной ноде реально работало то, что было предписано.
  • Container runtime - непосредственно запускает/останавливает контейнеры, управляет их образами и ресурсами (containerd/CRI-O/Docker - см. выше).
  • kube-proxy - сетевая часть: коммуникация между подами и балансировка нагрузки внутри кластера.

Под (Pod) и Service - что нового к уже разобранному выше

Каждому поду при создании выдаётся собственный IP-адрес. Но поды эфемерны - под может пересоздаться (например, если его нода "прилегла"), и при пересоздании IP МЕНЯЕТСЯ. Именно поэтому нужен Service - он даёт группе подов ОДИН стабильный IP и сам распределяет запросы между реально живыми подами прямо сейчас (балансировка нагрузки).

Декларативный конфиг (YAML)

Настройка кластера идёт через запрос к API Server с файлом конфигурации, обычно в формате YAML, описанным в декларативном стиле - мы описываем не последовательность действий, а то, каким должно быть конечное состояние, а Controller Manager сам приводит систему к этому состоянию.

Пример конфига для Deployment (шаблон, по которому создаются поды):

apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3
  template:
    spec:
      containers:
        - image: nginx

replicas: 3 - желаемое состояние "всегда 3 пода". Если один упадёт, Deployment-контроллер (часть Controller Manager) увидит расхождение с desired state и поднимет новый под взамен.

Kubernetes - альтернативы и совместимые runtime (уточнение)

Источник видео перечисляет как "альтернативы Kubernetes" сразу Docker Swarm, HashiCorp Nomad, AWS Fargate и RedHat OpenShift - два последних пункта не совсем корректно поставлены в один ряд:

  • Docker Swarm и HashiCorp Nomad - действительно самостоятельные оркестраторы-конкуренты Kubernetes. Корректная пара для сравнения.
  • AWS Fargate - это НЕ оркестратор, а serverless-движок для запуска контейнеров без управления серверами - работает ПОД капотом у ECS или EKS (управляемого Kubernetes от AWS), а не вместо них. Реальный аналог Kubernetes от AWS - это ECS (Elastic Container Service).
  • RedHat OpenShift - не альтернатива Kubernetes, а дистрибутив/платформа НА БАЗЕ Kubernetes (с добавленными enterprise-инструментами) - как Ubuntu не альтернатива ядру Linux, а дистрибутив на его основе.

Откуда взялось "k8s"

k8s - численоним (numeronym): K, затем число букв между K и s в слове "kubernetes" (u-b-e-r-n-e-t-e-s - ровно 8 букв), затем s. Тот же принцип, что в "i18n" (internationalization) или "a11y" (accessibility). Условность прижилась в сообществе Kubernetes/Google с самого открытия проекта (2014) - не единоличное "изобретение" одного человека, а стандартная для инженерного сообщества практика сокращения длинных слов.

Базовые команды kubectl

kubectl get pods              # список подов
kubectl get pods -o wide      # с доп. деталями (нода, IP)
kubectl describe pod <имя>    # подробности + события (полезно для диагностики)
kubectl logs <имя-пода>       # логи контейнера — первое, что смотришь при инциденте
kubectl exec -it <под> -- bash # зайти внутрь контейнера
kubectl get deployments
kubectl rollout restart deployment <имя>  # перезапустить (rolling, без простоя)

Docker vs containerd — есть ли K8s = обязательно Docker?

Нет, не обязательно буквально. С версии 1.24 (2022) Kubernetes убрал встроенную поддержку Docker (dockershim) — общается с контейнерами через CRI (Container Runtime Interface), и большинство кластеров сегодня используют containerd или CRI-O напрямую, без Docker Engine.

Важная деталь: containerd изначально был ЧАСТЬЮ Docker (Docker Engine сам внутри использует containerd) — K8s не отказался от "контейнеров", а убрал лишний промежуточный слой самого Docker Engine.

Практическое следствие: образы, собранные через docker build, всё равно работают в K8s — все следуют общему стандарту OCI (Open Container Initiative). Разработчики почти наверняка используют Docker локально для сборки, даже если прод-кластер бежит на containerd напрямую.

Честный ответ на собесе, если спросят "у вас же Docker раз K8s": "Docker-образы почти наверняка используются для сборки, но какой именно runtime в проде — Docker Engine или containerd напрямую — лучше уточнить, не буду предполагать."

Q&A

Q: Чем под отличается от контейнера? A: Под — обёртка вокруг одного (или нескольких тесно связанных) контейнеров, это единица, которой управляет K8s. Обычно 1 под = 1 контейнер приложения.

Q: Что делать, если под "упал" (CrashLoopBackOff)? A: kubectl logs <под> — посмотреть логи ПЕРЕД падением, kubectl describe pod — посмотреть события (например нехватка памяти, неправильный health-check).

Q: Зачем нужен Service, если есть под? A: У подов IP-адрес меняется при каждом пересоздании — Service даёт стабильную точку входа, которая сама находит актуальные поды.

Q: Что такое health-check (liveness/readiness probe)? A: Способ K8s узнать, жив ли под и готов ли принимать трафик. Liveness — "жив ли контейнер вообще" (если нет — перезапуск). Readiness — "готов ли принимать запросы прямо сейчас" (если нет — временно убрать из Service, не перезапускать).
