День 1 — Pydantic, декораторы, Strategy pattern

1.1 Pydantic — валидация данных

Почему это важно

В C# у тебя типы проверяет компилятор ДО запуска. В Python типов на рантайме никто не проверяет — def f(x: int) пропустит строку без единой жалобы. Pydantic закрывает эту дыру: BaseModel валидирует данные НА ГРАНИЦЕ системы (запрос пришёл по HTTP, JSON из файла, ответ внешнего API) и падает сразу с понятной ошибкой, а не где-то через три вызова функций.

Теория

BaseModel — класс, где поля объявляются как атрибуты класса с type hints. При создании экземпляра Pydantic проверяет и, где может, приводит типы ("5" → 5 для int, но не "abc" → int). Если данные не проходят — кидает ValidationError со списком всех проблемных полей сразу (не первая ошибка и стоп, как обычно бывает).

Это НЕ то же самое, что @dataclass — dataclass просто хранит поля, без единой проверки. Pydantic создан именно ради валидации.

Пример A — простая модель

from pydantic import BaseModel

class Point(BaseModel):
    latitude: float
    longitude: float

p = Point(latitude=59.94, longitude=30.31)
p2 = Point(latitude="59.94", longitude=30.31)  # OK — Pydantic приведёт строку к float
# p3 = Point(latitude="not a number", longitude=30.31)  # ValidationError

Пример B — Field с ограничениями и дефолтами

from pydantic import BaseModel, Field

class OrderResponse(BaseModel):
    order_id: int = Field(..., description="Уникальный идентификатор заказа")
    status: str = Field(default="created")
    price: float = Field(..., ge=0, description="Не может быть отрицательной")

... (Ellipsis) в Field(...) означает "обязательное поле, без дефолта". ge=0 — "greater or equal 0", валидация уже на уровне схемы, а не в ручном if.

Пример C — вложенные модели

class OrderRequest(BaseModel):
    start: Point
    end: Point
    passenger_name: str

Pydantic рекурсивно валидирует вложенные модели — если start придёт без longitude, ошибка укажет точный путь: start -> longitude: field required.

Пример D — обработка ошибки валидации

from pydantic import ValidationError

try:
    bad_order = OrderRequest(start={"latitude": 59.94}, end=p, passenger_name="Иван")
except ValidationError as e:
    print(e.errors())
    # [{'type': 'missing', 'loc': ('start', 'longitude'), 'msg': 'Field required', ...}]

🎤 Вопросы с собеседования

Q: Чем pydantic.BaseModel отличается от @dataclass? A: dataclass только хранит поля и генерирует __init__/__repr__ — никакой проверки данных. BaseModel валидирует типы при создании экземпляра и кидает ValidationError, если данные не соответствуют схеме. dataclass — структура данных, BaseModel — структура данных + контракт.

Q: Что произойдёт, если передать полю неверный тип, который нельзя привести? A: Pydantic попытается привести тип (coercion) там, где это однозначно (строка "5" → int), но если приведение невозможно ("abc" → int) — кидает ValidationError со списком всех невалидных полей сразу, а не только первого.

Q: Как сделать поле необязательным с дефолтным значением? A: status: str = Field(default="created") или просто status: str = "created" без Field, если ограничений не нужно.

Q: Как Pydantic связан с FastAPI? A: FastAPI использует Pydantic-модели как схему тела запроса и ответа. Когда JSON приходит на эндпоинт, FastAPI сам создаёт BaseModel из тела запроса — если валидация не прошла, клиент получает 422 автоматически, без единой строчки ручного кода на эндпоинте.

1.2 Декораторы — с нуля

Почему это важно

В курсе Strategy pattern и FastAPI везде используются декораторы (@app.get(...), @abstractmethod, @pytest.fixture). Если не понимать, что декоратор реально делает — это магические заклинания, а не инструмент.

Теория

Функции в Python — обычные объекты: их можно передать как аргумент, вернуть из другой функции, присвоить переменной. Декоратор — это функция, которая принимает функцию и возвращает функцию (обычно — обёртку вокруг оригинала). Синтаксис @decorator над def f() — просто сахар для f = decorator(f).

Пример A — простой декоратор

def log_time(func):
    def wrapper(*args, **kwargs):
        import time
        start = time.time()
        result = func(*args, **kwargs)
        print(f"{func.__name__} выполнилась за {time.time() - start:.3f} сек")
        return result
    return wrapper

@log_time
def slow_add(a, b):
    import time
    time.sleep(1)
    return a + b

slow_add(2, 3)  # напечатает время выполнения, вернёт 5

Без @ это было бы: slow_add = log_time(slow_add).

Пример B — functools.wraps (чтобы не терять метаданные)

from functools import wraps

def log_time(func):
    @wraps(func)  # сохраняет func.__name__, func.__doc__ у обёртки
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

Без @wraps после декорирования slow_add.__name__ стало бы "wrapper", а не "slow_add" — ломает отладку и интроспекцию.

Пример C — декоратор с параметрами (три уровня вложенности)

def retry(times: int):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            last_error = None
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    last_error = e
            raise last_error
        return wrapper
    return decorator

@retry(times=3)
def flaky_call():
    ...

retry(times=3) выполняется первым и возвращает decorator — вот этот decorator уже применяется к flaky_call как обычный однопараметрический декоратор.

Пример D — @property (мостик к C#)

class BankAccount:
    def __init__(self, owner: str):
        self._balance = 0
        self.owner = owner

    @property
    def balance(self) -> float:
        return self._balance

    @balance.setter
    def balance(self, value: float):
        if value < 0:
            raise ValueError("Баланс не может быть отрицательным")
        self._balance = value

acc = BankAccount("Иван")
acc.balance = 100      # вызывает setter
print(acc.balance)     # вызывает getter, напечатает 100

Это прямой аналог твоего C# { get; private set; } с валидацией — просто другой синтаксис. @property превращает МЕТОД в АТРИБУТ по чтению (без скобок), @balance.setter — второй декоратор, добавляющий версию для записи.

🎤 Вопросы с собеседования

Q: Что реально происходит, когда пишешь @my_decorator над функцией? A: Это синтаксический сахар для func = my_decorator(func) — функция под декоратором заменяется на то, что вернул декоратор (обычно — обёртку wrapper, вызывающую оригинал плюс что-то до/после).

Q: Зачем нужен functools.wraps? A: Без него обёртка (wrapper) заменяет метаданные оригинальной функции — __name__, __doc__, __module__. Это ломает отладку, логи, автогенерацию документации (например, FastAPI использует __name__/docstring эндпоинтов для Swagger). @wraps(func) копирует эти метаданные с оригинала на обёртку.

Q: Чем @property в Python похож на { get; set; } в C#? A: Оба превращают доступ к методу в синтаксис доступа к полю. Разница — в C# это отдельная языковая конструкция (property), в Python это обычный декоратор поверх обычного метода: @property для getter, @x.setter для setter. Логика валидации в setter'е работает идентично твоему примеру private set { if (value < 0) throw ... }.

Q: Как сделать декоратор, принимающий свои параметры (например, @retry(times=3))? A: Нужен дополнительный уровень вложенности функций: внешняя функция принимает параметры декоратора и возвращает СОБСТВЕННО декоратор (функцию от одного аргумента — целевой функции), которая уже возвращает wrapper. Три уровня: retry(times) → decorator(func) → wrapper(*args, **kwargs).

1.3 Strategy pattern через ABC + abstractmethod

Почему это важно

Ты уже проходил это в C# как abstract class/interface (Фаза 2). Задача — не учить паттерн заново, а увидеть, как ТОТ ЖЕ паттерн выглядит в Python, где нет interface как отдельного языкового элемента.

Теория

Модуль abc даёт ABC (Abstract Base Class) и декоратор @abstractmethod. Класс, унаследованный от ABC с хотя бы одним @abstractmethod, нельзя инстанцировать напрямую — только через наследника, реализовавшего ВСЕ абстрактные методы. Это прямой аналог C# abstract class (не interface — в Python ABC может иметь и обычные, не абстрактные методы с готовой реализацией, ровно как abstract class в C#).

Пример A — базовый контракт стратегии

from abc import ABC, abstractmethod

class PricingStrategy(ABC):
    @abstractmethod
    def calculate(self, distance_km: float) -> float:
        ...

class FixedPriceStrategy(PricingStrategy):
    def __init__(self, base_price: float):
        self.base_price = base_price

    def calculate(self, distance_km: float) -> float:
        return self.base_price

class DistancePriceStrategy(PricingStrategy):
    def __init__(self, price_per_km: float, base_fee: float = 50):
        self.price_per_km = price_per_km
        self.base_fee = base_fee

    def calculate(self, distance_km: float) -> float:
        return self.base_fee + distance_km * self.price_per_km

Пример B — что будет, если не реализовать метод

class BrokenStrategy(PricingStrategy):
    pass

# strategy = BrokenStrategy()
# TypeError: Can't instantiate abstract class BrokenStrategy
# with abstract method calculate

Ошибка — на этапе создания экземпляра, не на этапе объявления класса. Класс с недоделанным контрактом определить можно, инстанцировать — нельзя.

Пример C — использование стратегии (композиция, а не наследование)

class OrderPricer:
    def __init__(self, strategy: PricingStrategy):
        self.strategy = strategy

    def price_for(self, distance_km: float) -> float:
        return self.strategy.calculate(distance_km)

pricer = OrderPricer(FixedPriceStrategy(base_price=300))
print(pricer.price_for(distance_km=12))  # 300 — стратегия не смотрит на дистанцию

pricer.strategy = DistancePriceStrategy(price_per_km=25)
print(pricer.price_for(distance_km=12))  # 50 + 12*25 = 350

Стратегию можно поменять в рантайме простым присваиванием атрибута — ключевая идея паттерна: поведение — это объект, а не if/else внутри OrderPricer.

Пример D — альтернатива без ООП (higher-order function)

Python не заставляет решать всё через классы — то же самое можно сделать функциями:

from typing import Callable

def fixed_price(base_price: float) -> Callable[[float], float]:
    return lambda distance_km: base_price

def distance_price(price_per_km: float, base_fee: float = 50) -> Callable[[float], float]:
    return lambda distance_km: base_fee + distance_km * price_per_km

strategy_fn = distance_price(price_per_km=25)
print(strategy_fn(12))  # 350

Функциональный вариант короче, но теряет расширяемость (нельзя добавить стратегии со своим состоянием/методами так же легко) и явный контракт (ABC документирует сигнатуру, обычная функция — нет).

🎤 Вопросы с собеседования

Q: Чем ABC в Python отличается от interface в C#? A: ABC ближе к C# abstract class: может содержать как абстрактные методы (@abstractmethod, без реализации), так и обычные методы с готовым кодом. В Python нет отдельной языковой конструкции interface — если нужен "чистый контракт без реализации", это просто ABC, где ВСЕ методы абстрактные.

Q: Что произойдёт, если попытаться создать экземпляр класса-наследника ABC, не реализовав один из @abstractmethod? A: TypeError в момент вызова конструктора (ClassName()), а не при объявлении класса. Класс с недоделанным контрактом определить можно — Python проверяет полноту реализации только при инстанцировании.

Q: Мини-задание расширило calculate новым параметром is_night только в одном наследнике — что здесь не так с точки зрения ООП? A: Это нарушает Liskov Substitution Principle (ты проходил его в C# на SOLID) — если TimeOfDayStrategy требует параметр, которого нет в базовой сигнатуре, её нельзя подставить туда, где ожидается любой PricingStrategy, без дополнительных проверок типа. Правильно — либо добавить параметр в базовый абстрактный метод (даже если остальные стратегии его игнорируют), либо передавать контекст (время суток) через отдельный объект-параметр, который есть у всех стратегий.

Q: Зачем вообще Strategy, если можно передать функцию напрямую (Пример D)? A: Оба подхода валидны в Python. Функциональный вариант проще для простых случаев без внутреннего состояния сверх замыкания. Классовый (ABC) вариант лучше, когда стратегии должны хранить сложное состояние, иметь несколько связанных методов, или когда важен явный, проверяемый интерфейсом контракт — то есть ровно те случаи, где в C# тоже выбрали бы interface, а не Func<T>.

День 2 — Асинхронность и FastAPI

2.1 asyncio — основы

Почему это важно

Ты только что закапывался в C# concurrency (Ozon-банк подтвердил: это топ-1 тема на собесах). Хорошая новость — концепции переносятся, меняется только синтаксис и модель исполнения. Разница, которую важно не перепутать: C# async/await может реально исполняться на разных потоках пула потоков; Python asyncio — ОДИН поток, переключающийся между задачами кооперативно (GIL всё равно не даёт параллелизма для CPU-bound кода).

Теория

  • event loop — диспетчер, который знает обо всех незавершённых корутинах и переключается между ними, когда одна из них "отдаёт" управление на await.
  • корутина (async def) — функция, которая при вызове НЕ выполняется сразу, а возвращает объект-корутину. Выполняется только через await или через event loop.
  • Асинхронность помогает при I/O-bound (сеть, диск, БД, таймеры) — пока одна задача ждёт ответ, другая может работать. НЕ помогает при CPU-bound (для этого — multiprocessing, отдельные процессы, обходящие GIL).

Пример A — синхронная версия (медленно)

import time

def simulate_driver_sync(order_id: int, seconds: int):
    for i in range(seconds):
        time.sleep(1)
        print(f"Заказ {order_id}: секунда {i+1}")

simulate_driver_sync(1, 3)
simulate_driver_sync(2, 3)
# Итого 6 секунд — строго по очереди

Пример B — асинхронная версия с asyncio.gather

import asyncio

async def simulate_driver(order_id: int, seconds: int):
    for i in range(seconds):
        await asyncio.sleep(1)
        print(f"Заказ {order_id}: секунда {i+1}")

async def main():
    await asyncio.gather(
        simulate_driver(1, 3),
        simulate_driver(2, 3),
    )

asyncio.run(main())
# Итого ~3 секунды — оба "водителя" двигаются одновременно

asyncio.gather — прямой аналог Task.WhenAll в C#: запускает несколько корутин конкурентно и ждёт завершения всех.

Пример C — частая ошибка: заблокировать весь event loop

async def bad_driver(order_id: int):
    time.sleep(3)  # ОШИБКА: обычный blocking sleep, не asyncio.sleep
    print(f"Заказ {order_id} готов")

# Если запустить несколько bad_driver через gather — они всё равно
# выполнятся строго по очереди, потому что time.sleep блокирует
# ЕДИНСТВЕННЫЙ поток, на котором крутится весь event loop.

Это самая частая ошибка в асинхронном Python-коде: одна blocking-вызов (time.sleep, синхронный requests.get, тяжёлые вычисления) без await останавливает ВСЮ систему, а не только одну задачу — потому что поток один.

Пример D — сравнение терминов C# ↔ Python

C# Python Комментарий
async Task Method() async def method() корутина/асинхронный метод
await task await coro ждать результат, не блокируя поток
Task.WhenAll(t1, t2) asyncio.gather(c1, c2) запустить конкурентно, ждать все
Пул потоков (может быть параллелизм) Один event loop (без параллелизма, GIL) ключевое отличие модели исполнения
Task.Delay(1000) asyncio.sleep(1) неблокирующая задержка

🎤 Вопросы с собеседования

Q: Чем asyncio-корутина отличается от потока (thread)? A: Поток — реальная единица исполнения ОС, может выполняться параллельно на другом ядре. Корутина — объект, который выполняется на ОДНОМ потоке (event loop), переключаясь между задачами только в точках await. Конкурентность есть, параллелизма для CPU-bound кода — нет (из-за GIL).

Q: Что будет, если внутри async def вызвать time.sleep(5) вместо await asyncio.sleep(5)? A: Заблокируется ВЕСЬ event loop на 5 секунд — ни одна другая корутина не сможет выполниться в это время, потому что time.sleep не отдаёт управление диспетчеру, в отличие от await asyncio.sleep. Это одна из самых частых ошибок в асинхронном Python-коде.

Q: В чём разница между asyncio.gather(c1, c2) и await c1; await c2 по очереди? A: Последовательный await ждёт c1 полностью, потом запускает c2 — итого сумма времён. gather запускает обе корутины конкурентно, event loop переключается между ними на каждом await внутри них — итого время ~максимум из двух, а не сумма.

Q: Python asyncio однопоточный (из-за GIL) — какой в этом практический смысл? A: Для I/O-bound задач (сеть, БД, файлы) это не проблема — пока одна задача ждёт ответ от сети, event loop переключается на другую, процессор не простаивает. Для CPU-bound задач (тяжёлые вычисления) asyncio не даёт ускорения — нужен multiprocessing, который использует реальные отдельные процессы в обход GIL.

Q: Как это соотносится с Task.WhenAll в C#? A: Концептуально то же самое — запустить несколько асинхронных операций и дождаться всех. Ключевое отличие в исполнении: Task.WhenAll в C# может реально распараллелить работу на пуле потоков (для CPU-bound тоже), asyncio.gather — только конкурентность на одном потоке (эффективна только для I/O-bound).

2.2 aiohttp — асинхронные HTTP-запросы

Почему это важно

requests (стандартная синхронная библиотека) — БЛОКИРУЮЩАЯ. Вызов requests.get() внутри async def не станет асинхронным просто от того, что функция помечена async — она всё равно остановит весь event loop, как в Примере C выше. Для реальной асинхронности HTTP нужна асинхронная библиотека — aiohttp.

Теория

aiohttp.ClientSession — аналог HttpClient в C#: держит пул соединений, переиспользуется между запросами (не создаётся заново на каждый вызов — это дорого). Запросы делаются через async with session.get(url) as response.

Пример A — синхронная версия (медленно, для сравнения)

import requests
import time

def download_all_sync(urls: list[str]):
    start = time.time()
    for url in urls:
        requests.get(url)
    print(f"Синхронно: {time.time() - start:.2f} сек")

Пример B — асинхронная версия с aiohttp

import aiohttp
import asyncio
import time

async def fetch(session: aiohttp.ClientSession, url: str):
    async with session.get(url) as response:
        return await response.read()

async def download_all_async(urls: list[str]):
    start = time.time()
    async with aiohttp.ClientSession() as session:
        await asyncio.gather(*(fetch(session, url) for url in urls))
    print(f"Асинхронно: {time.time() - start:.2f} сек")

asyncio.run(download_all_async(["https://cataas.com/cat"] * 10))

Для 10 независимых запросов синхронная версия займёт ~сумму всех времён ответа, асинхронная — примерно время самого медленного одного запроса (все летят конкурентно).

Мини-задание 2.2

🎤 Вопросы с собеседования

Q: Почему нельзя просто вызвать requests.get() внутри async def и получить ускорение? A: requests синхронная и блокирующая — она не умеет отдавать управление event loop на await, потому что await перед ней в принципе невозможен (requests.get() не корутина). Обёртка функции в async def ничего не меняет — вызов всё равно остановит весь поток, на котором крутится event loop, пока не получит ответ.

Q: Что такое ClientSession и почему его открывают один раз, а не на каждый запрос? A: Это объект, управляющий пулом TCP-соединений (как HttpClient в C#) — переиспользование соединений (keep-alive) значительно быстрее, чем открывать новое соединение на каждый запрос. Создание ClientSession на каждый вызов — частая ошибка производительности, аналогичная созданию нового HttpClient на каждый запрос в C#.

2.3 FastAPI — сервис, DI, BackgroundTasks

Почему это важно

FastAPI — самый популярный async-фреймворк для Python-бэкенда в РФ прямо сейчас. Концептуально он очень похож на ASP.NET Core Minimal API: роутинг через декораторы вместо атрибутов, автоматическая валидация тела запроса через Pydantic (вместо [FromBody] + model binding), DI через Depends() вместо IServiceCollection.

Пример A — минимальное приложение

from fastapi import FastAPI

app = FastAPI(title="Taxi Service API")

@app.get("/")
def read_root():
    return {"status": "ok"}

# Запуск: fastapi dev main.py
# Swagger автоматически на http://127.0.0.1:8000/docs

Пример B — POST с Pydantic-моделью запроса и response_model

from pydantic import BaseModel

class OrderRequest(BaseModel):
    start: Point
    end: Point

class OrderResponse(BaseModel):
    order_id: int
    status: str

@app.post("/orders", response_model=OrderResponse)
def create_order(order: OrderRequest) -> OrderResponse:
    new_id = 42  # тут была бы реальная логика создания заказа
    return OrderResponse(order_id=new_id, status="created")

response_model — контракт ответа: даже если случайно вернуть лишнее поле или неверный тип, FastAPI отфильтрует/провалидирует по схеме перед отправкой клиенту. Это аналог явного DTO на выходе контроллера в ASP.NET Core — гарантия, что клиенты не получат "что попало".

Пример C — Depends() (DI)

from fastapi import Depends

class InMemoryOrdersDB:
    def __init__(self):
        self.orders: dict[int, OrderResponse] = {}

db_instance = InMemoryOrdersDB()  # "singleton" — один на всё приложение

def get_orders_db() -> InMemoryOrdersDB:
    return db_instance

@app.get("/orders/{order_id}", response_model=OrderResponse)
def get_order(order_id: int, db: InMemoryOrdersDB = Depends(get_orders_db)):
    return db.orders[order_id]

Depends(get_orders_db) — то же самое, что внедрение IOrdersRepository через конструктор в ASP.NET Core контроллере, только явно объявленное в сигнатуре ручки, а не через DI-контейнер снаружи. FastAPI сам вызывает get_orders_db() и подставляет результат.

Пример D — BackgroundTasks (fire-and-forget)

from fastapi import BackgroundTasks

def simulate_driver_movement(order_id: int):
    # долгая работа — двигать водителя, слать уведомления и т.д.
    ...

@app.post("/orders/{order_id}/start")
async def start_order(order_id: int, background_tasks: BackgroundTasks):
    background_tasks.add_task(simulate_driver_movement, order_id)
    return {"status": "начали, но не ждём завершения"}

Без BackgroundTasks эндпоинт "завис" бы до завершения simulate_driver_movement (клиент ждал бы ответ, пока вся долгая операция не закончится). С BackgroundTasks ответ уходит клиенту сразу, а функция выполняется после отправки ответа. Аналог в C# — что-то вроде IHostedService/Task.Run без ожидания, но проще и встроено во фреймворк специально под этот сценарий.

Мини-задание 2.3

🎤 Вопросы с собеседования

Q: Чем response_model полезен, если можно просто return dict? A: dict не гарантирует структуру — опечатка в ключе или неверный тип не будет обнаружена до тех пор, пока клиент не получит "битый" JSON. response_model — явная Pydantic-схема: FastAPI провалидирует и сериализует ответ по контракту, а несоответствие поймает на этапе разработки/тестов, а не в проде у клиента.

Q: Что делает Depends() и как это соотносится с DI в ASP.NET Core? A: Depends(get_orders_db) говорит FastAPI: перед вызовом эндпоинта вызови get_orders_db() и подставь результат как аргумент. Концептуально то же самое, что внедрение зависимости через конструктор контроллера в ASP.NET Core (services.AddSingleton<IOrdersRepository>) — разница в том, что в FastAPI это объявляется прямо в сигнатуре функции-обработчика, а не настраивается отдельно в Program.cs.

Q: Зачем BackgroundTasks, если можно просто await внутри ручки? A: await внутри ручки заставит клиента ЖДАТЬ полного завершения операции перед получением ответа. BackgroundTasks отправляет ответ клиенту сразу, а операция выполняется после — нужен именно тогда, когда клиенту не важен результат операции немедленно (лог, уведомление, долгая фоновая симуляция).

Q: Откуда Swagger берёт схему автоматически? A: Из type hints и Pydantic-моделей в сигнатурах эндпоинтов (OrderRequest, response_model=OrderResponse) — FastAPI строит OpenAPI-схему во время старта приложения, анализируя аннотации типов кода, без единой ручной строчки документации.

День 3 — Тестирование и инструменты

3.1 pytest — основы, паттерн AAA

Почему это важно

Ты знаешь xUnit — pytest концептуально то же самое (unit-тесты, паттерн AAA), синтаксис проще: не нужны атрибуты [Fact], обычный assert вместо Assert.Equal.

Теория

pytest находит тесты по маске: файлы test_*.py, функции test_*, классы Test* (без __init__). Паттерн AAA — Arrange (подготовка) → Act (выполнение) → Assert (проверка).

Пример A — функция + тесты

# math_utils.py
def increment(n: int) -> int:
    return n + 1

# test_math_utils.py
from math_utils import increment

def test_increment_positive():
    assert increment(5) == 6

def test_increment_negative():
    assert increment(-5) == -4

def test_increment_zero():
    assert increment(0) == 1

Запуск: pytest -vv (подробный вывод по каждому тесту) или pytest -q (только точки/F для быстрого прогона).

Пример B — тест по паттерну AAA явно

def test_distance_pricing():
    # Arrange
    strategy = DistancePriceStrategy(price_per_km=25, base_fee=50)
    # Act
    price = strategy.calculate(distance_km=12)
    # Assert
    assert price == 350

Мостик к C

xUnit pytest
[Fact] имя функции начинается с test_
[Theory] + [InlineData] @pytest.mark.parametrize
Assert.Equal(a, b) assert a == b
Assert.Throws<T>(...) pytest.raises(T)
Fixture (IClassFixture) @pytest.fixture

# - distance: большая дистанция дороже маленькой

🎤 Вопросы с собеседования

Q: Как pytest находит тесты без атрибутов вроде [Fact]? A: По соглашению об именовании (convention over configuration): файлы test_*.py/*_test.py, функции test_*, классы Test*. Никакой регистрации не требуется — в отличие от xUnit, где [Fact] явно помечает тестовый метод.

Q: Что означает паттерн AAA и почему он важен? A: Arrange (подготовка данных/объектов) → Act (вызов тестируемого кода) → Assert (проверка результата). Важен как структура: тест, где вперемешку подготовка и проверки, тяжело читать и поддерживать — при падении неочевидно, что именно не так.

3.2 Fixtures и параметризация

Теория

@pytest.fixture — функция, которая готовит данные/окружение для теста. pytest подставляет её РЕЗУЛЬТАТ в тест по СОВПАДЕНИЮ ИМЕНИ параметра теста с именем фикстуры (магии импорта нет — просто одинаковое имя). Фикстуры хранятся в conftest.py — общем файле, из которого pytest автоматически подхватывает их для всех тестов в директории.

@pytest.mark.parametrize — прогоняет ОДИН тест с разными наборами входных данных, вместо копипаста похожих тестов.

Пример A — простая фикстура

# conftest.py
import pytest

@pytest.fixture
def nevsky_point() -> Point:
    return Point(latitude=59.9311, longitude=30.3609)

@pytest.fixture
def palace_square_point() -> Point:
    return Point(latitude=59.9398, longitude=30.3146)

# test_orders.py
def test_order_creation(nevsky_point, palace_square_point):
    order = OrderRequest(start=nevsky_point, end=palace_square_point)
    assert order.start.latitude == 59.9311

pytest увидел параметры nevsky_point, palace_square_point у теста → нашёл фикстуры с такими же именами в conftest.py → вызвал их и подставил результат.

Пример B — фикстура, зависящая от другой фикстуры

@pytest.fixture
def sample_order(nevsky_point, palace_square_point) -> OrderRequest:
    return OrderRequest(start=nevsky_point, end=palace_square_point)

Фикстуры можно комбинировать — pytest сам разрешит цепочку зависимостей.

Пример C — parametrize

import pytest

@pytest.mark.parametrize("distance_km,expected_price", [
    (0, 50),      # граничный случай: нулевая дистанция всё равно с базовой ставкой
    (10, 300),
    (20, 550),
])
def test_distance_pricing(distance_km, expected_price):
    strategy = DistancePriceStrategy(price_per_km=25, base_fee=50)
    assert strategy.calculate(distance_km) == expected_price

Один тест, три прогона — pytest покажет каждый как отдельный результат (test_distance_pricing[0-50], и т.д.).

Пример D — фабрика фикстур (фикстура, возвращающая функцию)

@pytest.fixture
def make_order():
    def _make_order(start: Point, end: Point) -> OrderRequest:
        return OrderRequest(start=start, end=end)
    return _make_order

def test_custom_order(make_order, nevsky_point):
    custom_end = Point(latitude=60.0, longitude=30.0)
    order = make_order(nevsky_point, custom_end)
    assert order.end.latitude == 60.0

Нужна, когда одной фикстуры с фиксированными данными недостаточно — тест хочет сам передать параметры при вызове.

🎤 Вопросы с собеседования

Q: Как pytest узнаёт, какую фикстуру подставить в тест? A: По СОВПАДЕНИЮ ИМЕНИ параметра теста и имени функции-фикстуры (декорированной @pytest.fixture), видимой в текущей области (обычно conftest.py). Явного импорта или регистрации не требуется.

Q: Чем parametrize отличается от написания нескольких отдельных тестов? A: Один тест с parametrize — один и тот же код проверки, разные входные данные, заданные декларативно списком. Несколько отдельных тестов — дублирование логики теста ради разных данных. parametrize также даёт отдельный, читаемый результат на каждый набор данных при падении.

Q: Что такое conftest.py и зачем он? A: Специальный файл, откуда pytest автоматически подхватывает фикстуры для всех тестов в директории (и поддиректориях) без явного импорта. В больших проектах фикстуры также выносят в отдельные подпапки/файлы, если их становится много.

Q: Сравни с [InlineData] в C#. A: @pytest.mark.parametrize("a,b", [(1,2), (3,4)]) — прямой аналог нескольких [InlineData(1,2)]/[InlineData(3,4)] над одним [Theory]-методом. Механизм тот же: один тестовый метод, множество наборов данных, framework прогоняет каждый как отдельный тест-кейс.

3.3 Мокинг (pytest-mock, TestClient)

Почему это важно

Ты знаешь Moq в C#. pytest-mock (обёртка над стандартным unittest.mock) решает ровно ту же задачу: подменить внешнюю зависимость (сеть, БД, время), чтобы тест был быстрым, детерминированным и не зависел от реального внешнего сервиса.

Теория

Фикстура mocker (из pytest-mock) даёт методы: - mocker.patch("module.function") — заменяет функцию/объект в указанном модуле на мок на время теста - mock.assert_called_once() — проверка, что мок вызвали ровно один раз - mock.assert_called_with(args) — проверка аргументов вызова

TestClient (из fastapi.testclient) — позволяет делать запросы к FastAPI-приложению БЕЗ поднятия реального сервера — как WebApplicationFactory в ASP.NET Core тестах.

Пример A — мок внешней функции

def test_create_order_with_mocked_route(mocker):
    # Arrange
    mock_route = mocker.patch("main.fetch_route")
    mock_route.return_value = {"distance": 1240, "duration": 600}

    from fastapi.testclient import TestClient
    from main import app
    client = TestClient(app)

    # Act
    response = client.post("/orders", json={
        "start": {"latitude": 59.93, "longitude": 30.36},
        "end": {"latitude": 59.94, "longitude": 30.31},
    })

    # Assert
    assert response.status_code == 200
    mock_route.assert_called_once()

mocker.patch("main.fetch_route") подменяет функцию fetch_route ИМЕННО в модуле main (там, где её реально вызывают) на мок — реальный HTTP-запрос к OSRM никогда не уходит.

Пример B — негативный сценарий (внешний сервис упал)

def test_create_order_when_route_service_fails(mocker):
    mocker.patch("main.fetch_route", side_effect=TimeoutError("OSRM недоступен"))

    client = TestClient(app)
    response = client.post("/orders", json={...})

    # Заказ всё равно должен создаться, просто без точного времени в пути
    assert response.status_code == 200

side_effect — задаёт исключение (или функцию) вместо простого возврата значения. Проверяет, что код УСТОЙЧИВ к отказу внешней зависимости, а не только к успешному сценарию.

Пример C — мок метода объекта (репозитория/БД)

def test_get_order_with_mocked_db(mocker):
    fake_order = OrderResponse(order_id=1, status="created")
    mocker.patch.object(InMemoryOrdersDB, "get", return_value=fake_order)

    client = TestClient(app)
    response = client.get("/orders/1")

    assert response.json()["order_id"] == 1

Мостик к C

Moq (C#) pytest-mock
new Mock<IRepo>() mocker.patch(...) / mocker.patch.object(...)
.Setup(x => x.Get(1)).Returns(order) return_value=order
.Verify(x => x.Get(1), Times.Once()) mock.assert_called_once()
.Throws<TimeoutException>() side_effect=TimeoutError(...)

🎤 Вопросы с собеседования

Q: Чем это похоже на Moq в C# (Mock<T>, Setup, Verify)? A: Идея идентична: подменить реальную зависимость (внешний вызов, БД) объектом-заглушкой с заданным поведением, а потом проверить, что код вызвал её ожидаемым образом. mocker.patch ближе к Setup, assert_called_once() — к Verify(..., Times.Once()).

Q: Почему не стоит делать реальные HTTP-запросы в юнит-тестах? A: Тесты становятся медленными, нестабильными (падают из-за сети, а не из-за бага), непроверяемыми на сценарии ошибок (сложно заставить реальный внешний сервис вернуть таймаут по requestу), и внешний сервис может ограничить частоту запросов от тестового прогона.

Q: Что проверяет assert_called_once()? A: Что мок был вызван РОВНО один раз за время теста — не ноль (значит, код не дошёл до вызова) и не два+ (значит, лишний вызов, возможный баг — например, случайный повторный запрос).

3.4 Coverage (покрытие тестами)

Теория

pytest-cov показывает, какие строки кода реально ВЫПОЛНИЛИСЬ во время прогона тестов. HTML-отчёт (--cov-report=html) подсвечивает непокрытые строки красным.

pytest --cov=app --cov-report=html
# отчёт появится в htmlcov/index.html

🎤 Вопросы с собеседования

Q: Гарантирует ли 100% coverage отсутствие багов? A: Нет. Coverage показывает, что строка ВЫПОЛНИЛАСЬ хотя бы раз — не то, что она проверена на всех значимых сценариях (граничные случаи, неверные входные данные). Можно иметь 100% coverage и полное отсутствие содержательных assert в тестах. Coverage — метрика "что не забыто", не метрика качества тестов.

3.5 Инструменты разработчика (кратко, теория)

Почему это важно

Это НЕ хендс-он часть — просто чтобы на собесе не было пустого места, если спросят про экосистему.

  • Виртуальные окружения (venv, poetry) — изоляция зависимостей проекта от глобального Python и от других проектов (разные версии библиотек/Python на разных проектах — иначе конфликт). Аналог — NuGet-пакеты проекта в C#, только там изоляция версий менее болезненная (не нужен отдельный venv на проект).
  • Линтеры/форматеры (ruff, black) — аналог dotnet format/Roslyn-анализаторов: автоматическое форматирование и обнаружение проблем в коде до ревью.
  • Type hints + mypy — Python остаётся динамически типизированным ДАЖЕ с аннотациями типов: def f(x: int) не мешает вызвать f("строка") в рантайме без единой ошибки, если не подключен mypy как отдельный статический чекер (и даже тогда — только на этапе CI/линтинга, не в рантайме). Это принципиально отличается от C#, где типы проверяет компилятор и рантайм не даст присвоить несовместимый тип.
  • Логирование (logging модуль) — концептуальный аналог Serilog/ILogger в C#, но менее структурирован из коробки (JSON-логирование нужно настраивать отдельно, не встроено по умолчанию).

🎤 Вопросы с собеседования

Q: Зачем нужен virtual environment, если Python уже установлен глобально? A: Разные проекты часто требуют разные (и несовместимые) версии одной и той же библиотеки или даже самого Python. Виртуальное окружение изолирует зависимости конкретного проекта — установка/обновление пакета в одном проекте не ломает другой.

Q: Чем type hints в Python отличаются от строгой типизации в C#? A: Type hints — это ПОДСКАЗКА для читателя кода, IDE и статических анализаторов (mypy), но НЕ проверяются рантаймом Python. def f(x: int): ... можно вызвать как f("строка") без единой ошибки — интерпретатор аннотации типов игнорирует. В C# типы проверяются компилятором ДО запуска и обеспечены рантаймом — это принципиальная разница между "подсказкой" и "гарантией".

Итоговый мини-проект (если куда активировал курс)

Собери всё в один сервис Order Pricing API: - POST /orders — принимает OrderRequest (Pydantic, вложенные Point), считает цену через выбранную PricingStrategy (Strategy pattern, День 1), возвращает OrderResponse через response_model - Цена считается синхронно, но эндпоинт запускает BackgroundTasks, симулирующий движение водителя (asyncio.sleep в цикле, обновляющий "прогресс" в памяти) - GET /orders/{id} — отдаёт текущий прогресс, через Depends() на in-memory "репозиторий" - Тесты: pytest + fixtures (общие Point/Order для тестов) + мок внешнего вызова (fetch_route) + хотя бы один parametrize-тест на разные стратегии ценообразования + coverage-отчёт

Это тот объём, который реально закрывает "написал README-совместимый pet-project" на резюме за 2-3 дня, если триггер сработает.
