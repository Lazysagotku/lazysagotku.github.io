2.1 Классы и объекты

Аналогия: чертёж дома (класс) один, домов по нему (объекты) сколько угодно — у каждого свой участок, независимые друг от друга.

Суть: класс — чертёж, объект — экземпляр. Конструктор без возвращаемого типа, имя = имя класса, вызывается на new. this(...) — не вызов метода, а цепочка к ДРУГОМУ конструктору этого же класса, выполняется целиком ДО тела текущего.

public class Rectangle
{
    public double Width, Height;
    public Rectangle(double width, double height) { Width = width; Height = height; }

    // this(side, side) выполнится ПОЛНОСТЬЮ первым, потом пустое тело —
    // не дублируем логику инициализации в каждом конструкторе
    public Rectangle(double side) : this(side, side) { }
}

Q&A: - Конструктор vs обычный метод? → без возвращаемого типа, имя = имя класса, вызывается автоматически на new. - Что выполнится первым — this(...) или тело? → всегда this(...) целиком, потом тело. - Что если не написать ни одного конструктора? → компилятор создаст пустой public — но только если нет НИ ОДНОГО явного.

2.2 Инкапсуляция

Аналогия: банкомат не даёт залезть руками в сейф — только через контролируемый интерфейс (PIN, сумма).

Суть: private-поле + property с проверкой в set — контроль над изменением состояния, не просто "спрятать поля". Auto-property — компилятор сам генерирует backing field. init — присвоить можно только при создании (даже изнутри класса дальше нельзя), в отличие от private set (менять можно из любого метода класса в любой момент).

public decimal Balance
{
    get => _balance;
    private set // менять можно только изнутри класса
    {
        if (value < 0) throw new ArgumentException("Баланс не может быть отрицательным");
        _balance = value;
    }
}

Q&A: - Чем private set отличается от init? → private set — можно менять из любого метода класса в любой момент; init — только один раз, при создании. - Зачем private-поле+property, если можно public auto-property? → auto-property не даёт контроля/валидации при изменении значения.

2.3 Наследование

Аналогия: семейные черты — ребёнок наследует базовые черты родителя, но может развить свою версию (override), оставаясь узнаваемым потомком.

Суть: base(...) вызывает конструктор родителя. virtual+override — оба обязательны В ПАРЕ (без virtual в базовом — ошибка компиляции CS0506). sealed — запрещает дальнейшее наследование/переопределение. new (hiding) — это НЕ override: решается на этапе КОМПИЛЯЦИИ по типу переменной, а не по реальному типу объекта.

Penguin p = new Penguin();
p.Move();          // "Пингвин ковыляет" — переменная типа Penguin

Bird b = p;         // тот же объект, но переменная типа Bird
b.Move();           // "Птица передвигается" — вызвалась версия Bird! (это new, не override)

Q&A: - Разница override vs new (hiding)? → override — решение в рантайме, по реальному типу объекта; new — на компиляции, по типу переменной. - Что если не вызвать base(...) явно? → неявно вызовется пустой конструктор родителя, если он есть; если нет — ошибка компиляции. - Почему в C# нет множественного наследования классов? → чтобы избежать diamond problem; с интерфейсами эта проблема не возникает.

2.4 Полиморфизм — статический и динамический

Аналогия: кнопка "Вкл" на универсальном пульте — для телевизора включает экран, для кондиционера запускает охлаждение, в зависимости от того, что реально стоит за кнопкой.

Суть: статический (перегрузки/overload) — разные методы с разной сигнатурой, выбор на этапе КОМПИЛЯЦИИ. Динамический (virtual/override) — один и тот же вызов, разное поведение по РЕАЛЬНОМУ типу объекта, выбор в рантайме. Ловушка: вызов virtual-метода из конструктора БАЗОВОГО класса вызовет override-версию наследника ДО того, как поля наследника инициализированы.

public class Base
{
    public Base() => Init(); // опасно — вызов virtual ИЗ конструктора
    public virtual void Init() => Console.WriteLine("Base.Init");
}
public class Derived : Base
{
    private string _name = "готово";
    public override void Init() => Console.WriteLine($"_name = {_name}"); // выведет ПУСТУЮ строку!
}

Q&A: - Overload vs override? → overload — разные методы/сигнатуры, решается на компиляции; override — тот же метод, решается в рантайме по типу объекта. - Можно достичь полиморфизма без наследования от общего класса? → да, через интерфейсы.

2.5 Абстракция — abstract класс vs интерфейс

Аналогия: руль и педали в машине — жмёшь на газ, не зная, что происходит в двигателе. Детали реализации скрыты за контрактом.

Суть: abstract class — общий код/состояние, "это разновидность X", только ОДИНОЧНОЕ наследование. interface — чистый контракт (или default-методы с C#8+), "умеет делать Y", МНОЖЕСТВЕННАЯ реализация возможна.

public abstract class Shape
{
    public void PrintName() => Console.WriteLine(Name); // общий код — наследуется как есть
    public abstract double Area(); // контракт — наследник ОБЯЗАН написать
}
// var s = new Shape(); // ОШИБКА — нельзя создать объект abstract класса

Q&A: - abstract class vs interface — когда что? → общее состояние нужно всем наследникам → abstract class; несвязанные классы с общим "умением" → interface. - Может ли abstract класс иметь конструктор? → да, вызывается через base(...) из наследника при создании ЕГО объекта.

2.6 Интерфейсы — IComparable, IDisposable, IEnumerable, IEquatable

Аналогия: разъём USB — неважно, что внутри устройства, если разъём совпадает, оно подключится и заработает по общим правилам.

Суть: реализация стандартных интерфейсов "подключает" класс к языковым механизмам: IComparable<T> → Array.Sort()/.Sort(), IDisposable → using, IEnumerable<T> → foreach. record генерирует IEquatable-подобное сравнение автоматически — вручную (Пример D в теме) видно, что именно он делает за тебя.

public class Product : IComparable<Product>
{
    public decimal Price { get; init; }
    public int CompareTo(Product? other) =>
        other is null ? 1 : Price.CompareTo(other.Price);
}
products.Sort(); // теперь работает — использует твой CompareTo

Q&A: - Зачем generic IComparable<T>, если есть non-generic? → non-generic требует boxing и приведения типов, не типобезопасен. - Что если реализовать CompareTo, но не Equals/GetHashCode? → сортировка работает, но сравнение на равенство (==, ключ в Dictionary) остаётся по ССЫЛКЕ.

2.7 Принципы SOLID

Аналогия: кухня ресторана — у каждого повара своя зона (S), меню растёт без переписывания чужой работы (O), любой повар заменяет другого без сюрпризов (L), никто не обязан знать чужие рецепты (I), шеф просит "морковь по спецификации X", не важно кто принесёт (D).

Суть: S — один класс, одна причина для изменения. O — новое поведение через новый класс, не правку старого. L — наследник должен ПОЛНОЦЕННО заменять родителя (не кидать исключение там, где родитель работал). I — маленькие специфичные интерфейсы вместо одного гигантского. D — зависеть от абстракций (интерфейсов), конкретную реализацию передавать снаружи (= Dependency Injection).

public interface IDatabase { void Save(Order order); }
public class OrderService
{
    private readonly IDatabase _db;
    public OrderService(IDatabase db) => _db = db; // реализацию решает вызывающий код, не сам сервис
}

Q&A: - Как SOLID связан с Dependency Injection? → D — теоретический принцип, DI — практический механизм передачи абстракций (обычно через конструктор). - Пример скрытого нарушения LSP (не через exception)? → наследник формально совпадает по сигнатуре, но работает в разы медленнее/с побочными эффектами, которых вызывающий код не ожидает.

2.8 Статические классы и Singleton

Аналогия: один принтер на весь этаж офиса — все обращаются к одному и тому же устройству, не заводят себе персональную копию.

Суть: static class — вообще НЕ объект: нельзя передать как зависимость через интерфейс, нет полиморфизма, нельзя замокать в тестах. Singleton — обычный объект (приватный конструктор гарантирует единственность), можно спрятать за интерфейсом. Lazy<T> — потокобезопасный Singleton без ручного lock.

public class ConfigManager
{
    private static readonly Lazy<ConfigManager> _lazy = new(() => new ConfigManager());
    public static ConfigManager Instance => _lazy.Value; // Lazy<T> сам даёт потокобезопасность
    private ConfigManager() { }
}

Q&A: - Почему Singleton считают антипаттерном? → скрытая глобальная зависимость, сложно тестировать изолированно. - static class vs Singleton, если оба "один экземпляр логики"? → static class нельзя передать как зависимость/замокать; Singleton — обычный объект, можно спрятать за интерфейсом.

2.9 Record типы — глубже

Аналогия: бланк техпаспорта — два бланка с одинаковыми данными (тот же VIN) считаются одним документом по содержанию (value equality), не потому что это физически один лист бумаги, как было бы у class.

Суть: record даёт value equality (сравнение по значениям полей, а не по ссылке) и with — неразрушающую копию с изменением части полей. Ловушка: value equality зависит от того, переопределяет ли КАЖДОЕ поле свой Equals — string да (сравнение по содержимому встроено в язык), List<T> и подобные коллекции — нет (сравнение по ссылке для этого конкретного поля).

public record Order(string Id, List<string> Items);
var o1 = new Order("1", new List<string> { "хлеб" });
var o2 = new Order("1", new List<string> { "хлеб" });
Console.WriteLine(o1 == o2); // False! Items сравнивается по ссылке, не по содержимому

Q&A: - Почему record с List<T> внутри может дать False при одинаковых на вид данных? → List<T> не переопределяет Equals по значению — для этого поля сравнение идёт по ссылке. - Что делает with под капотом? → вызывает скрытый copy-конструктор, копирует все поля, затем переприсваивает указанные в { ... }. - Что обычно быстрее для маленьких неизменяемых данных — record или record struct? → record struct (value type, не грузит GC), но копируется целиком при каждой передаче.
