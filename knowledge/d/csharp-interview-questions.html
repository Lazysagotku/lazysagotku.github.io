1. Типы данных и память

Q: В чём разница между value type и reference type? A: Value type хранит данные напрямую (в стеке, если это локальная переменная), копируется целиком при присвоении. Reference type хранит ссылку на объект в куче — при присвоении копируется ссылка, оба указывают на один объект.

int a = 5; int b = a; b = 10; // a остаётся 5
var list1 = new List<int>(); var list2 = list1; list2.Add(1); // list1.Count тоже 1

✅ Фаза 1, тема 1.1.

Q: Что такое boxing и unboxing? Почему это дорого? A: Boxing — упаковка value type в object (выделение памяти в куче, копирование значения). Unboxing — обратное явное приведение. Дорого, потому что каждый boxing — это аллокация в куче + работа GC, а не просто копирование нескольких байт на стеке.

int x = 42;
object boxed = x;      // boxing — выделение в куче
int y = (int)boxed;    // unboxing — явное приведение

✅ Фаза 1, тема 1.2.

Q: Как работает Garbage Collector? Что такое поколения (generations)? A: GC автоматически освобождает объекты, на которые больше нет ссылок. Объекты делятся на поколения: Gen 0 (новые, часто собираются), Gen 1 (пережившие одну сборку), Gen 2 (долгоживущие, собираются редко) — это оптимизация: большинство объектов умирают молодыми, поэтому чаще сканировать молодое поколение эффективнее. ⚠️ Частично покрыто (Фаза 1, 1.2 — Stack/Heap), но поколения GC явно не разбирались — стоит добавить в Модуль 6 (подготовка к собесу).

Q: Чем struct отличается от class, кроме value/reference? A: struct не поддерживает наследование (кроме интерфейсов), не может иметь деструктор, всегда есть неявный конструктор без параметров (до C# 10), обычно используется для маленьких неизменяемых наборов данных (DateTime, Guid, Point). ✅ Фаза 1, тема 1.1 (упомянуто "когда что выбрать").

2. Строки и коллекции

Q: Почему string иммутабелен? Что происходит при s += "x" в цикле? A: Каждая операция создаёт НОВУЮ строку в куче, старая становится мусором для GC. В цикле с большим числом итераций — O(n²) и куча мусора. Решение — StringBuilder, который использует изменяемый внутренний буфер. ✅ Фаза 1, тема 1.3.

Q: В чём разница между == и .Equals() для строк? A: Для string оба сравнивают СОДЕРЖИМОЕ (не ссылку) — == для строк перегружен специально. Для обычных class без переопределения == сравнивает ссылки, а .Equals() по умолчанию тоже ссылки (пока не переопределён). ✅ Фаза 1, тема 1.3.

Q: Как работает foreach "под капотом"? Что такое IEnumerable/IEnumerator? A: Компилятор разворачивает foreach в вызов GetEnumerator(), затем цикл while(MoveNext()) с обращением к Current, и Dispose() в finally. IEnumerable — "я умею дать перечислитель", IEnumerator — "я умею двигаться по элементам". ✅ Фаза 1, тема 1.8.

Q: Что такое yield return и зачем он нужен? A: Позволяет писать метод, генерирующий последовательность ЛЕНИВО — элементы вычисляются по одному, только когда их запрашивают, без создания всей коллекции в памяти сразу. Компилятор превращает метод в state machine. ✅ Фаза 1, тема 1.8 (задание с Фибоначчи).

Q: List\<T> vs Array — когда что? A: Array — фиксированный размер, чуть быстрее для простого доступа по индексу. List<T> — динамический размер (внутри массив, который удваивается при переполнении), используется в 95% случаев, если размер заранее не известен точно. ✅ Фаза 1, тема 1.7.

Q: Dictionary\<TKey,TValue> — как достигается O(1) для поиска? A: Хеш-таблица — ключ хешируется через GetHashCode(), хеш определяет "корзину" (bucket), где хранится значение. Поиск не перебирает все элементы, а сразу вычисляет нужную корзину. ✅ Фаза 1, тема 1.7.

3. ООП — четыре столпа + SOLID

Q: Назови и объясни 4 столпа ООП. A: Инкапсуляция — скрытие внутреннего состояния, контроль доступа через свойства. Наследование — переиспользование кода через отношение "является". Полиморфизм — один вызов, разное поведение (перегрузка на этапе компиляции ИЛИ переопределение в рантайме). Абстракция — скрытие деталей реализации за интерфейсом/abstract-классом. ✅ Фаза 2, темы 2.2-2.5.

Q: virtual vs abstract — в чём разница? A: virtual — есть реализация по умолчанию, override необязателен. abstract — реализации нет вообще, override обязателен в первом неабстрактном наследнике. ✅ Фаза 2, тема 2.3.

Q: Почему в C# нет множественного наследования классов? A: Чтобы избежать "diamond problem" — неоднозначности, если два родителя дают одинаковый член с разной реализацией. Множественная реализация интерфейсов такой проблемы не создаёт. ✅ Фаза 2, тема 2.3.

Q: Расскажи про каждый принцип SOLID с примером. A: S — один класс, одна причина для изменения. O — новое поведение через новый класс, а не правку старого. L — наследник должен полноценно заменять родителя. I — маленькие специфичные интерфейсы вместо одного большого. D — зависеть от абстракций (интерфейсов), а не от конкретных классов. ✅ Фаза 2, тема 2.7 (там же примеры кода на каждую букву).

Q: abstract class vs interface — когда что? A: abstract class — когда есть общий код/состояние, "это разновидность X" (одиночное наследование). interface — когда классы не связаны, но "умеют одно и то же" (множественная реализация). ✅ Фаза 2, тема 2.5.

4. Static, Singleton, Records

Q: Чем static class отличается от Singleton? A: static class вообще не объект — нельзя передать как зависимость через интерфейс, нет полиморфизма, нельзя протестировать с моком. Singleton — обычный объект (просто гарантированно единственный экземпляр), можно спрятать за интерфейсом и подменить в тестах. ✅ Фаза 2, тема 2.8.

Q: Как сделать Singleton потокобезопасным? A: Через Lazy<T> (по умолчанию потокобезопасен) или ручной lock вокруг проверки/создания экземпляра. ✅ Фаза 2, тема 2.8.

Q: Чем record отличается от class? A: Value equality вместо reference equality (record сравнивает по значениям полей), встроенный with-выражение для неразрушающей мутации, позиционные свойства автоматически init-only. ✅ Фаза 2, тема 2.9.

Q: Может ли == вернуть False для двух record с одинаковыми на вид данными? A: Да, если внутри record есть mutable reference-type поле (например List<T>) — record сравнивает через Equals каждого поля, а List<T> сравнивается по ссылке, а не по содержимому. ✅ Фаза 2, тема 2.9 (разобрана эта конкретная ловушка).

5. Nullable и обработка null

Q: Что такое Nullable<T> и зачем нужны null-операторы ?., ??, ??=? A: Value types по умолчанию не могут быть null — Nullable<T>/T? оборачивает их. ?. — безопасный доступ (не бросает NullReferenceException, если объект null). ?? — значение по умолчанию, если слева null. ??= — присвоить, только если сейчас null. ✅ Фаза 1, тема 1.5.

6. Исключения — ✅ Фаза 3 (2026-08-12)

Полная теория, 4 примера и мини-задание — Phase3_Advanced.md, тема 3.0.1.

Q: Как работает try/catch/finally? A: try — код, который может бросить исключение. catch — обработка конкретного (или любого) типа исключения. finally — выполняется ВСЕГДА, даже если было исключение или return внутри try/catch — обычно для освобождения ресурсов (хотя для этого лучше using). ✅ Фаза 3, тема 3.0.1.

try
{
    var result = 10 / int.Parse(input);
}
catch (DivideByZeroException ex)
{
    Console.WriteLine("Деление на ноль");
}
catch (FormatException ex)
{
    Console.WriteLine("Не число");
}
finally
{
    Console.WriteLine("Выполнится всегда");
}

Q: Почему нельзя ловить catch (Exception ex) везде подряд? A: Это "проглатывает" ЛЮБУЮ ошибку, включая те, которые ты не предвидел и не умеешь правильно обработать (например OutOfMemoryException) — маскирует реальные баги, усложняет отладку. Лучше ловить конкретные типы, которые ты реально ожидаешь и умеешь обработать. ✅ Фаза 3, тема 3.0.1.

Q: Когда стоит создавать свой класс исключения? A: Когда нужно передать доменную бизнес-информацию об ошибке, которую не выразить стандартными исключениями — например InsufficientFundsException вместо generic Exception для банковского домена. ✅ Фаза 3, тема 3.0.1.

public class InsufficientFundsException : Exception
{
    public decimal Requested { get; }
    public decimal Available { get; }
    public InsufficientFundsException(decimal requested, decimal available)
        : base($"Недостаточно средств: запрошено {requested}, доступно {available}")
    {
        Requested = requested;
        Available = available;
    }
}

Q: throw vs throw ex — в чём разница? A: throw; (без указания переменной) внутри catch сохраняет ПОЛНЫЙ исходный stack trace. throw ex; перезаписывает stack trace, будто исключение возникло именно здесь — теряется информация, откуда оно пришло на самом деле. Всегда используй просто throw; при перевыбросе. ✅ Фаза 3, тема 3.0.1.

7. ref/out/in, params — ✅ Фаза 3 (2026-08-12)

Полная теория, 4 примера и мини-задание — Phase3_Advanced.md, тема 3.0.2.

Q: Чем ref, out и in параметры отличаются друг от друга? A: ref — передача по ссылке, переменная должна быть проинициализирована ДО вызова, метод может её прочитать и изменить. out — тоже по ссылке, но переменная может быть НЕ проинициализирована, метод ОБЯЗАН её присвоить перед выходом (типичный пример — int.TryParse(s, out int result)). in — по ссылке, но только для чтения внутри метода (защита от случайного изменения, чуть эффективнее для больших struct). ✅ Фаза 3, тема 3.0.2.

void Increment(ref int x) => x++;
bool TryDivide(int a, int b, out int result)
{
    if (b == 0) { result = 0; return false; }
    result = a / b;
    return true;
}

Q: Что делает params? A: Позволяет передать переменное количество аргументов одного типа как единый массив внутри метода.

int Sum(params int[] numbers) => numbers.Sum();
Sum(1, 2, 3);       // упаковывается в int[] { 1, 2, 3 }
Sum(1, 2, 3, 4, 5); // работает с любым количеством

✅ Фаза 3, тема 3.0.2.

8. Делегаты, события, LINQ — ✅ Фаза 3 (2026-08-08)

Полная теория, примеры и мини-задания — Phase3_Advanced.md, темы 3.2-3.3.

Q: Чем Action, Func, Predicate отличаются друг от друга? A: Action<T> — делегат без возвращаемого значения. Func<T, TResult> — с возвращаемым значением (последний параметр типа — тип результата). Predicate<T> — то же самое, что Func<T, bool>, просто именованный частный случай для условий. ✅ Фаза 3, тема 3.2.

Q: Deferred execution в LINQ — что это и в чём подвох? A: LINQ-запрос (Where, Select без .ToList()) не выполняется в момент объявления — только при переборе (foreach, .ToList(), .Count()). Подвох — если исходная коллекция изменится МЕЖДУ объявлением запроса и его выполнением, в результат попадут уже новые данные. ✅ Уже фактически разобрано в Фазе 1 (1.8, задание 2 про deferred execution) — хотя формально тема LINQ целиком в Фазе 3, тема 3.5.

9. Async/Await, многопоточность — ✅ Фаза 3 (2026-08-08)

Полная теория, примеры и мини-задания — Phase3_Advanced.md, темы 3.4-3.5.

Q: В чём разница между Task и Thread? A: Thread — реальный поток ОС, дорогой ресурс. Task — абстракция единицы работы, выполняется через ThreadPool (пул переиспользуемых потоков) — намного дешевле создавать, особенно много задач одновременно. ✅ Фаза 3, тема 3.4-3.5.

Q: Что такое deadlock и как его избежать при async/await? A: Классический deadlock в UI/ASP.NET (старом) — синхронное ожидание (.Result/.Wait()) асинхронного метода в потоке с контекстом синхронизации, который сам ждёт освобождения потока для продолжения. Решение — async до самого верха (async all the way), не смешивать sync/async вызовы. ✅ Фаза 3, тема 3.4.

Q: Что делает ConfigureAwait(false)? A: Говорит, что продолжение после await не обязано возвращаться в исходный контекст синхронизации (например, поток UI) — избегает лишних переключений контекста, снижает риск deadlock в библиотечном коде. ✅ Фаза 3, тема 3.4.

10. Generics — ✅ Фаза 3 (2026-08-08)

Полная теория, примеры и мини-задание — Phase3_Advanced.md, тема 3.1.

Q: Зачем нужны generics, если есть object? A: object требует boxing/unboxing для value types (дорого) и не даёт проверку типов на этапе компиляции (ошибка вылезет только в рантайме). Generics — типобезопасность на этапе компиляции, без boxing. ✅ Фаза 3, тема 3.1.

Q: Что делает where T : ... (constraint)? A: Ограничивает, какие типы допустимы в качестве T — например where T : class (только reference types), where T : IComparable<T> (только типы, которые можно сравнивать), where T : new() (только типы с публичным конструктором без параметров). ✅ Фаза 3, тема 3.1.

11. Dependency Injection — 🔜 Life Notes Фаза 2

Q: Что такое Dependency Injection и зачем он нужен? A: Практический механизм передачи зависимостей объекту ИЗВНЕ (обычно через конструктор), а не создания их самим объектом — реализация принципа D из SOLID. Позволяет подменять реализации (в тестах — моками, в проде — реальными сервисами) без изменения кода класса. 🔜 Покроем практически в Life Notes Фазе 2 (ASP.NET Core DI-контейнер), принцип уже разобран в Фазе 2, тема 2.7 (Dependency Inversion).

Q: Разница между Singleton, Scoped и Transient в DI-контейнере ASP.NET Core? A: Singleton — один экземпляр на всё приложение. Scoped — один экземпляр на один HTTP-запрос. Transient — новый экземпляр при каждом запросе зависимости. 🔜 Life Notes Фаза 2.

12. Паттерны проектирования

Q: Что такое Repository pattern и зачем он нужен? A: Прослойка между бизнес-логикой и способом хранения данных (БД, файл, память) — код работает с интерфейсом IRepository, не зная, EF Core там внутри или что-то ещё. Упрощает тестирование (подменить реальную БД фейком) и смену хранилища без переписывания бизнес-логики. ✅ Уже реализовано на практике в Фазе 1 (ContactBook) и будет формализовано через интерфейс в итоговом задании Фазы 2 (IContactRepository).

Q: Что такое Unit of Work? A: Паттерн, группирующий несколько операций с разными репозиториями в одну транзакцию — либо все изменения сохраняются, либо ни одно (атомарность). 🔜 Life Notes Фаза 2.

Иван прислал тайм-коды 4 реальных записанных технических собеседований с реальными офферами (Банк Эсхата 220к, Альфа-Банк 330к, НПФ Сбербанка 300к, Skillaz 320к) — не курсовой материал, а то, что спрашивают на практике. Кросс-анализ: темы, повторяющиеся в НЕСКОЛЬКИХ независимых собеседованиях — самый сильный сигнал "точно спросят".

Встретилось в 3 из 4 собеседований — максимальный приоритет:

Q: lock, Mutex, SemaphoreSlim — в чём разница и когда что использовать? A: lock — синтаксический сахар над Monitor, работает ТОЛЬКО внутри одного процесса, самый быстрый и простой примитив для взаимного исключения. Mutex — системный примитив ОС, может синхронизировать между процессами, но медленнее. SemaphoreSlim — разрешает N потоков одновременно (не только 1), в отличие от lock/Mutex — используется когда нужно ограничить, например, "не более 5 одновременных запросов к внешнему API". ✅ Фаза 3, тема 3.5 (Параллелизм) — все три примитива названы явно.

Q: Что такое race condition и как его обнаружить/предотвратить? A: Состояние гонки — когда результат зависит от непредсказуемого порядка выполнения потоков, обращающихся к общим данным без синхронизации. Предотвращается через lock/примитивы синхронизации, immutable-данные (без общего mutable-состояния гонки не будет в принципе), или потокобезопасные коллекции (ConcurrentDictionary и т.п.). ✅ Фаза 3, тема 3.5.

Q: Что такое паттерн Saga и какую проблему он решает? A: Способ управлять распределённой транзакцией между несколькими микросервисами БЕЗ классических ACID-транзакций (которые через сервисы не работают). Каждый шаг Saga — локальная транзакция одного сервиса + компенсирующее действие на случай отката ("если шаг 3 упал — откатываем шаг 2 и шаг 1 через их собственные компенсирующие операции"). Два вида: хореография (сервисы реагируют на события друг друга) и оркестрация (центральный координатор командует шагами). 🔜 Модуль 6 (собес, теория) — вместе с CQRS/Kafka.

Встретилось 1-2 раза, но конкретно:

Q: Что такое CAP-теорема? A: В распределённой системе можно гарантировать одновременно только 2 из 3: Consistency (согласованность — все узлы видят одни и те же данные), Availability (доступность — система всегда отвечает), Partition tolerance (устойчивость к разрыву сети между узлами). Partition tolerance обычно обязателен (сеть рвётся), поэтому реальный выбор — между C и A. 🔜 Модуль 6, теория.

Q: Что такое ACID применительно к транзакциям БД? A: Atomicity (всё или ничего), Consistency (БД остаётся в валидном состоянии до и после), Isolation (параллельные транзакции не видят промежуточных состояний друг друга), Durability (после коммита данные не теряются даже при сбое). 🔜 Модуль 6, теория — уже неявно знаком через PostgreSQL-опыт, просто назвать термином.

Q: Sharding vs Partitioning — в чём разница? A: Partitioning — разбиение ОДНОЙ базы на части (по диапазону, списку, хэшу) для управляемости, части могут быть на одном сервере. Sharding — разбиение данных МЕЖДУ разными серверами/базами (горизонтальное масштабирование) — каждый шард физически отдельная БД. Sharding — способ масштабирования, partitioning — способ организации. 🔜 Модуль 6, теория — прямая связь с "высоконагруженные системы" (МПП).

Q: Optimistic vs Pessimistic locking — когда что? A: Pessimistic — блокируешь строку/ресурс СРАЗУ при чтении с намерением изменить (SELECT ... FOR UPDATE), другие ждут. Хорошо при высокой конкуренции за одни и те же данные. Optimistic — не блокируешь, а при записи проверяешь не изменились ли данные с момента чтения (через version/timestamp столбец, в EF Core — concurrency token) — если изменились, конфликт и retry. Хорошо когда конфликты редки (большинство случаев). 🔜 Связано с уже пройденной 2.8 (там уже был lock для Singleton) + Life Notes Фаза 2 (EF Core concurrency tokens).

Q: Что такое double-checked locking и зачем он нужен? A: Оптимизация ленивой инициализации: проверяем условие ДО лока (дёшево), берём лок ТОЛЬКО если похоже что нужно создать объект, потом проверяем условие ЕЩЁ РАЗ уже внутри лока (другой поток мог успеть создать, пока мы ждали лок).

if (_instance == null) // проверка без лока — дёшево
{
    lock (_lock)
    {
        if (_instance == null) // проверка ВНУТРИ лока — на случай гонки
            _instance = new Singleton();
    }
}

В современном C# Lazy<T> (уже разобрано в 2.8) делает это за тебя — но важно понимать механизм руками, часто дают как задачу на собесе. 🔜 Связано с 2.8 (Singleton).

Q: Transaction isolation levels — какие есть и что такое Phantom read? A: Read Uncommitted, Read Committed, Repeatable Read, Serializable — по возрастанию строгости изоляции (и падению производительности). Phantom read — когда повторный запрос в той же транзакции возвращает НОВЫЕ строки, добавленные другой транзакцией между двумя чтениями (в отличие от non-repeatable read, где меняется/пропадает существующая строка). 🔜 Модуль 6 — строится на уже сильном SQL-опыте.

Q: Что происходит при коллизии хэшей в Dictionary? A: Несколько ключей с одинаковым хэшем попадают в одну "корзину" (bucket) — внутри корзины они хранятся как связный список/массив, и поиск внутри нее уже линейный. Много коллизий = деградация Dictionary с O(1) к O(n). Поэтому важен хороший GetHashCode(). 🔜 Дополнение к уже пройденной теме 1.7 (Dictionary).

Q: HTTP vs HTTPS, TCP vs UDP — в чём разница? A: HTTPS = HTTP поверх TLS/SSL (шифрование). TCP — с гарантией доставки и порядка (медленнее, для большинства веб-трафика), UDP — без гарантий, но быстрее (видео-стриминг, игры). 🔜 Модуль 6, база.

EF Core — специфичные детали (отдельно, для Life Notes Фазы 2): Lazy Loading (подгрузка связанных данных при обращении, а не сразу), Fluent API (конфигурация моделей через код вместо атрибутов — уже используем через IEntityTypeConfiguration), Include() vs автоматический join (Include явно указывает какие навигационные свойства подгрузить), Add vs Attach (Add — новая сущность для вставки, Attach — существующая сущность, которую нужно просто начать отслеживать), AsNoTracking() (для read-only запросов — не тратить память на change tracking), compiled queries (кэширование скомпилированного LINQ-запроса для горячих путей). 🔜 Life Notes Фаза 2 — конкретные подтемы EF Core, не общие слова.

Низкий приоритет (встретилось 1 раз, не универсально): - Паттерн Bridge — редко спрашивают, не добавляем целенаправленно - Frontend (React/Редукс/JS ==/===) — специфика конкретной компании (Альфа-Банк), не наш backend-only фокус

Новое, чего не было в разделах выше:

Q: Почему ручной вызов GC.Collect() считается опасной практикой? A: НЕ потому что удалит нужные объекты (частая ошибочная догадка на собесе) — GC всё равно помечает только реально недостижимые объекты. Опасность — трата ресурсов: принудительный вызов запускает полный цикл сборки (маркировка + сборка + уплотнение) даже когда это не нужно, забирая CPU без реальной необходимости. Используется практически только в отладке/экспериментах, не в продакшене.

Q: Полная реализация Dispose-паттерна — что происходит с финализатором? A: Внутри Dispose() нужно вызвать GC.SuppressFinalize(this) — это говорит GC "не ставь объект в очередь финализации, я уже сам всё освободил". Без этого объект всё равно попадёт в finalization queue и будет собран на цикл позже, чем мог бы — лишняя работа GC. Полный паттерн: Dispose() вызывается явно (через using), финализатор — подстраховка на случай если Dispose() забыли вызвать, и Dispose() отключает эту подстраховку через SuppressFinalize, если сам уже отработал.

Q: Почему LOH (Large Object Heap) медленнее SOH (Small Object Heap)? A: Не просто "порог 85 000 байт" — SOH компактится (объекты физически передвигаются в памяти для устранения фрагментации) при каждой сборке в своём поколении, и маленькие объекты дёшево двигать. LOH исторически НЕ компактится (дорого двигать большие блоки памяти) — вместо этого используется список свободных областей, что даёт фрагментацию кучи со временem. Это к тому же одна из причин, почему LOH обрабатывается вместе со 2-м поколением (реже всего).

Q: Почему lock берут на приватный object, а не на строковый литерал? A: Строковые литералы в .NET интернируются (interning) — одинаковая строка в разных, даже несвязанных местах кода (и даже в чужих библиотеках) физически может быть ОДНИМ И ТЕМ ЖЕ объектом в памяти. Залочившись на строку, можно случайно синхронизироваться с совершенно не связанным кодом, который лочится на ту же строку — источник трудноуловимых deadlock'ов. Приватный object-инстанс — гарантированно уникален.

Q: ConcurrentDictionary — почему быстрее, чем lock + обычный Dictionary? (реальный кандидат путался, верный ответ довёл интервьюер) A: Обычный lock вокруг Dictionary блокирует ВЕСЬ словарь на время операции — даже если два потока работают с совершенно разными ключами. ConcurrentDictionary внутри разбит на сегменты (buckets/partitions) — блокируется только тот сегмент, где реально идёт запись, остальные сегменты доступны для чтения/записи другим потокам параллельно.

Q: Postgres JSON vs JSONB — когда что и в чём разница? A: JSONB хранится в бинарном представлении (не текстом) — можно индексировать и делать запросы ВНУТРЬ структуры через операторы (->, ->>, @> и т.п.), в том числе GIN-индекс поверх JSONB-поля. Обычный JSON хранит как текст — быстрее писать, но нельзя эффективно искать по содержимому. Практический кейс из интервью: внешний контракт (интеграция с ФНС), который часто и не обратно совместимо меняется — вместо жёсткой реляционной схемы с постоянными миграциями, нестабильная часть данных кладётся в JSONB-поле.

Часть — не наш текущий Middle-уровень, но конкретные факты полезны, отмечаю где именно senior-специфика, а где применимо уже сейчас.

PostgreSQL — новое:

Q: PostgreSQL поддерживает все уровни изоляции транзакций? A: Нет — PostgreSQL физически не умеет "грязного чтения" (Read Uncommitted) из-за архитектуры MVCC (Multi-Version Concurrency Control): при UPDATE/DELETE строка не удаляется физически, а создаётся НОВАЯ версия строки, старая остаётся в индексе. Если запросить уровень Read Uncommitted, PostgreSQL тихо выполнит его как Read Committed — грязных чтений там не бывает никогда, вне зависимости от заявленного уровня. Дефолтный уровень — Read Committed. 🔜 Модуль 6, теория — прямое дополнение к уже пройденному "Transaction isolation levels" (раздел 13).

Q: Что такое connection pooling через балансировщик (PgBouncer-подобный), и какие есть режимы? A: Балансировщик держит пул подключений К БД отдельно от пула подключений ОТ приложения и мультиплексирует их. Режимы: session pooling (одно подключение приложения = одно подключение к БД на всю сессию), transaction pooling (подключение к БД возвращается в пул между транзакциями — следующая транзакция может уйти на другое физическое подключение), statement pooling (переключение даже между отдельными операциями). Транзакционный/statement-режим может незаметно ломать вещи, завязанные на "одно и то же физическое подключение" (advisory locks, temp-таблицы, SET на уровне сессии). 🔜 Модуль 6 — практический нюанс, не был явно в плане.

Q: EF Core — как именно отслеживает, какое конкретно поле изменилось (change tracking)? A: Не через версионирование/RowVersion (это ОТДЕЛЬНАЯ фича — optimistic concurrency token, легко перепутать!). Change tracking работает через снапшот: при загрузке сущности EF сохраняет копию исходных значений всех полей, при SaveChanges() сравнивает текущие значения с этим снапшотом поле за полем и генерирует UPDATE только для реально изменившихся колонок (dirty checking). RowVersion/[Timestamp] — это отдельный, необязательный механизм именно для optimistic concurrency (конфликт двух параллельных обновлений одной строки), не имеет отношения к тому, как EF понимает, какое поле поменялось. 🔜 Life Notes Фаза 2 (EF Core) — важно не путать два разных механизма под одним словом "версия".

Q: CREATE INDEX CONCURRENTLY — зачем нужен? A: Обычный CREATE INDEX берёт блокировку на таблицу, останавливающую записи на время построения индекса — опасно на проде с нагрузкой. CONCURRENTLY строит индекс без блокировки записи (дольше по времени, тратит больше ресурсов), специально для прод-таблиц под нагрузкой. 🔜 Модуль 6 — дополнение к уже пройденным индексам.

Q: VACUUM vs VACUUM FULL — в чём разница? A: VACUUM — фоновый процесс, освобождает место от "мёртвых" строк (оставшихся после UPDATE/DELETE из-за MVCC), обновляет статистику планировщика; работает автоматически (autovacuum) или вручную, таблицу почти не блокирует. VACUUM FULL — жёстче: физически переписывает/уплотняет таблицу (нужно ~50% свободного места на диске под перестановку строк), сильнее блокирует таблицу. Нужен, когда таблица под постоянной нагрузкой записи и autovacuum физически не успевает угнаться за очисткой. 🔜 Модуль 6 — практический факт про обслуживание Postgres, не было в плане.

Q: Практическая задача — сменить тип колонки (string→int) в боевой таблице без даунтайма. Как? A: Классический паттерн "expand-and-contract" (расширение-сжатие): (1) добавить НОВУЮ колонку v2 нужного типа, не трогая старую; (2) релиз, где приложение пишет в ОБЕ колонки (dual-write) и читает пока из старой; (3) когда все данные синхронизированы — переключить чтение на новую колонку; (4) отдельным релизом позже удалить старую колонку. Ключевое требование — обратная совместимость на каждом шаге (старая и новая версия приложения должны уметь работать одновременно во время раскатки). 🔜 Модуль 6 — отличный конкретный пример на "расскажи, как сделать миграцию без даунтайма", годится и для собеса, и для реальной практики в Life Notes.

Брокеры сообщений — новое (дополняет уже пройденный Outbox/Saga):

Q: Что такое Inbox pattern и чем он дополняет Outbox? A: Outbox (уже в плане) решает надёжную ОТПРАВКУ — событие пишется в таблицу outbox в той же транзакции, что бизнес-изменение. Inbox — обратная сторона, на стороне ПОЛУЧАТЕЛЯ: перед обработкой сообщения его ключ идемпотентности проверяется в таблице inbox — если уже есть, сообщение пропускается (уже обработано), если нет — обрабатывается и ключ записывается. Нужен, потому что большинство брокеров дают гарантию доставки "at least once" (минимум один раз, но возможен дубль) — без Inbox дубль сообщения обработается повторно. 🔜 Life Notes Фаза 5 (RabbitMQ) — прямое дополнение к уже запланированному Outbox.

Q: Kafka vs RabbitMQ — в чём архитектурная разница (не просто "оба брокеры")? A: RabbitMQ — модель push, "умный брокер, глупый клиент": брокер сам активно отправляет (пушит) сообщения подписанным потребителям. Kafka — модель pull, ближе к персистентному логу/шине: продюсер пишет в конец лога, потребители сами вычитывают оттуда с своей позиции (offset) — "глупый брокер, умный клиент". Kafka лучше масштabируется горизontально через партиции (несколько инстансов потребителей одной consumer group читают разные партиции параллельно), но выше порог входа в настройке. 🔜 Модуль 6 — уточняет уже запланированную тему "Kafka vs RabbitMQ — концептуальная разница" конкретной формулировкой push/pull.

Q: Гарантируется ли порядок сообщений в Kafka? A: Только ВНУТРИ одной партиции, не между партициями. Чтобы все события одной сущности (например, операции по одному счёту) обрабатывались в правильном порядке — их нужно класть в одну и ту же партицию через ключ партиционирования (например, хэш от ID сущности по модулю числа партиций). Без ключа события одной сущности могут случайно разлететься по разным партициям и обработаться не в том порядке. 🔜 Модуль 6 — практический нюанс к Kafka.

Архитектура — новое:

Q: Монолит vs микросервисы — по каким признакам понять, что пора делить? A: Сигналы к разделению: несколько команд работают в одном монолите и мешают друг другу (релиз одной команды откатывает изменения другой), рост числа разработчиков перестаёт давать пропорциональный рост скорости разработки (слишком много конкурентности за одну кодовую базу), нужно независимое горизонтальное масштабирование разных частей. Контраргумент — это НЕ всегда монолит→микросервисы: у low-latency систем (нужен мгновенный ответ) микросервисы могут навредить — сетевой overhead между сервисами добавляет задержку, которой нет при вызовах в рамках одного процесса. 🔜 Модуль 6 — уточняет архитектурную теорию (уже частично покрыта SOLID/Repository в разделе 12).

Q: Как понять, НА ЧТО именно делить монолит (сколько сервисов, по какой границе)? Каждый ограниченный контекст — кандидат на отдельный сервис. 🔜 Модуль 6, теория — конкретная методология, не просто "разделяй по доменам".

Q: Два record'а с одинаковым по СОДЕРЖАНИЮ строковым полем (string), но физически РАЗНЫМИ объектами строки в памяти — окажутся ли они равны через сгенерированный Equals? A: Да, будут равны — но не потому что record "особенный" со строками, а потому что сам string в C# переопределяет Equals/== для сравнения по содержимому (это уже так на уровне языка, независимо от records). Record генерирует сравнение через EqualityComparer<T>.Default для КАЖДОГО поля — для string это корректно даёт сравнение по значению. НО если поле — ссылочный тип, который САМ не переопределяет Equals/GetHashCode() (обычный класс без value-семантики), то по этому конкретному полю сравнение упадёт до сравнения по ССЫЛКЕ, и два record'а с "одинаковым по смыслу" вложенным объектом, но разными инстансами, окажутся НЕ равны в целом. ✅ Прямое уточнение к уже пройденной теме 2.9 (Record типы — value equality) — важный нюанс, которого там пока нет: value equality рекурсивно зависит от того, переопределяет ли КАЖДОЕ вложенное поле собственное равенство.

Q: Почему DbContext не стоит регистрировать как Singleton? A: Три причины: (1) ChangeTracker внутри DbContext копит отслеживаемые сущности и никогда не очищается сам — при Singleton он будет бесконечно расти (утечка памяти); (2) DbContext не потокобезопасен — два одновременных запроса к одному инстансу вызовут гонку; (3) риски согласованности данных между независимыми запросами, использующими один и тот же контекст. Решение — AsSplitQuery(): EF Core разбивает один тяжёлый JOIN-запрос на несколько отдельных простых запросов вместо одного огромного. 🔜 Life Notes Фаза 2 (EF Core) — конкретный, отдельный от N+1 практический гочка, не было в плане.

Если в колонке были данные — они будут ПОТЕРЯНЫ при применении такой миграции. Чтобы сохранить данные, нужно вручную открыть сгенерированный файл миграции и заменить пару DropColumn/AddColumn на один вызов migrationBuilder.RenameColumn(name: "OldName", newName: "NewName", table: "..."). Практический вывод: миграции нельзя слепо доверять и сразу применять — их нужно открывать и читать перед Update-Database, особенно после переименований. 🔜 Life Notes Фаза 2 (EF Core) — конкретный, опасный своей неочевидностью гочка; кандидат подтвердил, что сам с этим сталкивался в реальной работе.

Q: Расскажи про слоистую (Clean/Layered) архитектуру — какие слои и что в них? A: Классическое деление на 4 слоя: Domain — доменные сущности, то, ЧЕМ система оперирует, без зависимостей от остальных слоёв. Application — бизнес-логика: сценарии использования, расчёты, правила. Infrastructure — всё внешнее: работа с БД, файлами, брокерами сообщений, интеграции со сторонними сервисами. Presentation/Web — точка входа во внешний мир: контроллеры, глобальный exception-middleware, action-фильтры. Ключевое правило зависимостей — внешние слои зависят от внутренних (Presentation → Application → Domain), а не наоборот; Domain ни от кого не зависит. 🔜 Life Notes Фаза 2/5 — прямое обоснование того, ПОЧЕМУ в код-ревью ниже вынесение DbContext из контроллера — не вкусовщина, а нарушение конкретно этого правила зависимостей.

Q: Для чего использовался стек ELK (Elasticsearch, Logstash, Kibana)? A: Elasticsearch — индекс для быстрого полнотекстового поиска (в том числе по логам); Kibana — визуализация/просмотр этих данных. На практике логи в проде хранились в Elasticsearch, а разработчик смотрел их через Kibana вместо прямого чтения файлов на сервере — быстрее искать по большому объёму логов, чем grep по файлу. 🔜 Модуль 6 (логирование) — дополняет уже отмеченный Serilog: Serilog СОБИРАЕТ структурированные логи, ELK — куда их можно писать и как потом искать.

Q: Зачем нужен HttpClientFactory, чем он лучше, чем просто new HttpClient()? A: Несколько причин: (1) переиспользует пул сокет-соединений — new HttpClient() на каждый запрос исчерпывает сокеты (socket exhaustion) под нагрузкой; (2) поддерживает именованные и типизированные клиенты — под каждый внешний сервис своя настроенная конфигурация; (3) на каждый такой клиент можно навесить политики через Polly — retry, circuit breaker («после N подряд ошибок — временно перестать долбить упавший сервис»), логирование запроса/ответа; (4) централизованные тайм-ауты и заголовки в одном месте конфигурации, а не разбросаны по коду. 🔜 Life Notes Фаза 2/5 — практический факт про интеграции с внешними сервисами; кандидат честно признал, что не использовал, интервьюер объяснил.

Q: Как называется паттерн постепенного перехода от монолита к микросервисам, при котором старая и новая версия функционала работают одновременно, а трафик переключается порционно? A: Strangler Fig pattern ("душитель") — ставится API Gateway перед монолитом, часть запросов начинает направляться на новый отдельно развёрнутый микросервис, реализующий тот же функционал, а остальные продолжают идти в старый монолит. Когда новая часть проверена и стабильна — соответствующий кусок функционала в монолите просто вырезается. Для внешнего пользователя всё это время точка входа не меняется. Кандидат правильно описал МЕХАНИЗМ, не зная НАЗВАНИЯ паттерна — стоит запомнить именно термин, раз механику уже понимаешь. 🔜 Life Notes Фаза 2/5 — прямое имя для уже упомянутого в базе (мок #2) "monolith→microservices split" механизма.

Q: Как избежать дублирования логики авторизации в каждом микросервисе? A: Вынести аутентификацию/авторизацию на уровень API Gateway (в интервью — Ocelot, судя по описанию). Пользователь обращается только в Gateway — единую точку входа. Gateway проверяет и валидирует токен (JWT) один раз, и дальше проксирует запрос нужному микросервису, передавая токен в заголовках. Микросервис ДОВЕРЯЕТ Gateway и не перепроверяет валидность подписи токена заново — экономит дублирование этой логики в каждом сервисе по отдельности. 🔜 Life Notes Фаза 2/5 (микросервисы) — конкретная реализация паттерна "authentication на границе системы", дополняет уже отмеченные DDD bounded contexts.

Q: Как сохранить данные PostgreSQL в Docker при пересоздании контейнера (например, при переходе на образ с расширением PostGIS)? A: Через volumes в docker-compose.yml — пробросить директорию с данными БД внутри контейнера (/var/lib/postgresql/data) на внешний носитель: либо именованный Docker volume, либо bind mount прямо на локальный диск хоста. Тогда при docker rm контейнера и запуске нового (даже с другим образом) данные на диске остаются нетронутыми и новый контейнер увидит те же данные. 🔜 Life Notes (DevOps/Docker) — практический факт, ещё не было в плане.

Q: Как в Vue/аналогичных фреймворках реализована реактивность на техническом уровне — как фреймворк узнаёт, что нужно перерисовать DOM? A: Каждый реактивный объект оборачивается в Proxy с перехватом get/set (геттеры/сеттеры). Когда код меняет поле объекта, срабатывает перехваченный set — фреймворк узнаёт об изменении СРАЗУ (не по таймеру и не по перезагрузке страницы) и точечно обновляет только затронутый узел DOM-дерева, а не всю страницу — в отличие от классических multi-page приложений, где для отображения новых данных нужна полная перезагрузка страницы. 🔜 Life Notes/фронтенд — расширяет уже обсуждённое сравнение Vue/React (immutability в React vs мутируемость в Vue) конкретным механизмом ПОД капотом.

Q: Какие есть стадии жизненного цикла Vue-компонента? A: created (компонент создан, но ещё не вставлен в DOM) → mounted (вставлен в DOM, можно работать с реальными элементами) → updated (после каждого реактивного изменения и перерисовки) → destroyed/unmounted (компонент убран, самое место отписываться от подписок/таймеров, чтобы не было утечек). 🔜 Life Notes/фронтенд — низкий приоритет (C# — основной фокус), но встречается на собеседованиях с фуллстек-уклоном.

Q: Что такое замыкание (closure) в JavaScript — и то же ли это, что в C#? A: Концепция та же: внутренняя функция «запоминает» (захватывает) переменные из внешней области видимости, даже после того как внешняя функция завершила выполнение. В C# классическая иллюстрация — LINQ/лямбда, захватывающая переменную ПО ССЫЛКЕ на саму переменную, а не по значению на момент создания: если между объявлением лямбды и её вызовом переменная изменилась, вызов увидит НОВОЕ значение (характерный вопрос-ловушка про for-цикл и захват счётчика). 🔜 JS — низкий приоритет, но полезно как проверка, что C#-понимание closures переносится на другой язык.

Q: Что такое Event Loop в JavaScript? A: Механизм, который позволяет однопоточному JS эмулировать асинхронность: длительные операции (запрос к серверу, таймер) не блокируют единственный поток, а ставятся в очередь задач (task queue/microtask queue); когда основной стек вызовов пуст, Event Loop достаёт следующую задачу из очереди и выполняет её. Концептуальный аналог в C# — машина состояний, которую компилятор генерирует для async/await (см. мок-интервью #2/#3): тоже способ вернуть управление, не блокируя поток, и продолжить позже. 🔜 JS — низкий приоритет, но полезная аналогия для собственного понимания async/await в C#.

Q: var vs let vs const в JS — в чём разница? A: var — устаревший, у него ФУНКЦИОНАЛЬНАЯ/глобальная область видимости (не блочная) — можно объявить внутри if/for и переменная "утечёт" наружу, источник классических багов. let/const — блочная область видимости (видны только внутри { }, где объявлены), современный стандарт. Разница между ними: let допускает переприсвоение, const запрещает переприсвоение ССЫЛКИ (но если это объект/массив — его содержимое всё равно можно мутировать). Хороший тон — использовать const по умолчанию, let только когда переменная реально должна меняться. 🔜 JS — низкий приоритет, но простой и частый вопрос даже на бэкенд-собеседованиях с фуллстек-уклоном.

Q: Можно ли писать код ПОСЛЕ await next() в middleware — и что он будет делать? A: Да, можно — и это не редкий случай, а нормальная часть паттерна. await next() — это вызов следующего middleware в цепочке. Код ДО этого вызова выполняется на пути "вниз" (запрос идёт к исполняющему коду/контроллеру), код ПОСЛЕ — на пути "вверх" (когда результат уже посчитан и возвращается обратно через ту же цепочку в обратном порядке). Например, добавление заголовка ответа ПОСЛЕ await next() — абсолютно рабочий и частый паттерн (заголовок добавляется уже к готовому ответу). Аналогия — стек вызовов: middleware регистрируются как вложенные вызовы, next() — точка перехода вглубь, а после неё код выполняется уже "на обратном пути", как код после рекурсивного вызова. 🔜 Life Notes Фаза 2 — уточняет уже добавленный в часть 1 факт про порядок middleware конкретным разбором "что можно писать после next()".

Q: Что не так с контроллером, который читает DbContext напрямую через .AsNoTracking().ToListAsync()? A: Дополнение к уже собранному чек-листу код-ревью (см. выше, мок-интервью #3): здесь тот же смысл (не место DbContext в контроллере — нарушение слоя Presentation, должно быть в Infrastructure/Application), плюс отдельно — метод синхронного вида без суффикса Async, и метод принимает CancellationToken, но НЕ прокидывает его дальше в ToListAsync(token) — токен объявлен, но бесполезен, потому что не передан туда, где реально мог бы прервать операцию. ✅ Дополняет уже существующий практический чек-лист код-ревью — добавлена одна строка в саму теорию (см. чек-лист выше).

Q: Если сделать var user = await db.Users.AsNoTracking().FirstAsync(...), а потом изменить user.Name = "..." и вызвать SaveChangesAsync() — сохранится ли изменение? A: НЕТ. AsNoTracking() отключает ChangeTracker для этого запроса — EF Core вообще не знает, что объект user как-то связан с базой, и не отслеживает изменения его полей. Присвоение user.Name = "..." меняет только объект в памяти. SaveChangesAsync() в этот момент не находит НИ ОДНОЙ отслеживаемой изменённой сущности — вызывается "вхолостую", запрос к БД не отправляется вообще, изменение имени в БД не попадает. Практический вывод: если объект после чтения нужно МЕНЯТЬ — не используй AsNoTracking() для этого запроса (она только для read-only сценариев, где производительность важнее — тогда трекинг лишний оверхед). 🔜 Life Notes Фаза 2 (EF Core) — прямое практическое следствие уже отмеченной темы change tracking (мок #2/#3), конкретный "как сломать себе SaveChanges и не понять почему".

Q: (кратко) Что такое uint и как маппится XML-колонка PostgreSQL через Fluent API? A: uint — целое БЕЗ знака (unsigned int): диапазон от 0 до ~4 млрд (в 2 раза больше верхней границы обычного int, зато нет отрицательных значений). Через modelBuilder.Entity<T>().Property(...) можно явно указать тип колонки в БД, включая нестандартные для реляционных СУБД типы вроде xml (PostgreSQL поддерживает нативный XML-тип колонки для полуструктурированных данных). 🔜 Низкий приоритет — нишевая деталь (uint в реальных проектах почти не встречается, XML-колонки — редкость на фоне JSON/JSONB).

Q: Три класса: A (abstract, virtual Print()), B : A (override Print()), C : B (new Print(), БЕЗ override). Приводим экземпляр C к типу A и вызываем Print() — что выведется? A: Выведется версия B, не C и не A. Почему: виртуальная диспетчеризация у A/B работает через одну "линию" переопределений (virtual-таблица) — A.Print → переопределена в B.Print. Когда C объявляет Print() через new, он НЕ продолжает эту линию, а начинает СВОЮ, независимую — компилятор трактует C.Print как совершенно отдельный метод, никак не связанный с виртуальной диспетчеризацией A/B. Поэтому вызов через переменную типа A (или B) ищет самую "глубокую" версию именно в виртуальной цепочке A→B — и находит B, потому что C из этой цепочки СЕБЯ ИСКЛЮЧИЛ через new. Если бы C тоже использовал override, вызов через A вывел бы C (обычный динамический полиморфизм). Добавлено как расширение примера E (hiding через new) — там был 2-уровневый пример (Bird/Penguin), здесь то же самое, но нагляднее на 3 уровнях: new не просто "скрывает от родителя", а обрывает цепочку виртуальной диспетчеризации для всех, кто ниже по иерархии. ✅ Расширяет уже пройденную тему 2.3 (hiding через new) — добавлен пример в саму теорию.

Q: Есть struct Reader { public string Message; }. Метод void Read(Reader r) { r.Message = "прочитано"; } — изменится ли Message у оригинального объекта после вызова? A: НЕТ. struct — значимый тип, при передаче в метод копируется ЦЕЛИКОМ. Read работает со своей локальной копией r, оригинал снаружи не видит изменений. Чтобы метод реально изменил оригинал — нужно передавать по ссылке явно: ref Reader r (можно и читать, и писать, вызывающий обязан передать существующую переменную) или out Reader r (только для "метод обязан присвоить значение", вызывающий может передать неинициализированную переменную). ✅ Расширяет уже пройденную тему 1.1 (передача struct в методы, копирование по значению) — добавлен пример в саму теорию.

Q: foreach (var item in list) { if (нужно удалить) list.Remove(item); } — скомпилируется? Выполнится? A: Скомпилируется без ошибок. Но в РАНТАЙМЕ бросит InvalidOperationException: Collection was modified; enumeration operation may not execute — как только foreach под капотом видит несовпадение версии коллекции ПОСЛЕ первого Remove внутри цикла (см. 1.8 — как компилятор разворачивает foreach в GetEnumerator()/MoveNext()). Нельзя модифицировать коллекцию, по которой в данный момент идёт перебор тем же foreach. Практическое решение — либо for с обратным перебором индексов, либо list.RemoveAll(предикат), либо сначала собрать элементы на удаление в отдельный список и удалить их ПОСЛЕ завершения foreach. ✅ Расширяет уже пройденную тему 1.8 (foreach под капотом) — добавлен пример в саму теорию.

Топ по реальной частоте использования — вот что спрашивают буквально всегда

Q: Какие примитивы синхронизации вы знаете, какой принцип работы? (18 грейд, 2733 использования — САМЫЙ частый вопрос во всём банке) A: Monitor/lock (внутрипроцессный, взаимное исключение), Mutex (может быть именованным — межпроцессный), Semaphore/SemaphoreSlim (N потоков одновременно, Slim — async+CancellationToken, не именованный), ReaderWriterLockSlim (раздельные блокировки чтения/записи), ManualResetEvent/AutoResetEvent/CountdownEvent (сигнальные примитивы), Interlocked (атомарные операции без блокировки для простых случаев типа инкремента), System.Collections.Concurrent (потокобезопасные коллекции), System.Threading.Channels (асинхронные очереди producer/consumer).

Q: Можно ли использовать lock с async/await? (1786 использований) A: Нет — ошибка компиляции (await физически запрещён внутри lock). Если обойти через Monitor.Enter/Exit напрямую — ошибка РАНТАЙМА, если Exit вызывается в другом потоке, чем был Enter (после await продолжение может пойти в другом потоке из пула). Решение: убрать асинхронный код из-под лока или использовать SemaphoreSlim.WaitAsync().

Q: Во что разворачивается lock, работает ли он со значимыми типами? (1730 использований) A: lock(obj) { ... } → Monitor.Enter(obj, ref lockTaken); try { ... } finally { Monitor.Exit(obj); }. Со значимыми типами НЕ работает (не скомпилируется) — value type передаётся по значению, каждый поток блокировал бы свою копию, а не общий объект.

Q: Можно ли использовать lock для межпроцессного взаимодействия? (309 использований) A: Нет — lock разворачивается в Monitor, который сериализует доступ только ВНУТРИ процесса. Для межпроцессной синхронизации — именованный Mutex или Semaphore.

Q: Во что разворачивается async-await? Для чего он нужен? (1984 + 2179 использований — вместе почти 4200!) A: Метод с async разворачивается в машину состояний (state machine) — компилятор генерирует отдельный класс, переходы между состояниями — места использования await. Нужен чтобы писать асинхронный код, который выглядит как синхронный; await дожидается результата awaitable-объекта (Task/Task<T>), не блокируя поток.

Q: Зачем нужны и стек и куча? Почему не хранить всё в куче? (1913 использований) A: Стек — для локальной памяти потока/быстрой неконкурентной работы, выделение и удаление быстрее (просто сдвиг указателя). Куча — для долгоживущих и общих ресурсов, но выделение/удаление дороже (работа GC). ✅ Уже пройдено в Фазе 1 (1.2) — здесь просто подтверждение что это САМЫЙ частый вопрос про память (1913 раз), стоит освежить перед собесом отдельно.

Concurrency и async/await (✅ Фаза 3 — самый приоритетный блок банка Ozon, теперь в теории)

Q: Во что конкретно разворачивается async/await — из чего состоит сгенерированная машина состояний? A: Компилятор генерирует класс-структуру с полями: <>1__state (текущее состояние), builder (AsyncTaskMethodBuilder), awaiter-поля (по одному на каждый await) и временные локальные переменные метода. Каждый await — точка перехода между состояниями MoveNext(). Источник: канонический перевод серии Стивена Тоуба (разработчик .NET runtime) — самый авторитетный русскоязычный материал по теме, часть 4-6 разбирают именно это. ✅ Фаза 3, тема 3.4.

Q: Что именно "теряется"/"пропускается" при ConfigureAwait(false), и зачем нужен TaskScheduler в этой картине? A: Захват SynchronizationContext — то, что при возврате из await продолжение (continuation) планируется обратно на исходный поток (например, UI-поток в WPF). ConfigureAwait(false) явно отключает этот захват — продолжение может пойти на любом потоке из пула. TaskScheduler — второй, менее известный механизм возврата продолжения, используется когда SynchronizationContext отсутствует (например, консоль/сервис). Источник: часть 7 серии Тоуба. ✅ Фаза 3, тема 3.4.

Q: Распиши по шагам классический дедлок на .Result в UI/ASP.NET (не WebApi) контексте. A: (1) UI-поток вызывает SomeAsyncMethod().Result — блокирует сам себя в ожидании. (2) Внутри метода после await продолжение пытается вернуться на ТОТ ЖЕ UI-поток (SynchronizationContext захвачен). (3) UI-поток занят ожиданием на шаге (1) и не может выполнить продолжение из шага (2) — взаимная блокировка, никто не двигается. В современном ASP.NET Core SynchronizationContext отсутствует, поэтому классический вариант этого дедлока там не воспроизводится — но .Result/.Wait() всё равно опасны по другой причине (см. следующий вопрос). Источник: разбор async/await + .Result. ✅ Фаза 3, тема 3.4.

Q: В ASP.NET Core SynchronizationContext нет — значит ли это, что .Result безопасен? Что реально происходит при CPU-нагрузке всего 8%? A: Нет, не безопасен — механизм убийства другой: ThreadPool starvation. .Result синхронно блокирует поток из пула, пока не завершится асинхронная операция — поток "заморожен", но числится занятым. Реальный замер: 50 000 RPS с p99=40мс превращаются в 12 000 RPS с p99=4 сек при загрузке CPU всего 8% — потому что почти все потоки пула физически заблокированы в ожидании, а не заняты работой. ThreadPool наращивает число потоков по алгоритму hill-climbing (WavePeriod=4, окно ≈6.4 сек, MaxChangePerSecond=4) — но на массово заблокированных потоках это даёт разрушительную положительную обратную связь (наращивание потоков не поспевает за блокировкой). Диагностика в проде: dotnet-counters — метрики threadpool.thread.count и threadpool.queue.length растут аномально. Решение — не "лечить" через Task.Run() (создаёт ещё один блокирующий поток), а убрать .Result полностью и/или добавить bulkhead через Channel<T>. Источник: разбор ThreadPool starvation с метриками. ✅ Фаза 3, тема 3.4.

Q: Что такое System.Threading.Channels и чем он лучше BlockingCollection<T>? A: Channel<T> — lock-free producer/consumer очередь с полноценным async API (WriteAsync, TryWrite, WaitToWriteAsync, ReadAllAsync) — в отличие от BlockingCollection<T>, который под капотом использует блокирующий Monitor.Wait и не даёт async-варианта. Bounded-канал поддерживает 4 режима переполнения (BoundedChannelFullMode: Wait / DropNewest / DropOldest / DropWrite). Флаги SingleReader/SingleWriter — оптимизация в разы, если гарантированно один читатель/писатель. Источник: разбор Channels. ✅ Фаза 3, тема 3.5.

Q: КАК именно LINQ-запрос через IQueryable превращается в SQL? Q: Zero-downtime миграция БД — распиши по фазам добавление колонки, удаление колонки и смену типа/переименование. A: Добавление: колонка nullable → выкатить новую версию приложения, которая её заполняет → дозаполнить существующие строки → сделать NOT NULL. Удаление: сначала сделать nullable + убрать использование из кода нового релиза → только потом физически дропнуть колонку отдельной миграцией. Переименование/смена типа: классический expand-and-contract в 4 фазы (добавить новую колонку → писать в обе → перенести чтение на новую → дропнуть старую). Отдельное правило: миграционный скрипт запускается СТРОГО один раз, отдельно от приложения, через CI/CD — не через авто-Migrate() при старте. Источник: миграции без даунтайма. ✅ Расширяет уже существующий в курсе (собес #2, смена типа string→int) ответ про expand-and-contract с одного абзаца/одного сценария до трёх полностью разобранных сценариев.

Q: Какие типы индексов есть в PostgreSQL и когда какой выбирать? A: B-Tree — дефолт, для равенства/диапазонов/сортировки. GIN — для JSONB/массивов/полнотекстового поиска (WHERE tags @> ARRAY['electronics']). GiST — геоданные и сложные операторы. BRIN — для очень больших таблиц с естественной физической упорядоченностью (например, время вставки): реальный кейс — 120 МБ BRIN против 40 ГБ B-Tree на 100 млн записей в день при сохранении скорости запроса. Планировщик учитывает селективность — если под условие подходит 30-40% строк, seq scan может оказаться дешевле индекса. LIKE '%text' требует отдельного триграммного индекса. Индекс на каждую фильтруемую колонку = write amplification (замедление вставок) и раздувание БД. Неиспользуемые индексы находятся через pg_stat_user_indexes. Источники: гайд по индексам PostgreSQL, SQL-антипаттерны + составной индекс под фильтр+сортировку. 🔜 Модуль 6 / PostgreSQL — в курсе про индексы был только один факт (sargable-предикаты из банка Ozon). Composite-индекс под связку WHERE status = 'active' ORDER BY created_at DESC — готовый пример: CREATE INDEX idx_orders_status_created_at ON orders(status, created_at DESC).

Q: Как читать план EXPLAIN ANALYZE и на что смотреть в первую очередь? A: Читать снизу вверх и изнутри наружу. cost/rows — ПРОГНОЗ планировщика, actual time/rows — ФАКТ выполнения (два числа в actual time — до первой и до последней строки). Rows Removed by Filter — сколько строк индекс/скан отбросил уже после чтения (эффективность фильтра). Узлы: Seq Scan (полное сканирование) / Index Scan / Bitmap Scan, Hash Join / Nested Loop / Merge Join. BUFFERS: shared hit — из кэша, read — с диска (дороже). Типовые диагнозы: устаревшая статистика (лечится ANALYZE), Nested Loop там где нужен Hash Join, сортировка на диске вместо памяти. Источник: EXPLAIN ANALYZE подробно. 🔜 Модуль 6 / PostgreSQL — пара к предыдущему вопросу: один учит выбирать индекс, второй — проверять, что он реально применился (а не Seq Scan вместо ожидаемого Index Scan).

Q: Что физически лежит в системном столбце xmin, и почему у PostgreSQL есть предел по числу транзакций? A: xmin/xmax — 32-битный ID транзакции, создавшей/удалившей конкретную ВЕРСИЮ строки (MVCC). Счётчик 32-битный (~4 млрд значений) — на высоконагруженной БД переполнение возможно раз в сутки. Механизм защиты — заморозка (FrozenTransactionId + счётчик эпох, появился в версии 8.2 — до этого при переполнении сервер просто падал). Долгие открытые транзакции блокируют VACUUM FREEZE, что при накоплении риска переполнения означает простой всей БД. Источник: XID изнутри, команда Postgres Professional. ✅ Расширяет уже существующий в курсе факт "xmin — аналог RowVersion для optimistic concurrency" (собес #4) объяснением, ЧТО ТАКОЕ xmin физически и почему у него есть предел — сильно повышает уровень ответа про MVCC выше "просто версии строк".

Q: Какие есть аргументированные минусы у паттерна Generic Repository? A: (Это авторская позиция одной статьи, не общий консенсус — подавать как "есть такая критика", не как истину.) Q: Развенчай миф "CQRS = обязательно разделить чтение и запись физически на разные хендлеры/базы". Q: gRPC vs REST — сравни и назови протокольные ошибки, с которыми реально сталкиваются. A: REST = HTTP + JSON, человекочитаемый, ключи дублируются в каждом сообщении. gRPC = HTTP/2 + Protocol Buffers, бинарный формат без повторяющихся ключей + 4 режима стриминга (unary, server, client, bidirectional) против отсутствия нативного стриминга в REST. По бенчмарку — gRPC быстрее REST в 7-10 раз. Минусы gRPC: браузер не умеет работать с ним напрямую, порог входа выше, экосистема беднее. Реальные грабли (протокольные, переносятся на C# один в один): (1) в gRPC поля не nullable — есть только значения по умолчанию, которые не передаются по сети, поэтому "не прислали" и "прислали 0" неразличимы без сгенерированных hasField(); (2) значения enum должны быть уникальны в пределах пакета — отсюда правило Google "префиксовать каждое значение именем типа"; (3) ленивая инициализация соединения — первые запросы стабильно вылетают по deadline; (4) обратная совместимость держится на НОМЕРАХ полей, а не на именах. Источники: REST vs gRPC, почему выбрать gRPC, реальные грабли gRPC. 🔜 Модуль 6 — gRPC vs REST в Tier 0 плана, всплывал на собесе #4, но не был разобран. Слоистая (Layered/Clean) — понятная структура, но риск каскадных отказов при сильной связности слоёв. Микросервисы — независимое масштабирование, но отладка через 20+ сервисов и интеграционное тестирование становится отдельной проблемой. Event-Driven — слабая связанность, но "отладка превращается в детектив" + eventual consistency. Serverless — не думаешь об инфраструктуре, но cold start и vendor lock-in. Гексагональная/Ports&Adapters — тестируемое изолированное ядро, но оверинжиниринг на маленьких проектах. Термин "распределённый монолит" — антипаттерн, когда микросервисы формально разделены, но их нельзя выкатывать по отдельности (скрытые синхронные зависимости). Источники: 6 архитектурных паттернов с trade-off'ами, Hexagonal Architecture (детали Hexagonal — теперь прямо в теории, Phase2_OOP.md 2.7). 🔜 Модуль 6 — в курсе Clean Architecture (собес #4) разобрана только в позитивном ключе. "А какие минусы у вашей архитектуры" — стандартный вопрос на Middle+.

Q: Чем API Gateway отличается от BFF (Backend for Frontend)? A: API Gateway просто маршрутизирует запросы к нужному сервису. BFF трансформирует данные — агрегирует вызовы нескольких сервисов, меняет формат ответа под конкретного клиента, фильтрует лишние поля, считает производные значения. Мотивация: мобильному приложению не нужны все 40 финансовых полей, которые отдаёт бэкенд, — только геолокация и сумма. Минусы BFF: дублирование логики между несколькими BFF (свой на мобилку, свой на веб) и риск неверной гранулярности. Источник: BFF-архитектура. ✅ Дополняет уже существующий в курсе (собес #4) факт про API Gateway и вынос авторизации на границу — Gateway и BFF легко путают, а на собесе именно это различие любят уточнять.

Q: Сравни Kafka, RabbitMQ, NATS+JetStream по throughput и гарантиям доставки. A: Порядки величин: Kafka 500K–1M+ msg/sec (10-50 мс), RabbitMQ 50K–100K (5-20 мс), NATS+JetStream 200K–400K (1-5 мс). Таксономия гарантий доставки — три уровня: at-most-once / at-least-once / exactly-once. RabbitMQ умеет только at-least-once, Kafka и Pulsar — вплоть до exactly-once. Отказоустойчивость: у Kafka — replication factor через ISR (In-Sync Replicas), у RabbitMQ — quorum queues на Raft, у NATS — R3-кластеризация. Источник: сравнение брокеров 2025 с цифрами. ✅ Расширяет уже существующий в курсе Kafka vs RabbitMQ через push/pull (собес #2) конкретными цифрами и полной таксономией гарантий — на "почему RabbitMQ, а не Kafka" цифры убедительнее общих слов.

Q: Как несколько инстансов воркера Outbox не разошлют одно событие дважды? A: Безопасное чтение таблицы outbox несколькими воркерами конкурентно — через FOR UPDATE SKIP LOCKED в PostgreSQL/MySQL (ROWLOCK, UPDLOCK, READPAST в SQL Server): воркер блокирует строку, которую взял в обработку, остальные воркеры её просто пропускают вместо ожидания. Дополнительно: ретранслятор стоит выносить в отдельный процесс, а не в API-сервис; нужна регулярная чистка таблиц outbox/inbox; наблюдаемость — возраст самого старого неотправленного события, скорость поступления против скорости обработки. Гарантия остаётся "at least once", не "exactly once" — это проговаривается честно. Источник: Transactional Outbox от теории до продакшена. ✅ Расширяет уже существующий в курсе Outbox/Inbox (банк Ozon 1433 использования, собес #2) с уровня "что это" до уровня "как конкретно не отправить дважды при нескольких воркерах" — конкретный ответ, отличающий читавшего от делавшего.

Q: В чём была реальная ошибка в настройке Polly (AddRetryPolicy().AddCircuitBreakerPolicy().AddTimeoutPolicy()), и когда retry вообще делает систему хуже? A: Реальный разбор четырёх ошибок в одной цепочке: (1) jitter посчитан один раз и переиспользуется — ретраи разных клиентов синхронизируются заново, нужен DecorrelatedJitterBackoffV2 внутри лямбды, а не снаружи; (2) Circuit Breaker создаётся заново на каждый запрос — никогда не накапливает статистику отказов; (3) три слоя таймаутов (на попытку/операцию/дефолт HttpClient) в неверном порядке обрывают операцию раньше, чем отработают ретраи; (4) политики Polly — декораторы, порядок критичен: Circuit Breaker перед Retry не срабатывает, потому что Retry маскирует ошибки от него. Отдельно, когда retry вредит: retry storm — 10% ошибок от 10 000 запросов/мин порождают +1000 повторов, которые провоцируют следующую волну ошибок; лечится exponential backoff с потолком + jitter (расфазировка синхронных волн клиентов) + Circuit Breaker (Closed → Open → Half-open) против thundering herd. Retry уместен ТОЛЬКО для временных сбоев (сеть, 503/504/429), не для ошибок валидации/логики — повторный запрос с невалидными данными просто повторит ошибку. Источники: 4 ошибки в 3 строках Polly, когда retry ухудшает систему. 🔜 Life Notes Фаза 2/5 — Polly в курсе был упомянут одной строкой внутри HttpClientFactory. Ошибка №4 (порядок политик) — сильный ответ на "а вы Polly реально настраивали?".

Q: Какие есть алгоритмы балансировки нагрузки и в чём слабое место каждого следующего по сложности? A: Round Robin — работает только при одинаковых серверах и одинаковой "стоимости" запросов, плохо ведёт себя на p95/p99. Weighted Round Robin — веса руками, статика, не адаптируется. Dynamic Weighted RR — веса считаются из латентности, уже адаптивно. Least Connections — по числу активных соединений, дефолт в AWS и опция в nginx. PEWMA — экспоненциально взвешенное среднее по латентности недавних запросов, самый точный из перечисленных. Источник: балансировка нагрузки 2025 (L4/L7, sticky sessions и consistent hashing НЕ разобраны — если спросят конкретно про них, это отдельная тема). 🔜 Модуль 6 / system design basics — балансировщик в курсе упоминался только как "PgBouncer-подобный пул соединений", алгоритмов распределения нагрузки не было вообще.

Q: Redis — какие есть политики вытеснения при переполнении памяти, и какие есть способы сделать очередь на Redis? A: Eviction policies: volatile-lru/volatile-ttl/volatile-random работают только по ключам с выставленным TTL; allkeys-lru/allkeys-random — по всем ключам вообще. Три способа очереди: Pub/Sub (сообщение получают все текущие подписчики, без подписчиков — теряется безвозвратно), список FIFO через RPUSH/LPOP (один потребитель забирает сообщение), Streams (сообщение хранится, пока явно не подтверждено прочитанным — ближе всего по семантике к Kafka/RabbitMQ). Источник: Redis для кэша и очередей. 🔜 Life Notes / Redis — Redis в Tier 0, но в курсе не разобран вообще. "Что случится, когда у Redis кончится память" — рабочий вопрос на собесе.

Q: Зачем вообще нужен отдельный Redis, если PostgreSQL и так справляется? A: Честный бенчмарк (Go-сервер, k6, 30 млн записей, 2 CPU/8 ГБ): Redis — 11 000+ rps на чтении, PostgreSQL с unlogged-таблицами — 7 400 rps (обычные logged-таблицы просели втрое относительно unlogged). 7 400 rps — это больше полумиллиарда операций в сутки, то есть большинству проектов отдельная зависимость на Redis не нужна ДО этой границы — UNLOGGED TABLE в Postgres часто хватает. Источник: Redis vs Postgres в роли кэша. ✅ Готовый аргумент на частый вопрос "зачем вам тут вообще Redis" — не "так принято", а конкретная граница, после которой он оправдан.

Q: Как устроен гибридный (двухуровневый) кэш в .NET, и в чём была проблема самописного варианта? A: Самописный L1 (локальный, в памяти процесса) + L2 (Redis, общий) кэш даёт ошибки многопоточной синхронизации и проблему инвалидации — L1 на других инстансах приложения не узнаёт вовремя, что L2 изменился. Решение — Microsoft.Extensions.Caching.Hybrid (.NET 9): L1 инвалидируется автоматически при изменении L2. Отдельная фича — инвалидация по тегам (например, отдельно для авторизованных и анонимных пользователей). Источник: гибридный кэш на Redis. 🔜 Life Notes / Redis — объясняет, зачем вообще два уровня кэша и почему инвалидация распределённого кэша сложнее, чем кажется — готовый ответ на "какие проблемы у кэша".

Тестирование и CI/CD

Q: Что такое мутационное тестирование, и почему высокий процент покрытия тестами не гарантирует их качество? A: Покрытие кода тестами показывает, какие СТРОКИ выполнились при прогоне тестов — но не проверяет, ловят ли тесты реальные баги. Мутационное тестирование (Stryker.NET на .NET: dotnet tool install -g dotnet-stryker, работает с xUnit/NUnit/MSTest) вносит в код искусственные "мутации" (меняет + на -, инвертирует булевы значения, удаляет вызовы методов) и проверяет, упадёт ли хоть один тест. Метрика — Mutation Score ("of total" и "of covered" — два разных числа). Реальное ограничение с банковского проекта на миллионы строк: полный прогон занимал ~12 часов, поэтому в CI на каждый коммит не встроить — запускали после релиза на master. Источник: мутационное тестирование на .NET в Газпромбанке. 🔜 Life Notes / unit-тесты — сильный дифференциатор на Middle-собесе: "покрытие 90% ещё не значит, что тесты что-то ловят" + конкретное название инструмента для .NET.

Q: Назови три "продвинутых" приёма Moq, которые отличают "пишу тесты каждый день" от "прошёл туториал". A: Capture.In(collection) — перехват ВСЕХ аргументов вызова в коллекцию (можно проверить и значения, и порядок вызовов, не только последний через колбэк). .Verifiable() + .Verify() — верифицировать только помеченные setup'ы, а не абсолютно все подряд. Mock.Of (LINQ to Mocks) — декларативная настройка мока одним выражением вместо блока инициализации. Источник: малоизвестные фичи Moq. 🔜 Life Notes / unit-тесты — ответить про Capture.In заметно сильнее на собесе, чем про базовый It.IsAny<T>().

Q: Чем Continuous Integration, Continuous Delivery и Continuous Deployment отличаются друг от друга? A: CI — автоматическая проверка (сборка+тесты) каждого изменения. Continuous Delivery — код ВСЕГДА готов к выкатке в прод, но сам релиз запускается вручную. Continuous Deployment — каждый коммит, прошедший тесты, уезжает в прод автоматически, без ручного шага. Канонические стадии пайплайна: Source → Build → Test → Security (SAST/SCA) → Staging → Deploy. По данным DORA, элитные команды деплоят в 208 раз чаще и восстанавливаются после инцидента в 2604 раза быстрее отстающих. Источник: что такое CI/CD. 🔜 Модуль 6 / GitLab CI/CD — этот пункт Tier 0 не был разобран в курсе вообще ни разу. Delivery vs Deployment — классический вопрос-различалка, на котором сыплются даже те, кто пайплайны реально настраивал.

Q: Назови 3-4 практики правильного Dockerfile для .NET-приложения, которые реально спрашивают. A: (1) Порядок COPY под кэш слоёв — зависимости копируются и ставятся ДО кода приложения, иначе любая правка кода инвалидирует слой с зависимостями и пересборка идёт дольше. (2) Multi-stage build — компилятор (SDK-образ) и исходники не должны попадать в финальный образ, только результат публикации на минимальном runtime-образе. (3) Контейнер запускается НЕ от root — отдельный пользователь с явными UID/GID. (4) .dockerignore исключает .git, тесты, README, секреты из контекста сборки. Источник: Dockerfile — больше чем FROM и RUN. 🔜 Life Notes / Docker — Docker в Tier 0, стандартный вопрос, если в резюме заявлен Docker: "а зачем multi-stage build и почему не от root".

Q: Какие типичные ошибки деплоя реально ломают прод — и какими конкретными настройками их лечат? A: Смешение readinessProbe (готов принимать трафик) и livenessProbe (процесс жив, не завис) на один эндпоинт — лечится РАЗНЫМИ эндпоинтами /health и /alive + initialDelaySeconds для медленно стартующих сервисов. Тег latest в проде — при инциденте физически некуда откатиться, нужен семвер или хеш коммита. Общие секреты между окружениями dev/staging/prod — раздельные пути в Secret Manager. Источник: топ-5 ошибок деплоя, Газпромбанк. ✅ Инфраструктурное дополнение к уже существующему в курсе кейсу "миграция без даунтайма через expand-and-contract" (собес #2) — как выкатывается сам сервис, не только схема БД.

Поколения Garbage Collector — закрывает явный пробел из раздела 14

Q: Опиши, как GC делит объекты на поколения и почему. A: Идея — "большинство объектов живут недолго" (weak generational hypothesis). Gen 0 — новые объекты, собирается чаще всего и быстрее всего. Gen 1 — буфер между Gen 0 и Gen 2, пережившие одну сборку Gen 0. Gen 2 — долгоживущие объекты, сборка самая дорогая (сканирует больше). Фазы сборки: Stop-The-World → маркировка достижимых объектов от корней → удаление недостижимых → компактизация (сдвиг живых объектов, чтобы не было фрагментации). LOH (Large Object Heap) — объекты >85 КБ, живёт отдельно от Gen 0/1/2 и НЕ компактится по умолчанию (дорого двигать большие объекты) — источник фрагментации на долгоживущих сервисах. Server GC (несколько потоков, по потоку на ядро, для throughput) vs Workstation GC (для отзывчивости UI) — оба могут работать в background-режиме (не полностью Stop-The-World). Источник: Garbage Collector в .NET. ✅ Закрывает явно отмеченный в разделе 14 (сводка пробелов) пункт "Поколения GC — не разбирались явно", с частотой 900-1900+ использований в банке Ozon за отдельные аспекты этой темы.

Оконные функции — закрывает пробел из сводки (источник: YouTube, Артём Шумейко)

Q: Чем оконная функция принципиально отличается от GROUP BY? A: GROUP BY СЖИМАЕТ данные — группа строк схлопывается в одну агрегированную. Оконная функция (OVER (PARTITION BY ... ORDER BY ...)) данные НЕ сжимает — все исходные строки остаются на месте, но агрегат считается отдельно внутри каждого окна (партиции). Даёт то, что GROUP BY в принципе не может — например, ранжирование строк внутри группы без потери самих строк. ✅ Закрывает явно отмеченный в сводке пробелов пункт "Оконные функции" (1453 использования в банке Ozon).

Q: Как найти дубликаты, если важно понять, какая запись оригинал, а какие — повторы (например, отличается только timestamp)? A: ROW_NUMBER() OVER (PARTITION BY <совпадающие поля> ORDER BY <дата или id>). Строка с ROW_NUMBER() = 1 — оригинал (самая ранняя по сортировке), всё, что > 1 — дубликаты. Если просто нужно найти сам факт дублирования строк целиком (не важно, какая из них "оригинал") — достаточно GROUP BY по всем колонкам + HAVING COUNT(*) > 1, оконная функция не нужна.

Q: Когда EXISTS лучше, чем JOIN? A: Когда нужен только факт существования связанной записи (например, "есть ли у пользователя платёж"), а сами данные из связанной таблицы не нужны. JOIN в этом случае тащит лишние данные и рискует размножить строки, если соединяемая колонка не уникальна (у пользователя с 10 заказами после LEFT JOIN orders будет 10 копий строки пользователя). WHERE EXISTS (SELECT 1 FROM ...) даёт сопоставимую скорость, но без побочных эффектов и читается яснее.

Q: Почему NOT IN может внезапно вернуть 0 строк там, где ожидались строки? A: Если в наборе значений для NOT IN есть NULL (частая история при работе с джойнами) — из-за трёхзначной логики SQL (сравнение с NULL всегда даёт NULL, не TRUE/FALSE) вся конструкция NOT IN возвращает NULL для КАЖДОЙ строки — молчаливо пустой результат вместо ошибки. Решение: профильтровать NULL из набора заранее, либо использовать NOT EXISTS — там этой ловушки нет. 🔜 Модуль 6 — классическая, но легко забываемая ловушка; хороший конкретный ответ на "какие грабли в SQL встречали".
