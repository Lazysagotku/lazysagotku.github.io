🎭 Аналогия

Ресепшн в бизнес-центре. Посетитель не бегает по этажам в поисках нужной компании - он говорит на ресепшене, кого ему надо, и его направляют. Клиент видит одну дверь, за ней может быть что угодно.

🗺 Карта мест

Сделать: поставить nginx перед сервисом hello из слоя 0, дать серверу имя (sslip.io, без покупки домена), выпустить сертификат Let's Encrypt, настроить логи с полезным форматом.

Понять: nginx - единственная дверь снаружи. Клиент стучится в 443, nginx проверяет TLS и передаёт запрос сервису, который слушает только 127.0.0.1:8000. Сертификат живёт на nginx, приложение о HTTPS не знает.

Где писать: /etc/nginx/sites-available/hello и симлинк в sites-enabled/; формат логов - в /etc/nginx/nginx.conf; сертификат - командой certbot, файлы кладутся в /etc/letsencrypt/.

Чем запустить: sudo nginx -t && sudo systemctl reload nginx - сначала проверка синтаксиса, потом перечитать конфиг без обрыва соединений. Сертификат: sudo certbot --nginx -d домен.

Где смотреть результат:

curl -I https://домен            # код ответа и заголовки через HTTPS
curl -I http://домен             # должен быть 301 на https
sudo tail -f /var/log/nginx/access.log /var/log/nginx/error.log
systemctl status nginx
sudo certbot certificates        # срок действия сертификата

Как понять, что получилось: в браузере замок без предупреждений; остановил hello - nginx отдаёт 502, а в error.log написано, почему; curl по http уходит на https.

📖 Теория

Forward против reverse

О чём: forward proxy прячет клиента, reverse proxy прячет серверы; nginx перед приложением - второе.

Forward proxy Reverse proxy
Кого прячет клиента от сервера сервер от клиента
Кто настраивает клиент у себя владелец сервиса
Пример корпоративный прокси, VPN nginx перед приложением
Знает ли клиент да, он его прописал нет, для него это и есть сайт

⚠️ Их путают чаще всего. Вопрос звучит буквально: «чем forward отличается от reverse». Отвечать через направление: forward защищает того, кто ходит, reverse защищает того, к кому ходят.

Зачем reverse proxy нужен: - один вход на 80 и 443, за ним сколько угодно приложений; - TLS терминируется в одном месте; - балансировка между экземплярами; - отдача статики без участия приложения - nginx делает это в разы быстрее; - ограничение скорости и защита от медленных клиентов; - единая точка логирования всех запросов.

Иерархия конфига

О чём: http → server → location: настройка наследуется вниз и переопределяется на месте.

http {                      # общие настройки
    upstream tracker {      # группа бэкендов
        server 127.0.0.1:8000;
        server 127.0.0.1:8001;
    }
    server {                # виртуальный хост
        listen 443 ssl;
        server_name tracker.example.ru;
        location / {        # правило для группы путей
            proxy_pass http://tracker;
        }
    }
}

Как выбирается server: по паре «порт + server_name». Если ни один не подошёл - первый с default_server или просто первый. Отсюда «открываю по IP, а показывается чужой сайт».

Как выбирается location - по приоритету, а не по порядку в файле:

  1. location = /path - точное совпадение, побеждает сразу;
  2. location ^~ /path - префикс, отключает проверку регулярок;
  3. location ~ регулярка и ~* - регулярки, первая совпавшая по порядку;
  4. location /path - самый длинный совпавший префикс.

Ключевое: регулярки проверяются после префиксов, но при совпадении побеждают их.

Заголовки - почему это отдельный вопрос

О чём: за прокси приложение видит адрес nginx, а не клиента; X-Real-IP и X-Forwarded-For это чинят.

Без proxy_set_header приложение видит IP прокси вместо IP клиента. Все логи заполняются адресом 127.0.0.1, блокировки по IP не работают, геолокация врёт.

Заголовок Что несёт
Host какое имя запросил клиент
X-Real-IP адрес клиента одной строкой
X-Forwarded-For цепочка всех прокси по пути
X-Forwarded-Proto http или https, иначе приложение построит ссылки на http

⚠️ X-Forwarded-For подделывается клиентом. Доверять ему можно только для прокси из своего контура - директива set_real_ip_from.

TLS и certbot

О чём: сертификат выдаётся на имя, живёт 90 дней, продлевается сам; TLS заканчивается на nginx.

Аналогия. Нотариально заверенный паспорт. Ключ доказывает, что домен твой, а подпись центра сертификации - что паспорт настоящий.

Сертификат Let's Encrypt живёт 90 дней, продление автоматическое за 30 дней до конца.

Как проходит проверка владения (HTTP-01): certbot кладёт файл в /.well-known/acme-challenge/, центр сертификации ходит за ним по 80 порту. Отсюда правило: 80 порт нельзя закрывать целиком, иначе продление отвалится. Редирект на https не мешает, полное закрытие мешает.

Балансировка

О чём: upstream с несколькими серверами и проверка живости - как nginx выводит упавший из ротации.

Директива Как раздаёт Когда нужна
по умолчанию round-robin, по кругу одинаковые бэкенды без состояния
least_conn; тому, у кого меньше активных запросы разной длительности
ip_hash; один клиент всегда на один бэкенд липкие сессии в памяти приложения
hash $request_uri; по ключу кэширование по пути

Пассивные проверки есть в бесплатной версии: max_fails=3 fail_timeout=30s. Три неудачи подряд - бэкенд выводится из ротации на 30 секунд.

⚠️ Активные health checks есть только в коммерческом Nginx Plus. Знание границы - хороший ответ.

Коды ответа - разбор по причинам

О чём: 502 - за nginx никого, 504 - есть, но молчит, 499 - клиент не дождался; по коду видно слой проблемы.

502 Bad Gateway. Nginx достучался до бэкенда и получил мусор либо не достучался вовсе. Проверять: жив ли сервис, слушает ли порт, отвечает ли curl localhost, что в error.log. Типичные причины: приложение упало; слушает не на том адресе; опечатка в порту proxy_pass.

504 Gateway Timeout. Бэкенд жив, но не ответил за таймаут. Причины: тяжёлый запрос к базе, блокировка, внешний вызов без таймаута, нехватка воркеров. Лечится не повышением proxy_read_timeout - это прячет симптом, очередь растёт дальше. Сначала найти медленный запрос.

499. Клиент закрыл соединение, не дождавшись. Код придуман nginx. Много 499 означает, что пользователи устают ждать - фактически тот же 504 со стороны клиента.

413. client_max_body_size меньше загружаемого файла. По умолчанию 1 мегабайт.

403 и 404 на статике. Права либо путаница root и alias:

location /static/ { root  /opt/tracker; }          # ищет /opt/tracker/static/file
location /static/ { alias /opt/tracker/assets/; }  # ищет /opt/tracker/assets/file

root дописывает путь из запроса, alias заменяет совпавший префикс.

🔧 Практика

Предпосылки. Слой 0 закрыт: файрвол пропускает 22, 80 и 443, сервис hello из слоя 0 слушает 127.0.0.1:8000. Он и будет «приложением за nginx» - трекер приедет в слое 2, и конфиг для него отличается одной строкой. Каждый шаг: что делаем → команды с комментариями → что должно показаться.

1. Поставить nginx и понять, где он живёт

sudo apt update && sudo apt install -y nginx   # поставить из репозитория Ubuntu
systemctl status nginx                          # уже запущен: active (running)
ss -tlnp | grep nginx                           # слушает 0.0.0.0:80 - весь мир
curl -I localhost                               # HTTP/1.1 200 OK и заголовок Server: nginx

С компа открой http://сервер в браузере - страница «Welcome to nginx». Это дефолтный сайт, его сейчас заменим.

Где что лежит:

ls /etc/nginx/                    # nginx.conf - главный конфиг, он подключает всё остальное
ls /etc/nginx/sites-available/    # здесь лежат конфиги сайтов - все, включая выключенные
ls -l /etc/nginx/sites-enabled/   # здесь символические ссылки на включённые; default - тот самый Welcome
ls /var/log/nginx/                # access.log - каждый запрос, error.log - проблемы

Логика папок: конфиг пишется в sites-available, включается ссылкой в sites-enabled. Выключить сайт - удалить ссылку, файл остаётся.

2. Первый конфиг: nginx перед hello

Что делаем. Снаружи стучатся в nginx на 80, он передаёт запрос сервису на 127.0.0.1:8000 и возвращает ответ. Это и есть reverse proxy.

sudo nano /etc/nginx/sites-available/hello

server {
    listen 80;                          # на каком порту принимать
    server_name _;                      # для какого имени; _ означает «любое», домена пока нет

    access_log /var/log/nginx/hello_access.log;   # свои логи, чтобы не искать в общих
    error_log  /var/log/nginx/hello_error.log warn;

    location / {                        # все пути
        proxy_pass http://127.0.0.1:8000;          # куда передавать - наш сервис
        proxy_set_header Host $host;                # передать сервису, к какому имени обращались
        proxy_set_header X-Real-IP $remote_addr;    # и настоящий адрес клиента - иначе сервис видит 127.0.0.1
        proxy_connect_timeout 5s;                   # сколько ждать соединения с сервисом
        proxy_read_timeout 60s;                     # сколько ждать ответа
    }
}

Включить свой сайт, выключить дефолтный, проверить, применить:

sudo ln -s /etc/nginx/sites-available/hello /etc/nginx/sites-enabled/hello   # ln -s - символическая ссылка
sudo rm /etc/nginx/sites-enabled/default                                    # убрать Welcome
sudo nginx -t                    # проверить синтаксис: syntax is ok, test is successful
sudo systemctl reload nginx      # перечитать конфиг без разрыва соединений

Всегда -t перед reload. Битый конфиг при restart уронит сайт, при reload nginx откажется применять и оставит старый рабочий.

Окно результата:

curl localhost                              # «стенд живой» - ответ hello пришёл через nginx
sudo tail -3 /var/log/nginx/hello_access.log   # твой запрос записан: адрес, путь, код 200

С компа: http://сервер в браузере показывает «стенд живой». Сервис при этом слушает только 127.0.0.1 - снаружи к нему попасть можно только через nginx, ровно как задумано.

3. Имя и сертификат

Что делаем. HTTPS нужен сертификат, сертификат выдаётся на имя, а не на IP. Домен покупать не обязательно: сервис sslip.io превращает IP в имя - 104-171-139-80.sslip.io резолвится в 104.171.139.80 сам, без регистрации. Let's Encrypt такие имена подписывает. Купишь домен - заменишь имя в одной строке.

nslookup 104-171-139-80.sslip.io     # подставь свой IP через дефисы; ответ - твой адрес

В конфиге server_name _; заменить на своё имя:

    server_name 104-171-139-80.sslip.io;

sudo nginx -t && sudo systemctl reload nginx

Сертификат выпускает certbot: он сам проверит, что имя ведёт на этот сервер, сам получит сертификат и сам допишет в конфиг блок для 443:

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d 104-171-139-80.sslip.io   # спросит почту и согласие; на вопрос про редирект - 2 (redirect)
sudo cat /etc/nginx/sites-available/hello           # посмотри, что certbot дописал: listen 443 ssl, пути к ключам, редирект с 80
sudo certbot renew --dry-run                        # проверка, что автопродление сработает через 90 дней

Окно результата:

curl -I http://104-171-139-80.sslip.io      # 301 - редирект на https
curl -I https://104-171-139-80.sslip.io     # 200 - через HTTPS
sudo certbot certificates                   # имя, срок действия, пути

В браузере - замок без предупреждений.

4. Логи с полезным форматом

Что делаем. Стандартный формат лога не показывает, сколько времени занял запрос и сколько из него думал сервис. Добавляем свой формат - это первое, что нужно при разборе «сайт тормозит».

В /etc/nginx/nginx.conf, внутри блока http { ... }, до строки include /etc/nginx/sites-enabled/*;:

    log_format detailed '$remote_addr - $host "$request" '
                        '$status $body_bytes_sent '
                        'rt=$request_time urt=$upstream_response_time '
                        '"$http_user_agent"';

В конфиге сайта строку access_log дополнить именем формата:

    access_log /var/log/nginx/hello_access.log detailed;

sudo nginx -t && sudo systemctl reload nginx
curl -s https://104-171-139-80.sslip.io > /dev/null
sudo tail -1 /var/log/nginx/hello_access.log     # в конце строки rt=0.002 urt=0.001

rt - весь запрос от клиента до ответа, urt - сколько думал сервис за nginx. Большая разница между ними означает, что время ушло в самом nginx или на медленного клиента, а не в приложении.

5. Четыре однострочника разбора логов

Учить наизусть - на собеседовании просят написать на доске. Каждая - конвейер: взять колонку → отсортировать → посчитать одинаковые → отсортировать по числу.

awk '{print $9}' hello_access.log | sort | uniq -c | sort -rn          # коды ответа: сколько 200, сколько 502
awk '{print $7}' hello_access.log | sort | uniq -c | sort -rn | head   # самые частые URL
awk '{print $1}' hello_access.log | sort | uniq -c | sort -rn | head   # самые активные IP - кто долбит
grep -oP 'rt=\K[0-9.]+' hello_access.log | sort -rn | head             # самые медленные запросы

awk '{print $N}' - взять N-ю колонку, uniq -c - схлопнуть одинаковые соседние строки и посчитать, sort -rn - по числу, по убыванию. Номера колонок зависят от формата лога: в detailed код ответа стоит седьмым, посчитай по своей строке.

Сгенерируй себе материал: for i in $(seq 1 50); do curl -s -o /dev/null https://104-171-139-80.sslip.io/page$((i % 5)); done - и прогони четыре команды.

6. Когда приедет трекер

В слое 2 конфиг для трекера - копия этого файла с другим именем сервера и той же строкой proxy_pass http://127.0.0.1:8000. Балансировка на два экземпляра через upstream - в теории слоя, на стенде это лишнее до появления второго экземпляра.

💥 Сломай намеренно

Предпосылки: nginx с сертификатом отдаёт hello, логи в формате detailed. Ломаем - смотрим, как выглядит - чиним.

1. Получить 502 своими руками:

sudo systemctl stop hello
curl -I https://104-171-139-80.sslip.io           # 502 Bad Gateway
sudo tail -3 /var/log/nginx/hello_error.log       # connect() failed (111: Connection refused) while connecting to upstream
sudo systemctl start hello

Запомни эту строку в error.log: 502 всегда означает «nginx жив, за ним никого нет».

2. Получить 504. В конфиге сайта поставить proxy_read_timeout 2s;, применить. Сервис hello не умеет спать, поэтому сымитируй медленный бэкенд: sudo systemctl stop hello, потом в отдельном окне python3 -c "import socket,time; s=socket.socket(); s.bind(('127.0.0.1',8000)); s.listen(1); c,_=s.accept(); time.sleep(10)" - сервер принимает соединение и молчит. curl -I https://... через две секунды даст 504 Gateway Time-out. Вернуть таймаут, запустить hello.

3. Убрать строку X-Real-IP, применить, и посмотреть в journalctl -u hello -n 3: сервис видит 127.0.0.1 вместо твоего адреса. Вернуть.

4. Сломать конфиг: убрать точку с запятой в любой строке, sudo nginx -t - текст ошибки с номером строки. Заметь: сайт при этом продолжает работать на старом конфиге. Вернуть.

5. Закрыть 443 в файрволе: sudo ufw deny 443/tcp, curl -I https://... с компа висит и падает по таймауту, а curl -I http://... отвечает 301. Так выглядит «сертификат в порядке, а сайт недоступен» - проблема не в nginx. sudo ufw allow 443/tcp.

6. Уронить nginx целиком: sudo systemctl stop nginx, curl -I http://... - Connection refused, без кода ответа вообще. Разница между «refused» (никто не слушает) и 502 (слушает nginx, а за ним пусто) - вопрос на любом собеседовании по эксплуатации.

🧪 Проверь себя

1. curl -I https://сайт отвечает 502. Что это значит? - [ ] сертификат просрочен - [ ] nginx не запущен - [x] nginx жив, а приложение за ним не отвечает на соединение - [ ] клиент закрыл соединение

Почему: 502 Bad Gateway - nginx не смог соединиться с upstream. В error.log будет connect() failed ... upstream.

2. Чем 504 отличается от 502? - [x] при 504 приложение соединение приняло, но не ответило за proxy_read_timeout - [ ] 504 - это ошибка сертификата - [ ] ничем, оба про недоступный бэкенд - [ ] 504 возвращает клиент, 502 - сервер

Почему: 502 - за nginx никого, 504 - есть, но молчит. Лечится по-разному: перезапуск против поиска медленного запроса.

3. Почему nginx -t надо делать перед reload, если reload и так не применит битый конфиг? - [ ] потому что reload применяет всё без проверки - [x] чтобы прочитать ошибку с номером строки сразу, а не искать её в error.log после - [ ] потому что без -t reload зависает - [ ] это требование certbot

Почему: reload при ошибке откажет и оставит старый конфиг. -t показывает, что именно не так, и делает это до того, как ты что-то тронул.

4. Приложение за nginx пишет в логи адрес 127.0.0.1 у всех клиентов. Что не так? - [ ] приложение слушает не тот порт - [x] в location нет proxy_set_header X-Real-IP $remote_addr - [ ] nginx не может определить адрес клиента через TLS - [ ] так и должно быть за прокси

Почему: для приложения клиентом является nginx. Настоящий адрес передаётся заголовком, его надо добавить руками.

5. В логах много 499. Что происходит? - [ ] nginx не может отдать статику - [ ] сертификат не доверен клиентам - [x] клиенты закрывают соединение, не дождавшись ответа - сайт медленный - [ ] превышен client_max_body_size

Почему: 499 придумал nginx для «клиент ушёл раньше ответа». Это 504 глазами пользователя: смотреть urt в логах.

🌍 Из жизни

Про закрытый 80 порт. Классическая история: команда закрывает 80 «для безопасности», через три месяца сертификат истекает, сайт падает. Причину ищут часами, потому что связь между закрытым портом и сертификатом неочевидна.

Про reload вместо restart. На проде под трафиком restart рвёт все активные соединения. Пользователи видят обрыв загрузки. reload поднимает новые воркеры с новым конфигом и даёт старым доработать текущие запросы. Разница слышна на собеседовании сразу.

Про повышение таймаута. Самое частое «лечение» 504 - поднять proxy_read_timeout до 300 секунд. Симптом уходит, а очередь растёт: медленный запрос теперь держит соединение впятеро дольше, и при нагрузке всё встаёт целиком. Правильный ответ на собеседовании - «сначала нахожу, что медленно, таймаут поднимаю осознанно».

❓ Вопросы с ответами

Чем forward отличается от reverse?

Направлением защиты. Forward прячет клиента и настраивается на его стороне. Reverse прячет сервер, стоит перед приложением и настраивается владельцем сервиса.

Клиент получает 502. Ваши действия?

Смотрю error.log nginx - там причина одной строкой. Параллельно: жив ли сервис, слушает ли порт, отвечает ли curl localhost. Если локально отвечает, а через nginx нет - смотрю адрес в proxy_pass и права на соединение.

Чем 502 отличается от 504?

502 - бэкенд не ответил или ответил мусором. 504 - ответил бы, но не успел за таймаут. Первое чинится подъёмом сервиса, второе - ускорением запроса.

Как настроить балансировку?

Блок upstream, по умолчанию round-robin. least_conn для запросов разной длительности, ip_hash если нужны липкие сессии. Пассивные проверки через max_fails и fail_timeout.

Зачем X-Forwarded-For?

Чтобы приложение видело настоящий IP клиента. Без него все логи забиты адресом прокси, а блокировки по IP не работают.

Как перезагрузить конфиг без разрыва соединений?

nginx -t, потом systemctl reload nginx. Reload поднимает новые воркеры и даёт старым доработать текущие запросы.

Что будет, если закрыть 80 при работающем https?

Перестанет продлеваться сертификат Let's Encrypt - проверка владения ходит по 80. Редирект держать можно, закрывать порт нельзя.

Как понять, тормозит бэкенд или сам nginx?

Сравниваю $request_time и $upstream_response_time в логе. Близки - время съел бэкенд. request_time заметно больше - дело в nginx или в медленном клиенте.
