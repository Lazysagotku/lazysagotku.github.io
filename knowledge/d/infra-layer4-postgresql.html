🎭 Аналогия

Разница между водителем и механиком. Писать SQL умеет водитель: сел, поехал, доехал. Держать базу живой умеет механик - он смотрит под капот, знает, что греется, и меняет масло до поломки.

Вторая аналогия, для MVCC. Черновик с правками. При исправлении строки Postgres не стирает старую версию, а пишет новую и помечает старую отмершей. Пока идущие транзакции могут её видеть, она лежит. Уборщик приходит потом.

Третья, для планировщика. Навигатор. EXPLAIN показывает предполагаемый маршрут, EXPLAIN ANALYZE прогоняет машину и говорит, сколько заняло на самом деле. Пробки видны только во втором случае.

🗺 Карта мест

Сделать: увидеть, что в базе прямо сейчас; прочитать план запроса и ускорить его индексом; регламентный расчёт джобом; бэкап и восстановление в отдельную базу.

Понять: база - это процессы и файлы, как любой сервис. План запроса объясняет «почему медленно» лучше любой догадки. Три причины большинства инцидентов с базой: блокировки, раздувание таблиц без VACUUM, кончившиеся соединения.

Где писать: SQL и служебные запросы - в psql; настройки - ALTER SYSTEM SET или postgresql.conf; джобы - pg_cron или crontab; бэкап - скрипт с pg_dump (или pgBackRest).

Чем запустить: psql -U пользователь -d база; внутри \timing on, потом EXPLAIN (ANALYZE, BUFFERS) запрос;. После смены конфига - sudo systemctl restart postgresql (часть параметров - SELECT pg_reload_conf(); без рестарта).

Где смотреть результат:

SELECT pid, state, wait_event, query FROM pg_stat_activity WHERE state <> 'idle';  -- кто что делает
SELECT * FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;         -- самые тяжёлые запросы
SELECT * FROM pg_locks WHERE NOT granted;                                          -- кто кого ждёт

Логи: /var/log/postgresql/. Метрики: postgres_exporter в Grafana.

Как понять, что получилось: один и тот же запрос в EXPLAIN ANALYZE до индекса - Seq Scan и сотни миллисекунд, после - Index Scan и единицы; копия, поднятая из бэкапа, отвечает на SELECT count(*) тем же числом, что оригинал.

📖 Теория

Как Postgres устроен внутри

Компонент Что делает Почему это важно знать
Backend-процесс по одному на каждое соединение тысяча соединений = тысяча процессов, отсюда нужен пул
shared_buffers кэш страниц в памяти обычно 25% ОЗУ, больше не всегда лучше
WAL журнал упреждающей записи сначала пишем в журнал, потом в файлы данных
Checkpointer сбрасывает грязные страницы на диск всплеск ввода-вывода в момент чекпоинта
Autovacuum убирает мёртвые версии строк не справился - таблица распухла
WAL sender шлёт журнал на реплики основа потоковой репликации

Зачем WAL. Запись в журнал последовательная и быстрая, запись в файлы данных случайная и медленная. Сначала фиксируем изменение в журнале, отвечаем клиенту, а страницы сбрасываем позже. При падении база проигрывает журнал и восстанавливается. Тот же журнал уезжает на реплики и в архив для восстановления на точку времени.

Чтение плана - что смотреть по порядку

EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

⚠️ ANALYZE действительно выполняет запрос. Для UPDATE и DELETE оборачивать:

BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;
  1. Seq Scan там, где ждал Index Scan. Полный проход. Причины: индекса нет; индекс есть, но не подходит под условие; планировщик решил, что строк много и последовательное чтение дешевле.
  2. Расхождение rows= оценённых и actual rows=. Мимо в разы - статистика устарела, нужен ANALYZE таблица. Планировщик решает по статистике, и врущая статистика даёт плохой план при живых индексах.
  3. Nested Loop на больших объёмах. Для маленьких выборок норма, для больших обычно и есть тормоз.
  4. Rows Removed by Filter. Прочитали много, выкинули почти всё - явный признак недостающего индекса.
  5. BUFFERS: shared read против shared hit. hit из кэша, read с диска. Много read означает, что данные не помещаются в память.
Узел Что делает Когда тревожно
Seq Scan читает таблицу целиком на большой таблице с узким фильтром
Index Scan по индексу, потом в таблицу норма
Index Only Scan всё нужное есть в индексе лучший случай
Bitmap Heap Scan битмап по индексу, потом страницы норма при средней выборке
Nested Loop для каждой строки слева ищет справа плохо на больших объёмах
Hash Join строит хеш-таблицу норма
Sort сортирует смотреть Sort Method: external merge Disk плохо

🔥 Оптимизация на конкретных примерах

Это то, что просят разобрать вслух. Каждый случай надо узнавать по симптому.

Случай 1. Функция на колонке убивает индекс.

-- ПЛОХО: индекс по created_at не используется
SELECT * FROM events WHERE date(created_at) = '2026-09-10';

-- ХОРОШО: диапазон, индекс работает
SELECT * FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';

Обычный индекс хранит значения колонки, а не результат функции от неё. Альтернатива - индекс по выражению: CREATE INDEX ON events (date(created_at));

Случай 2. Поиск по подстроке.

-- btree не работает: совпадение не с начала
SELECT * FROM users WHERE name ILIKE '%иван%';

Решение - триграммный индекс:

CREATE EXTENSION pg_trgm;
CREATE INDEX ON users USING gin (name gin_trgm_ops);

Для ILIKE 'иван%' (совпадение с начала) хватит обычного btree с классом text_pattern_ops.

Случай 3. OFFSET на глубоких страницах.

-- ПЛОХО: чтобы отдать 20 строк, читает и выбрасывает 100000
SELECT * FROM vacancies ORDER BY id LIMIT 20 OFFSET 100000;

-- ХОРОШО: keyset pagination, читает ровно 20
SELECT * FROM vacancies WHERE id > 100000 ORDER BY id LIMIT 20;

Время OFFSET растёт линейно с номером страницы. На больших таблицах последние страницы открываются секундами.

Случай 4. OR мешает планировщику.

-- ПЛОХО: часто уходит в Seq Scan
SELECT * FROM finds WHERE employer = 'Сбер' OR name = 'DevOps';

-- ХОРОШО: два индекса работают по отдельности
SELECT * FROM finds WHERE employer = 'Сбер'
UNION
SELECT * FROM finds WHERE name = 'DevOps';

Случай 5. COUNT(*) на большой таблице. Postgres обязан посчитать честно из-за MVCC - у разных транзакций разное число видимых строк. На миллионах это секунды.

-- приблизительно и мгновенно
SELECT reltuples::bigint FROM pg_class WHERE relname = 'finds';

Для точного счёта на горячих таблицах держат отдельный счётчик, обновляемый триггером.

Случай 6. Порядок полей в составном индексе. Индекс (a, b, c) работает для условий по a, по a, b, по a, b, c. Для условия только по b он бесполезен - это правило левого префикса.

-- под запрос WHERE status = 'new' ORDER BY found_at DESC
CREATE INDEX ON finds (status, found_at DESC);

Сначала колонка с равенством, потом колонка сортировки. Так индекс закрывает и фильтр, и ORDER BY.

Случай 7. N+1. Приложение делает один запрос за списком и потом по запросу на каждый элемент. Сто элементов - сто один запрос. Лечится JOIN или загрузкой пачкой через WHERE id = ANY($1).

Случай 8. Частичный индекс.

-- если запросы всегда с этим условием
CREATE INDEX ON finds (found_at) WHERE status = 'new';

Меньше по размеру, быстрее, дешевле в обслуживании.

Чем индексы вредят. Каждый замедляет INSERT, UPDATE, DELETE и занимает место. Неиспользуемые надо находить:

SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

🕐 Джобы: регламентные расчёты

Для АСУ управления рыночными рисками это центральная тема. Расчёт риска идёт заданиями по расписанию: переоценка позиций на закрытие дня, пересчёт лимитов, стресс-тесты. Вопрос «что происходит, когда расчёт не успевает к сроку» - почти наверняка прозвучит.

Где живут джобы:

Механизм Где Плюсы Минусы
pg_cron расширение внутри Postgres расписание рядом с данными, ничего не поднимать джоба падает вместе с базой, нет сложных зависимостей
cron ОС системный планировщик просто, привычно урезанное окружение, нет зависимостей
systemd timer системный логи в journald, зависимости, Persistent только на одной машине
Airflow, Nifi отдельный оркестратор графы зависимостей, повторы, история целая система в обслуживании

pg_cron на практике:

CREATE EXTENSION pg_cron;

-- пересчёт витрины каждую ночь в 02:00
SELECT cron.schedule('refresh-risk', '0 2 * * *',
                     $$ REFRESH MATERIALIZED VIEW CONCURRENTLY risk_summary $$);

-- чистка старого раз в неделю
SELECT cron.schedule('cleanup', '0 3 * * 0',
                     $$ DELETE FROM events WHERE happened_at < now() - interval '180 days' $$);

-- посмотреть расписание и историю
SELECT * FROM cron.job;
SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 20;

SELECT cron.unschedule('cleanup');

Пять правил джобы, которые надо назвать вслух:

  1. Идемпотентность. Повторный запуск не должен ломать и плодить. В загрузке это ON CONFLICT DO NOTHING, в пересчёте - полная перезапись периода вместо дописывания.
  2. Защита от наложения. Джоба идёт дольше интервала - запустятся две копии. В ОС это flock -n, внутри базы - консультативная блокировка: sql SELECT pg_try_advisory_lock(42); -- false означает «уже идёт, выхожу»
  3. Отметка о выполнении. Отдельная таблица с началом, концом, статусом и числом обработанных строк. Без неё невозможно ответить, отработала джоба или нет.
  4. Пачками, а не одной транзакцией. Обновление миллиона строк одной транзакцией держит блокировки часами и раздувает таблицу. Резать на пачки по несколько тысяч с коммитом.
  5. Мониторинг двух видов. Первый - «упала». Второй, который забывают, - «не запустилась». Молчащая джоба выглядит как здоровая, пока кто-то не заметит устаревшие данные.

Таблица учёта запусков:

CREATE TABLE job_runs (
    id          bigserial PRIMARY KEY,
    job_name    text NOT NULL,
    started_at  timestamptz NOT NULL DEFAULT now(),
    finished_at timestamptz,
    status      text NOT NULL DEFAULT 'running',
    rows_done   bigint,
    error       text
);

-- алерт: джоба не отработала за последние сутки
SELECT 'refresh-risk' AS job
WHERE NOT EXISTS (
    SELECT 1 FROM job_runs
    WHERE job_name = 'refresh-risk'
      AND status = 'ok'
      AND finished_at > now() - interval '25 hours'
);

Обработка пачками:

DO $$
DECLARE
    moved integer;
BEGIN
    LOOP
        WITH batch AS (
            SELECT id FROM events
            WHERE happened_at < now() - interval '180 days'
            LIMIT 5000
        )
        DELETE FROM events WHERE id IN (SELECT id FROM batch);
        GET DIAGNOSTICS moved = ROW_COUNT;
        EXIT WHEN moved = 0;
        COMMIT;
    END LOOP;
END $$;

«Что делать, когда расчёт не успевает к сроку» - готовый ответ:

Сначала смотрю, это разовое отставание или тренд. Разовое - ищу, что помешало: блокировка от чужой транзакции, всплеск объёма, соседняя нагрузка. Тренд означает, что джоба переросла окно, и надо либо ускорять запрос, либо резать на части, либо переносить окно.

Параллельно поднимаю вопрос про регламент: кого и когда уведомляем, есть ли деградированный режим - отдать вчерашние цифры с пометкой вместо ничего. Это решение бизнеса, но задать вопрос должен сопровождающий.

Что происходит в базе прямо сейчас

SELECT pid, usename, state, wait_event_type, wait_event,
       now() - query_start AS длительность,
       left(query, 120) AS запрос
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
state Значение Тревога
active выполняет запрос смотреть длительность
idle простаивает между запросами норма
idle in transaction транзакция открыта, работы нет держит блокировки, мешает vacuum
idle in transaction (aborted) транзакция сломалась, никто не откатил то же самое

⚠️ idle in transaction - причина номер один ситуации «база встала без нагрузки». Пока такая транзакция жива, autovacuum не может убирать мёртвые строки во всей базе.

-- висящие дольше пяти минут
SELECT pid, now() - state_change AS висит, left(query, 100)
FROM pg_stat_activity
WHERE state LIKE 'idle in transaction%'
  AND now() - state_change > interval '5 minutes';

SELECT pg_cancel_backend(pid);     -- отменить запрос, сессия жива
SELECT pg_terminate_backend(pid);  -- закрыть соединение целиком

Блокировки

Аналогия. Очередь в одну кабинку. Проблема не в тех, кто стоит, а в том, кто сидит внутри и не выходит.

SELECT blocked.pid    AS ждёт_pid,
       blocked.query  AS ждёт_запрос,
       blocking.pid   AS держит_pid,
       blocking.query AS держит_запрос,
       now() - blocked.query_start AS ждёт_уже
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event_type = 'Lock';

pg_blocking_pids(pid) сразу отдаёт список блокирующих. Знание её вместо ручного разбора pg_locks хорошо смотрится в ответе.

Что блокирует что: - SELECT берёт ACCESS SHARE - почти ничему не мешает; - UPDATE и DELETE берут ROW EXCLUSIVE - мешают изменению тех же строк; - ALTER TABLE, VACUUM FULL, REINDEX берут ACCESS EXCLUSIVE - блокируют даже чтение.

⚠️ Отсюда правило релизов: миграции с ALTER TABLE идут в окно. Даже быстрый ALTER встанет в очередь за долгим SELECT и заблокирует всех, кто пришёл после него - очередь блокировок честная, обгонять нельзя.

SET lock_timeout = '5s';           -- не ждать блокировку дольше
CREATE INDEX CONCURRENTLY ...;     -- строит индекс без блокировки записи

Дедлок - две транзакции держат по ресурсу и просят чужой. Postgres обнаруживает сам и откатывает одну с ошибкой. Профилактика: обращаться к таблицам и строкам в одинаковом порядке во всём коде.

MVCC, VACUUM и bloat

  • VACUUM помечает место от мёртвых версий свободным для повторного использования. Файл не уменьшается.
  • VACUUM FULL перестраивает таблицу и возвращает место системе, но берёт ACCESS EXCLUSIVE - только в окно.
  • autovacuum делает обычный VACUUM сам, по порогам изменённых строк.
SELECT relname,
       n_live_tup AS живых,
       n_dead_tup AS мёртвых,
       round(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS процент_мёртвых,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;

Больше 20 процентов мёртвых и старый last_autovacuum - autovacuum не справляется. Причины: мягкие пороги на горячей таблице; долгая транзакция или idle in transaction; реплика с hot_standby_feedback, удерживающая версии.

ALTER TABLE busy_table SET (autovacuum_vacuum_scale_factor = 0.02);

Wraparound - счётчик транзакций 32-битный, и если vacuum не проходит очень долго, база останавливается для защиты данных. Мониторить через age(datfrozenxid).

Индексы - типы

Тип Для чего
B-tree по умолчанию, сравнения и диапазоны
GIN массивы, JSONB, полнотекстовый и триграммный поиск
GiST геометрия, диапазоны, пересечения
BRIN огромные физически упорядоченные таблицы, логи по времени, дёшев

Уровни изоляции

Уровень Что может случиться В Postgres
Read Uncommitted грязное чтение ведёт себя как Read Committed
Read Committed неповторяемое чтение, фантомы по умолчанию
Repeatable Read фантомов нет благодаря снимку доступен

В Read Committed каждый оператор видит свой свежий снимок, поэтому два SELECT подряд в одной транзакции могут вернуть разное.

Соединения и пул

Каждое соединение - отдельный процесс ОС со своей памятью. Тысяча соединений съест ресурсы, даже простаивая.

Режимы PgBouncer: session - соединение на всю сессию клиента; transaction - на одну транзакцию, самый экономный и самый частый; statement - на один оператор, ломает транзакции.

Резервные копии и репликация

pg_dump -Fc -d база > база.dump      # логический дамп
pg_restore -d база база.dump
pg_basebackup -D /backup -Ft -z      # физическая копия кластера

Логический дамп переносим между версиями, медленный на объёмах, восстановление на точку времени невозможно. Физическая копия плюс WAL-архив - основа восстановления на момент времени (PITR).

Репликация: асинхронная - мастер не ждёт реплику, при аварии возможна потеря последних транзакций. Синхронная - мастер ждёт подтверждения, потери нет, каждая запись медленнее. Выбор - компромисс между скоростью и допустимой потерей.

SELECT client_addr, state, sent_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS отставание_байт
FROM pg_stat_replication;

Что мониторить

-- попадание в кэш, норма выше 95%
SELECT sum(blks_hit) * 100.0 / NULLIF(sum(blks_hit + blks_read), 0) AS cache_hit_pct
FROM pg_stat_database;

-- топ тяжёлых запросов
SELECT round(total_exec_time::numeric, 0) AS всего_мс,
       calls, round(mean_exec_time::numeric, 1) AS среднее_мс,
       left(query, 100)
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 15;

pg_stat_statements включается в shared_preload_libraries. Это главный инструмент поиска того, что жрёт базу - упомянуть обязательно.

Про Pangolin

С Pangolin не работал, он внутри вашего контура. Это PostgreSQL, и всё, что я делал на нём, переносится: планы, блокировки, обслуживание, хранимые процедуры. Интересно, чем ваша сборка отличается от ванильной - расширения, изменения в репликации, что-то по отказоустойчивости?

🔧 Практика на базе трекера

  1. Включить pg_stat_statements, погонять трекер, найти три самых тяжёлых запроса.
  2. EXPLAIN (ANALYZE, BUFFERS) на каждом. Найти хотя бы один Seq Scan и убрать индексом. Записать время до и после - это цифра для собеседования.
  3. Проверить, что индекс реально используется: после создания повторить EXPLAIN и увидеть смену узла.
  4. Воспроизвести три случая оптимизации из списка выше на своих таблицах: функция на колонке, глубокий OFFSET, составной индекс под фильтр плюс сортировку.
  5. Поставить джобу через pg_cron: ночная чистка старых находок в scout.db-подобной таблице трекера, с записью в job_runs и защитой через pg_try_advisory_lock.
  6. Собрать в Grafana панель по базе: соединения, cache hit ratio, мёртвые строки, время последней успешной джобы.
  7. Живой прогон backup/restore, добавлено 15.09 под техсобес. Теория выше (раздел «Резервные копии и репликация») без этого пункта остаётся пересказом документации, а не своим опытом: - pg_dump -Fc -d vacancy_tracker > vacancy_tracker.dump на сервере. - Поднять рядом пустую базу vacancy_tracker_restore_test, pg_restore -d vacancy_tracker_restore_test vacancy_tracker.dump. - Сверить SELECT count(*) FROM vacancies; и companies в обеих базах - числа обязаны сойтись. - Проверить права: \du и \dp vacancies в восстановленной базе - роли переносятся дампом, но не всегда с теми же паролями. - Замерить время дампа и время восстановления секундомером - это и есть RTO этого конкретного стенда на этом объёме данных. RPO - интервал между дампами, если бы это был регламент, а не разовая проверка. - Записать три цифры (размер дампа, время дампа, время восстановления) сюда же в файл - готовый ответ на «как проверяли, что бэкап реально восстанавливается», без «мы делаем бэкапы» без доказательства.

💥 Сломай намеренно

1. idle in transaction своими руками. В одной сессии:

BEGIN;
UPDATE vacancies SET priority = priority WHERE id = 1;
-- и ничего не делать

В другой смотреть pg_stat_activity, увидеть состояние, посмотреть, что растёт n_dead_tup и autovacuum не убирает. Потом ROLLBACK и увидеть, как всё отпустило.

2. Блокировка из двух сессий. Первая: BEGIN; UPDATE vacancies SET priority=1 WHERE id=1; без коммита. Вторая: тот же UPDATE - повиснет. Найти виновника через pg_blocking_pids, снять pg_cancel_backend.

3. ALTER TABLE в очереди. Открыть долгий SELECT pg_sleep(60) FROM vacancies LIMIT 1;, следом ALTER TABLE vacancies ADD COLUMN tmp int;, следом обычный SELECT. Увидеть, что третий запрос встал за ALTER, хотя ему ничего не мешало. Это и есть причина, по которой миграции идут в окно.

4. Убить план индексом-который-не-работает. Сделать запрос с WHERE date(created_at) = ... при индексе на created_at, посмотреть Seq Scan. Переписать в диапазон, увидеть Index Scan.

5. Раздуть таблицу. Обновить разом много строк несколько раз подряд, посмотреть рост n_dead_tup и размер таблицы через pg_total_relation_size. Запустить VACUUM и увидеть, что размер файла не изменился, а место переиспользуется. Потом VACUUM FULL и увидеть, как файл ужался.

6. Наложить джобу саму на себя. Поставить джобу с pg_sleep(120) и расписанием раз в минуту, посмотреть в cron.job_run_details, как копятся параллельные запуски. Добавить pg_try_advisory_lock и увидеть, что осталась одна.

✅ Задание

  • Таблица «было-стало» по трём запросам: план до, что изменил, план после, время в миллисекундах.
  • Работающая джоба через pg_cron с записью в job_runs и защитой от наложения.
  • Запрос-алерт «джоба не отработала за сутки», выведенный в Grafana.
  • Можешь вслух разобрать план EXPLAIN ANALYZE по шагам.

Критерий готовности: показываешь замер «было-стало» по своему запросу и объясняешь, что именно изменилось в плане и почему.

🌍 Из жизни

Опыт Ивана. Хранимые процедуры на PostgreSQL и MS SQL, включая замену громоздких легаси-процедур на компактные и быстрые. Легаси-процедуры в TimeReport считались долго - переписал компактнее и с правильными индексами. Это готовая история для вопроса про оптимизацию, и она своя.

Про idle in transaction в проде. Типичный сценарий: приложение открыло транзакцию, ушло за данными во внешний сервис, сервис не отвечает, таймаута нет. Транзакция висит час. За этот час autovacuum не убирает мёртвые строки по всей базе, таблицы пухнут, запросы замедляются. Внешне выглядит как «база вдруг стала тормозить без причины».

Про миграции в банке. Причина, по которой ALTER TABLE катят ночью, не в самом ALTER - он часто мгновенный. Причина в очереди блокировок: он встаёт за любым долгим запросом и держит за собой всех остальных. Днём под нагрузкой это означает остановку сервиса на время самого долгого запроса.

Про джобы, которые «не запустились». Мониторинг обычно ловит упавшие задания и не ловит незапустившиеся: нет запуска - нет ошибки - нет алерта. Обнаруживается через день, когда кто-то замечает вчерашние цифры. Поэтому проверка «была ли успешная отработка за последние N часов» важнее проверки на ошибку.

Про COUNT(*). Разработчики, пришедшие из MySQL с MyISAM, ждут мгновенного счёта. В Postgres из-за MVCC точный счёт означает проход по строкам, потому что видимость у каждой транзакции своя. На отчётной странице с COUNT(*) по миллионам строк это заметно сразу.

❓ Вопросы с ответами

Запрос стал медленным. Действия?

EXPLAIN (ANALYZE, BUFFERS). Смотрю Seq Scan там, где ждал индекс, и расхождение оценённых и фактических строк - если мимо, делаю ANALYZE. Дальше тип join и Rows Removed by Filter. Потом проверяю индекс под фильтр и под сортировку и порядок полей в составном.

База встала, нагрузки нет. Что смотрите?

pg_stat_activity на idle in transaction и долгие запросы. Потом блокировки через pg_blocking_pids. Чаще всего висит незакрытая транзакция, которая держит блокировки и мешает autovacuum.

Что такое VACUUM и почему таблица растёт?

Postgres при обновлении пишет новую версию строки и помечает старую мёртвой. VACUUM освобождает место под повторное использование, autovacuum делает это сам. Не справляется - таблица распухает. VACUUM FULL возвращает место системе, но берёт эксклюзивную блокировку, поэтому только в окно.

Почему не поставить индексы на все колонки?

Каждый замедляет запись и занимает место, плюс планировщику дороже выбирать. Ставлю под реальные запросы и периодически чищу неиспользуемые через pg_stat_user_indexes.

Индекс есть, а запрос его не использует. Почему?

Обычно одно из трёх: на колонке стоит функция, и индекс по значению не подходит; условие с LIKE '%...' не ловится btree; или статистика устарела и планировщик считает, что вернётся слишком много строк. Проверяю EXPLAIN, делаю ANALYZE, при необходимости переписываю условие в диапазон.

Как сделать миграцию без простоя?

CREATE INDEX CONCURRENTLY вместо обычного. ALTER TABLE - в окно, с lock_timeout, чтобы не встать в очередь за долгим запросом и не заблокировать всех позади. Добавление колонки с DEFAULT в свежих версиях не переписывает таблицу, в старых переписывает - проверяю по версии.

Как устроены регламентные расчёты и что с ними может пойти не так?

Джоба по расписанию: pg_cron внутри базы, cron или systemd timer снаружи, оркестратор при сложных зависимостях. Ломается четырьмя способами: не запустилась, упала, наложилась сама на себя, не успела в окно. Поэтому у джобы должна быть таблица учёта запусков, защита через advisory lock, обработка пачками и два алерта - на падение и на отсутствие успешной отработки.

Что делать, когда расчёт не успевает к сроку?

Сначала понять, разовое это или тренд. Разовое - искать помеху: блокировка, всплеск объёма, соседняя нагрузка. Тренд - джоба переросла окно, надо ускорять запрос, резать на части или переносить окно. Параллельно уточнить регламент: кого уведомляем и есть ли деградированный режим, когда лучше отдать вчерашние цифры с пометкой, чем ничего.

Какой уровень изоляции по умолчанию?

Read Committed. Каждый оператор видит свой свежий снимок, поэтому два SELECT в одной транзакции могут вернуть разное. Нужна стабильная картина - Repeatable Read.

Чем синхронная репликация отличается от асинхронной?

Асинхронная: мастер не ждёт реплику, быстро, но при аварии можно потерять последние транзакции. Синхронная: мастер ждёт подтверждения, потери нет, каждая запись медленнее. Выбор - это решение о допустимой потере, а не техническое предпочтение.

Зачем нужен PgBouncer, если приложение и так открывает соединения? (добавлено 15.09)

Каждое соединение Postgres - процесс ОС, тысяча простаивающих клиентов держат тысячу процессов и память под них. PgBouncer терминирует клиентские соединения сам и держит к базе маленький пул реальных. Симптом без пула: FATAL: too many connections, рост pg_stat_activity без роста полезной работы, память сервера уходит на holding, а не на кэш. Резать в проде себе не давал - объяснил бы принцип и разницу режимов, дальше поднял бы transaction pooling в Docker рядом с трекером, если бы дали 20 минут на живом стенде.

Реплика упала. Что делаете - просто переключаете трафик?

Нет, failover - это процедура, а не тумблер. Сначала подтвердить, что мастер действительно недоступен, а не просто медленно отвечает - ложный failover хуже простоя. Дальше поднять реплику в роль мастера (pg_ctl promote или через Patroni, если он есть), переключить приложения на новый адрес - через DNS, VIP или сервис-дискавери, не руками в конфиге каждого клиента. После - поднять новую реплику взамен старой, иначе кластер живёт без резерва. Автоматический failover без карантина на «split brain» - когда старый мастер ожил и оба принимают запись - опаснее ручного с задержкой в минуту.
