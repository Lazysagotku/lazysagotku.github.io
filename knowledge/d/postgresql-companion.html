Циклы в PL/pgSQL (твой named-гэп)

Раз у тебя уже есть реальный опыт с триггерами/хранимыми процедурами, база явно есть — но декларативный SQL (обычные запросы) и процедурный PL/pgSQL (код внутри функций/процедур) — разные режимы мышления. Циклы живут только во втором.

Структура блока:

DO $$
DECLARE
    counter INT := 1; -- переменные объявляются в DECLARE
BEGIN
    -- тело
END $$;

Или именованная функция: CREATE FUNCTION ... RETURNS ... AS $$ ... $$ LANGUAGE plpgsql;

Четыре вида циклов:

-- 1. Базовый LOOP — бесконечный, обязателен ручной EXIT
LOOP
    counter := counter + 1;
    EXIT WHEN counter > 10;
END LOOP;

-- 2. WHILE — условие проверяется ДО каждой итерации
WHILE counter <= 10 LOOP
    counter := counter + 1;
END LOOP;

-- 3. FOR по числовому диапазону
FOR i IN 1..10 LOOP
    RAISE NOTICE 'i = %', i;
END LOOP;
-- FOR i IN REVERSE 10..1 LOOP — тоже работает

-- 4. FOR по результату запроса ("cursor for loop") — построчно
FOR rec IN SELECT id, name FROM users WHERE active = true LOOP
    RAISE NOTICE 'user % - %', rec.id, rec.name;
END LOOP;

-- 5. FOREACH по массиву
FOREACH item IN ARRAY my_array LOOP
    -- ...
END LOOP;

Управление внутри цикла — EXIT WHEN (break) и CONTINUE WHEN (continue), работают как в C#, просто другой синтаксис.

Обработка исключений (тоже процедурное, вероятный соседний гэп):

BEGIN
    -- рискованная операция
EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'поймали: %', SQLERRM;
    WHEN OTHERS THEN
        RAISE NOTICE 'неожиданная ошибка: %', SQLERRM;
END;

[!info]+ Важный практический момент — не для галочки SQL по своей природе множественный (set-based), а не построчный. Цикл в PL/pgSQL — обработка строка-за-строкой (в индустрии это называют RBAR — Row By Agonizing Row, известный антипаттерн) — почти всегда медленнее эквивалентного одного запроса. Циклы реально нужны для сложной многошаговой процедурной логики, динамического SQL или по-настоящему последовательной обработки с состоянием. Но для задач "вроде цикла" — обход иерархии, накопительный итог — часто более идиоматичный и быстрый вариант — WITH RECURSIVE (рекурсивный CTE), множественный, а не процедурный. На собесе "как обойти дерево без цикла" чаще спрашивают именно это.

Представления (VIEW) — обычные и материализованные

Обычный VIEW — сохранённый ЗАПРОС, не данные. Каждое обращение к view заново выполняет исходный SELECT.

CREATE VIEW active_users AS
SELECT id, name, email FROM users WHERE active = true;

SELECT * FROM active_users; -- под капотом выполнится исходный SELECT с фильтром

Зачем нужен: спрятать сложную логику (джойны/фильтры) за простым именем; безопасность — дать доступ к view, показывающей только нужные колонки/строки, не давая прав на саму таблицу целиком (row-level/column-level security без отдельного механизма). Простой view (одна таблица, без агрегации/DISTINCT/GROUP BY/оконных функций) можно UPDATE/INSERT/DELETE напрямую через него — сложный, как правило, нет (нужны INSTEAD OF триггеры).

MATERIALIZED VIEW — в отличие от обычного, данные физически сохраняются на диске в момент создания.

CREATE MATERIALIZED VIEW sales_summary AS
SELECT product_id, SUM(amount) AS total FROM sales GROUP BY product_id;

REFRESH MATERIALIZED VIEW sales_summary; -- данные НЕ обновляются сами — нужен ручной/по расписанию refresh
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_summary; -- без блокировки чтения (нужен уникальный индекс на view заранее)

Ключевая ловушка/компромисс, который стоит проговорить на собесе: данные в материализованном view становятся УСТАРЕВШИМИ сразу после изменения исходных таблиц — обновляются только по явному REFRESH. Это осознанный размен свежести на скорость — подходит для дорогих агрегаций/отчётов над большими объёмами, которым не нужна реалтайм-точность.

Партиционирование — прямой ответ на "большие данные" и "изначальные установки на будущее"

Не путать с шардированием (уже разобрано в курсе, банк Ozon) — шардирование делит данные между РАЗНЫМИ серверами БД. Партиционирование делит ОДНУ логическую таблицу на несколько физических под-таблиц внутри ОДНОЙ базы — прозрачно для запросов: обращаешься к "родительской" таблице, Postgres сам направляет запрос в нужную партицию.

CREATE TABLE orders (
    id BIGINT,
    created_at DATE NOT NULL,
    amount NUMERIC
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

Типы: RANGE (по диапазону — чаще всего по дате, для таблиц логов/событий/заказов), LIST (по дискретной категории, например по региону), HASH (равномерное распределение, если нет естественного ключа для range/list).

Почему это отвечает именно на твоё "изначальные установки на будущее": запрос, фильтрующий по ключу партиционирования, вообще не сканирует нерелевантные партиции ("partition pruning") — вместо full scan гигантской таблицы сканируется только нужный кусок. Плюс обслуживание становится дешёвым: вместо DELETE FROM orders WHERE created_at < ... (медленно, миллионы строк, распухший WAL) — просто DROP TABLE orders_2020_01 (мгновенно). Но выбрать ключ партиционирования нужно на этапе создания таблицы — переразбить на партиции уже выросшую до миллионов строк таблицу заметно тяжелее, чем спроектировать это сразу. Отсюда и растёт то самое "не так глубоко подумал в начальном запросе о том, что будет дальше" — это ровно тот момент, где нужно решать заранее, а не постфактум.

Postgres вместо Redis/RabbitMQ — где реально работает, где есть потолок

Принцип "используй то, что уже есть в компании, прежде чем вводить новую инфраструктуру с новой операционной нагрузкой" — реальный, уважаемый в индустрии архитектурный подход (иногда называют избеганием "operational complexity tax"), не наивность. Но важно знать границу — это ровно то, что отличает "звучит модно" от "продумал".

Вместо Redis (кэш) — уже подтверждено бенчмарком выше в этом же файле-семье курса: Redis 11 000+ rps на чтении против Postgres на UNLOGGED TABLE — 7 400 rps. Для большинства проектов 7 400 rps (это больше полумиллиарда операций в сутки) достаточно — отдельная зависимость не нужна ДО этого порога. Дополнительно: LISTEN/NOTIFY — встроенный лёгкий pub/sub в Postgres, закрывает часть простых сценариев без Redis Pub/Sub.

Вместо RabbitMQ (очередь) — тоже реально, через FOR UPDATE SKIP LOCKED (уже разбирали в Transactional Outbox): таблица-очередь, несколько воркеров безопасно разбирают строки, не блокируя друг друга. LISTEN/NOTIFY добавляет push-уведомление о новой записи вместо постоянного поллинга. В индустрии для этого паттерна даже есть отдельное имя — "Postgres as a queue", есть готовые библиотеки (pgmq и подобные).

⚠️ Честный потолок, который стоит проговорить на собесе, а не только плюсы: - Throughput. Брокер-таблица в Postgres не приближается к пропускной способности выделенного брокера — даже RabbitMQ (50-100К msg/sec) кратно обгоняет Postgres-очередь под конкурентной записью, не говоря про Kafka (500К-1М+). - Продвинутая маршрутизация. Topic exchange, fanout, dead-letter exchange, приоритетные очереди — в RabbitMQ из коробки, в Postgres — вручную поверх таблицы. - Самое важное — это ЧУЖАЯ нагрузка на ТВОЮ основную БД. Таблица-очередь конкурирует за I/O/соединения с реальными транзакционными данными, требует своего вакуума (много INSERT/DELETE = много мёртвых строк), раздувает WAL. Связывать паттерн нагрузки очереди со здоровьем основной OLTP-базы — реальный операционный риск, не бесплатный трюк.

Итог для собеса: правильный ответ — не "всегда Redis/RabbitMQ" и не "всегда только Postgres", а умение назвать порог, после которого выделенная инфраструктура оправдана (нагрузка, требования к маршрутизации, изоляция рисков от основной БД) — та же логика "когда что", что уже была в SOLID и abstract-class-vs-interface.

Быстрая практика для support/разбора инцидентов (МТС L1/L2, 2026-08-25)

Не глубокая теория — набор паттернов, которые реально нужны, когда SQL используется для "найти данные/разобрать инцидент", а не для архитектуры БД.

Найти записи за период:

SELECT * FROM incidents
WHERE created_at BETWEEN '2026-08-01' AND '2026-08-25'
ORDER BY created_at DESC;

Посчитать инциденты по статусу (типичный вопрос "сколько чего"):

SELECT status, COUNT(*) AS cnt
FROM incidents
GROUP BY status
ORDER BY cnt DESC;

Связать инцидент с пользователем (JOIN — почти всегда нужен для "кто и что"):

SELECT i.id, i.description, u.full_name
FROM incidents i
JOIN users u ON u.id = i.user_id
WHERE i.status = 'open';

Поиск по тексту в логах/описании (ILIKE — регистронезависимый):

SELECT * FROM incidents WHERE description ILIKE '%timeout%';

Найти "зависшие" инциденты без ответа (LEFT JOIN + IS NULL — частый паттерн диагностики):

SELECT i.id, i.created_at
FROM incidents i
LEFT JOIN responses r ON r.incident_id = i.id
WHERE r.id IS NULL; -- инциденты, на которые ещё не ответили

Q&A: - Почему ILIKE, а не LIKE? → LIKE регистрозависим, ILIKE — нет, для поиска по логам/тексту почти всегда нужен ILIKE. - Как найти записи без совпадения в другой таблице? → LEFT JOIN + WHERE правая_таблица.id IS NULL — стандартный паттерн "чего не хватает". - WHERE vs HAVING? → WHERE фильтрует строки ДО группировки, HAVING — группы ПОСЛЕ GROUP BY (например HAVING COUNT(*) > 5).

EXPLAIN ANALYZE - чтение плана

Аналогия. Маршрут в навигаторе. EXPLAIN показывает предполагаемый маршрут, EXPLAIN ANALYZE прогоняет машину по нему и говорит, сколько заняло на самом деле. Пробки видны только во втором случае.

EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

⚠️ ANALYZE действительно выполняет запрос. Для UPDATE и DELETE оборачивать в транзакцию с откатом:

BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;

На что смотреть по порядку:

  1. Seq Scan там, где ждал Index Scan. Полный проход по большой таблице. Причины: нет индекса; индекс есть, но не подходит под условие; планировщик решил, что строк вернётся много и последовательное чтение дешевле.
  2. Расхождение rows= оценённых и actual rows=. Если оценка мимо в разы - статистика устарела, нужен ANALYZE таблица. Планировщик принимает решения по статистике, и врущая статистика даёт плохой план при живых индексах.
  3. Nested Loop на больших объёмах. Для маленьких выборок это норма, для больших - обычно и есть тормоз. Hash Join и Merge Join на объёмах ведут себя лучше.
  4. Rows Removed by Filter. Прочитали много, выкинули почти всё - явный признак недостающего индекса.
  5. BUFFERS: shared read против shared hit. hit - взяли из кэша, read - пошли на диск. Много read означает, что данные не помещаются в память.

Типы узлов, которые надо узнавать:

Узел Что делает Когда тревожно
Seq Scan читает таблицу целиком на большой таблице с узким фильтром
Index Scan идёт по индексу, потом в таблицу норма
Index Only Scan всё нужное есть в индексе лучший случай
Bitmap Heap Scan собрал битмап по индексу, потом читает страницы норма при средней выборке
Nested Loop для каждой строки слева ищет справа плохо на больших объёмах
Hash Join строит хеш-таблицу норма
Sort сортирует смотреть Sort Method: quicksort в памяти хорошо, external merge Disk плохо

Мой случай из практики: легаси-процедуры в TimeReport считались долго - переписал компактнее и с правильными индексами.

Что происходит в базе прямо сейчас

-- активные сессии
SELECT pid, usename, state, wait_event_type, wait_event,
       now() - query_start AS длительность,
       left(query, 120) AS запрос
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;

Состояния и что они значат:

state Значение Тревога
active выполняет запрос смотреть на длительность
idle простаивает между запросами норма
idle in transaction транзакция открыта, работы нет держит блокировки, мешает vacuum
idle in transaction (aborted) транзакция сломалась, никто не откатил то же самое

⚠️ idle in transaction - причина номер один в ситуации «база встала без нагрузки». Приложение открыло транзакцию и забыло закрыть: не отпустило соединение, упало между BEGIN и COMMIT, или в пуле висит незакрытая сессия. Пока такая транзакция жива, autovacuum не может убирать мёртвые строки во всей базе.

Найти зависшие надолго:

SELECT pid, now() - state_change AS висит, left(query, 100)
FROM pg_stat_activity
WHERE state LIKE 'idle in transaction%'
  AND now() - state_change > interval '5 minutes';

Прибить:

SELECT pg_cancel_backend(pid);     -- отменить запрос, сессия жива
SELECT pg_terminate_backend(pid);  -- закрыть соединение целиком

Порядок правильный: сначала cancel, потом terminate.

Блокировки

Аналогия. Очередь в одну кабинку. Пока первый не вышел, остальные стоят. Проблема не в том, кто стоит, а в том, кто сидит внутри и не выходит.

Кто кого ждёт - готовый запрос:

SELECT blocked.pid       AS ждёт_pid,
       blocked.query     AS ждёт_запрос,
       blocking.pid      AS держит_pid,
       blocking.query    AS держит_запрос,
       now() - blocked.query_start AS ждёт_уже
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event_type = 'Lock';

pg_blocking_pids(pid) - функция, которая сразу отдаёт список блокирующих. Знание её вместо ручного разбора pg_locks заметно экономит время и хорошо смотрится в ответе.

Что блокирует что: - SELECT берёт ACCESS SHARE - не мешает почти ничему; - UPDATE и DELETE берут ROW EXCLUSIVE - мешают только изменению тех же строк; - ALTER TABLE, VACUUM FULL, REINDEX берут ACCESS EXCLUSIVE - блокируют даже чтение.

Отсюда правило релизов: миграции с ALTER TABLE идут в окно. Даже быстрый ALTER встанет в очередь за долгим SELECT и заблокирует всех, кто пришёл после него.

Смягчение:

SET lock_timeout = '5s';   -- не ждать блокировку дольше пяти секунд
CREATE INDEX CONCURRENTLY ...;  -- строит индекс без блокировки записи

MVCC, VACUUM и bloat

Аналогия. Черновики с правками. При исправлении строки Postgres не стирает старую версию, а пишет новую и помечает старую отмершей. Пока идущие транзакции могут её видеть, она лежит.

Отсюда следствия: - UPDATE физически создаёт новую строку; - таблица растёт даже при неизменном числе записей; - нужен уборщик.

VACUUM помечает место от мёртвых версий как свободное для повторного использования. Файл при этом не уменьшается. VACUUM FULL перестраивает таблицу и возвращает место операционной системе, но берёт ACCESS EXCLUSIVE - только в окно. autovacuum делает обычный VACUUM сам, по порогам изменённых строк.

Проверить, что autovacuum справляется:

SELECT relname,
       n_live_tup AS живых,
       n_dead_tup AS мёртвых,
       round(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS процент_мёртвых,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

Больше 20 процентов мёртвых и старый last_autovacuum - autovacuum не успевает. Причины: слишком мягкие пороги на горячей таблице; долгая транзакция или idle in transaction, из-за которой старые версии нельзя убрать; реплика с hot_standby_feedback, удерживающая версии.

Настройка порогов на конкретную таблицу:

ALTER TABLE busy_table SET (autovacuum_vacuum_scale_factor = 0.02);

Wraparound - вопрос уровнем выше, но упоминание ценится: счётчик транзакций 32-битный, и если vacuum не проходит очень долго, база останавливается для защиты данных. Мониторить через age(datfrozenxid).

Индексы

Тип Для чего Пример
B-tree по умолчанию, сравнения и диапазоны WHERE created_at > ..., ORDER BY
GIN массивы, JSONB, полнотекстовый поиск WHERE data @> '{"k":"v"}'
GiST геометрия, диапазоны пересечения интервалов
BRIN огромные таблицы, физически упорядоченные логи по времени, дёшев по объёму
Hash только равенство редко нужен, B-tree обычно не хуже

Составной индекс - правило левого префикса. Индекс (a, b, c) работает для условий по a, по a, b и по a, b, c. Для условия только по b он бесполезен. Порядок полей выбирается по селективности и по тому, как реально фильтруют.

Частичный индекс - индексируем только нужную часть:

CREATE INDEX ON orders (created_at) WHERE status = 'pending';

Меньше по размеру и быстрее, если запросы всегда идут с этим условием.

Покрывающий индекс даёт Index Only Scan:

CREATE INDEX ON orders (user_id) INCLUDE (amount, status);

Чем индексы вредят: каждый замедляет INSERT, UPDATE, DELETE и занимает место. Неиспользуемые надо находить и убирать:

SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

Транзакции и уровни изоляции

Уровень Что может случиться В Postgres
Read Uncommitted грязное чтение ведёт себя как Read Committed
Read Committed неповторяемое чтение, фантомы по умолчанию
Repeatable Read фантомы (в Postgres их нет благодаря снимку) доступен
Serializable ничего доступен, ценой откатов при конфликте

В Read Committed каждый оператор внутри транзакции видит свой свежий снимок. Поэтому два SELECT подряд в одной транзакции могут вернуть разное. В Repeatable Read снимок фиксируется на всю транзакцию.

Дедлок - две транзакции держат по ресурсу и просят чужой. Postgres обнаруживает это сам и откатывает одну из них с ошибкой. Профилактика: обращаться к таблицам и строкам в одинаковом порядке во всём коде.

Соединения и пул

SHOW max_connections;
SELECT count(*), state FROM pg_stat_activity GROUP BY state;

Каждое соединение в Postgres - отдельный процесс операционной системы с собственной памятью. Тысяча соединений съест ресурсы, даже если они простаивают. Отсюда пул: PgBouncer снаружи либо пул в приложении.

Режимы PgBouncer: session - соединение отдаётся на всю сессию клиента; transaction - на одну транзакцию, самый экономный и самый частый; statement - на один оператор, ломает транзакции. Знание transaction как основного режима - хороший маркер.

Резервные копии и репликация

pg_dump -Fc -d база > база.dump      # логический дамп одной базы
pg_restore -d база база.dump
pg_basebackup -D /backup -Ft -z      # физическая копия кластера

Логический дамп - переносимый между версиями, медленный на больших объёмах, восстановление на точку времени невозможно. Физическая копия плюс WAL-архив - основа для восстановления на момент времени (PITR).

Репликация: потоковая, мастер шлёт WAL на реплику. - асинхронная - мастер не ждёт реплику, при аварии возможна потеря последних транзакций; - синхронная - мастер ждёт подтверждения, потери нет, но каждая запись медленнее.

Выбор - компромисс между скоростью и допустимой потерей. На этом вопросе проверяют, понимает ли человек цену.

Задержка репликации:

SELECT client_addr, state, sent_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS отставание_байт
FROM pg_stat_replication;

Что мониторить у базы - готовый список

  • число соединений против max_connections;
  • длительные транзакции и idle in transaction;
  • задержку репликации;
  • попадание в кэш (cache hit ratio), норма выше 95 процентов;
  • мёртвые строки и время последнего autovacuum;
  • размер базы и рост крупнейших таблиц;
  • самые долгие запросы через pg_stat_statements.
-- попадание в кэш
SELECT sum(blks_hit) * 100.0 / NULLIF(sum(blks_hit + blks_read), 0) AS cache_hit_pct
FROM pg_stat_database;

-- топ медленных запросов
SELECT round(total_exec_time::numeric, 0) AS всего_мс,
       calls, round(mean_exec_time::numeric, 1) AS среднее_мс,
       left(query, 100)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 15;

pg_stat_statements - расширение, включается в shared_preload_libraries. Это главный инструмент поиска того, что жрёт базу. Упомянуть его стоит обязательно.

Про Pangolin

Pangolin - сборка PostgreSQL внутри Сбера, снаружи опыта с ней нет ни у кого. Формулировка:

С Pangolin не работал, он внутри вашего контура. Это PostgreSQL, и всё, что я делал на нём, переносится: планы, блокировки, обслуживание, хранимые процедуры. Интересно, чем ваша сборка отличается от ванильной - расширения, изменения в репликации, что-то по отказоустойчивости?

Быстрые ответы

Запрос стал медленным. Действия?

EXPLAIN (ANALYZE, BUFFERS). Смотрю Seq Scan там, где ждал индекс, и расхождение оценённых и фактических строк - если оценка мимо, делаю ANALYZE. Дальше тип join и Rows Removed by Filter. Потом проверяю индекс под фильтр и под сортировку.

База встала, нагрузки нет. Что смотрите?

pg_stat_activity на предмет idle in transaction и долгих запросов. Потом блокировки через pg_blocking_pids. Чаще всего висит незакрытая транзакция, которая держит блокировки и мешает autovacuum.

Что такое VACUUM и почему таблица растёт?

Postgres при обновлении пишет новую версию строки и помечает старую мёртвой. VACUUM освобождает место под повторное использование, autovacuum делает это сам. Если не справляется - таблица распухает. VACUUM FULL возвращает место системе, но берёт эксклюзивную блокировку, поэтому только в окно.

Почему не поставить индексы на все колонки?

Каждый индекс замедляет запись и занимает место. Плюс планировщику становится дороже выбирать. Ставлю под реальные запросы и периодически чищу неиспользуемые через pg_stat_user_indexes.

Какой уровень изоляции по умолчанию?

Read Committed. Каждый оператор видит свой свежий снимок, поэтому два SELECT в одной транзакции могут вернуть разное. Если нужна стабильная картина - Repeatable Read.

Как сделать миграцию без простоя?

CREATE INDEX CONCURRENTLY вместо обычного. ALTER TABLE с ACCESS EXCLUSIVE - только в окно, с lock_timeout, чтобы не встать в очередь за долгим запросом и не заблокировать всех позади. Добавление колонки с DEFAULT в свежих версиях не переписывает таблицу, в старых переписывает - это надо проверять по версии.
