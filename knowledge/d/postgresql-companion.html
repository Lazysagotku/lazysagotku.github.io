Циклы в PL/pgSQL (твой named-гэп)

Раз у тебя уже есть реальный опыт с триггерами/хранимыми процедурами, база явно есть — но декларативный SQL (обычные запросы) и процедурный PL/pgSQL (код внутри функций/процедур) — разные режимы мышления. Циклы живут только во втором.

Структура блока:

DO $$
DECLARE
    counter INT := 1; -- переменные объявляются в DECLARE
BEGIN
    -- тело
END $$;

Или именованная функция: CREATE FUNCTION ... RETURNS ... AS $$ ... $$ LANGUAGE plpgsql;

Четыре вида циклов:

-- 1. Базовый LOOP — бесконечный, обязателен ручной EXIT
LOOP
    counter := counter + 1;
    EXIT WHEN counter > 10;
END LOOP;

-- 2. WHILE — условие проверяется ДО каждой итерации
WHILE counter <= 10 LOOP
    counter := counter + 1;
END LOOP;

-- 3. FOR по числовому диапазону
FOR i IN 1..10 LOOP
    RAISE NOTICE 'i = %', i;
END LOOP;
-- FOR i IN REVERSE 10..1 LOOP — тоже работает

-- 4. FOR по результату запроса ("cursor for loop") — построчно
FOR rec IN SELECT id, name FROM users WHERE active = true LOOP
    RAISE NOTICE 'user % - %', rec.id, rec.name;
END LOOP;

-- 5. FOREACH по массиву
FOREACH item IN ARRAY my_array LOOP
    -- ...
END LOOP;

Управление внутри цикла — EXIT WHEN (break) и CONTINUE WHEN (continue), работают как в C#, просто другой синтаксис.

Обработка исключений (тоже процедурное, вероятный соседний гэп):

BEGIN
    -- рискованная операция
EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'поймали: %', SQLERRM;
    WHEN OTHERS THEN
        RAISE NOTICE 'неожиданная ошибка: %', SQLERRM;
END;

[!info]+ Важный практический момент — не для галочки SQL по своей природе множественный (set-based), а не построчный. Цикл в PL/pgSQL — обработка строка-за-строкой (в индустрии это называют RBAR — Row By Agonizing Row, известный антипаттерн) — почти всегда медленнее эквивалентного одного запроса. Циклы реально нужны для сложной многошаговой процедурной логики, динамического SQL или по-настоящему последовательной обработки с состоянием. Но для задач "вроде цикла" — обход иерархии, накопительный итог — часто более идиоматичный и быстрый вариант — WITH RECURSIVE (рекурсивный CTE), множественный, а не процедурный. На собесе "как обойти дерево без цикла" чаще спрашивают именно это.

Представления (VIEW) — обычные и материализованные

Обычный VIEW — сохранённый ЗАПРОС, не данные. Каждое обращение к view заново выполняет исходный SELECT.

CREATE VIEW active_users AS
SELECT id, name, email FROM users WHERE active = true;

SELECT * FROM active_users; -- под капотом выполнится исходный SELECT с фильтром

Зачем нужен: спрятать сложную логику (джойны/фильтры) за простым именем; безопасность — дать доступ к view, показывающей только нужные колонки/строки, не давая прав на саму таблицу целиком (row-level/column-level security без отдельного механизма). Простой view (одна таблица, без агрегации/DISTINCT/GROUP BY/оконных функций) можно UPDATE/INSERT/DELETE напрямую через него — сложный, как правило, нет (нужны INSTEAD OF триггеры).

MATERIALIZED VIEW — в отличие от обычного, данные физически сохраняются на диске в момент создания.

CREATE MATERIALIZED VIEW sales_summary AS
SELECT product_id, SUM(amount) AS total FROM sales GROUP BY product_id;

REFRESH MATERIALIZED VIEW sales_summary; -- данные НЕ обновляются сами — нужен ручной/по расписанию refresh
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_summary; -- без блокировки чтения (нужен уникальный индекс на view заранее)

Ключевая ловушка/компромисс, который стоит проговорить на собесе: данные в материализованном view становятся УСТАРЕВШИМИ сразу после изменения исходных таблиц — обновляются только по явному REFRESH. Это осознанный размен свежести на скорость — подходит для дорогих агрегаций/отчётов над большими объёмами, которым не нужна реалтайм-точность.

Партиционирование — прямой ответ на "большие данные" и "изначальные установки на будущее"

Не путать с шардированием (уже разобрано в курсе, банк Ozon) — шардирование делит данные между РАЗНЫМИ серверами БД. Партиционирование делит ОДНУ логическую таблицу на несколько физических под-таблиц внутри ОДНОЙ базы — прозрачно для запросов: обращаешься к "родительской" таблице, Postgres сам направляет запрос в нужную партицию.

CREATE TABLE orders (
    id BIGINT,
    created_at DATE NOT NULL,
    amount NUMERIC
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

Типы: RANGE (по диапазону — чаще всего по дате, для таблиц логов/событий/заказов), LIST (по дискретной категории, например по региону), HASH (равномерное распределение, если нет естественного ключа для range/list).

Почему это отвечает именно на твоё "изначальные установки на будущее": запрос, фильтрующий по ключу партиционирования, вообще не сканирует нерелевантные партиции ("partition pruning") — вместо full scan гигантской таблицы сканируется только нужный кусок. Плюс обслуживание становится дешёвым: вместо DELETE FROM orders WHERE created_at < ... (медленно, миллионы строк, распухший WAL) — просто DROP TABLE orders_2020_01 (мгновенно). Но выбрать ключ партиционирования нужно на этапе создания таблицы — переразбить на партиции уже выросшую до миллионов строк таблицу заметно тяжелее, чем спроектировать это сразу. Отсюда и растёт то самое "не так глубоко подумал в начальном запросе о том, что будет дальше" — это ровно тот момент, где нужно решать заранее, а не постфактум.

Postgres вместо Redis/RabbitMQ — где реально работает, где есть потолок

Принцип "используй то, что уже есть в компании, прежде чем вводить новую инфраструктуру с новой операционной нагрузкой" — реальный, уважаемый в индустрии архитектурный подход (иногда называют избеганием "operational complexity tax"), не наивность. Но важно знать границу — это ровно то, что отличает "звучит модно" от "продумал".

Вместо Redis (кэш) — уже подтверждено бенчмарком выше в этом же файле-семье курса: Redis 11 000+ rps на чтении против Postgres на UNLOGGED TABLE — 7 400 rps. Для большинства проектов 7 400 rps (это больше полумиллиарда операций в сутки) достаточно — отдельная зависимость не нужна ДО этого порога. Дополнительно: LISTEN/NOTIFY — встроенный лёгкий pub/sub в Postgres, закрывает часть простых сценариев без Redis Pub/Sub.

Вместо RabbitMQ (очередь) — тоже реально, через FOR UPDATE SKIP LOCKED (уже разбирали в Transactional Outbox): таблица-очередь, несколько воркеров безопасно разбирают строки, не блокируя друг друга. LISTEN/NOTIFY добавляет push-уведомление о новой записи вместо постоянного поллинга. В индустрии для этого паттерна даже есть отдельное имя — "Postgres as a queue", есть готовые библиотеки (pgmq и подобные).

⚠️ Честный потолок, который стоит проговорить на собесе, а не только плюсы: - Throughput. Брокер-таблица в Postgres не приближается к пропускной способности выделенного брокера — даже RabbitMQ (50-100К msg/sec) кратно обгоняет Postgres-очередь под конкурентной записью, не говоря про Kafka (500К-1М+). - Продвинутая маршрутизация. Topic exchange, fanout, dead-letter exchange, приоритетные очереди — в RabbitMQ из коробки, в Postgres — вручную поверх таблицы. - Самое важное — это ЧУЖАЯ нагрузка на ТВОЮ основную БД. Таблица-очередь конкурирует за I/O/соединения с реальными транзакционными данными, требует своего вакуума (много INSERT/DELETE = много мёртвых строк), раздувает WAL. Связывать паттерн нагрузки очереди со здоровьем основной OLTP-базы — реальный операционный риск, не бесплатный трюк.

Итог для собеса: правильный ответ — не "всегда Redis/RabbitMQ" и не "всегда только Postgres", а умение назвать порог, после которого выделенная инфраструктура оправдана (нагрузка, требования к маршрутизации, изоляция рисков от основной БД) — та же логика "когда что", что уже была в SOLID и abstract-class-vs-interface.

Быстрая практика для support/разбора инцидентов (МТС L1/L2, 2026-08-25)

Не глубокая теория — набор паттернов, которые реально нужны, когда SQL используется для "найти данные/разобрать инцидент", а не для архитектуры БД.

Найти записи за период:

SELECT * FROM incidents
WHERE created_at BETWEEN '2026-08-01' AND '2026-08-25'
ORDER BY created_at DESC;

Посчитать инциденты по статусу (типичный вопрос "сколько чего"):

SELECT status, COUNT(*) AS cnt
FROM incidents
GROUP BY status
ORDER BY cnt DESC;

Связать инцидент с пользователем (JOIN — почти всегда нужен для "кто и что"):

SELECT i.id, i.description, u.full_name
FROM incidents i
JOIN users u ON u.id = i.user_id
WHERE i.status = 'open';

Поиск по тексту в логах/описании (ILIKE — регистронезависимый):

SELECT * FROM incidents WHERE description ILIKE '%timeout%';

Найти "зависшие" инциденты без ответа (LEFT JOIN + IS NULL — частый паттерн диагностики):

SELECT i.id, i.created_at
FROM incidents i
LEFT JOIN responses r ON r.incident_id = i.id
WHERE r.id IS NULL; -- инциденты, на которые ещё не ответили

Q&A: - Почему ILIKE, а не LIKE? → LIKE регистрозависим, ILIKE — нет, для поиска по логам/тексту почти всегда нужен ILIKE. - Как найти записи без совпадения в другой таблице? → LEFT JOIN + WHERE правая_таблица.id IS NULL — стандартный паттерн "чего не хватает". - WHERE vs HAVING? → WHERE фильтрует строки ДО группировки, HAVING — группы ПОСЛЕ GROUP BY (например HAVING COUNT(*) > 5).
