🎭 Аналогия

Конвейер на заводе. Деталь заходит с одного конца, проходит станки в заданном порядке, и на выходе получается изделие. Никто не носит деталь руками между станками, поэтому изделия одинаковые, а ошибки ловятся на том станке, где возникли.

🗺 Карта мест

Сделать: пайплайн GitHub Actions: тесты → деплой на сервер по SSH → проверка /health; скрипт отката на сервере.

Понять: пайплайн - это код в репозитории (.github/workflows/*.yml), который GitHub выполняет на своих машинах после каждого push. Секреты (ключ SSH, адрес сервера) лежат в настройках репозитория, в код не попадают. Деплой = зайти по SSH, обновить код, перезапустить сервис, проверить, что живой.

Где писать: .github/workflows/deploy.yml в репо трекера; /opt/tracker/rollback.sh на сервере; секреты - GitHub → Settings → Secrets and variables → Actions.

Чем запустить: git push в main. Вручную - вкладка Actions → Run workflow.

Где смотреть результат: - GitHub, вкладка Actions: каждый шаг раскрывается, лог как в терминале. - На сервере: journalctl -u tracker -n 30, curl localhost:8000/health, git -C /opt/tracker log -1.

Как понять, что получилось: после push зелёная галочка, на сервере новая версия отвечает на /health; сломал тест - деплой не пошёл, старая версия осталась; rollback.sh возвращает предыдущую за секунды.

📖 Теория

Что означают буквы

Термин Расшифровка Смысл
CI Continuous Integration каждый коммит автоматически собирается и проверяется тестами
CD (Delivery) Continuous Delivery артефакт всегда готов к выкатке, кнопку жмёт человек
CD (Deployment) Continuous Deployment выкатка тоже автоматическая, без человека

⚠️ Delivery и Deployment путают постоянно. Разница в одном: кто нажимает кнопку на прод. В банках почти всегда Delivery - выкатка требует согласования и окна.

Стадии типового пайплайна

  1. Build - собрать образ или пакет.
  2. Test - прогнать тесты, линтеры, проверку типов.
  3. Scan - проверить зависимости и образ на уязвимости.
  4. Publish - положить артефакт в реестр с тегом.
  5. Deploy - выкатить на стенд, потом на прод.

Ключевой принцип: собираем один раз, катим везде. Один и тот же артефакт проходит стенд, препрод и прод. Пересборка под каждое окружение означает, что на проде окажется не то, что тестировали.

Стратегии выкатки

Стратегия Как Простой Откат
Recreate погасить старое, поднять новое есть перевыкатка
Rolling заменять по одному экземпляру нет обратный rolling
Blue-Green поднять полную копию, переключить трафик нет переключить обратно, секунды
Canary пустить 5% трафика на новое, смотреть метрики нет убрать канарейку

Blue-Green требует двойных ресурсов. Canary требует хорошего мониторинга, иначе непонятно, по чему судить.

Секреты

⚠️ Пароли и токены никогда не лежат в репозитории. Даже в приватном: репозиторий переезжает, форкается, попадает в бэкапы. Правильные места: секреты CI-системы, Vault, переменные окружения на сервере с правами 600.

Проверка своего репозитория на утёкшее:

git log -p | grep -iE "password|token|secret|api_key" | head

🔧 Практика

1. Написать пайплайн GitHub Actions - файл .github/workflows/deploy.yml:

name: Deploy tracker

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: ruff check .
      - run: pytest -q

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: Выкатка по SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.STAND_HOST }}
          username: ${{ secrets.STAND_USER }}
          key: ${{ secrets.STAND_SSH_KEY }}
          script: |
            cd /opt/tracker
            git pull --ff-only
            .venv/bin/pip install -r requirements.txt
            sudo systemctl restart tracker
            sleep 3
            curl -sf http://127.0.0.1:8000/health || exit 1

Что тут важно: - needs: test - деплой идёт только после зелёных тестов; - ключ и хост лежат в секретах репозитория, а не в файле; - проверка после выкатки через /health с exit 1 - без неё пайплайн зелёный, а сервис лежит.

2. Добавить эндпоинт здоровья в трекер:

@app.get("/health")
def health():
    """Проверяет то, без чего сервис бесполезен: живую базу."""
    with SessionLocal() as s:
        s.execute(text("SELECT 1"))
    return {"status": "ok"}

⚠️ Проверка, которая всегда возвращает ok, бесполезна. Живость означает, что сервис делает работу: ходит в базу, проверяет очередь.

3. Написать скрипт отката /opt/tracker/rollback.sh:

#!/usr/bin/env bash
set -euo pipefail
cd /opt/tracker
PREV=$(git rev-parse HEAD~1)
git checkout "$PREV"
.venv/bin/pip install -r requirements.txt
sudo systemctl restart tracker
sleep 3
curl -sf http://127.0.0.1:8000/health && echo "откат на $PREV выполнен"

💥 Сломай намеренно

1. Сломать тест и увидеть, что деплой не запустился. Проверить, что на сервере осталась старая версия.

2. Выкатить заведомо битый код (синтаксическая ошибка после тестов), увидеть, как /health возвращает ошибку и пайплайн краснеет.

3. Прогнать откат из скрипта выше и убедиться, что сервис вернулся.

4. Убрать needs: test и посмотреть, как деплой уезжает параллельно с падающими тестами. Вернуть обратно.

5. Положить пароль в код, закоммитить, потом попробовать удалить: git log -p | grep пароль покажет, что он остался в истории. Вывод: утёкший секрет надо менять, а не «убирать из репозитория».

✅ Задание

  • Пуш в main запускает тесты, при зелёных - выкатывает на стенд.
  • После выкатки автоматически дёргается /health, при ошибке пайплайн красный.
  • Есть рабочий скрипт отката, проверенный вживую.
  • Ни одного секрета в репозитории.

Критерий готовности: можешь показать историю запусков, где виден и зелёный прогон, и красный с падением на тестах.

🌍 Из жизни

Опыт Ивана. В ТРИНФИКО релизы накатывались через Jenkins, а после накатки проверка шла через Postman и запросами к базе. Это ровно та же логика, что /health в пайплайне выше, только руками. На собеседовании стоит сказать именно так: «проверка после выкатки у меня была всегда, сначала руками через Postman и SQL, теперь автоматически».

Про «зелёный пайплайн при лежащем сервисе». Самая обидная категория инцидентов: деплой прошёл, статус зелёный, а приложение не поднялось. Причина всегда одна - в пайплайне нет проверки после выкатки. Один curl с exit 1 закрывает этот класс проблем целиком.

Про утёкшие секреты. Боты сканируют публичные репозитории и находят ключи облаков за минуты. Известны случаи со счетами на десятки тысяч долларов за майнинг на украденных ключах. Поэтому правило жёсткое: секрет, попавший в git, считается скомпрометированным навсегда и подлежит замене.

❓ Вопросы с ответами

Чем Continuous Delivery отличается от Continuous Deployment?

Кто нажимает кнопку на прод. Delivery - артефакт всегда готов, выкатывает человек. Deployment - выкатка автоматическая. В банках обычно Delivery, потому что нужны согласование и окно.

Что должно быть в пайплайне обязательно?

Тесты до сборки артефакта, один артефакт на все окружения, проверка живости после выкатки и подготовленный откат. Без проверки после выкатки пайплайн может быть зелёным при лежащем сервисе.

Как выкатывать без простоя?

Rolling, если экземпляров несколько. Blue-Green, если нужен мгновенный откат и есть ресурсы на вторую копию. Canary, если есть мониторинг, по которому видно, что новой версии стало хуже.

Где хранить секреты?

В секретах CI-системы или в Vault, на сервере - в переменных окружения или файле с правами 600. В репозитории никогда: он форкается, переезжает, попадает в бэкапы. Секрет, попавший в git, считаю скомпрометированным и меняю.

Как откатить неудачный релиз?

Заранее подготовленным сценарием, а не импровизацией. У меня это скрипт, который откатывает на предыдущий коммит, переставляет зависимости, перезапускает сервис и проверяет здоровье. Откат надо прогонять на стенде, иначе в момент аварии выяснится, что он не работает.
