Что такое API

Аналогия из жизни (из источника, отличная — сохраняю): официант в ресторане — интерфейс твоего взаимодействия с кухней. Просишь меню, делаешь заказ, просишь счёт — не зная, как готовится еда и как считается чек. Официант скрывает сложные детали и просто передаёт запрос/ответ между тобой и кухней.

Суть: API — описание способов взаимодействия между программами: как они общаются и передают данные. API даёт доступ ТОЛЬКО к тем функциям, которые заложил разработчик — нельзя попросить того, чего там нет (официант не почитает вслух книгу, если это не его функционал).

API бывает не только клиент-сервер, но и сервер-сервер — например сайт продажи авиабилетов сам вызывает API стороннего сервиса погоды, чтобы показать прогноз (и вероятно платит за каждый запрос). API также существует у операционных систем и железа (например доступ к камере устройства) — не только у веб-сервисов через HTTP.

SOAP — исторический предшественник REST

⚠️ Исправление точности: в источнике SOAP расшифрован как "Service Object Access Protocol" — это ОШИБКА. Правильно: Simple Object Access Protocol.

Суть: SOAP — протокол (не архитектурный стиль, в отличие от REST), задаёт строгий синтаксис сообщений. Все сообщения — обязательно в формате XML (Extensible Markup Language — данные в тегах, читаемо и человеком, и машиной), передаются через HTTP или SMTP.

Аналогия из источника (сохраняю — точная и смешная): SOAP — как завернуть каждое сообщение в XML, "надеть на него шапочку и шарфик" — много обязательной формальности вокруг сути сообщения.

REST / RESTful

Суть: REST — архитектурный СТИЛЬ (не протокол). Данные — ресурсы, у каждого свой уникальный URL. API, соответствующий REST — называется RESTful. Использует HTTP-методы (GET/POST/и другие — см. Postman companion) для работы с ресурсами.

Отличие от SOAP: RESTful поддерживает разные форматы данных (текст, HTML, YAML, XML, JSON), SOAP — только XML. JSON (JavaScript Object Notation) — самый популярный формат, простые пары ключ-значение.

Аналогия из жизни: REST-ресурс — как точный адрес в городе: идёшь прямо по адресу (URL) и взаимодействуешь с тем, что там есть, без формального протокола записи на приём, как в SOAP.

gRPC

Суть: используется в основном для связи МЕЖДУ сервисами (не для публичных веб-API). Быстрый благодаря HTTP/2 (сжатие заголовков и другие оптимизации) и формату Protocol Buffers (protobuf) вместо JSON/XML — бинарный, компактный, требует меньше ресурсов.

Аналогия из жизни: JSON/XML — как писать полное предложение в письме ("Здравствуйте, меня зовут Иван, мне 28 лет") — понятно человеку, но многословно. Protobuf — как заранее согласованный код между двумя людьми, которые давно знают формат друг друга: компактная последовательность, непонятная постороннему напрямую, зато очень быстрая, потому что обе стороны заранее знают точную структуру (схему).

Забавный факт: официального фиксированного значения буквы "g" в gRPC нет — Google в разных релизах даёт разные шуточные расшифровки (в этом источнике — "gRPC Remote Procedure Calls" — это один из принятых Google вариантов, не ошибка, просто такова природа названия).

GraphQL

Суть: язык запросов для API — позволяет клиенту указать ТОЧНО те данные, которые нужны, и получить их одним вызовом, даже если данные приходят из нескольких источников.

Аналогия из источника (сохраняю — хорошо передаёт идею): планируешь поездку в Дубай — нужен билет у окна, жильё с видом на Бурдж-Халифу и нарукавники с принтом Свинки Пеппы. Без GraphQL — три отдельных обращения в три места. С GraphQL — один вызов API с адресами всех трёх источников, получаешь всё нужное сразу.
