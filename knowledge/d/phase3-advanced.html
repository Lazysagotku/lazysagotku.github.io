3.0.1 Исключения — try/catch/finally

Почему это важно

Обработка ошибок — то, с чем сталкивается любой код, работающий с внешним миром (ввод пользователя, файлы, сеть, БД). Правильно понятый try/catch/finally — это не просто синтаксис, а гарантия, что ресурсы освобождаются и код ведёт себя предсказуемо даже при сбое.

Аналогия из жизни

Готовишь ужин (try). Если на сковороде вспыхнуло масло - хватаешь ИМЕННО ТОТ огнетушитель, что подходит под этот тип возгорания (catch конкретного типа), не первый попавшийся. Но плиту выключаешь и фартук снимаешь ВСЕГДА в конце - сгорел ужин или нет (finally).

Теория

try — блок кода, который может бросить исключение. catch — перехват и обработка конкретного (или любого) типа исключения; порядок catch-блоков важен — от самого специфичного типа к самому общему, иначе компилятор укажет на недостижимый код. finally — выполняется ВСЕГДА: было исключение или нет, был return внутри try/catch или нет — обычно используется для освобождения ресурсов (хотя для этого чаще подходит using, см. Phase1_CSharp_Fundamentals.md §1.8 про IDisposable).

Пример A — базовая структура и порядок catch

try
{
    var result = 10 / int.Parse(input);
}
catch (DivideByZeroException ex)       // сначала более специфичный тип
{
    Console.WriteLine("Деление на ноль");
}
catch (FormatException ex)
{
    Console.WriteLine("Не число");
}
catch (Exception ex)                    // общий тип — всегда ПОСЛЕДНИМ
{
    Console.WriteLine($"Неожиданная ошибка: {ex.Message}");
}
finally
{
    Console.WriteLine("Выполнится всегда");
}

[!info]+ Если поставить catch (Exception ex) раньше catch (DivideByZeroException ex) — компилятор выдаст ошибку "A previous catch clause already catches all exceptions of this or of a super type": более общий catch делает следующие недостижимыми.

Пример B — finally выполняется даже при return

static int Test()
{
    try
    {
        return 1;
    }
    finally
    {
        Console.WriteLine("finally — ДО того как 1 реально вернётся вызывающему коду");
    }
}

Пример C — свой класс исключения

public class InsufficientFundsException : Exception
{
    public decimal Requested { get; }
    public decimal Available { get; }

    public InsufficientFundsException(decimal requested, decimal available)
        : base($"Недостаточно средств: запрошено {requested}, доступно {available}")
    {
        Requested = requested;
        Available = available;
    }
}

// Зачем: доменная информация об ошибке, которую не выразить стандартным Exception
if (balance < amount)
    throw new InsufficientFundsException(amount, balance);

Пример D — throw vs throw ex

Аналогия из жизни: throw; - переслать письмо (Forward) целиком, со всей цепочкой переписки внизу: получатель видит, кто и когда написал первое сообщение. throw ex; - скопировать последний абзац в НОВОЕ письмо от своего имени: получатель думает, что это ты автор, а история, кто написал изначально, потеряна.

void Repro()
{
    try
    {
        DoSomethingThatThrows();
    }
    catch (Exception ex)
    {
        // throw;     — сохраняет ПОЛНЫЙ исходный stack trace (откуда ошибка ПРИШЛА)
        // throw ex;  — перезаписывает stack trace этой строкой (будто ошибка родилась ЗДЕСЬ)
        throw; // всегда используй так при перевыбросе
    }
}

[!info]+ Почему нельзя ловить catch (Exception ex) бездумно везде Это "проглатывает" любую ошибку, включая ту, что ты не предвидел и не умеешь правильно обработать (например OutOfMemoryException) — маскирует реальные баги вместо того чтобы дать им проявиться там, где их можно исправить.

Пример E — IDisposable под капотом: using это тот же try/finally

using var file = new StreamWriter("file.txt");
file.WriteLine("hello");

// компилятор разворачивает это ровно в то, что уже разобрано в Примере A-B:
StreamWriter file = new StreamWriter("file.txt");
try
{
    file.WriteLine("hello");
}
finally
{
    file?.Dispose(); // вызовется ВСЕГДА, даже если WriteLine бросит исключение
}

[!info]+ Полная механика Dispose-паттерна (финализатор, GC.SuppressFinalize, почему финализатор — лишь подстраховка) — уже разобрана в Phase1_CSharp_Fundamentals.md §1.8, не дублирую здесь. Важное именно для этой темы: using — не отдельный механизм освобождения ресурсов, а ровно тот же try/finally, который мы только что разбирали, просто с автоматически подставленным Dispose() в finally.

Мини-задание 3.0.1

// Метод ParseAndDivide(string a, string b) должен:
// - распарсить оба аргумента как int
// - поделить первое на второе
// - вернуть результат
// Обработай отдельно: FormatException (не число), DivideByZeroException (деление на 0)
// В finally выведи "Попытка завершена"
// Добавь свой класс исключения NegativeNumberException — бросай его,
// если результат деления получился отрицательным

🎤 Вопросы с собеседования

Q: Как работает try/catch/finally? A: try — код, который может бросить исключение. catch — обработка конкретного (или любого) типа исключения. finally — выполняется ВСЕГДА, даже если было исключение или return внутри try/catch.

Q: Почему нельзя ловить catch (Exception ex) везде подряд? A: Маскирует реальные баги и ошибки, которые ты не предвидел и не умеешь правильно обработать — усложняет отладку. Лучше ловить конкретные типы, которые реально ожидаешь.

Q: Когда стоит создавать свой класс исключения? A: Когда нужно передать доменную бизнес-информацию об ошибке, которую не выразить стандартными исключениями.

Q: throw vs throw ex — в чём разница? A: throw; сохраняет полный исходный stack trace. throw ex; перезаписывает его, будто исключение возникло здесь — теряется информация, откуда оно пришло на самом деле.

Q: Как using связан с try/finally? A: using — синтаксический сахар: компилятор оборачивает код в try и вызывает Dispose() в finally — та же гарантия освобождения ресурса даже при исключении, что и у ручного try/finally, просто без ручного написания.

3.0.2 ref/out/in, params — передача аргументов

Почему это важно

По умолчанию в C# аргументы передаются по значению (копией) для value types и по значению ссылки для reference types (см. Phase1_CSharp_Fundamentals.md §1.1). ref/out/in меняют это поведение явно — регулярно спрашивают на Middle-собесах именно потому, что три модификатора легко перепутать друг с другом.

Аналогия из жизни

ref - даёшь другу свой блокнот с записями: может дописать или зачеркнуть, возвращает изменённым. out - даёшь ЧИСТЫЙ блокнот, друг обязан хоть что-то в него вписать перед возвратом. in - даёшь блокнот со словами "только почитай, не пиши". params - вместо одного блокнота вручаешь стопку стикеров любой высоты, сколько нужно.

Теория

ref — передача по ссылке, переменная должна быть проинициализирована ДО вызова, метод может её и прочитать, и изменить. out — тоже по ссылке, но переменная может быть НЕ проинициализирована заранее — метод ОБЯЗАН её присвоить перед выходом (классический пример — int.TryParse(s, out int result)). in — по ссылке, но только для чтения внутри метода: используется для больших struct, чтобы не копировать их при каждом вызове, при этом компилятор не даёт их случайно изменить.

Пример A — ref

void Increment(ref int x) => x++;

int number = 5;
Increment(ref number); // number должен быть проинициализирован ДО вызова
Console.WriteLine(number); // 6 — метод изменил ОРИГИНАЛ, не копию

Пример B — out (TryParse-паттерн)

bool TryDivide(int a, int b, out int result)
{
    if (b == 0) { result = 0; return false; } // ОБЯЗАН присвоить result в любой ветке
    result = a / b;
    return true;
}

if (TryDivide(10, 2, out int quotient))
    Console.WriteLine(quotient); // 5
// result не нужно инициализировать заранее — компилятор проверит,
// что метод присвоил его во ВСЕХ путях выполнения

Пример C — in (readonly reference)

readonly struct Vector3D { public double X, Y, Z; }

// Без in — Vector3D копируется при КАЖДОМ вызове
double Length(Vector3D v) => Math.Sqrt(v.X * v.X + v.Y * v.Y + v.Z * v.Z);

// С in — передаётся по ссылке, копирования нет, но изменить v внутри нельзя
double LengthFast(in Vector3D v) => Math.Sqrt(v.X * v.X + v.Y * v.Y + v.Z * v.Z);

Пример D — params

int Sum(params int[] numbers) => numbers.Sum();

Sum(1, 2, 3);       // упаковывается в int[] { 1, 2, 3 }
Sum(1, 2, 3, 4, 5); // работает с любым количеством
Sum();              // тоже валидно — пустой массив

[!info]+ Ограничение, которое часто ловит на собесе: ref/out/in нельзя использовать в async-методах csharp async Task Foo(out int x) { ... } // ошибка компиляции State machine, в которую компилятор превращает async-метод (см. тему 3.4 ниже), не может гарантированно сохранить ссылку на стековую переменную через await — стек может быть уже другим к моменту продолжения.

// 2. Напиши TryParseCoordinates(string input, out double x, out double y)
//    — парсит строку вида "3.5,7.2" в две координаты, false если формат неверный

🎤 Вопросы с собеседования

Q: Чем ref, out и in параметры отличаются друг от друга? A: ref — передача по ссылке, переменная должна быть проинициализирована до вызова, метод может её прочитать и изменить. out — тоже по ссылке, но переменная может быть не проинициализирована, метод обязан её присвоить перед выходом. in — по ссылке, только для чтения (защита от изменения, эффективнее для больших struct).

Q: Что делает params? A: Позволяет передать переменное количество аргументов одного типа как единый массив внутри метода.

Q: Можно ли использовать ref/out в async-методах? A: Нет — компилятор не разрешит. State machine async-метода не может гарантированно сохранить ссылку на стековую переменную через await.

3.1 Generics — обобщённые типы

Почему это важно

Без generics — либо дублировать код под каждый тип (IntStack, StringStack, ...), либо использовать object и терять типобезопасность (плюс boxing/unboxing для value types — дорого). Generics дают код, который пишется один раз и работает с любым типом безопасно на этапе компиляции.

Аналогия из жизни

Универсальный ящик для переезда - один и тот же ящик подходит и для книг, и для посуды, и для одежды. Ты каждый раз кладёшь в него что-то ОДНО конкретное, подписываешь снаружи, что внутри - но сам ящик один и тот же, не нужно проектировать отдельный ящик под каждый тип вещей.

Теория

T — заглушка для реального типа, который подставится при использовании. Компилятор проверяет типы на этапе компиляции — ошибка несовпадения типов ловится сразу, не в рантайме. Для value types generics избегают boxing: List<int> хранит int напрямую, а не упакованный в object.

Пример A — generic метод

// Без generics — либо object (boxing + потеря типобезопасности), либо дублирование
public static T Max<T>(T a, T b) where T : IComparable<T> =>
    a.CompareTo(b) > 0 ? a : b;

int maxInt = Max(5, 10);           // T выведен как int
string maxStr = Max("a", "b");     // T выведен как string — тот же метод, без дублирования

Пример B — generic класс

public class Repository<T> where T : class
{
    private readonly List<T> _items = [];

    public void Add(T item) => _items.Add(item);
    public IEnumerable<T> GetAll() => _items;
    public T? Find(Func<T, bool> predicate) => _items.FirstOrDefault(predicate);
}

var contactRepo = new Repository<Contact>();      // T = Contact
var productRepo = new Repository<Product>();      // T = Product — тот же класс, два независимых хранилища

Пример C — constraints (where)

public class Cache<T> where T : class, new()
//                            ^класс (не struct)  ^есть публичный конструктор без параметров
{
    public T CreateDefault() => new T(); // new() constraint разрешает вызывать new T()
}

// Другие частые constraints:
// where T : struct           — только value types
// where T : IComparable<T>   — только типы, которые можно сравнивать (см. Пример A)
// where T : SomeBaseClass    — T обязан наследовать конкретный базовый класс
// where T : U                — T обязан быть тем же типом или наследником другого generic-параметра U

Пример D — ковариантность и контравариантность (out/in)

// IEnumerable<out T> — КОВАРИАНТНЫЙ: можно присвоить более узкий тип более широкой переменной
IEnumerable<string> strings = new List<string> { "a", "b" };
IEnumerable<object> objects = strings; // OK — string это object, и IEnumerable только ЧИТАЕТ T

// Action<in T> — КОНТРАВАРИАНТНЫЙ: можно присвоить более широкий тип более узкой переменной
Action<object> logAny = obj => Console.WriteLine(obj);
Action<string> logString = logAny; // OK — если умеет обработать любой object, справится и со string

[!info]+ Почему List<T> НЕ ковариантен, а IEnumerable<T> — да Ковариантность (out T) безопасна только для типов, которые ТОЛЬКО ВОЗВРАЩАЮТ T (только для чтения) — IEnumerable<T>, IReadOnlyList<T>. List<T> же позволяет и Add(T item) — если бы List<string> можно было присвоить List<object>, ничто не помешало бы вызвать list.Add(42) (int — тоже object) и получить InvalidCastException при попытке достать элемент как string. Поэтому изменяемые коллекции — инвариантны.

🎤 Вопросы с собеседования

Q: Зачем нужны generics, если есть object? A: object требует boxing/unboxing для value types (дорого) и не даёт проверку типов на этапе компиляции (ошибка вылезет только в рантайме). Generics — типобезопасность на этапе компиляции, без boxing.

Q: Что делает where T : ... (constraint)? A: Ограничивает, какие типы допустимы в качестве T — например where T : class (только reference types), where T : IComparable<T> (только типы, которые можно сравнивать), where T : new() (только типы с публичным конструктором без параметров).

Q: В чём разница между ковариантностью (out T) и контравариантностью (in T)? A: Ковариантность — можно присвоить более узкий (производный) тип более широкой переменной, безопасна только для "только чтения" (IEnumerable<out T>). Контравариантность — можно присвоить более широкий тип более узкой переменной, безопасна для "только записи/приёма" (Action<in T>). Изменяемые структуры вроде List<T> — ни то, ни другое (инвариантны), иначе легко сломать типобезопасность.

3.2 Делегаты и события

Почему это важно

Делегат — типобезопасная ссылка на метод: можно передать метод как параметр, сохранить в переменную, вызвать позже. Вся LINQ построена на делегатах (Func, Predicate). События — способ уведомить "кого-то" о произошедшем, не зная заранее, кто именно подписан.

Аналогия из жизни

Делегат - это розетка определённого стандарта: в неё можно включить любой прибор с подходящей вилкой, не важно чайник это или лампа - главное, форма совпадает. Event - это звонок в дверь подъезда: жильцы подписываются на звонок (+=/-=), но позвонить в чужую дверь снаружи или стереть чужую подписку может только хозяин подъезда, не любой прохожий.

Теория

Делегат объявляет СИГНАТУРУ метода (параметры + тип возврата), а не конкретную реализацию. Любой метод с подходящей сигнатурой можно присвоить переменной этого типа делегата.

Пример A — свой делегат

public delegate int Operation(int a, int b); // сигнатура: два int → int

int Add(int a, int b) => a + b;
int Multiply(int a, int b) => a * b;

Operation op = Add;
Console.WriteLine(op(2, 3));   // 5

op = Multiply;
Console.WriteLine(op(2, 3));   // 6 — та же переменная, другой метод

Пример B — встроенные делегаты: Action, Func, Predicate

Action<string> log = msg => Console.WriteLine($"[LOG] {msg}");        // без возврата
Func<int, int, int> add = (a, b) => a + b;                             // с возвратом (последний параметр — тип результата)
Predicate<int> isEven = n => n % 2 == 0;                               // Func<T, bool>, именованный частный случай

log("Старт");
Console.WriteLine(add(2, 3));       // 5
Console.WriteLine(isEven(4));       // True

Пример C — multicast-делегаты

Action pipeline = () => Console.WriteLine("Шаг 1");
pipeline += () => Console.WriteLine("Шаг 2");
pipeline += () => Console.WriteLine("Шаг 3");
pipeline(); // вызовутся ВСЕ три по порядку добавления

// Ловушка: если делегат ВОЗВРАЩАЕТ значение — при вызове ты получишь
// результат только ПОСЛЕДНЕГО метода в цепочке, промежуточные результаты потеряны.
Func<int> multi = () => 1;
multi += () => 2;
multi += () => 3;
Console.WriteLine(multi()); // 3, не 1+2+3 и не список [1,2,3]

Пример D — события (event)

public class Logger
{
    // event поверх делегата: снаружи класса можно ТОЛЬКО += / -=, нельзя вызвать
    // напрямую или перезаписать = (в отличие от обычного public поля-делегата)
    public event Action<string>? OnMessage;

    public void Log(string message)
    {
        Console.WriteLine(message);
        OnMessage?.Invoke(message); // null-conditional — если подписчиков нет, ничего не сломается
    }
}

var logger = new Logger();
logger.OnMessage += msg => Console.WriteLine($"Подписчик 1 увидел: {msg}");
logger.OnMessage += msg => File.AppendAllText("log.txt", msg + "\n");
logger.Log("Что-то произошло"); // выведется, плюс оба подписчика сработают

🤖 AI-инженерия: агентные системы часто описывают инструменты как Func<ToolCall, Task<Result>> — делегат, принимающий вызов инструмента и асинхронно возвращающий результат. Реестр инструментов агента — по сути Dictionary<string, Func<...>>, где ключ — имя инструмента.

// Метод ProcessOrder(decimal amount), который "обрабатывает" заказ и вызывает событие.

🎤 Вопросы с собеседования

Q: Чем Action, Func, Predicate отличаются друг от друга? A: Action<T> — делегат без возвращаемого значения. Func<T, TResult> — с возвращаемым значением (последний параметр типа — тип результата). Predicate<T> — то же самое, что Func<T, bool>, просто именованный частный случай для условий.

Q: Чем event отличается от обычного публичного поля-делегата? A: event ограничивает доступ снаружи класса только до +=/-= — нельзя вызвать напрямую (logger.OnMessage() не скомпилируется извне) и нельзя перезаписать через =, стерев все чужие подписки. Обычное публичное поле-делегат этого не защищает — инкапсуляция подписки, а не только вызова.

Q: Что произойдёт при вызове multicast-делегата, который возвращает значение? A: Вызовутся ВСЕ подписанные методы по порядку, но вызывающий код получит результат только ПОСЛЕДНЕГО — промежуточные результаты теряются молча. Частая причина багов, если ожидать список результатов.

3.3 LINQ — глубже

Почему это важно

Основы (Where/Select/Sum, отложенное выполнение) уже разобраны в Фазе 1 (1.8). Здесь — то, что реально спрашивают на Middle+: КАК LINQ превращается в SQL для IQueryable, и полный набор операторов, которыми пользуешься каждый день.

Аналогия из жизни

LINQ-запрос без .ToList() - это список покупок, лежащий на столе, а не поход в магазин. Пока список просто составлен - в холодильнике ничего не меняется. Как только кто-то реально идёт в магазин (foreach/.ToList()) - вот тогда список исполняется, и если содержимое исходных данных за это время поменялось, в магазине купят уже по новому списку.

Теория

LINQ — это набор extension-методов над IEnumerable<T> (LINQ to Objects, выполняется в памяти) и IQueryable<T> (LINQ to Entities/SQL через EF Core, выполняется в СУБД). Метод-синтаксис (.Where(...)) и query-синтаксис (from x in ... where ...) компилируются в одно и то же — метод-синтаксис используется в разы чаще на практике.

Пример A — основные операторы

var numbers = new List<int> { 5, 3, 8, 1, 9, 2 };

var filtered = numbers.Where(n => n > 3);                    // фильтр
var doubled = numbers.Select(n => n * 2);                    // преобразование
var sorted = numbers.OrderBy(n => n);                        // сортировка (ASC)
var grouped = numbers.GroupBy(n => n % 2 == 0 ? "чёт" : "нечёт"); // группировка
var joined = numbers.Join(doubled, n => n, d => d / 2, (n, d) => (n, d)); // соединение по ключу

// Агрегация — выполняется НЕМЕДЛЕННО (см. Пример B)
var sum = numbers.Sum();
var max = numbers.Max();
var count = numbers.Count(n => n > 3);

Пример B — отложенное vs немедленное выполнение (напоминание из 1.8 + расширение)

var query = numbers.Where(n => n > 3).OrderBy(n => n); // НИЧЕГО не выполнилось — построен план
numbers.Add(100);                                       // добавили ПОСЛЕ построения запроса

foreach (var n in query) Console.WriteLine(n);           // ВОТ здесь выполнилось, 100 тоже попадёт

// Откладывают: Where, Select, OrderBy, GroupBy, Join, Skip, Take
// Выполняют немедленно: ToList, ToArray, Count, Sum, First(OrDefault), Any, Max, Min

Пример C — IQueryable vs IEnumerable: как это доезжает до SQL

// IQueryable<T> (EF Core) — .Where() НЕ содержит логики фильтрации.
// Он строит Expression Tree и передаёт её в IQueryProvider.CreateQuery() —
// это создаёт НОВЫЙ объект запроса, ничего не выполняя.
IQueryable<Contact> query = dbContext.Contacts.Where(c => c.Name.StartsWith("И"));
// В этот момент SQL ещё не отправлен — только построено дерево выражений

var results = query.ToList(); // ВОТ тут IQueryProvider транслирует дерево в SQL и выполняет запрос в БД

// IEnumerable<T> (LINQ to Objects) — тот же .Where() тут уже настоящий делегат,
// выполняется built-in кодом .NET прямо в памяти, никакого SQL вообще нет.

[!info]+ 🆕 Механика IQueryable — откуда берётся трансляция в SQL Extension-методы IQueryable<T> не выполняют работу сами — они достраивают дерево выражений (Expression Tree) и через IQueryProvider.CreateQuery() создают новый экземпляр запроса. Реальное выполнение (и трансляция в SQL) запускается только при Execute() — то есть при материализации (.ToList(), foreach, и т.д.). Источник: разбор механики IQueryable-провайдеров (Habr, research-проход 2026-08-02).

Пример D — yield return для собственных LINQ-совместимых последовательностей

// Напоминание из 1.8: yield делает метод "ленивым генератором" — совместим с любым LINQ-оператором
IEnumerable<int> Fibonacci()
{
    int a = 0, b = 1;
    while (true) // бесконечная последовательность — безопасно благодаря лени
    {
        yield return a;
        (a, b) = (b, a + b);
    }
}

var first5 = Fibonacci().Take(5).ToList(); // [0, 1, 1, 2, 3] — вычислено ровно 5 значений, не больше

// На списке List<Contact> (с полем WorkContact.Company у части записей):
// 1. Сгруппируй контакты по Company через GroupBy (для Contact без Company — своя группа "без компании").
// 2. Для каждой группы выведи количество контактов и отсортируй группы по убыванию размера.

🎤 Вопросы с собеседования

Q: .Where(), .OrderBy(), .Select() — все они откладывают выполнение? А .FirstOrDefault(), .Count()? A: .Where(), .OrderBy(), .Select() — ВСЕ откладывают выполнение. .FirstOrDefault(), .Count(), .Any(), .Sum(), .ToList() — выполняются немедленно. Для IQueryable (EF Core) .FirstOrDefault() транслируется в SQL с LIMIT 1 — не тянет всю таблицу.

Q: КАК именно LINQ-запрос через IQueryable превращается в SQL? A: Extension-методы IQueryable строят дерево выражений (Expression Tree) через IQueryProvider.CreateQuery(), не выполняя ничего. Трансляция в SQL и реальное выполнение запускаются только при материализации (.ToList(), foreach).

3.4 Async/Await — под капотом

Почему это важно

По банку реальных вопросов Ozon — async/await internals (~4200 использований суммарно) и связанные темы (Task vs Thread, deadlock, ConfigureAwait) — один из самых частых блоков вопросов вообще. Поверхностного "это машина состояний" уже недостаточно на Middle+ уровне.

Аналогия из жизни

Заказ в ресторане, не готовка дома. Сделал заказ (await) - официант не стоит рядом, пока жарится стейк, а уходит и обслуживает другие столики. Тебя позовут, когда стейк готов. ThreadPool - это ограниченное число официантов на весь зал: если все столики одновременно закажут долгую готовку, официантов на всех не хватит, и обслуживание встанет, даже если кухня не занята.

Теория

async/await — синтаксический сахар над явной композицией продолжений (continuations). Компилятор разворачивает async-метод в отдельный сгенерированный класс — машину состояний.

Пример A — базовый синтаксис

async Task<int> GetDataAsync()
{
    await Task.Delay(1000); // не блокирует поток — освобождает его на время ожидания
    return 42;
}

int result = await GetDataAsync(); // await "разворачивает" Task<int> в int

Пример B — что генерирует компилятор (машина состояний)

// Компилятор превращает async-метод в класс-структуру с полями:
// - <>1__state          — текущее состояние (в каком месте метода мы находимся)
// - builder             — AsyncTaskMethodBuilder, управляет жизненным циклом Task
// - awaiter-поля        — по одному на каждый await в методе
// - временные локальные — переменные метода, "переживающие" await
//
// Каждый await — точка перехода между состояниями MoveNext().
// Именно поэтому исключение в async-методе "прилетает" туда, где его ждали (await),
// а не туда, где было брошено — Task хранит исключение, await его перевыбрасывает.

[!info]+ 🆕 Источник — канонический разбор Стивена Тоуба (разработчик .NET runtime) Это описание — не пересказ "по слухам", а прямое изложение серии статей Стивена Тоуба про внутреннее устройство async/await (перевод на Habr, research-проход 2026-08-02) — самый авторитетный русскоязычный материал по теме из найденных.

Пример C — классический дедлок на .Result, пошагово

// В UI/классическом ASP.NET (не ASP.NET Core) с SynchronizationContext:
async Task<int> SlowMethodAsync()
{
    await Task.Delay(1000); // после await продолжение хочет вернуться на UI-поток
    return 42;
}

// В обработчике клика UI-потока:
int result = SlowMethodAsync().Result; // ДЕДЛОК

Пошагово, почему зависает: 1. UI-поток вызывает .Result — блокирует САМ СЕБЯ, ожидая завершения задачи. 2. Внутри SlowMethodAsync после await Task.Delay(1000) продолжение пытается вернуться на ТОТ ЖЕ UI-поток (SynchronizationContext захвачен). 3. UI-поток занят ожиданием на шаге 1 — не может выполнить продолжение из шага 2. 4. Взаимная блокировка: никто не двигается.

В ASP.NET Core SynchronizationContext отсутствует — классический вариант этого дедлока там не воспроизводится. Но .Result/.Wait() там всё равно опасны — см. Пример D.

Пример D — ConfigureAwait(false) и почему .Result убивает ASP.NET Core иначе

// ConfigureAwait(false) — явно говорит: "продолжению не обязательно
// возвращаться в исходный SynchronizationContext/контекст, можно на любом потоке пула"
await SomeMethodAsync().ConfigureAwait(false);
// Хорошая практика для БИБЛИОТЕЧНОГО кода — не тащит за собой контекст без необходимости.
// TaskScheduler — второй, менее известный механизм возврата продолжения,
// используется когда SynchronizationContext отсутствует (например, в консоли/сервисе).

[!info]+ 🆕 ASP.NET Core: .Result не даёт дедлок, но убивает через ThreadPool starvation — с реальными цифрами Замер: 50 000 RPS с p99=40мс превращаются в 12 000 RPS с p99=4 сек при загрузке CPU всего 8%. Причина не дедлок, а массовая блокировка потоков пула: .Result синхронно блокирует поток, пока не завершится асинхронная операция — поток "заморожен", но числится занятым. ThreadPool наращивает число потоков по алгоритму hill-climbing (медленно, с задержкой ~6.4 сек на решение) — на массово заблокированных потоках это даёт разрушительную положительную обратную связь. Диагностика: dotnet-counters, метрики threadpool.thread.count/threadpool.queue.length. Решение — убрать .Result полностью, НЕ "лечить" через Task.Run() (создаёт ещё один блокирующий поток). Источник: research-проход по Habr, 2026-08-02.

[!info]+ 🆕 CPU-bound vs I/O-bound — тема, где "даже опытные кандидаты проваливаются" await НЕ занимает поток на время ожидания I/O (сеть, диск, БД) — поток освобождается обратно в пул, а не простаивает. Для CPU-bound работы (реальные вычисления, не ожидание) await сам по себе ничего не ускоряет — там нужен Task.Run(), чтобы явно уйти в пул потоков. Путать эти два случая — источник и дедлоков, и ненужной траты потоков.

Что будет, если забыть await:

async Task DoWorkAsync()
{
    SomeAsyncMethod(); // забыли await — метод ЗАПУЩЕН, но никто не ждёт его завершения
    Console.WriteLine("Готово"); // выведется РАНЬШЕ, чем SomeAsyncMethod реально закончит
    // Плюс: если SomeAsyncMethod бросит исключение — оно "потеряется",
    // никто его не перехватит (Task, за которым никто не следит через await).
}

CancellationToken — кооперативная отмена:

async Task DoWorkAsync(CancellationToken token)
{
    for (int i = 0; i < 1000; i++)
    {
        token.ThrowIfCancellationRequested(); // сам метод должен ПРОВЕРЯТЬ токен
        await Task.Delay(10, token);
    }
}
// Отмена — КООПЕРАТИВНАЯ: токен сам ничего не останавливает силой,
// метод должен согласиться проверять его и вежливо выйти.

🎤 Вопросы с собеседования

Q: Во что конкретно разворачивается async/await — из чего состоит сгенерированная машина состояний? A: Класс-структура с полями: <>1__state (текущее состояние), builder (AsyncTaskMethodBuilder), awaiter-поля (по одному на каждый await), временные локальные переменные метода. Каждый await — точка перехода между состояниями MoveNext().

Q: В чём разница между Task и Thread? A: Thread — реальный поток ОС, дорогой ресурс. Task — абстракция единицы работы, выполняется через ThreadPool (пул переиспользуемых потоков) — намного дешевле создавать, особенно много задач одновременно.

Q: Что такое deadlock и как его избежать при async/await? A: Классический deadlock в UI/старом ASP.NET — синхронное ожидание (.Result/.Wait()) асинхронного метода в потоке с контекстом синхронизации, который сам ждёт освобождения потока для продолжения. Решение — async до самого верха (async all the way), не смешивать sync/async вызовы.

Q: В ASP.NET Core SynchronizationContext нет — значит ли это, что .Result безопасен? A: Нет. Механизм убийства другой — ThreadPool starvation: .Result блокирует поток пула, поток числится занятым, но фактически простаивает в ожидании. При массовой блокировке throughput обваливается (см. Пример D — 50k→12k RPS при CPU всего 8%).

Q: Что делает ConfigureAwait(false)? A: Говорит, что продолжение после await не обязано возвращаться в исходный контекст синхронизации — избегает лишних переключений контекста, снижает риск deadlock в библиотечном коде.

Q: Что будет, если забыть await перед асинхронным вызовом? A: Метод запустится, но выполнение продолжится сразу дальше, не дожидаясь его завершения ("fire and forget" непреднамеренно) — плюс исключение из незаконченного Task потеряется, если за ним никто не следит.

Q: Как отменить асинхронную задачу через CancellationToken? A: CancellationToken передаётся ВНУТРЬ метода как параметр. Метод сам периодически проверяет token.IsCancellationRequested/ThrowIfCancellationRequested() и прерывает работу. Отмена кооперативная — токен ничего не останавливает силой.

3.5 Параллелизм — примитивы синхронизации

Почему это важно

По банку реальных вопросов Ozon это самый частый вопрос вообще — 2733 использования, больше любой другой темы в базе.

Аналогия из жизни

lock - ключ от переговорки: пока один человек внутри с ключом, остальные ждут в коридоре, зайти не может никто, даже если у них "срочно". SemaphoreSlim - та же переговорка, но рассчитанная на несколько человек сразу (например максимум 3 одновременно), а не строго на одного.

Теория

Когда несколько потоков одновременно читают/пишут общее состояние — нужна синхронизация, иначе race condition (гонка данных): результат зависит от непредсказуемого порядка выполнения потоков.

Пример A — lock (Monitor)

private readonly object _lock = new();
private int _counter;

public void Increment()
{
    lock (_lock) // только один поток одновременно внутри блока
    {
        _counter++;
    }
}
// lock(obj) { ... } разворачивается в:
// Monitor.Enter(obj, ref lockTaken); try { ... } finally { Monitor.Exit(obj); }
// НЕ работает со значимыми типами (value type копировался бы, каждый поток блокировал бы свою копию).
// НЕ работает с await внутри — ошибка КОМПИЛЯЦИИ, не рантайма.

Пример B — Mutex (межпроцессный)

using var mutex = new Mutex(false, "Global\\MyAppSingleInstance");
if (mutex.WaitOne(TimeSpan.Zero))
{
    // единственный экземпляр процесса во всей системе, не только в этом процессе
}
// lock работает только ВНУТРИ процесса. Для межпроцессной синхронизации — именованный Mutex/Semaphore.

Пример C — SemaphoreSlim (async-совместимый, N потоков одновременно)

private readonly SemaphoreSlim _semaphore = new(initialCount: 3); // максимум 3 одновременно

public async Task DoLimitedWorkAsync()
{
    await _semaphore.WaitAsync(); // в отличие от lock — совместим с await
    try
    {
        await SomeExpensiveOperationAsync();
    }
    finally
    {
        _semaphore.Release();
    }
}

Пример D — Interlocked (атомарные операции без блокировки)

private int _counter;

public void Increment() => Interlocked.Increment(ref _counter);
// Для простых операций (инкремент, сложение, обмен значений) — быстрее lock,
// не создаёт блокировку вообще, атомарность обеспечивает сам процессор.

[!info]+ 🆕 System.Threading.Channels — явно назван в банке Ozon, но раньше нигде не разбирался Channel<T> — lock-free producer/consumer очередь с полноценным async API (WriteAsync, TryWrite, WaitToWriteAsync, ReadAllAsync) — в отличие от устаревшего BlockingCollection<T> (блокирующий Monitor.Wait, нет async-варианта). Bounded-канал поддерживает 4 режима переполнения (BoundedChannelFullMode: Wait / DropNewest / DropOldest / DropWrite). Источник: research-проход по Habr, 2026-08-02. csharp var channel = Channel.CreateBounded<int>(capacity: 100); await channel.Writer.WriteAsync(42); // producer await foreach (var item in channel.Reader.ReadAllAsync()) { /* consumer */ }

[!info]+ Race condition — пример и почему его сложно заметить csharp // Без синхронизации: _counter++ — это ЧТЕНИЕ + ИНКРЕМЕНТ + ЗАПИСЬ, три отдельных шага. // Два потока могут прочитать одно и то же значение ДО того, как первый запишет своё — // один инкремент "теряется". На маленькой нагрузке баг может не проявляться вообще.

🎤 Вопросы с собеседования

Q: Какие примитивы синхронизации вы знаете, какой принцип работы? A: Monitor/lock (внутрипроцессный), Mutex (может быть именованным — межпроцессный), Semaphore/SemaphoreSlim (N потоков одновременно, Slim — async+CancellationToken), ReaderWriterLockSlim (раздельные блокировки чтения/записи), Interlocked (атомарные операции без блокировки), System.Threading.Channels (асинхронные очереди producer/consumer).

Q: Можно ли использовать lock с async/await? A: Нет — ошибка компиляции (await физически запрещён внутри lock). Решение — убрать асинхронный код из-под лока или использовать SemaphoreSlim.WaitAsync().

Q: Во что разворачивается lock, работает ли он со значимыми типами? A: lock(obj) { ... } → Monitor.Enter(obj, ref lockTaken); try { ... } finally { Monitor.Exit(obj); }. Со значимыми типами НЕ работает — value type передаётся по значению, каждый поток блокировал бы свою копию, а не общий объект.

Q: Можно ли использовать lock для межпроцессного взаимодействия? A: Нет — lock разворачивается в Monitor, сериализует доступ только ВНУТРИ процесса. Для межпроцессной синхронизации — именованный Mutex или Semaphore.

Q: Что такое race condition и как его обнаружить/предотвратить? A: Результат зависит от непредсказуемого порядка выполнения потоков при одновременном доступе к общему состоянию. Предотвращается синхронизацией (lock, Interlocked, потокобезопасные коллекции). Обнаружить сложно — баг может не проявляться на малой нагрузке и всплыть только в проде под реальной конкуренцией потоков.

Q: Что такое System.Threading.Channels и чем он лучше BlockingCollection<T>? A: Lock-free producer/consumer очередь с полноценным async API. BlockingCollection<T> использует блокирующий Monitor.Wait и не даёт async-варианта вообще.

🧩 Собираем всё вместе — переходный пример перед итоговым заданием

// Generics (3.1) + LINQ (3.3) + Async (3.4) + примитивы (3.5) на одной задаче:
// асинхронный generic-репозиторий с потокобезопасным кэшем.

public class AsyncCachedRepository<T> where T : class
{
    private readonly Dictionary<int, T> _cache = new();
    private readonly SemaphoreSlim _lock = new(1, 1); // async-совместимая защита кэша

    public async Task<T?> GetOrLoadAsync(int id, Func<int, Task<T?>> loader)
    {
        await _lock.WaitAsync();
        try
        {
            if (_cache.TryGetValue(id, out var cached))
                return cached; // уже в кэше — не грузим повторно

            var loaded = await loader(id); // асинхронная загрузка (условно — из БД/API)
            if (loaded is not null)
                _cache[id] = loaded;

            return loaded;
        }
        finally
        {
            _lock.Release();
        }
    }

    // LINQ поверх закэшированных данных — уже загруженное, синхронное чтение
    public IEnumerable<T> GetAllCached() => _cache.Values;
}

Что здесь произошло: AsyncCachedRepository<T> (generic, 3.1) хранит что угодно → SemaphoreSlim (3.5) защищает кэш от гонки при параллельных запросах, при этом совместим с await внутри → GetOrLoadAsync (3.4) асинхронно грузит данные только один раз на id, дальше отдаёт из кэша → GetAllCached() открывает результат для LINQ (3.3) без дублирования логики хранения.
