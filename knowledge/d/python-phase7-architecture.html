🎭 Аналогия

Планировка квартиры. Кухня отдельно от спальни не потому, что так красивее, а потому, что запахи и шум. Слои в приложении разделяют по той же причине: чтобы изменение в одном не тянуло за собой остальные.

📖 Теория

Слои

Домен          сущности и правила, ничего не знает о базе и вебе
Приложение     сценарии: «создать вакансию», «сменить статус»
Инфраструктура база, HTTP-клиенты, очереди
Интерфейс      маршруты FastAPI, CLI

Правило зависимостей: стрелки внутрь. Домен не импортирует SQLAlchemy. Проверяется просто - grep -r "sqlalchemy" domain/ должен быть пуст.

⚠️ Чистая архитектура в маленьком проекте даёт больше папок, чем пользы. Для трекера трёх слоёв достаточно: маршруты, сервисы, доступ к данным. Умение сказать, где она избыточна, ценится не меньше, чем умение её построить.

Repository и Unit of Work

class VacancyRepo:
    def __init__(self, session: Session):
        self._session = session

    def get(self, vid: int) -> Vacancy | None:
        return self._session.get(Vacancy, vid)

    def by_status(self, status: Status) -> list[Vacancy]:
        return list(self._session.scalars(
            select(Vacancy).where(Vacancy.status == status)
        ))

Repository прячет способ хранения. Unit of Work - это сессия SQLAlchemy: она уже держит транзакцию на группу изменений, отдельный класс поверх обычно не нужен.

Инструмент Когда
BackgroundTasks мелочь, потеря не страшна
RQ простые задачи, Redis уже есть
Celery расписание, повторы, цепочки, мониторинг
Таблица заданий в базе задач мало, лишний сервис не нужен

⚠️ Задача обязана быть идемпотентной: при повторе она выполнится ещё раз. Тот же принцип, что у джоб в слое 4 инфра-роадмапа.

Кэш

import redis, json

r = redis.Redis(decode_responses=True)

def top_vacancies(limit: int = 20) -> list[dict]:
    key = f"top:{limit}"
    if (cached := r.get(key)):
        return json.loads(cached)
    data = compute_top(limit)
    r.setex(key, 300, json.dumps(data, ensure_ascii=False))
    return data

Три вопроса к любому кэшу: 1. Сколько живёт запись. 2. Что происходит при изменении данных - сбрасываем или ждём истечения. 3. Что будет при недоступности Redis - приложение падает или работает медленнее.

Третий вопрос забывают чаще всего. Правильный ответ: кэш - ускоритель, приложение обязано работать без него.

Cache stampede: запись истекла, сто запросов одновременно пошли считать заново. Лечится блокировкой на пересчёт или разбросом времени жизни.

Отказоустойчивость

Приём Что делает
Таймаут ограничивает ожидание внешнего вызова
Повтор с ростом паузы переживает кратковременный сбой
Джиттер разводит одновременные повторы
Circuit breaker перестаёт звонить в мёртвый сервис
Деградация отдаёт часть данных вместо ошибки

⚠️ Повтор без ограничения одновременности превращает мелкий сбой в лавину: сервис прилёг на секунду, все клиенты ретраятся разом, он ложится совсем.

Выбор фреймворка

Когда брать
FastAPI новое API, async, автодокументация
Django админка из коробки, ORM, готовая аутентификация, CMS-подобное
Flask маленький сервис, полный контроль, готовое окружение

У Ивана реальный опыт с Flask и Django, и это надо называть: выбор осознанный, а не единственный знакомый вариант.

🔧 Практика

  1. Вынести бизнес-логику трекера из маршрутов в сервисный слой, маршруты оставить тонкими.
  2. Repository для вакансий и событий.
  3. Проверить правило зависимостей: grep -r "fastapi\|sqlalchemy" services/ должен быть пуст.
  4. Кэш на тяжёлую выборку разведчика с временем жизни и корректной работой при выключенном Redis.
  5. Обёртка @retry с экспоненциальной паузой и джиттером на сетевые вызовы разведчика.
  6. Написать в docs/ARCHITECTURE.md схему слоёв трекера с обоснованием, почему выбраны три, а не четыре.

💥 Сломай намеренно

  1. Выключить Redis и проверить, что трекер работает медленнее, а не падает. Если падает - починить.
  2. Убрать время жизни у кэша и посмотреть, как страница показывает устаревшее.
  3. Сделать повтор без ограничения и запустить сто задач против отвечающего с ошибкой сервиса.
  4. Импортировать SQLAlchemy в сервисный слой и убедиться, что проверка grep это ловит.
  5. Сделать задачу неидемпотентной и запустить дважды - получить дубли.

✅ Задание

Трекер с разделёнными слоями, тонкими маршрутами, репозиториями и кэшем, который переживает недоступность Redis. docs/ARCHITECTURE.md объясняет решения, включая то, где чистая архитектура была бы избыточна.

Критерий: можешь провести по схеме от HTTP-запроса до строки в базе и назвать, что придётся менять при замене PostgreSQL на другую базу.

🌍 Из жизни

Про архитектуру ради архитектуры. Проект на триста строк с пятью слоями, интерфейсами на каждый репозиторий и контейнером зависимостей. Читать его дольше, чем переписать. Признак зрелости - умение назвать, где слои избыточны.

Про кэш, который роняет приложение. Redis лёг, а приложение перестало отвечать целиком, потому что обращение к кэшу не обёрнуто. Кэш - ускоритель, и падать вместе с ним нельзя.

Про лавину повторов. Известный сценарий каскадного отказа: сервис прилёг на секунду, тысяча клиентов начала ретраиться одновременно, он не встал вообще. Джиттер и ограничение одновременности стоят двух строк кода.

❓ Вопросы с ответами

Как организуете код в проекте?

Слоями: маршруты только принимают и отдают, сервисы держат логику, слой данных знает про базу. Зависимости идут внутрь: сервисы не импортируют FastAPI, домен не импортирует SQLAlchemy. В маленьком проекте трёх слоёв хватает, полная чистая архитектура там даёт больше папок, чем пользы.

Когда нужна очередь, а когда хватит фоновой задачи?

BackgroundTasks для мелочи, потеря которой не страшна: она живёт в процессе и исчезает при перезапуске. Очередь нужна, когда задачу нельзя потерять, нужны повторы, расписание или видимость статуса.

Как кэшируете?

С явным временем жизни и сбросом при изменении данных. Главное правило - приложение обязано работать при недоступности кэша, медленнее, но работать. Плюс защита от одновременного пересчёта после истечения.

Как защищаетесь от отказов внешних сервисов?

Таймаут на каждый вызов, повтор с растущей паузой и джиттером, ограничение одновременности. Для часто отказывающего - размыкатель, чтобы не звонить в мёртвый сервис. И деградация: отдать часть данных с пометкой лучше, чем ошибку.

FastAPI, Django или Flask - как выбираете?

По задаче. FastAPI для нового API с async и автодокументацией. Django, когда нужны админка, ORM и аутентификация из коробки. Flask для маленького сервиса с полным контролем. Работал с Flask и Django на реальных задачах, поэтому выбор осознанный.
