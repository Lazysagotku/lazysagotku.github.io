Основной (курс System Design.docx, менторы Авито/Альфа-Банк/Premier, Глава 8) — 5 этапов

Единственная явная цифра по времени во всей главе: "скорее всего, у тебя будет не больше часа от начала интервью до его завершения" — поэтапной раскладки по минутам в источнике НЕТ, только общий лимит ~1 час. Не выдумываю раскладку, которой нет в материале.

  1. Требования. Ключевая мысль: "на этом собеседовании не тебе задают вопросы, а ты их задаёшь". Функциональные — роли, что каждая роль может делать, как работает поиск, способы оплаты. Нефункциональные — обязательно спросить: DAU и MAU (чтобы посчитать RPS — не средние цифры, а именно ПИКОВУЮ нагрузку: "во сколько раз пик превышает среднюю?"), число пользователей через N лет, объём загружаемых данных, соотношение чтение/запись, срок хранения данных.
  2. Расчёты. Точность не нужна — порядок величины важен (месяц = 30 дней, а не 30.44 — это нормально). Зачем: (а) понять масштаб системы (10 серверов или 10 000?), (б) выявить критичные компоненты (огромный трафик → нужен агрессивный кэш+CDN), (в) обосновать архитектурные решения. Держать под рукой таблицы степеней 10 и таблицу задержек.
  3. Домены и API. Выписать все сущности, вместе с интервьюером отметить, что вне скоупа задачи. Дальше — выбор API (REST/GraphQL) с явным обоснованием выбора, не молча.
  4. High Level Design. Рисовать на высоком уровне, не закапываться в детали раньше времени. Начинать проще — от пользователя. Подписанные стрелки облегчают понимание. Не обязательно сразу несколько дата-центров — один достаточен для старта, но стоит упомянуть, что для отказоустойчивости рассматривается мультирегион. Избегать циклических зависимостей.
  5. Low Level Design. Вернуться по архитектуре и принять конкретные решения по каждому компоненту — не только проговорить, но и прописать: какие были варианты, почему выбран этот, плюсы/риски.

Тайминг на 40-45 минут, если интервьюер даёт структуру по времени: представление задачи (~5) → требования (~5) → сущности (~2) → API (~5) → потоки данных (~5) → high-level дизайн (~10-15) → углубление в узкое место (~10). Выбрать 3 основные фичи и сфокусироваться, не пытаться охватить всё; вести встречу самому.

Частые ошибки на собесе (Глава 8, дословно — это то, что реально роняет кандидатов)

1. Использование в архитектуре незнакомых технологий. "Если ты упомянул Kafka, будь готов объяснить, почему она лучше RabbitMQ для этого кейса. Если ты разбираешься в теме на уровне «где-то слышал», то, скорее всего, это всплывёт именно сейчас. Лучше выбери решение, которое тебе знакомо, даже если оно звучит не очень круто." — прямое применение к тебе: не вставлять в схему то, что не сможешь защитить на низком уровне.

2. Требования ради требований. Спросил "сколько пользователей через 5 лет" — а зачем тебе это число? Если не можешь ответить, для чего именно оно используется дальше в расчётах — вопрос был для галочки, а не по делу.

3. "Строительство космолёта". Три сплетённых ошибки: пытаться сказать всё, что знаешь; расширять систему за рамки задачи; пытаться спроектировать систему, меняющую мир, за один час. Лечится: чётко вычеркнуть домены не по теме сразу на этапе 3, помнить про реальные ограничения (большинство компаний — не Google по бюджету).

4. Игнорирование продуктовых метрик. "Разработчик, который мыслит в терминах бизнеса (DAU, retention, conversion rate) и понимает, как технические решения влияют на эти метрики, ценится намного выше." — не только "как построить", но и "зачем бизнесу это нужно".

Зоны ответственности backend-разработчика в system design (Глава 5)

  • Архитектура и управление данными — где/как хранятся данные, схема, масштабируемая от тысяч до миллионов записей, целостность в распределённых системах. Контрольный вопрос себе: "Что будет, если база данных внезапно упадёт?"
  • API и интеграции — гарантия, что новые версии не ломают старых клиентов. Контрольный вопрос: "Что будет, если сервис отвечает с задержкой, и как это влияет на пользователя?"
  • Бизнес-логика — например, платёжный флоу с транзакциями; обработка дублей запросов и таймаутов, когда неизвестно, применился ли эффект.
  • Инфраструктура и производительность — кэширование, шардирование/партиционирование, мониторинг, CI/CD.

Типовые задачи на собесе (названы явно в курсе): URL Shortener, Chat, лента соцсети, платёжная система (ACID + фрод), видеоплатформа.

Разобранный пример — URL Shortener: Frontend → API Gateway/LB → Backend (URL Service создаёт короткую ссылку / Redirect Service перенаправляет / Analytics Service собирает статистику) → БД (таблицы urls и clicks) → Cache (Redis, для быстрых редиректов) → брокер (Kafka/RabbitMQ, асинхронная отправка событий кликов в Analytics). Ключевая мысль: не нужно 30 компонентов и 10 микросервисов — показывай схему, которая реально обоснована требованиями.

Что реально оценивает интервьюер (4 пункта): системное мышление (видишь картину целиком, думаешь про отказы и edge cases) → моделирование данных (схемы БД, выбор типа БД, шардирование) → масштабируемость (типовые узкие места, горизонтальное масштабирование) → практичность (обоснование выбора технологий, операционные риски).

Масштабирование и нагрузка (Глава 5, часть 2)

  • Вертикальное (Scale Up) — усилить один сервер, есть физический потолок.
  • Горизонтальное (Scale Out) — добавлять узлы. Пример из курса: ВКонтакте стартовал на одном PostgreSQL, вырос до тысяч узлов с собственными системами хранения по мере роста аудитории.
  • Эластичность — авто-подстройка под нагрузку (K8s HPA), но есть cold start — увеличение ресурсов не мгновенно.

5 техник, которые реально используются: шардирование, репликация (Master-Slave / Multi-Master), event-driven + очереди (Kafka/RabbitMQ), CQRS + Event Sourcing (разделить команды и запросы; хранить историю изменений, не только текущее состояние), кэширование на всех уровнях (приложение → распределённый кэш → CDN).

Типы узких мест и лечение: CPU-bound → параллелизм/асинхронность/выделенные воркеры. Memory-bound → оптимизация структур данных, распределённый кэш. I/O-bound → асинхронный I/O, батчинг, кэш, очереди. Network-bound → сжатие данных, gRPC вместо REST, CDN.

Стратегии смягчения перегрузки (это компромиссы, не бесплатные решения): Graceful Degradation (отключить часть функциональности), Rate Limiting/Throttling, Backpressure (система сигнализирует, что не может принять больше), Circuit Breaker, Bulkhead Pattern (изолировать ресурсы, чтобы отказ одного компонента не утопил всё).

Метрики для мониторинга: Latency, Throughput (RPS/QPS), Error Rate, Resource Utilization, Saturation. Инструменты: Prometheus+Grafana, OpenTelemetry, ELK/EFK, Jaeger.

Балансировка нагрузки (Глава 5, часть 3 — расширяет уже имевшуюся находку из Tproger)

L4 (транспортный) — по IP/порту, быстрый, не видит содержимое запроса. L7 (прикладной) — анализирует HTTP-заголовки/пути/куки, гибкая маршрутизация (/api/payments → один сервис, /api/profile → другой).

Внешние vs внутренние балансировщики: внешние принимают пользовательский трафик, гасят DDoS, терминируют SSL (пример из курса — Яндекс.Музыка через CDN+внешние балансировщики). Внутренние — минимальная задержка внутри микросервисной архитектуры. Отдельная категория — балансировщики БД (разделение чтения/записи).

Алгоритмы (расширяет уже известное): Round Robin, Weighted Round Robin, Least Connections, Weighted Least Connections, Response Time-based, Consistent Hashing (один и тот же пользователь всегда попадает на один сервер — пример: кэш изображений листинга не гоняется между серверами при повторном открытии).

Хранение сессий: Sticky sessions → cookie-based → IP-based (ненадёжно) → внешнее хранилище (Redis/БД) — любой сервер может обработать запрос, крах сервера не роняет сессию → Stateless (JWT).

Health checks: активные (балансировщик сам шлёт тестовые запросы) vs пассивные (анализ реальных запросов). При отказе — сервер убирается из пула, включается Circuit Breaker.

Микросервисные паттерны: Service Discovery (Consul/etcd/K8s), Traffic Splitting/Canary (1% → 10% → 100%), Feature Flags.

Хранение данных — 10-шаговый процесс проектирования (Глава 5, часть 4)

  1. Цели и сценарии использования — что храним, кто потребляет, какой SLA (держать в уме CAP-теорему).
  2. Классификация данных — по структуре (структурированные/полу/неструктурированные), по жизненному циклу (hot/warm/cold), по критичности (деньги/заказы vs логи/кэш).
  3. Нефункциональные требования — объём, темп роста, consistency vs availability (снова CAP), частота доступа.
  4. Выбор модели хранения — реляционная (строгая схема/транзакции) / документная / key-value (быстрый доступ) / колоночная (аналитика, ClickHouse/Cassandra) / графовая / объектная (S3). Можно комбинировать разные типы под разные задачи.
  5. Логическая схема — сущности/связи, ключи, индексы.
  6. Физическая схема — шардирование (по пользователю/региону/дате), репликация, архивирование холодных данных.
  7. Оптимизация — индексы, кэш, материализованные представления, партиционирование.
  8. Отказоустойчивость — регулярные бэкапы (полные+инкрементальные), гео-репликация, тестирование disaster recovery.
  9. Мониторинг и алерты — время ответа запросов, рост БД, нагрузка на реплики; алерты на упавшую реплику/нехватку места.
  10. Документация и регулярный пересмотр стратегии по мере роста системы.

Практический совет из курса: начинать с одной БД (обычно PostgreSQL), добавлять NoSQL и кэш по мере роста нагрузки. Всегда проектировать бэкап/восстановление заранее — "сэкономит много нервов".
