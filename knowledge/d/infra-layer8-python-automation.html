Второе требование в вакансии Сбера: «навыки автоматизации на любом скриптовом языке и желание их регулярно применять». Формулировка про желание - подсказка: ищут человека, который сам находит рутину и убирает её.

🎭 Аналогия

Конвейер станков. Каждая команда - станок с одним входом и одним выходом, | - лента между ними. Задача решается расстановкой станков, а не одним умным устройством.

Аналогия для GIL. Одна касса в магазине. Пока кассир пробивает товар, очередь стоит. Но если кассир ждёт, пока клиент найдёт карту, он может обслужить соседнего. Поэтому потоки помогают на ожидании и не помогают на счёте.

🗺 Карта мест

Сделать: bash-скрипт с правильной шапкой, задача в cron, Python-скрипт эксплуатации с логами, аргументами и кодами выхода, плюс десяток однострочников наизусть.

Понять: скрипт эксплуатации - конвейер команд с одним входом и одним выходом. Ценится предсказуемость: set -euo pipefail, лог каждого запуска, код возврата, идемпотентность (второй запуск не ломает результат первого).

Где писать: /opt/scripts/ на сервере (в репо, не только на диске); расписание - crontab -e или systemd timer; Python - в своём venv.

Чем запустить: bash script.sh, python3 script.py; cron запускает сам, ты только ждёшь.

Где смотреть результат:

echo $?                          # код выхода последней команды: 0 - хорошо
tail -f /var/log/scripts/имя.log # свой лог скрипта
grep CRON /var/log/syslog        # запускал ли cron и когда
systemctl list-timers            # если через systemd timer

Как понять, что получилось: скрипт, запущенный дважды подряд, даёт тот же результат; в логе виден каждый запуск по расписанию с датой; упавший шаг останавливает скрипт с понятным сообщением, а не идёт дальше молча.

Когда автоматизировать не надо - ответ, показывающий зрелость:

Когда задача разовая, когда правила меняются каждую неделю, и когда цена ошибки автоматики выше цены ручной работы. Скрипт, который молча делает не то, хуже человека, который делает медленно.

Однострочники, которые просят написать

# коды ответа в access.log
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# топ URL и топ IP
awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -20
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# ошибки по типу в логе приложения
grep -oP 'ERROR \K\w+' app.log | sort | uniq -c | sort -rn

# самые медленные запросы
grep -oP 'rt=\K[0-9.]+' access.log | sort -rn | head

# что занимает место
du -h / --max-depth=1 2>/dev/null | sort -rh | head -20

# удалить логи старше 30 дней
find /var/log -name "*.log" -mtime +30 -delete

Связка sort | uniq -c | sort -rn - главная. uniq считает только соседние повторы, поэтому сортировка перед ним обязательна. Уметь писать вслепую.

Флаги, отличающие знающего: grep -c посчитать, -v исключить, -A5 -B5 контекст, -oP вырезать часть, zgrep искать в сжатых, cut -d',' -f2,5 колонки, sort -u с удалением дублей.

Шапка bash-скрипта

#!/usr/bin/env bash
set -euo pipefail
Флаг Что делает
-e выйти при первой ошибке
-u ошибка при обращении к необъявленной переменной
-o pipefail код возврата конвейера - первый ненулевой

⚠️ -e мешает там, где ненулевой код ожидаем - например в цикле проверки хостов. Тогда set -uo pipefail и проверка кода руками. Умение назвать это исключение отличает понимающего от скопировавшего.

Три ловушки cron

  1. Урезанное окружение. PATH короткий, переменных из профиля нет. Абсолютные пути везде.
  2. Вывод исчезает. Всегда >> /var/log/имя.log 2>&1.
  3. Наложение запусков. flock -n /tmp/task.lock в строке cron.

Что ценят в Python-скриптах эксплуатации

  • Стандартная библиотека вместо зависимостей - скрипт запустится на любом сервере.
  • argparse вместо разбора sys.argv - сразу появляется --help.
  • logging вместо print - уровни, время, вывод в файл.
  • subprocess.run(..., check=True, capture_output=True, timeout=30) вместо os.system.
  • Точечная обработка ошибок. Голый except прячет опечатки вместе с сетевыми сбоями.
  • Таймауты на всё сетевое. Без них скрипт однажды повиснет навсегда.
  • Идемпотентность. Повторный запуск не должен плодить: ON CONFLICT DO NOTHING, проверка существования.

Python как язык - апдейт

  • Что нового в 3.12 и 3.13: сообщения об ошибках, типизация, экспериментальный free-threaded режим.
  • Типизация: аннотации, mypy, dataclasses, pydantic.
  • GIL: threading для ввода-вывода, asyncio для высоконагруженного ввода-вывода, multiprocessing для счёта.
  • Тесты: pytest, фикстуры, параметризация, моки.

🔧 Практика - три скрипта в репозиторий

Сложить в l2code/Playground/scripts/, залить в git.

1. log_errors.py - разбор лога с подсчётом по типу и фильтром по времени:

#!/usr/bin/env python3
"""Считает ошибки по типу в логе. Тип - первое слово после ERROR."""
import re, sys
from collections import Counter

def count_errors(path: str, since: str | None = None) -> Counter:
    pattern = re.compile(r"ERROR\s+(\w+)")
    found = Counter()
    with open(path, encoding="utf-8", errors="replace") as f:
        for line in f:
            if since and since not in line:
                continue
            if (m := pattern.search(line)):
                found[m.group(1)] += 1
    return found

if __name__ == "__main__":
    since = sys.argv[2] if len(sys.argv) > 2 else None
    for kind, count in count_errors(sys.argv[1], since).most_common():
        print(f"{count:6d}  {kind}")

Что отметят: построчное чтение вместо read() целиком - лог может быть в гигабайты; errors="replace" - в логах бывает битая кодировка.

2. check_hosts.py - параллельная проверка доступности:

#!/usr/bin/env python3
"""Проверяет доступность хостов по TCP-порту. Параллельно, с таймаутом."""
import socket, sys
from concurrent.futures import ThreadPoolExecutor

def check(host: str, port: int = 443, timeout: float = 3.0) -> tuple[str, bool]:
    try:
        with socket.create_connection((host, port), timeout=timeout):
            return host, True
    except OSError:
        return host, False

def main() -> int:
    hosts = [l.strip() for l in open(sys.argv[1], encoding="utf-8")
             if l.strip() and not l.startswith("#")]
    port = int(sys.argv[2]) if len(sys.argv) > 2 else 443
    with ThreadPoolExecutor(max_workers=20) as pool:
        results = list(pool.map(lambda h: check(h, port), hosts))
    failed = [h for h, ok in results if not ok]
    for host, ok in results:
        print(f"{host:<30} {'OK' if ok else 'FAIL'}")
    return 1 if failed else 0

if __name__ == "__main__":
    sys.exit(main())

Что отметят: таймаут обязателен, иначе зависнет на первом мёртвом хосте; ненулевой код возврата, чтобы cron и CI увидели проблему.

3. csv_to_db.py - загрузка пачками с защитой от повторного запуска:

BATCH = 1000
cur.executemany(
    "INSERT INTO t (id, name, amount) VALUES (%s, %s, %s) "
    "ON CONFLICT (id) DO NOTHING", batch)

Что отметят: пачками вместо построчной вставки - на миллионе строк разница в десятки раз; ON CONFLICT DO NOTHING делает скрипт перезапускаемым; коммит по пачкам, чтобы транзакция не висела часами.

4. Бонус: daily_report.sh - собирает состояние стенда (место, память, статус сервисов, число пятисоток за сутки) и шлёт в Telegram. В cron через flock.

5. Покрыть Скаута тестами, добавить типизацию, прогнать mypy.

🌍 Из жизни

Про метрику «руководство справилось само». Это лучшее, что можно сказать про инструмент. Она говорит и про качество кода, и про то, что автор думал о пользователе. На собеседовании такая метрика весит больше, чем перечисление технологий.

Про молчащие скрипты в cron. Самый частый способ потерять автоматизацию: скрипт перестал работать полгода назад, вывод шёл в никуда, никто не заметил. Поэтому у любой периодической задачи должен быть не только алерт на падение, но и алерт на отсутствие успешной отработки.

❓ Вопросы с ответами

Bash или Python - что выберете?

Bash, если задача склеить существующие утилиты в конвейер: разбор логов, обход файлов, проверки. Python, когда появляется логика, структуры данных, работа с API или базой. Граница там, где в bash начинаются массивы и вложенные условия.

Как решаете, что автоматизировать?

Смотрю, что делается часто и одинаково. Разовую задачу дешевле сделать руками. Автоматизирую то, где ручная работа регулярна и где ошибка человека повторяется.

Что означает set -euo pipefail?

Выйти при первой ошибке, ругаться на необъявленные переменные, брать код возврата конвейера по первому неуспеху. Исключение - циклы, где ненулевой код ожидаем.

Скрипт работает из терминала и падает из cron. Почему?

Урезанное окружение: короткий PATH, нет переменных из профиля. Лечится абсолютными путями и перенаправлением вывода в лог, иначе падение вообще не видно.

Что такое идемпотентность и зачем она в скриптах?

Повторный запуск не ломает и не плодит. В загрузке данных это ON CONFLICT DO NOTHING, в создании ресурсов - проверка существования. Скрипт, который нельзя перезапустить, нельзя и поставить в автоматику.

Что блокирует GIL?

Одновременное выполнение байткода Python в нескольких потоках. На вводе-выводе GIL отпускается, поэтому потоки там помогают. На счёте не помогают - нужен multiprocessing.
