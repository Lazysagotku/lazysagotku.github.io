3.0.1 Исключения — try/catch/finally

Аналогия: готовишь ужин (try) → вспыхнуло масло, берёшь ИМЕННО тот огнетушитель (catch по типу) → плиту выключаешь всегда, сгорело или нет (finally).

Суть: try — код, который может бросить исключение. catch — обработка конкретного (или любого) типа, порядок ОТ специфичного к общему. finally — выполняется ВСЕГДА, даже при return внутри try/catch. throw; при перевыбросе сохраняет исходный stack trace, throw ex; его перезаписывает — теряется, откуда ошибка пришла на самом деле.

try { var r = 10 / int.Parse(input); }
catch (DivideByZeroException) { /* конкретный тип первым */ }
catch (FormatException) { /* ... */ }
catch (Exception ex) { /* общий — последним */ }
finally { /* всегда */ }

Q&A: - Почему нельзя ловить catch (Exception ex) везде? → маскирует непредвиденные ошибки, усложняет отладку. - throw vs throw ex? → throw; сохраняет stack trace, throw ex; его сбрасывает на текущую строку. - Как using связан с try/finally? → синтаксический сахар — компилятор вызывает Dispose() в finally. Полная механика Dispose-паттерна — Phase1 §1.8.

3.0.2 ref/out/in, params

Аналогия: ref — блокнот с записями, друг дописывает и возвращает; out — чистый блокнот, друг обязан заполнить; in — блокнот "только почитай"; params — стопка стикеров любой высоты.

Суть: ref — по ссылке, переменная должна быть проинициализирована ДО вызова, метод читает и меняет. out — по ссылке, без обязательной инициализации ДО, но метод ОБЯЗАН присвоить перед выходом (TryParse-паттерн). in — по ссылке, только чтение, экономит копирование больших struct. params — переменное число аргументов как массив. Ни один из ref/out/in не работает в async-методах (ошибка компиляции).

void Increment(ref int x) => x++;
bool TryDivide(int a, int b, out int result)
{
    if (b == 0) { result = 0; return false; }
    result = a / b; return true;
}

Q&A: - Главное отличие ref от out? → ref требует инициализации ДО вызова, out — нет, но out обязателен к присвоению ВНУТРИ метода. - Зачем in? → не копировать большой struct при каждом вызове, при этом запретить его менять.

3.1 Generics

Аналогия: универсальный ящик для переезда — один и тот же ящик под книги, посуду или одежду, просто каждый раз кладёшь в него что-то одно конкретное.

Суть: T — заглушка для типа, подставляется при использовании. Типобезопасность на компиляции + для value types никакого boxing. where T : ... — ограничивает допустимые типы (class, struct, new(), IComparable<T>, конкретный базовый класс). IEnumerable<out T> ковариантен (только читает T), Action<in T> контравариантен (только принимает T) — изменяемые коллекции вроде List<T> инвариантны.

public class Repository<T> where T : class, new()
{
    private readonly List<T> _items = [];
    public void Add(T item) => _items.Add(item);
    public T CreateDefault() => new T(); // new() constraint разрешает это
}

Q&A: - Зачем generics, если есть object? → без boxing, ошибка типа ловится на компиляции, не в рантайме. - Почему List<T> не ковариантен, а IEnumerable<T> — да? → List<T>.Add() мог бы сломать типобезопасность при ковариантности; IEnumerable<T> только читает — безопасно.

3.2 Делегаты и события

Аналогия: делегат — розетка стандартной формы, включаешь любой прибор с подходящей вилкой. event — звонок в подъезд: жильцы подписываются (+=/-=), но звонить снаружи или стирать чужие подписки может только хозяин.

Суть: делегат — типобезопасная ссылка на метод (сигнатура, не реализация). Action — без возврата, Func — с возвратом (последний параметр — тип результата), Predicate<T> = Func<T, bool>. Multicast (+=) вызывает ВСЕ подписанные методы, но при возврате значения отдаёт результат только последнего. event поверх делегата ограничивает снаружи класса до +=/-= — нельзя вызвать напрямую или стереть чужие подписки через =.

public event Action<string>? OnMessage;
public void Log(string msg) { Console.WriteLine(msg); OnMessage?.Invoke(msg); }

Q&A: - Чем event отличается от публичного поля-делегата? → event не даёт вызвать напрямую и не даёт перезаписать =, только +=/-=. - Что вернёт multicast-делегат с несколькими подписчиками? → результат ТОЛЬКО последнего в цепочке, промежуточные теряются.

3.3 LINQ — глубже

Аналогия: список покупок на столе — пока никто не пошёл в магазин, в холодильнике ничего не меняется. Пошёл (foreach/.ToList()) — вот тогда список исполняется по актуальным данным.

Суть: .Where()/.Select()/.OrderBy()/.GroupBy() откладывают выполнение, .ToList()/.Count()/.Sum()/.First(OrDefault) выполняют немедленно. Для IQueryable (EF Core) методы строят Expression Tree через IQueryProvider.CreateQuery() — SQL генерируется и выполняется только при материализации, не раньше.

var query = numbers.Where(n => n > 3).OrderBy(n => n); // ничего не выполнилось
numbers.Add(100);                                       // добавили ПОСЛЕ
foreach (var n in query) { }                             // выполнилось здесь, 100 тоже попадёт

Q&A: - КАК IQueryable превращается в SQL? → строит дерево выражений, транслирует и выполняет только при .ToList()/foreach. - IEnumerable vs IQueryable — где выполняется код? → IEnumerable — в памяти (LINQ to Objects), IQueryable — транслируется в SQL и выполняется в БД.

3.4 Async/Await — под капотом

Аналогия: заказ в ресторане, не готовка дома — сделал заказ (await), официант уходит обслуживать другие столики, а не стоит у плиты. ThreadPool — ограниченное число официантов на зал.

Суть: компилятор превращает async-метод в машину состояний (<>1__state, builder, awaiter-поля). await не блокирует поток на I/O — освобождает его в пул. .Result/.Wait() в UI/старом ASP.NET с SynchronizationContext → классический дедлок (поток ждёт сам себя). В ASP.NET Core дедлока нет, но .Result вызывает ThreadPool starvation — массовая блокировка потоков пула роняет throughput в разы при низкой CPU-загрузке. ConfigureAwait(false) — продолжению не обязательно возвращаться в исходный контекст. CancellationToken — кооперативная отмена, метод сам обязан проверять.

async Task<int> SlowAsync() { await Task.Delay(1000); return 42; }
int r = SlowAsync().Result; // дедлок в UI-потоке с SynchronizationContext

Q&A: - Из чего состоит машина состояний async-метода? → <>1__state, AsyncTaskMethodBuilder, awaiter-поля (по одному на await), временные локальные. - Почему .Result опасен в ASP.NET Core, если дедлока там нет? → ThreadPool starvation: поток блокирован, но числится занятым — throughput падает даже при низкой CPU-загрузке. - Что будет, если забыть await? → метод запущен, но не ожидается — код продолжится раньше времени, исключение из Task может потеряться.

3.5 Параллелизм — примитивы синхронизации

Аналогия: lock — ключ от переговорки, пока один внутри, остальные ждут в коридоре. SemaphoreSlim — та же переговорка, но на несколько человек сразу (например 3), не строго одного.

Суть: lock/Monitor — внутрипроцессный, НЕ работает со значимыми типами и НЕ совместим с await внутри (ошибка компиляции). Mutex — межпроцессный (именованный). SemaphoreSlim — N потоков одновременно, async-совместим (WaitAsync()). Interlocked — атомарные операции без блокировки вообще, для простых случаев (инкремент и т.п.). Channels — lock-free async producer/consumer очередь, замена устаревшему BlockingCollection<T>.

private readonly SemaphoreSlim _lock = new(1, 1);
await _lock.WaitAsync();
try { /* критическая секция, можно с await внутри */ }
finally { _lock.Release(); }

Q&A: - Можно ли lock с async/await? → нет, ошибка КОМПИЛЯЦИИ. Решение — SemaphoreSlim.WaitAsync(). - Работает ли lock со значимыми типами? → нет — value type копируется, каждый поток блокировал бы свою копию. - Работает ли lock межпроцессно? → нет, только Mutex/Semaphore (именованные).
