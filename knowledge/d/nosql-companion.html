NoSQL — живой companion-документ

99 строк · источник l2code/NoSQL_Companion.md

Как остальные companion-файлы — постоянно пополняется. Источник — присланный видео-конспект (часть 1: "Что такое NoSQL"), структурирован и проверен на точность, с исправлением пары неточностей.

Сначала SQL — от чего мы говорим "No"

Аналогия из жизни: реляционная БД — как таблица в Excel, только с возможностью СВЯЗЫВАТЬ данные между разными листами через общий идентификатор.

Суть: реляционные БД хранят данные в таблицах (строки + столбцы), логически связанных между собой (relation = связь). Столбец — тип данных, ячейка — значение, строка — набор значений одного объекта. Первичный ключ — уникальный идентификатор строки; используется в другой таблице как внешний ключ для связи.

Ключевые свойства: - Схема (schema) — жёсткое описание структуры таблицы заранее. Изменение структуры (добавить/убрать столбец) затрагивает ВСЕ данные в таблице. - ACID — целостность и согласованность данных гарантирована даже при сбоях сети/железа. Критично для финансовых данных.

Примеры: MS SQL Server, Oracle Database, MySQL, PostgreSQL.

NoSQL — узкоспециализированные форматы под конкретные задачи

Общая идея: хранить данные НЕ в реляционных таблицах — ради производительности, масштабируемости или удобства под конкретный сценарий использования.

1. Key-Value (ключ-значение)

Аналогия из жизни: гардероб в театре — сдаёшь пальто, получаешь номерок (ключ). Чтобы забрать пальто (значение), нужен только номерок — никто не спрашивает, из чего пальто сшито и какого оно фасона.

Суть: пара "уникальный ключ → значение", без предопределённой структуры (значением может быть число, строка, даже другая пара ключ-значение). Многие такие БД хранят данные в RAM — меньше объём, но огромная скорость. Никаких сложных запросов и связей — только "запиши по ключу" / "получи по ключу".

Где использовать: кэш, пользовательские сессии, корзина в интернет-магазине (ключ — id пользователя, значение — товары в корзине).

Примеры: Redis, Memcached, DynamoDB.

2. Wide-Column (широкие столбцы / колоночные)

Суть: развитие key-value — в значении можно хранить сразу несколько столбцов. Похоже на реляционную БД, но БЕЗ схемы — можно хранить разнородные неструктурированные данные.

Где использовать: логи, данные с IoT-устройств, аналитика больших объёмов.

Примеры: Cassandra, HBase, (⚠️ см. ниже про ClickHouse).

[!info]+ Уточнение точности — ClickHouse не совсем та же категория Источник объединяет Cassandra/HBase и ClickHouse в одну группу — это упрощение. Cassandra/HBase — классические wide-column NoSQL для быстрой записи и поиска по ключу при огромном масштабе. ClickHouse — колоночная аналитическая (OLAP) база для быстрой агрегации по большим таблицам — решает другую задачу (аналитика/отчёты, не key-based lookup). На собесе стоит различать эти два случая, если разговор зайдёт глубже "оба хранят данные по столбцам".

3. Document DB (документоориентированные)

Аналогия из жизни (из источника, хорошая — сохраняю): шкаф с ящиками на работе — в один ящик кладём трудовые договоры, в другой — договоры с партнёрами. Ничто не мешает свалить всё в кучу, но так удобнее. Ящики — это и есть коллекции. Отсутствие схемы позволяет класть в один ящик документы, логически похожие, но разные по структуре внутри.

Суть: документ — набор пар ключ-значение, без схемы, можно свободно добавлять/удалять поля (в отличие от реляционных БД, где это затронуло бы всю таблицу). Документы могут быть вложенными. Форматы — XML, YAML, чаще всего JSON. Документы группируются в коллекции.

Где использовать: мобильные приложения, игры, блоги, интернет-магазины — везде, где много контента с плавающей структурой.

Примеры: MongoDB, Amazon DynamoDB, CouchDB.

4. Graph DB (графовые)

Аналогия из жизни: карта друзей в соцсети — важнее не то, что написано в профиле у каждого человека, а КТО с КЕМ знаком и как связи ветвятся дальше.

Суть: узлы (данные) + рёбра (связи между данными) — связь хранится напрямую, не через отдельную таблицу, как в реляционных БД.

Где использовать: рекомендательные алгоритмы, соцсети, управление сетями и маршрутизацией, обнаружение мошенничества.

Примеры: Neo4j, Dgraph.

5. Search-engine DB (поисковые)

Аналогия из жизни (из источника, хорошая — сохраняю): указатель терминов в конце книги — вместо того чтобы читать всю книгу в поисках слова, смотришь в указатель и сразу попадаешь на нужную страницу.

Суть: документы с текстом индексируются заранее; поиск сканирует только индекс, не все документы целиком.

Где использовать: полнотекстовый поиск, хранение и анализ логов.

Примеры: Elasticsearch, Solr, Algolia.

6. Time-Series DB (временных рядов)

Аналогия из жизни: фитнес-браслет, который каждую минуту пишет пульс — важен не поиск "по имени", а вопросы вроде "какой был пульс в 15:00" или "покажи тренд за день".

Суть: оптимизированы для данных с отметкой времени (значение + момент времени).

Где использовать: мониторинг систем (нагрузка сервера, число подключений).

Примеры: InfluxDB, Prometheus.

7. Multi-model (много-модульные)

Суть: одна БД поддерживает несколько моделей данных сразу — не нужно выбирать один тип NoSQL раз и навсегда.

Пример: Redis — база в первую очередь key-value, но с дополнительными модулями умеет документы и time-series.

[!info]+ Уточнение точности — графовый модуль Redis устарел Источник упоминает, что Redis "умеет в графы" — это ссылка на модуль RedisGraph, который Redis Inc. официально свернул (EOL) в 2023 году, рекомендовав пользователям переходить на форк FalkorDB или отдельные графовые БД. На собесе безопаснее не заявлять "Redis работает с графами" как актуальный факт.
