🎭 Аналогия

Библиотека против картотеки. PostgreSQL хранит книги по полкам - удобно взять одну книгу целиком. ClickHouse хранит картотеку по признакам - неудобно собрать одну книгу, зато мгновенно ответит «сколько книг издано в 1998 году».

🗺 Карта мест

Сделать: поднять ClickHouse в докере, залить данные трекера, выполнить один и тот же агрегирующий запрос здесь и в PostgreSQL, записать цифры.

Понять: колоночное хранение: считать по столбцам - мгновенно, менять одну строку - дорого. Это витрина для аналитики рядом с PostgreSQL, а не его замена.

Где писать: docker-compose.yml с clickhouse-server; SQL - в clickhouse-client.

Чем запустить: docker compose up -d; docker exec -it clickhouse clickhouse-client.

Где смотреть результат: время выполнения в выводе clickhouse-client и \timing в psql рядом; system.query_log в ClickHouse - история запросов с длительностью.

Как понять, что получилось: у тебя есть табличка «запрос: PostgreSQL X мс, ClickHouse Y мс» и своими словами объяснение, почему так - на собеседовании собственный замер звучит совсем иначе, чем статья.

📖 Теория (40 минут)

Колоночное хранение. Строчная СУБД кладёт рядом все поля одной записи, колоночная - все значения одной колонки. Аналитический запрос читает две колонки из тридцати, и колоночная прочитает только их. Отсюда разница в разы на агрегатах.

Почему точечные обновления плохие. Данные лежат сжатыми блоками по колонкам. Изменить одну строку означает переписать блоки. ClickHouse умеет ALTER TABLE ... UPDATE, но это тяжёлая асинхронная операция, а не обычный UPDATE.

PostgreSQL ClickHouse
Хранение по строкам по колонкам
Сильная сторона точечные операции, транзакции агрегаты по большим объёмам
Слабая сторона агрегаты по десяткам миллионов точечные обновления, JOIN'ы
Транзакции полноценные практически нет
Когда выбирать бизнес-логика, деньги, учёт логи, метрики, аналитика

MergeTree - основной движок. Данные пишутся кусками, фоном сливаются. Партиционирование обычно по месяцу, сортировка по ключу, по которому фильтруют.

🔧 Практика

1. Поднять ClickHouse в докере:

docker run -d --name ch -p 8123:8123 -p 9000:9000 clickhouse/clickhouse-server

2. Залить данные из трекера - выгрузить таблицу находок или событий и загрузить в ClickHouse.

3. Сравнить агрегирующий запрос с PostgreSQL и записать цифры. На собеседовании собственный замер звучит совсем иначе, чем статья.

💥 Сломай намеренно

1. Сделать точечный UPDATE одной строки и посмотреть, во что это превращается - ALTER TABLE ... UPDATE идёт асинхронно и переписывает блоки.

2. Соединить две большие таблицы через JOIN и сравнить время с тем же запросом в PostgreSQL.

❓ Вопросы с ответами

Когда выберете ClickHouse, а когда останетесь на PostgreSQL?

ClickHouse - когда нужны агрегаты по большим объёмам и данные пишутся один раз: логи, метрики, аналитика. PostgreSQL - когда нужны транзакции, точечные операции и связи. У меня был замер на своих данных: [цифра] против [цифра] на одном и том же агрегате.
