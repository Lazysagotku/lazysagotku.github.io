Agent-coding и AI-терминология

P0

🎭Аналогия

LLM - двигатель. Prompt - что вы ему говорите сделать прямо сейчас. Context - что двигатель уже знает о ситуации. Skill - инструкция «как чинить именно эту модель мотора». Tool - гаечный ключ конкретного размера. MCP - стандартный разъём, через который любой ключ подходит к любому мотору. Harness - вся мастерская: инструменты, правила техники безопасности, журнал работ, тормоза на случай ошибки. Orchestration - бригадир, который решает, кто из мастеров что делает и в каком порядке. Ни один из этих терминов не заменяет остальные.

📖Теория

Agent-coding workflow

Этап Что делает инженер
Context даёт агенту требования, ограничения, source of truth
Plan проверяет план и границы изменений до старта
Implementation агент меняет код в ограниченном scope
Verification tests/lint/build/diff/security checks
Review инженер проверяет correctness, архитектуру, регрессии
Evidence фиксируются команды, результаты, diff, unresolved risks

Сильная позиция на интервью: агент ускоряет реализацию и анализ, но ответственность за требования, архитектурные границы, проверку и принятие результата остаётся у инженера.

AI/agent-архитектура - карта терминов

Термин Что это Какую проблему решает Чем отличается от соседних Нужен ли Hydra сейчас Пример в нашей системе
LLM большая языковая модель генерация/понимание текста по запросу ядро, вокруг которого строится всё остальное да, это Claude/ChatGPT/Codex сама модель, отвечающая в этом чате
Prompt конкретный запрос модели прямо сейчас сформулировать задачу для одного вызова часть context, но не весь context да, каждое сообщение текст этой задачи
Context всё, что модель знает о ситуации в момент ответа дать модели нужные факты без переобучения шире prompt - включает историю, файлы, инструкции да SESSION_CONTEXT.md, CLAUDE.md, история чата
RAG (Retrieval-Augmented Generation) поиск релевантного контекста во внешнем корпусе перед обращением к модели retrieval/context problem - какие данные дать модели прямо сейчас не сама генерация, а подготовка контекста для неё нет, пока проект умещается в прямое чтение файлов не используется - grep/Read заменяют retrieval при текущем объёме
Embeddings / vector DB векторное представление фрагментов данных / поиск по семантической близости типичный retrieval-слой RAG, когда полнотекстового поиска мало инфраструктура под RAG, не альтернатива ему нет не используется
Skill повторяемая инструкция - как выполнять класс задач не переизобретать процесс каждый раз не сама возможность действовать (это Tool), а инструкция, как её применять да, частично graphify, docx, code-review skills в этой среде
Tool / CLI конкретная возможность/действие: выполнить команду, прочитать репозиторий, вызвать API дать агенту физическую способность что-то сделать Tool - что можно сделать, Skill - как это делать хорошо да Bash, Read, Edit, git
MCP стандартизированный доступ к инструментам/данным между агентом и внешним миром единый протокол вместо кастомной интеграции под каждый инструмент не RAG и не orchestration engine - просто стандартный разъём да, частично MCP-серверы этой сессии (ccd_session, Claude_Browser и т.п.)
Agent модель, работающая в цикле с контекстом, инструментами и правилами, способная выбирать/выполнять действия в пределах разрешений автономность в рамках заданных границ шире, чем просто LLM - включает цикл действие→наблюдение→решение да Claude Code, Codex CLI
Harness среда вокруг агента: правила, инструменты, контекст, ограничения, логи, проверки, recovery, feedback loops делает поведение агента безопасным и воспроизводимым не одна функция, а вся обвязка сразу да этот же Claude Code: permission-режимы, pre-commit хук, OPEN_LOOPS как recovery-механизм
Orchestration кто и когда выполняет шаг, куда маршрутизируется задача, как агрегируются результаты, что при ошибке координация нескольких агентов/шагов не сам агент и не harness - слой над ними да, пока в лёгкой форме Иван вручную решает, что идёт Claude, что Codex, что ChatGPT
LangChain библиотека/экосистема компонентов для LLM-приложений (модели, prompts, retrieval, tools, chains, интеграции) не писать интеграционный код с нуля для типовых LLM-паттернов инструмент/библиотека, не архитектурное решение само по себе нет не используется - прямые вызовы моделей и MCP хватает
LangGraph движок для stateful workflow: состояние, ветвления, retries, checkpoints, циклы, multi-agent orchestration нужен, когда оркестрация реально требует состояния и ветвлений, не просто потому что существует orchestration-уровень поверх LangChain или отдельно нет, текущая оркестрация - Иван вручную плюс markdown-артефакты не используется

Полезная иерархия для текущей Hydra: Prompt → Plan → Harness → Orchestration. RAG решает retrieval/context problem, а не заменяет harness. LangGraph нужен, когда workflow действительно требует состояния, ветвлений, retries/checkpoints и сложной оркестрации - не по умолчанию.

Hydra - реальный кейс оркестрации людей и агентов

Ivan = human orchestrator
  │
  ├─ Claude  → implementation / deep working context
  ├─ Codex   → technical evidence / repo & server investigation
  └─ ChatGPT → independent review / architecture / teaching

shared artifacts/context:
  SESSION_CONTEXT.md, PROJECT_MAP.md, OPEN_LOOPS.md, handoff-тексты,
  git-история, тесты, pre-commit leak scanner

Эволюция, пройденная этим же проектом за несколько дней - реальная, не гипотетическая:

human orchestration
  → shared task model (единый вопрос всем трём)
  → artifacts/state/logging (SESSION_CONTEXT/OPEN_LOOPS/git как общая память)
  → controlled server identities (codex-ro: forced command, least privilege)
  → worker/tool boundary (dispatcher-скрипт вместо полного shell-доступа)
  → retrieval/RAG - только когда объём контекста этого потребует (пока не потребовал)
  → workflow engine/LangGraph - только когда сложность оркестрации этого потребует (пока не потребовала - Иван справляется вручную)

Ключевое наблюдение: каждый следующий шаг эволюции добавлялся по факту возникшей проблемы (например, codex-ro появился, когда понадобился реальный доступ к серверу, а не «на будущее»), а не заранее «на всякий случай». Это и есть правильный порядок принятия архитектурных решений в agent-системах - совпадает с trade-off-мышлением из Фазы 4.

Hydra - полная цепочка одного цикла (готовый interview case)

task → context → plan → implementation → independent review
  → tests → evidence → human decision → commit

Реальный проход этой цепочки в этом же проекте (реставрация учебных материалов, 19-20.09 - не гипотетический пример):

Шаг Что происходило
Task Иван просит вписать пояснения из внешнего конспекта в уже существующий сайт, явно уточняя - совпадение темы не повод считать материал дублем
Context Claude читает текущее состояние файлов, независимый review внешнего агента (ChatGPT) по этому же вопросу уже зафиксирован в общем OPEN_LOOPS.md
Plan Claude предлагает конкретный план (восстановить старое из git-истории и дополнить, а не переписывать заново) и явно спрашивает подтверждение, а не действует по умолчанию
Implementation Claude пишет объединённый материал; отдельный внешний агент независимо собирает доказательную базу по смежному вопросу (реальный сервер)
Independent review Второй агент (ChatGPT) параллельно анализирует ту же тему по своим источникам - два независимых взгляда сходятся на одном выводе, что и стало доп. подтверждением
Tests Автоматический сканер утечек (knowledge-base/scanner.py) прогоняется на каждый новый/изменённый файл перед публикацией - не «на глаз»
Evidence git diff --stat, рендер в браузере перед коммитом, явный список изменённых файлов
Human decision Иван выбирает между вариантами явно (через структурированный вопрос с трейд-оффами), не через молчаливое допущение агента
Commit Публикация только после решения, с сообщением коммита, объясняющим, что решено и почему

Это не единичный случай - тот же цикл повторился несколько раз подряд в этом проекте (для разных материалов, разных решений) - воспроизводимый паттерн, а не разовая удача.

Разбор чужой методологии agent-coding (видео) - критически, не как догма

Схема автора: опрос требований → specification → plan → tests before implementation → implementation/test feedback loop → orchestrator → parallel workers → git worktree isolation.

Что подтверждается и совпадает с уже устоявшейся практикой:

  • Агенту нужны acceptance/validation criteria - да, это ровно колонки Context/Plan в таблице workflow выше.
  • Контекст должен сохраняться между этапами - да, это буквально то, зачем существуют SESSION_CONTEXT.md/OPEN_LOOPS.md/PROJECT_MAP.md в Hydra.
  • «Готово, всё работает» - не evidence - да, полностью совпадает с шагом Evidence в цепочке выше и с дисциплиной leak-scanner/git diff перед публикацией в этом проекте.

Что не принимается как догма, с обоснованием:

  • «Tests всегда до implementation» - нет, зависит от фазы работы. TDD-first оправдан, когда поведение уже понятно и стабильно - багфиксы, известный API-контракт, рефакторинг с сохранением поведения. Для exploration/прототипа - наоборот: тесты, написанные до того, как форма решения устоялась, фиксируют форму, которую скорее всего выбросят - дороже, чем спайк сначала и тесты после стабилизации. Пример из этого же проекта: vacancy-tracker месяцами не имел ни одного теста, оставаясь реальным работающим инструментом (Фаза 3) - первые тесты имело смысл писать только когда форма API устоялась, не раньше.
  • Parallel workers через git worktree isolation - реальная и полезная техника, но не бесплатная. Плюс - избегает конфликтов при переключении веток, позволяет агентам работать в изолированных чекаутах одновременно. Минусы: overhead координации растёт с числом воркеров, нагрузка на review растёт пропорционально, контекст приходится дублировать или синхронизировать между воркерами. Race/conflict/integration - два агента, трогающие пересекающиеся файлы или схему данных, нуждаются в явном шаге интеграции с тестами как гейтом, иначе либо merge-конфликт, либо (хуже) тихий логический конфликт, который тесты не поймают, если написаны порознь.
  • Multi-agent реально полезен, когда задача действительно декомпозируется на независимые куски (разные модули, разные сервисы) - не для тесно связанных мелких правок, где последовательная работа с обзором дешевле и надёжнее.
  • Context/security/secrets - видео (по пересказу) не заостряет на этом внимание, а зря. Как только воркеры получают полуавтономность, это становится вопросом номер один: узкие, а не общие права у каждой identity - ровно то, что уже реализовано в Hydra через codex-ro (Agent_Access_Lab.md) - forced command, без sudo, без Docker-группы.
  • Human review не отменяется никаким уровнем автоматизации. Ни один шаг схемы автора формально не заменяет человека, принимающего решение - в Hydra это явный шаг Human decision, не подразумеваемый.

Честное сравнение с Hydra: сегодняшняя Hydra ближе к «последовательный пайплайн со специализацией ролей плюс независимый cross-review» (Claude реализует, Codex расследует в своей зоне, ChatGPT проверяет независимо), чем к «один orchestrator, декомпозирующий одну задачу на параллельно работающих воркеров в изолированных git worktree». Это не пробел, а следствие того же принципа «по факту возникшей проблемы, не заранее» - параллельные изолированные воркеры имеет смысл вводить, когда появится реально декомпозируемая параллельная задача, не раньше.

Audit: lavish-axi - INSTALL / PILOT / SKIP

lavish-axi (github.com/kunchenguid/lavish-axi) - skill, превращающий HTML-вывод агента (план, диаграмма, сравнение, код-дифф) в аннотируемую страницу в браузере: пользователь кликает/выделяет, фидбек уходит агенту через long-polling. Запускается через npx -y lavish-axi - живой Express-сервер на localhost, состояние сессии - в .lavish-axi/ внутри рабочей директории.

Критерий Вывод
Проблема реальная - превращает текстовый review в кликабельный, для визуального контента (диаграммы, сравнения, код-диффы)
Dependencies Node.js/npm экосистема - новый рантайм в Python-центричном проекте
Scripts npx -y каждый раз тянет последнюю версию пакета из npm без явного пиннинга - supply-chain риск, не статичный skill-файл
Permissions спавнит локальный процесс, слушает порт, пишет в рабочую директорию (.lavish-axi/)
Network access локальный сервер; есть env-переменная LAVISH_AXI_ALLOWED_HOSTS - значит инструмент рассчитан и на нелокальные сценарии (например, за туннелем)
Telemetry не подтверждено ни в одну, ни в другую сторону по доступной документации - открытый вопрос, не проверенный факт
Artifacts .lavish-axi/ в рабочей директории - требует явного .gitignore, иначе риск случайного коммита сессионных данных
Security implications код исполняется из npm при каждом запуске (не пиннут по умолчанию); при туннелировании (у этого проекта уже есть привычка выводить локальные сервисы наружу через Cloudflare) сессия ревью потенциально становится доступной снаружи
Overlap с Hydra низкий - нынешний cross-review Claude↔ChatGPT осознанно текстовый и ручной («Иван вставит сам, без автоматической интеграции» - правило CLAUDE.md); lavish решает другую задачу - review внутри одной агентской сессии, не между агентами
Реальная польза для review agent outputs умеренная - помогает для действительно визуального контента (диаграммы, side-by-side сравнения), не даёт выигрыша для текстовых git-diff-центричных review, которыми этот проект и так пользуется

Вердикт: PILOT, не INSTALL. Не устанавливать как постоянный инструмент сейчас. Если пробовать - в одноразовом/изолированном контексте, с закреплённой версией (npx lavish-axi@x.y.z, не голый -y), без туннелирования наружу, с .lavish-axi/ сразу в .gitignore, и с проверкой сетевого трафика во время тестового запуска. Причина - не «плохой инструмент», а несоответствие момента: текущий bottleneck проекта - решения по OPEN_LOOPS.md №15 и время подготовки к интервью, не UX ревью агентского вывода.

💥Сломай намеренно

  • Утверждать на собеседовании, что «LangGraph необходим для любой мультиагентной системы» - и тут же привести контрпример: эта самая Hydra-система координирует четыре стороны (Ivan + 3 модели) вручную, без единого workflow-движка, и это осознанный, а не вынужденный выбор.
  • Спутать RAG и MCP в объяснении - RAG решает «что дать модели в контекст», MCP - «как агент технически достаёт инструменты/данные». Один можно иметь без другого.
  • Установить lavish-axi через голый npx -y без пиннинга версии и без .gitignore на .lavish-axi/ - показать, почему это ровно то, чего вердикт выше просил не делать.

❓Вопросы с ответами

Как ты используешь coding agents и как проверяешь их работу?

Даю контекст и границы, проверяю план до старта, после реализации - тесты/lint/diff, сам проверяю корректность и архитектуру, фиксирую evidence. Ответственность за требования и принятие результата не передаётся агенту.

Чем RAG отличается от MCP?

RAG - про то, какие данные дать модели в контекст прямо сейчас (retrieval problem). MCP - про то, как агент технически получает доступ к инструментам и данным (стандартизированный протокол доступа). Можно иметь MCP без RAG (прямой доступ к файлам без поиска по векторам) и наоборот.

LangChain/LangGraph обязательны для агентных систем?

Нет. Это инструменты для конкретных задач - LangChain для сборки типовых LLM-паттернов без написания интеграций с нуля, LangGraph для workflow, которому реально нужны состояние, ветвления и checkpoints. Реальная многоагентная система (Hydra в этом же проекте) работает без них - оркестрация человеком плюс общие текстовые артефакты пока справляются.

Как ты оцениваешь, устанавливать ли новый агентский инструмент?

По конкретным критериям: какую проблему решает, зависимости и способ их получения (пиннинг версий), permissions и network access, telemetry, где остаются артефакты, пересечение с уже работающим процессом, и реальная (не гипотетическая) польза прямо сейчас. Пример - разбор lavish-axi: вердикт PILOT, не INSTALL, с конкретными причинами, не «нравится/не нравится».

Нужно ли всегда писать тесты до реализации?

Нет, зависит от фазы работы. Если поведение уже понятно и стабильно (багфикс, известный API-контракт, рефакторинг с сохранением поведения) - тесты до кода оправданы и дёшевы. Если форма решения ещё не устоялась (exploration, прототип) - тесты, написанные заранее, фиксируют форму, которую вероятно выбросят; дешевле сделать спайк, а тесты писать после стабилизации. Реальный пример - vacancy-tracker месяцами не имел тестов, оставаясь рабочим инструментом; первые тесты написаны только когда форма API устоялась.

Когда параллельные AI-агенты (multi-agent) реально оправданы?

Когда задача действительно декомпозируется на независимые куски - разные модули, разные сервисы. Тогда git worktree isolation - рабочая техника: каждый агент в своём чекауте, без конфликтов веток. Для тесно связанных мелких правок overhead координации и review не окупается - последовательная работа с одним исполнителем дешевле. Наша Hydra сегодня - это специализация ролей в последовательности с независимым cross-review, не параллельные воркеры на одной задаче, и это осознанный выбор под текущий объём работы, не пробел.
